# WonderEcho 음성 — 안내 재생·녹음·PC 한국어 인식

> **현재 상태 (WBS 4.7.4~4.7.7 · 4.7.10·4.7.11 · 4.7.14)** — `voice_pipeline.py`가
> 종단 대화 루프다: 모듈 마이크 → faster-whisper → 로컬 GGUF LLM → Piper TTS →
> 모듈 스피커. `start_voice.ps1`로 기동(COM5 + 관제 API :8090). 웨이크워드
> "메카독"에만 응답하고 "그만"은 종료가 아니라 대기 모드다.
>
> - **전송층 추상화 (4.7.9 선행)** — `transport.py`가 링크 경계다. 루프·지식·
>   시나리오·웹 API는 전부 전송 무관이고, COM5 시리얼은 `SerialTransport` 구현
>   하나일 뿐이다. Wi-Fi 중계는 같은 표면의 새 구현으로 `open_transport()`에 꽂는다.
> - **시나리오 테이블 (4.7.7)** — `scenarios.py`에 규칙 기반 시나리오 35종
>   (신원확인·방문자확인, PPE 종류별·제한구역·고전압·화학물질·지게차·금연·촬영
>   경고, 화재대피·비상접수, 순찰·방문자 안내, 교대·식사·점검·출하·안전수칙·공지,
>   우천·한파·폭염, 야간순찰·대피훈련, 상태브리핑·안전점검·분실물·자기소개 등).
>   신원·안전 판정은 LLM 없이 결정론적이고, 음성 트리거 또는 `POST /scenario`로
>   실행한다 — **시나리오를 바꿔도 모듈을 다시 굽지 않는다** (대사·판정·음성
>   데이터는 전부 PC 소유).
> - **음성 응답 라이브러리** — `phrases.py`에 카테고리 25종·150여 문구. 실제
>   산업 매뉴얼(산업안전보건법 근로자 의무, KOSHA 지게차 수칙, 화재 대피 매뉴얼,
>   포스코·LS MnM 출입통제 규정)에서 차용한 표현 기반. `gen_voice_cache.py`로
>   전 문구를 WAV로 미리 렌더링해 `voice_cache/`에 둘 수 있다(생성물, 커밋 제외).
> - **로봇 상태 음성 응답 (4.7.10)** — `robotlink.py`가 대시보드
>   `GET /api/telemetry`를 읽어 "배터리 어때" 등의 질의에 **실측값**으로 답한다.
> - **음성 명령 화이트리스트 (4.7.11)** — 정확히 일치하는 구문만 로봇 명령
>   엔드포인트로 간다 (`비상정지`→estop, `수동모드/수동해제`→manual on/off,
>   `순찰시작/순찰정지`→`POST /api/command/patrol`). 순찰 시작은 런타임의
>   `ask_patrol` 예약 경로를 타고(기동 리셋과의 순서 충돌 방지), 순찰 정지는
>   `PATROL→MANUAL→IDLE` 수동 경유로 정상 정착한다 — 래치를 거는 ESTOP이 아니다.
>   LLM 자유 텍스트는 절대 명령으로 변하지 않고, failsafe 해제(reset)처럼 사람의
>   현장 확인이 필요한 명령은 의도적으로 제외했다.
> - **대화·경고 이력 + 일일 리포트 (4.7.12)** — `eventlog.py`가 모든 발화·응답·
>   시나리오·명령·비상 이벤트를 `logs/voice-YYYY-MM-DD.jsonl`에 날짜별로 남긴다
>   (쓰기 실패는 로그만 — 음성 루프를 멈추지 않음). 로봇 측 사건(person_found 등
>   블랙박스 확정 검출)도 `GET /api/events?since=` 커서 폴링으로 `robot_evt`
>   역할로 합쳐진다 — 음성 로그와 로봇 로그가 한 리포트에 모인다.
>   `daily_report.py`가 하루를 집계해 마크다운 리포트를 만들고, `GET /report`가
>   당일 요약을 돌려준다.
>
> 관제 API는 `/status` 상태 브리핑, `/say` 공지 방송(긴급 우선 큐), `/scenario`
> 시나리오 트리거, `/scenarios` 목록, `/mode`, `/transcript`, `/report` — 링크는 메인 루프가
> 단독 소유하고 웹 요청은 큐로 직렬화한다. `knowledge/`의 문서들은 **전부 합성
> 데모 데이터**이며 실사 자료가 아니다. 안전 규정·매뉴얼은 실제 문서로 교체해 같은 RAG 경로를 쓰되,
> 작업현황·출하·설비 상태처럼 바뀌는 값은 문서로 교체하지 않고 가상 MES 경로로 옮긴다
> (FR-12 · ADR-34 · WBS `4.7.15~4.7.18`).
> 커스텀 펌웨어는 v27(`voice_stream.c` 체크섬 검증 + `voice_prompt.c` 부팅 코덱
> 예열)이 현재 설치본이다. **COM5는 임시 전송층**이고 목표 경로는 로봇 4핀
> I²C ↔ ESP32 ↔ Wi-Fi(4.7.9)다 — 링크 소유 규칙과 상위 루프는 그대로 쓴다.

모듈이 마이크와 스피커를 맡고, **판단은 PC가 한다.** 모듈에서 한국어 인식을 하지 않는다.

## 계획된 현장지원 모드 (`assist`)

현장지원은 핵심 경비·PPE 기능과 분리한 **부가기능**이다. 가상 MES 데이터 경로는
구현됐다 — `factory_mes.py`(SQLite + 읽기 전용 API `:8095`)와 `factorylink.py`
(질의 분류 → 결정론적 답변 템플릿)가 들어 있고, `route_query()`에서
emergency 뒤·status 앞의 `factory` 경로로 탄다. `assist` 모드 게이트 자체는
아직 없다 — 현재는 정보 질의가 active 모드에서도 응답한다.
판정 경로 전체 지도는 **[VOICE_ROUTING.md](VOICE_ROUTING.md)** 참조.

| 질문 | 데이터 원본 | 처리 |
|---|---|---|
| 안전 규정·설비 매뉴얼 | `knowledge/` 문서 | 검색 근거 안에서 LLM이 절차를 설명 |
| 로봇 배터리·상태 | 대시보드 telemetry API | 실측값을 그대로 답변 |
| 생산량·출하·작업·설비 상태 | 합성 SQLite 가상 MES | 규칙 기반 조회 → 출처·갱신 시각·TTL 검사 → LLM은 설명만 |

LLM은 SQL, 숫자, 상태, 로봇 명령을 만들지 않는다. 오래된 값이나 조회 실패는 **최신 정보를 확인할 수
없다고 답하고**, 자유문장 결과는 인증·PPE 판정·L3/F 해제로 연결하지 않는다. 현재 `knowledge/`에 있는
작업현황·출하스케줄 파일은 이 이관 전까지의 합성 시나리오 자료이며 최신 운영값의 정본이 아니다.

### 설정 데이터의 정본 — `voice_data.db` (선택적 오버레이)

음성 DB는 **3테이블(settings·roster·phrases)**로 정리했다. 고정 규칙 5종은
`voice_data.rules.json` 한 파일로 관리하며, DB/원격 조회 없이 변경 시에만 다시 읽는다.
기존 8테이블 사용자는 `migrate_voice_db.py --db voice_data.db`로 백업·이전한다.
관리자 추가 문구도 JSON/DB 이중 저장을 없애 `phrases`로 통합했다.
일반 설정은 DB 장애 시 기본값을 쓸 수 있지만 **사용 중인 신원 명단의 빈 결과·오류는
승인 대상 0명**으로 처리한다. DB가 아예 없는 기존 데모만 파일 명단을 쓴다.
비상정지 보호 구문과 로봇 실행 화이트리스트는 코드에 유지한다.

`voice_store.py --seed`와 `factory_mes.py --seed`는 기존 데이터를 보존한다.
의도적 초기화는 `--seed --reset`으로 하며 자동 백업한다.
Supabase 스키마 SQL도 기존 MES를 지우거나 자동 재시드하지 않는다.

[DB_GUIDE.md](DB_GUIDE.md)에 메인 안전 이력 DB와의 관계, 전체 테이블의 역할,
**로컬 합성 자료 → 검증 JSON → SQLite/Supabase SQL 가져오기** 절차를 정리했다.
`db_transfer.py`는 기존 키와 원본 시각을 보존하고 반복 가져오기 중복을 막는다.
규정·매뉴얼 RAG와 사건 JSONL은 기존 저장 경로를 유지한다.

```
[음성 모듈]                                   [PC]
 마이크 → 코덱 ADC → Speex 압축(3 KB/s) ──→ faster-whisper medium (CUDA)
                                            → "사원 홍길동입니다."
                                            → 이름 추출
 스피커 ← 코덱 DAC ← TC8002D 앰프  ←──────  재생 명령
```

PC 환경 구축은 **[SETUP.md](SETUP.md)** 를 따른다. 모델 파일은 이 저장소에 없다.

## 검증된 것

2026-09-14 실물에서 **안내 재생 → 5초 녹음 → 한국어 인식 → 이름 추출** 전 과정이 통과했다.

| 단계 | 결과 |
|---|---|
| 스피커 안내 재생 | 사용자 청취 확인(2회 재현) |
| 녹음 | 250프레임, checksum·length·timeout 오류 0, 정상 종료 |
| 인식 | `"사원 홍길동입니다."` `no_speech_prob` 0.042 |
| 이름 추출 | `claimed_name: "홍길동"` |

**청취 대신 루프백으로 판정한다.** `--loopback` 으로 안내를 재생하면서 마이크를 녹음하면,
재생 구간과 무음 구간의 dBFS 를 비교해 사람 귀 없이 판정할 수 있다. 위 앰프 문제를 가른 것이
이 측정이다 — 무음일 때 **+0.0 dB**, 고친 뒤 **+33.4 dB**(재생 -26.7 dBFS / 무음 -60.1 dBFS,
peak 144 → 16,272). `USE_AEC_MODULE` 이 0 이어야 유효하다. 반향 제거가 켜져 있으면 모듈이
자기 스피커 소리를 마이크에서 지워 **소리가 나도 루프백에 안 잡힌다.**

`identity_verified` 는 항상 `false` 다. **말한 이름을 받아 적은 것이지 신원을 인증한 것이 아니다.** 인증은 상위 시스템의 몫이고, 인식 텍스트를 실행 명령으로 쓰지 않는다.

## 검증되지 않은 것

- **한국어 인식 정확도를 측정하지 않았다.** 위 결과는 특정 발화 한 건이다. 여러 화자·소음·장시간은 미검증이다.
- 사원 DB 대조, 무선 중계, 상시 서비스는 구현하지 않았다.
- 이 폴더는 소스와 절차만 담는다. **벤더 SDK·펌웨어 이미지·모델·음원·측정 원본은 포함하지 않는다.** 파일을 내려받았다는 것이 빌드·설치 준비 완료를 뜻하지 않는다.

## 하드웨어에서 확인한 사실

무음 추적 과정에서 확정한 것들이다. 같은 실수를 반복하지 않기 위해 남긴다.

**스피커 앰프는 `TC8002D`** — 8002 계열 클래스-AB **아날로그** 파워앰프(SOP-8, 보드 뒷면 각인으로 확인). 핀1=SD(high면 셧다운), 핀4=-IN(오디오 입력).

→ **앰프가 아날로그 입력이므로 오디오는 내장 코덱의 아날로그 출력으로 나가야 한다.** IIS0 패드나 PDM 블록으로 내보내려던 시도는 처음부터 성립하지 않았다. Hiwonder 문서의 "digital signals into analog" 는 앰프가 아니라 코덱 DAC 을 가리키는 표현이다.

**앰프 극성 자동판별을 켜지 말 것** — 이것 하나로 하루를 날렸다. `CI-D02GS01J.c` 의
`pad_config_for_power_amplifier()` 는 `GS0XJ_BOARD_PA_AUTO` 가 1 이면 앰프의 유효 극성을
**부팅할 때마다 판별한다.**

```c
dpmu_set_io_pull(PC4, DPMU_IO_PULL_DISABLE);      /* 내부 풀을 끈다 */
uint8_t lvl = gpio_get_input_level(PC, pin_4);    /* 그 상태로 읽는다 */
g_pa_pin_valid_level = (lvl == 0) ? 1 : 0;
```

**내부 풀을 끄고 읽으므로 외부 풀이 약하면 핀이 뜬다.** 읽히는 값은 전원이 올라오는 파형에
좌우되고, 반대로 잡히면 `power_amplifier_on()` 이 `PC4` 를 high 로 올린다. `TC8002D` 는
**SD 가 high 면 셧다운**이므로 앰프만 꺼진다. 코덱·재생 카운터·마이크는 전부 정상으로 돌아
**진단 수치가 완벽하게 나오는데 소리만 없다.**

증상이 이렇게 나타났다 — 같은 이미지가 한 번은 소리가 나고, USB 포트를 바꿔 꽂은 뒤로는
계속 무음이었다. 재현되지 않아 스피커·앰프·배선 파손을 의심하고 손상 기전을 표로 정리하는
데까지 갔지만 **하드웨어는 처음부터 멀쩡했다.**

**SDK 기본값은 0 이다** (`sdk_default_config.h` 에 `//0、关闭（默认低电平有效）`). 켜지 말 것.
일반화하면 — **뜬 핀을 읽어 동작을 정하는 벤더 옵션은 켜지 않는다.** 재현되지 않는 고장이 된다.
그리고 **하드웨어 파손을 의심하기 전에 벤더 기본값과 우리 설정의 차이를 먼저 본다.**

**앰프 기동 지연** — 셧다운에서 깨어나는 데 시간이 걸린다. SDK 플레이어는 **재생이 시작되는
바로 그 순간에** 앰프를 켜므로, 음원 앞의 무음이 유일한 쿠션이다. 250 ms 로는 부족해서
"신원을"이 "인원을"로 들렸다.

루프백 녹음을 원본과 같은 시간축에 놓고 재면 얼마가 잘리는지 보인다.

| 시각 | 원본 진폭 | 스피커에서 녹음된 진폭 |
|---|---|---|
| 0.250 s | 755 ← "신" 시작 | 86 (잡음 바닥) |
| 0.300 s | 3,951 | 92 |
| 0.375 s | 10,768 | 116 |
| 0.400 s | 17,211 | 7,758 ← 여기서 갑자기 |

**앞 150 ms 가 통째로 없다.** 여린 시작이 사라지고 음절 중간부터 들리니 다른 말로 들린다.

**음원 앞 무음을 늘리는 것보다 재생 전에 앰프를 먼저 켜고 기다리는 편이 낫다.** 플래시가 늘지
않기 때문이다(user 영역 여유는 53,248 B 뿐이고 1.5 초짜리 음원이 이미 48,000 B 를 쓴다).
벤더 SDK 도 다른 곳에서 `vTaskDelay(300); //等待功放开启` 로 기다린다.

**예약 레지스터를 읽지 말 것** — 진단으로 내장 코덱 레지스터 `0x00~0x3B` 를 재생 중에 읽었더니 아날로그 출력이 죽었다. `0x00~0x2F` 로 줄이자 소리가 났다. `reg30` 다음은 예약 영역과 ALC 레지스터다. **읽기 전용 진단이라도 하드웨어에 부작용이 있다.** (범위만 되돌린 A/B 재현으로 확정하지는 않았다 — 유력한 설명이다.)

**I²C 슬레이브를 켜려면 두 개를 켜야 한다** — `MSG_USE_I2C_EN` 만으로는 동작하지 않는다.
그것은 `i2c_communicate_init()` 를 컴파일에 넣을 뿐이고, 그 함수가 부르는
`pad_config_for_i2c()` 는 보드 파일에서 `#if USE_IIC_PAD` 로 묶여 있다. `USE_IIC_PAD` 의 SDK
기본값은 0 이라, 켜지 않으면 `board_default.c` 의 `__WEAK` 스텁(`mprintf("no function: …")`)이
링크된다. **IIC0 가 핀 없이 초기화되어 주소에 응답할 수 없다.**

`CI-D02GS01J` 의 I²C 패드는 **`PB7`(IIC0_SDA)·`PC0`(IIC0_SCL)** 이고, 전력앰프는 `PC4` 라
서로 겹치지 않는다. 슬레이브 주소는 `iic_interrupt_init(IIC0,100,0x64,…)` 에
`/*7位设备地址0x64*/` 라고 적혀 있어 7 비트 `0x64` 다.

**로봇 버스 실측(2026-09-14)** — 로봇 ESP32 에 읽기 전용 스캔을 넣어 확인했다.

| 버스 | 핀 | 모듈 연결 | 모듈 분리 |
|---|---|---|---|
| IIC1 | SDA22 / SCL23 | `0x34` · `0x6A`(IMU) · `0x77`(초음파) | `0x6A` · `0x77` |
| IIC2 | SDA19 / SCL13 | 없음 | 없음 |

`0x34` 만 사라지므로 **모듈이 `0x34` 로 응답한다.** 그런데 그때 모듈 펌웨어는
`MSG_USE_I2C_EN` 이 0 이었고 SDK 어디에도 다른 `iic_interrupt_init` 호출이 없다.
**따라서 `0x34` 는 우리 user code 가 아니다.** 벤더가 제공하는 2 번 코어 코드
(`[1]code.bin` = `libs/libfbin.a`, 매 빌드마다 원본 그대로 합친다)일 가능성이 높고,
기판의 별개 칩일 가능성도 남아 있다. **확정하지 못했다.** 주소가 ACK 한다는 것이
프로토콜이 동작한다는 뜻은 아니다.

**IIC1 은 안전 버스다.** IMU(`0x6A`)와 초음파(`0x77`)는 전도 감지·정지 판정에 쓰이는
1 순위 입력이다. 오디오를 이 버스로 흘리려면 경쟁을 전제로 설계해야 한다.

**user 영역 여유는 실측 53,248 바이트** — 16 kHz 16-bit 로 약 1.66초분이다. 문구를 여러 개 넣으려면 압축이 필요하다.

## LLM 확장 — 이 구조가 열어두는 것

**판단이 PC 에 있다는 점이 이 설계의 핵심이다.** 모듈은 마이크와 스피커만 맡으므로, PC 쪽을 바꾸는 것만으로 기능이 올라간다. 모듈 펌웨어를 다시 굽지 않아도 된다.

지금 PC 가 하는 일은 세 가지다 — 음성 인식(faster-whisper), 이름 추출(정규식), 음원 합성(Orpheus, 사전 생성). 여기에 LLM 을 얹으면 이렇게 확장된다.

| 지금 | LLM 을 얹으면 |
|---|---|
| `사원 OOO 입니다` 형식만 인식 | 자유 발화에서 의도와 이름을 뽑아냄 |
| 고정 문구 4개를 인덱스로 재생 | 상황에 맞는 문장을 그때그때 생성 |
| 단발 질의응답 | 되묻기·맥락 유지가 있는 대화 |
| 규칙 기반 판단 | 상황 판단, 이상 상황 설명 생성 |

### 자원은 이미 충분하다

검증 환경(RTX 5070, VRAM 12 GB) 기준으로 동시 적재가 가능하다.

| 구성 | VRAM |
|---|---|
| faster-whisper medium (float16) | 약 1.5 GB |
| 8B 급 LLM (4-bit 양자화) | 약 5~6 GB |
| **동시 운용** | **약 7~8 GB** |

음성 합성(Orpheus 3B, 약 6.5 GB)은 미리 음원을 만들어 두는 오프라인 작업이라 동시에 올릴 필요가 없다.

### 먼저 풀어야 할 것

**동적 음성은 전송 문제부터 해결해야 한다.** LLM 이 문장을 만들어도 그것을 말하려면 음성을 실시간으로 모듈에 보내야 하는데, 현재 UART 115200 은 11.5 KB/s 이고 16 kHz 16-bit PCM 은 32 KB/s 를 먹는다. 지금처럼 **플래시에 미리 구워둔 고정 문구를 인덱스로 재생하는 방식은 이 제약 때문에 택한 것**이다. 동적 음성을 하려면 ADPCM 압축(4:1), UART 921600 승격, 또는 I²C 400 kHz 중 하나가 필요하다.

**지연을 측정해야 한다.** 현재 인식만 1.6초다. 여기에 LLM 추론과 음성 합성이 더해지면 대화로 느껴질지 확인이 필요하다.

### 신원 확인 경로에는 넣지 말 것

`claimed_name()` 이 `사원 OOO 입니다` 형식만 받고 다른 말이 섞이면 거부하는 것은 의도된 설계다. **LLM 은 이름을 지어낼 수 있다.** 실제로 이 프로젝트에서 Whisper 가 무음에 `"오늘도 시청해 주셔서 감사합니다."` 를 `no_speech_prob 0.753` 으로 만들어낸 적이 있다.

LLM 은 **대화·안내·상황 설명**에 쓰고, **신원 판정은 규칙 기반으로 남겨두는 것**이 맞다고 본다. 둘을 섞으면 "모델이 그렇게 말했다"는 이유로 통과하는 경로가 생긴다.

## 참고 — 검토한 다른 TTS

Orpheus 준서 목소리로 확정했지만, 고르는 과정에서 다음을 비교했다. 필요하면 참고할 것.

|---|---|---|---|
| **Orpheus 3B 한국어** | 전용 파인튜닝, 화자 2명(유나·준서) | Apache 2.0 표기, Llama-3.2-3B 파생 | **채택** |
| Supertonic 3 | 31개 언어 중 ko | 코드 MIT / 가중치 OpenRAIL-M | 미채택. ONNX·CPU 로 가볍고 제작사 자체 벤치마크의 한국어 CER 이 더 낮았다(3.26 vs 4.07). 저장소가 아카이브됨 |
| Qwen3-TTS 0.6B | 10개 언어 중 한국어, 화자 sohee | Apache 2.0 (코드·가중치) | 미채택. 청취 결과 안내 방송에는 톤이 과했다 |

| k2-fsa/OmniVoice | 참조 음성 필요 | 가중치 **CC-BY-NC(비상업)** | 부적합 |
| ResembleAI/chatterbox | 참조 음성 필요 | MIT | 내장 화자가 없어 남의 목소리를 복제해야 한다. 동의 없는 복제는 산출물에 쓸 수 없다 |

OpenRAIL-M 은 사용 제한이 있지만 원문에 `"Licensor claims no rights in the Output You generate using the Model"` 이 있어 **생성된 음성 자체에는 라이선스 주장이 없다.**

## 파일 구성

**PC 쪽**

| 파일 | 역할 |
|---|---|
| `protocol.py`, `stream_client.py` | WEC1 프레임·체크섬·순번·진단 해석, 캡처. 250프레임 연속과 정상 종료가 없으면 성공으로 표시하지 않는다 |
| `transcribe_local.py` | 완료된 5초 16 kHz PCM16 캡처만 로컬 faster-whisper 로 처리 |
| `build_prompt_audio.py` | 합성 원본을 모듈이 받는 16 kHz 모노 16-bit 로 변환·정규화. 48~128,000 바이트 제한 검사 |
| `synth_prompt_orpheus.py` | Orpheus 한국어 합성(권장). `--temperature 0.4` 를 쓸 것 — 0.6 에서는 "신원"을 오발음했다 |
| `synth_scenario.py` | 출입 통제 4문구 일괄 생성. 현재 용량 초과라 그대로는 안 들어간다 |

**장치 쪽 (SDK 에 적용하는 소스·패치)**

| 파일 | 역할 |
|---|---|
| `voice_stream.*`, `voice_encoder.*` | 마이크 수집·압축·전송 어댑터 |
| `voice_prompt.*` | 안내 재생과 진단 스냅샷 |
| `prepare_*.py`, `fix_*.py`, `trace_*.py` | 별도로 확보한 호환 SDK 사본에 적용하는 준비·수정 스크립트. 원본 SDK 와 공장 복구 이미지를 보존하고 확인된 입력 해시에만 적용한다 |

## 주의

- **포트를 확인하고 쓸 것.** 본체나 다른 모듈의 포트를 쓰지 않는다. 음성 모듈과 본체가 둘 다 CH340 이라 VID/PID 로는 구분되지 않는다 — 한쪽 USB 를 뽑아 사라지는 포트로 확인한다.
- **음성 모듈 USB 와 로봇 I²C 포트의 5V 를 동시에 인가하지 않는다.** 역전류 위험이 있다.
- 패키징 후 `user_code/` 에 파일이 3개인지, `[1]code.bin` 이 64,264 바이트인지 확인하고 이미지를 만든다. 공식 merge 를 건너뛰면 두 번째 코어 코드가 빠진 채로 크기 검사만 통과한다.

현재 WBS 3.5.5 / 4.7 계열의 근거다. 공장 문구·ID 방식의 전체 완료 판정은 하지 않는다. 본체·카메라 기능을 바꾸지 않는다.
