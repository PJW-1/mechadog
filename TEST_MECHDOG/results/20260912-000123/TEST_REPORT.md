  RSSI -63~-57dBm(평균 -58.8) · 카메라 HTTP 응답 중앙 73ms(최대 2558ms)
  로봇 UDP 중앙 6.8ms(범위 3.4~19.8ms) · PSRAM 8,247,867B 고정(변동 0)
  → 보조배터리만으로 30분 동안 한 번도 끊기지 않았다. 전파 세기와 메모리가 전혀 흔들리지 않아 전원이 안정적임을 뜻한다. HTTP 최대 2558ms는 카메라가 영상 스트림을 동시에 보내던 순간의 지연이며 끊김은 아니다.
  ※ 케이블 없이 30분 완전 무선 운용 가능
  자료  TEST_MECHDOG/results/stability_2_3_2.csv (60행)

[WBS 4.1.4]  10Hz 텔레메트리 송신 · 스키마
  정상 · 10.0Hz (61건/6.1초 = 10.02Hz) · 수신 61건 전량 수락 · 폐기 0건
  boot_id 부팅마다 생성(3191ea44fe8a42f2) · device_id mechdog-01 · seq 1부터 증가
  batt_v 8.32~8.34V(평균 8.328) · imu pitch 0.74도 roll 2.25도 · last_cmd_age_ms 46
  → 로봇이 자기 상태를 0.1초마다 한 줄씩 보낸다. 규격이 요구하는 10Hz를 정확히 맞췄고, 팀장의 수신 검증기가 61건을 하나도 버리지 않았다. IMU는 실제 QMI8658 칩에서 읽은 값이라 로봇이 거의 수평임을 보고하고 있다.
  ※ 로봇이 자기 상태를 실시간으로 보고하기 시작
  비고  upstream dev 에는 이미 독립 구현이 있다 — #70 "add stationary sensor telemetry
        and diagnostics", #73 "센서+구동 통합 빌드 — 걷는 중 텔레메트리 10Hz (실기 확인)".
        구조는 그쪽이 낫다(`src/telemetry_publisher` 로 분리, device_id 를 MAC 에서 생성).
        ⚠️ 그럼에도 ASSIGNMENTS 에는 4.1.4 가 여전히 🟢 미완료로 남아 있다 — 코드는
        올라왔는데 문서가 따라가지 않았거나 DoD 를 아직 닫지 않은 것으로 보인다.
  비고  yaw는 0 고정이다. 가속도계로는 수직축 회전을 볼 수 없어 규격상 필수 필드를
        0으로 채웠다. 방위로 사용하면 안 된다 (WBS 2.1.4 · OI-23).
        dist_cm은 0이다. 초음파(0x77) 드라이버가 없어 측정 불가를 0으로 보고한다 —
        큰 값을 적으면 "앞이 비었다"는 위험한 쪽 거짓말이 된다 (WBS 2.1.3 · 3.2.6).

  정상 · 8.33V (경고 7.0 / 셧다운 6.6)

  ※ 배터리는 정상이며 서보 시험을 막지 않음

## 8. 권고

1. 작업 사본을 upstream dev 최신으로 맞춘다. 이 시험은 #69~#73 이전 스냅샷에서
   돌았고, 그 때문에 이미 있는 텔레메트리를 로컬에서 다시 구현하는 중복이 생겼다.
   측정 자체는 유효하나, 다음 회차는 dev 최신 빌드로 다시 재야 한다.
2. 공유기에 DHCP 고정 할당을 건다. 측정 중 두 기기 주소가 모두 바뀌었다
   (로봇 .61에서 .86, 카메라 .170에서 .245). 대역 훑기가 찾아내 측정은 진행됐다.
3. 비전 성능 수치는 기준 PC에서 다시 재야 한다. 이 PC(Celeron N5095, GPU 가속 없음)의
   705ms는 코드 성능이 아니라 환경 성능이다.
4. WBS 4.1.4 의 문서 상태를 확인한다. 코드는 dev 에 있는데 ASSIGNMENTS 에는
   🟢 미완료로 남아 있어, 다음 사람이 같은 중복을 반복할 수 있다.
5. WBS 2.1.3 센서 기본 동작 확인이 다음 순서다. 텔레메트리가 열렸으므로 초음파와
   IMU 를 무선으로 관측할 수 있고, 그것이 dist_cm 과 yaw 의 0 고정을 해소한다.
