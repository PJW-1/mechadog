# 카메라 프레임 실측 — 공유기 근접 배치 + PC 유선 (2026-09-14)

공유기를 로봇·카메라와 같은 방으로 옮기고 PC 를 랜선으로 붙인 뒤 스트림 수신률을 쟀다.
카메라는 그대로 Wi-Fi 다.

카메라만 읽었다. 로봇 명령(MOVE/POSE/STOP/RESET_SAFE) 미송신, COM 접근 없음, 플래시 쓰기 없음.
카메라 프로파일은 런타임 `/profile` 로만 바꿨고 시험 후 원래 값(VGA·상한 25)으로 되돌렸다.

## 구성

| 항목 | 값 |
| --- | --- |
| 카메라 | XIAO ESP32S3 · OV3660 · Wi-Fi · **RSSI −14 dBm** |
| PC | 이더넷(랜선). 스트림 연결의 소스 IP 로 유선 경로 확인 |
| 도구 | `tools/camera_link_check.py` (카메라 전용) |

09-12 최적화 측정 당시 RSSI 는 −64 ~ −50 dBm 이었다.

## 결과

| # | 조건 | 프레임 | fps | gap p95 | gap max | JPEG 평균 |
| --- | --- | --- | --- | --- | --- | --- |
| 01 | VGA · 상한 25 | 717 | **23.95** | 72.9 ms | 594.7 ms | 17,074 B |
| 02 | VGA · 상한 40 | 756 | **25.24** | 71.9 ms | 113.2 ms | 17,353 B |
| 03 | QVGA · 상한 40 (참고) | 551 | 27.63 | 41.3 ms | 78.3 ms | 6,352 B |
| 04 | VGA · 상한 25 (재현) | 711 | **23.76** | 73.5 ms | 109.3 ms | 17,492 B |

전 구간 `discarded 0` · `resyncs 0`. 01·02·04 는 `all_vga true`.

01 의 `gap_max` 594.7 ms 는 **1회성 이상값**이다 — 같은 조건 재현(04)이 109.3 ms 였다.
상한을 올려서 gap 이 좋아졌다고 읽으면 안 된다(02 는 113.2 ms 로 04 와 사실상 같다).

### 09-12 대비

JPEG 크기가 비슷한 구간끼리 비교한다.

| | 09-12 최적화본 | 2026-09-14 |
| --- | --- | --- |
| RSSI | −64 ~ −50 dBm | **−14 dBm** |
| JPEG 16.8 KB 구간 | 18.13 fps | — |
| JPEG 17.1 KB · 상한 25 | — | **23.95 fps** |
| 전체 구간 fps 범위 | 13.67 ~ 18.13 | 23.76 ~ 25.24 |

크기가 비슷한 구간끼리 놓으면 **18.13 → 23.95 fps (+32%)** 다.
다만 장면·조명이 같지 않으므로 통제된 A/B 는 아니다.

## 확인된 것

### 1. 지금 병목은 무선이 아니라 카메라 파이프라인이다

상한을 25 → 40 으로 풀어도 25.24 fps 에서 멈춘다. QVGA 로 내려 JPEG 를 6.4 KB(1/3)로
줄여도 27.63 fps 로 10% 만 오른다. 해상도를 1/4 로 줄였는데 fps 가 그만큼 안 오른다는 것은
**전송이 아니라 센서·인코딩이 약 25~28 fps 에서 한계**라는 뜻이다.

무선 여유는 충분하다 — 25 fps × 17 KB ≈ 3.4 Mbps, `discarded`·`resyncs` 0.

2026-09-08 검수 때 장치 로그가 27.5·27.8 fps 였던 것과도 맞는다.

### 2. 두 번째 접속은 0 프레임을 받는다

`:81/stream` 에 A 를 먼저 열고 8초 뒤 B 를 붙였다. 2회 반복, 같은 결과다.

| | 1회차 | 2회차 |
| --- | --- | --- |
| A — B 접속 전 | 21.0 fps | 22.71 fps |
| A — B 가 붙어 있는 동안 | 23.86 fps | 21.86 fps |
| **B (나중 접속)** | **0.0 fps · TimeoutError** | **0.0 fps · TimeoutError** |

먼저 붙은 쪽은 **전혀 영향받지 않고**, 나중에 붙은 쪽이 통째로 굶는다. 나눠 갖지 않는다.

`firmware_xiao_vision/README.md` 의 "두 번째 접속은 대기한다"를 클라이언트 입장에서 보면
**죽은 스트림과 구분되지 않는다** — 한 장도 못 받고 타임아웃으로 끝난다. 화면이 검게
비어 있을 때 카메라 고장이나 네트워크 문제로 오진하기 쉬우므로 먼저 다른 수신자를 의심한다.

공유기를 옮겨도 이 제약은 그대로다.

## 상한을 올릴 것인가 — 결정 사항

상한 25 는 실측 파이프라인 한계(약 25.2)보다 낮아 **현재 자신이 제한 요인**이다.
`config.yaml` 의 `vision.stream_fps_limit` 를 30 으로 올리면 약 **+5%**(23.8 → 25.2) 나온다.

그런데 이 저장소는 상한의 목적을 명시해 두었다:

> 상한을 두는 목적은 낮추는 것이 아니라 **예측 가능하게 만드는 것이다.**
> 상한이 없으면 JPEG 크기가 화면 내용에 따라 변하고 발열에 따라 fps 가 흘러서,
> 명령 타임아웃(300ms) 대비 최악 부하를 계산할 수 없다.

즉 상한을 올리면 최악 대역폭 가정도 같이 올라간다. **+5% fps 와 부하 예측 가능성의
맞바꿈이므로 이 문서에서 값을 바꾸지 않았다.** 팀이 판단할 사항이다.

올리기로 한다면 `config/config.yaml` 의 `vision.stream_fps_limit` 한 곳만 바꾸면 된다
(펌웨어 기본값 25 는 폴백이라 재설치가 필요 없다).

## 남는 것

- 카메라 **단독 스트림 수신률**이다. 추론을 붙였을 때·보행 중·장시간 값이 아니다.
- 통제된 A/B 가 아니다. 공유기 이동·PC 유선·거리가 함께 바뀌어 각 기여도를 분리하지 못했다.
  PC 를 Wi-Fi 로 되돌린 대조군은 재지 않았다.
- 기체 1대의 카메라 1대다. 다른 기체에 값을 복사하지 않는다.

측정 원본과 SHA256 은 로컬 `05_실물_측정결과/2026-09-14/카메라_프레임/` 에 있다.

## 2차 — 미완료 WBS 대상 추가 측정

카메라 성능 관련 미완료 WBS 를 훑어 잴 수 있는 것을 다 쟀다.
대상: `6.3.1`(성능 프로파일링), `6.4.2`(G2 비전 파이프라인 검수), `3.7.3`, `6.4.3`.

### 장시간 5분 연속 — 신규

지금까지 "장시간 미검증"으로 남아 있던 항목이다. 09-08 검수는 11초였다.

| 항목 | 값 |
| --- | --- |
| 시간 / 프레임 | 300.0 초 · **6,792** |
| fps | **22.65** (window 22.64) |
| discarded / resyncs | **0 / 0** |
| gap p95 / max | 77.0 ms / **276.5 ms** |
| all_vga · 15fps 기준 | true · 통과 |

5분 내내 스톨·재연결·프레임 폐기가 한 건도 없었다. 최대 공백 276.5 ms 는 스톨 판정
기준(2000 ms)의 14% 다.

### 스트림 차단 후 자동 재연결 — 실물 카메라에서 확인

`6.4.2` G2 항목이다. 기존 `4.3.4` 검증은 **로컬 가짜 서버**를 죽였다 살리는 방식이었고,
이번에는 **실물 카메라**에서 했다.

차단을 만들려고 방화벽·전원을 건드리지 않았다. 스트림이 단일 클라이언트이므로 다른
클라이언트가 붙잡고 있게 두면 호스트 `StreamReader` 입장에서는 실제 outage 다.

| 구간 | 결과 |
| --- | --- |
| 다른 클라이언트가 점유 (0~20 초) | `StreamReader` 프레임 **0** |
| 그동안 재시도 | `failures 4` · `backoff_slept 15.0 s` (1→2→4→8 지수 백오프) |
| 점유 해제 후 첫 프레임 | 25.161 초 = **복구 5.161 초** |
| 해제 후 수신 | 456 프레임 · `connects 1` · `stalls 0` |

복구 5.16 초는 해제 시점이 8초 백오프 중간이었기 때문이며, `4.3.4` 의 가짜 서버
검증값 5.08 초와 일치한다.

### 유선/무선 대조군 — 실패로 기록

같은 도구·같은 파서로 인터페이스만 바꿔 재려고 `socket.create_connection` 에
`source_address` 를 끼웠다. 유선은 60초 1351 프레임 · 22.54 fps 로 정상이었으나
**무선은 `WinError 10065` 로 연결 자체가 안 됐다** — Windows 가 소스 바인딩만으로는
경로를 내주지 않는다(strong host).

무선으로 강제하려면 어댑터 metric 변경이나 유선 어댑터 비활성화가 필요한데
사용자 네트워크 설정이라 바꾸지 않았다. **따라서 PC 유선 전환의 기여도는 여전히
분리되지 않았다** — 09-12 대비 개선은 공유기 이동·거리·유선화가 뭉뚱그려진 값이다.
