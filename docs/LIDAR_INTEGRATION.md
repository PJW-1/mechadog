# LiDAR 측위·순찰 병합 노트 (FR-6 · FR-7 · Phase 2)

> 외부에서 작성한 **LiDAR SLAM · 구역 순찰 알고리즘**을 이 저장소의 규약과 구조에
> 맞춰 합친 결과다. 이 문서는 **무엇을 고쳤고 어떤 결정이 확정됐는지**를 적는다.
>
> **배치는 README 의 각 폴더 용도를 따랐다** (1절). 설정값은 바꾸지 않고
> `config.yaml`과 `requirements-dev.txt`에 항목을 추가했으며, 팀장 리뷰에서
> `PROTOCOL.md`에 LiDAR 정본 확장 링크를 더했다. 확인 방법은 6절에 있다.
>
> `docs/PROTOCOL.md`가 `docs/PROTOCOL_LIDAR.md`를 정본 확장으로 참조한다.
> LiDAR 규약은 별도 문서에 두되 기존 제어·텔레메트리 규약과 같은 효력을 갖는다.

## 0. ROS2 와의 관계 — ADR-9 의 범위를 그대로 따랐다

[ADR-9](DECISIONS.md) 가 이미 정해 둔 것을 그대로 지켰다.

> Phase 1 을 **순수 Python 단일 프로세스로 완결**. ROS2 는 Phase 2 에서
> `slam_toolbox` 하나로 범위를 한정해 *"스캔을 넣으면 맵과 위치를 반환하는
> **블랙박스**"* 로만 쓴다. / **Phase 2 에 nav2 를 쓰지 않는다.**

그래서 이 병합의 성격이 정해진다.

| 부분 | ADR-9 에 따른 처지 | 이 병합에서 |
| :--- | :--- | :--- |
| **SLAM** (`slam/scan_match.py`) | P2 에서 `slam_toolbox` 로 **교체** | 그 자리를 채우는 **잠정 구현**으로 명시 |
| **경로계획** (`behavior/planner.py`) | **nav2 거부** → 우리 것 | 그대로 남는다 |
| **구역 · 스케줄러** (`behavior/zones.py`) | 우리 것 (WBS 3.9.1/3.9.2) | 그대로 남는다 |
| **순찰 제어** (`behavior/patrol.py`) | 우리 것 — 규약이 UDP 이므로 ROS2 무관 | 그대로 남는다 |

### 교체가 성립하도록 한 것 — 지도 형식

블랙박스로 갈아끼우려면 **그 블랙박스가 낸 지도를 이쪽이 그대로 소비**할 수
있어야 한다. 그래서 `OccupancyGrid` 가 ROS2 맵을 **읽고 쓴다.**

| 방향 | 형식 |
| :--- | :--- |
| 쓰기 | `*.npy`+`map_meta.json` (작업 형식) **와** `*.pgm`+`*.yaml` (ROS2) 둘 다 |
| 읽기 | 작업 형식 우선, **없으면 ROS2 쌍** — `slam_toolbox` 만 돌린 경우가 그것이다 |

**실제로 확인했다** — `slam_map.npy` 를 지우고 ROS2 쌍만 남긴 상태로 순찰을
돌렸고, 결과가 완전히 같았다 (사이클 1 · 구역 3 · 오탐 0 · 전문 579).
`test_load_falls_back_to_the_ros2_pair` 가 그 계약을 고정한다.

> ⚠️ **판독의 함정 하나가 컸다.** map_server 기본 미지값 **205** 의 확률이
> `(255-205)/255 = 0.196` 이고, 그것이 하필 `free_thresh` 기본값과 **같다.**
> 임계로 분류하지 않고 확률을 그대로 넣으면 **미지가 자유로 둔갑하고**,
> A* 가 한 번도 관측하지 않은 공간을 최단 경로로 골라 로봇을 내보낸다.
> 지도는 그럴듯해 보이므로 눈으로 잡히지 않는다
> (`test_slam_toolbox_unknown_value_does_not_become_free`).

### 아직 만들지 않은 것 — 제 몫이 아니거나 선행이 안 끝났다

| 항목 | 왜 |
| :--- | :--- |
| `docker/ros2/` | **WBS 5.4.1 · 담당 C · P2 승인 선행.** 제가 만들 것이 아니다 |
| `SCAN` → `LaserScan` 브리지 | 구현은 위 작업의 몫. **필드 매핑은 [PROTOCOL_LIDAR 6절](PROTOCOL_LIDAR.md)에 사양으로 못박아 두었다** — 각도 부호·빈 칸 `inf` 처리 하나가 어긋나면 지도가 조용히 뒤집힌다 |
| tf `odom` → `base_link` | ⚠️ **오도메트리가 없다.** `gait_calibration` 이 비어 있고 `WBS 2.2.3` 이 미착수다. ADR-9 가 경계한 실패 양상 네 가지 중 하나가 정확히 `odom` 드리프트인데, 우리는 드리프트가 아니라 **odom 자체가 없다.** `2.2.3` 은 **LiDAR·마스트 없이 지금 할 수 있다** |

## 1. 무엇이 들어왔는가

원본은 파이썬 3개 파일이었다 (`LiDAR_SLAM.py` · `Zone_Coordination.py` ·
`Patrol_Automation.py`). 각각이 소켓을 열고 시각을 읽고 지도를 그리고 명령을
보내는 **한 덩어리**였다. **README 가 각 폴더에 부여한 용도**대로 나눴다.

### `host/common/` — *"통신 규약 · 로깅 · config"*

| 파일 | 역할 | 원본 |
| :--- | :--- | :--- |
| `lidar_link.py` | 스캔 데이터그램 검증 (규칙 ①~⑥). **`protocol.py` 의 형제다** | `receive_scan_udp` |
| `units.py` | 전선(mm·deg·ms) ↔ 내부(m·rad·s) 변환 **한 곳** | 세 파일에 흩어져 있었다 |

### `host/behavior/` — *"FSM · 명령 송신"*

| 파일 | 역할 | 근거 |
| :--- | :--- | :--- |
| `zones.py` | 구역 앵커 + **순차·랜덤 순찰 스케줄러** | **WBS 3.9.1 · 3.9.2 가 이 경로를 지정한다** |
| `planner.py` | 팽창 · A* · 웨이포인트 · 신규 장애물 감지 | ADR-9 가 **nav2 를 거부**했으므로 경로계획은 우리 것이다 |
| `patrol.py` | 순찰 판단 → **규약 의도**. FSM 13종 사상 | `commander.py`·`actions.py`·`fsm.py` 의 형제 |

> `zones.py` 에 스케줄러가 함께 있는 것은 작업 사전이 그렇게 정했기 때문이다 —
> `3.9.1`(구역 앵커)과 `3.9.2`(순찰 스케줄러)의 산출물이 둘 다
> `behavior/zones.py` 다. 실제로 붙어 있는 것이 맞다: 다음 구역을 고르는 일은
> **구역 목록과 도착 판정 반경을 함께 봐야** 한다.

### `host/slam/` — SLAM 코어 (`WBS 3.9.1` 의 선행 항목)

| 파일 | 역할 | P2 에서 |
| :--- | :--- | :--- |
| `scan_match.py` | 스캔 정합 측위 · 매핑 | **`slam_toolbox` 로 교체** |
| `occupancy.py` | 점유격자 · 로그오즈 · **ROS2 맵 읽기·쓰기** | 남는다 (맵 소비자) |
| `settings.py` | `lidar` 절 검증 + 파라미터 조립 | 남는다 |
| `simulation.py` · `viz.py` | 가상 스캔 · 시각화 (개발 도구) | 남는다 |

> 이름은 작업 사전의 어휘를 그대로 쓴 것이다 — `WBS 3.9.1` 의 선행이
> *"P2 승인 · **SLAM 코어** 완료"* 다.
>
> ⚠️ **README 의 `host/` 목록에 없는 새 디렉터리다.** 기존 다섯 개 중 어느
> 용도에도 측위·매핑이 들어가지 않는다. 새 디렉터리가 규칙 위반은 아니다 —
> `WBS 4.8.1` 이 `host/cloud/vlm_report.py` 를 산출물로 두고 있고 그것도
> README 목록에 없다. 작업이 도착하면서 디렉터리가 생기는 구조다.

### `tools/` — *"목업 · 지연 측정 · 텔레오퍼레이션 · 가중치 받기"*

## 2. 규약 위반 — 고친 것들

**이것이 이 병합의 본체다.** 원본은 자체 스키마로 말하고 있었고, 그대로
붙이면 로봇이 명령을 전부 폐기한다.

| # | 원본 | 왜 안 되는가 | 지금 |
| :-- | :--- | :--- | :--- |
| 1 | `{"cmd": "FORWARD", "ts": time.time()}` | 규약에 없는 스키마. `type`·`seq` 가 없고 `ts` 가 **초 단위 실수**라 규칙 ②·⑤ 로 폐기 | `Commander` 가 만드는 `MOVE` |
| 2 | `TURN_LEFT` · `TURN_RIGHT` | **제자리 회전은 지원하지 않는다** (DR-11). 로봇이 할 수 없는 동작 | 호(arc) `MOVE{step, angle}` — `steering_for()` |
| 3 | 위험 시 `send("STOP")` | `STOP` 은 일반 보행 정지이고 **FAILSAFE 를 걸지 않는다** | `ESTOP` (즉시 · 래치) |
| 4 | 첫 전문이 아무거나 | 로봇이 seq 역전으로 **명령을 통째로 폐기한다** | `open_session()` = `STOP` seq=1 |
| 5 | 상태 `MOVING`·`ROTATING`·`PLANNING`·`ARRIVED`·`ESTOP` | **FSM 13종에 없다.** 로봇이 폐기 + WARN 하고 텔레메트리 `state` 가 이전 값에 머문다 | 13종으로 사상 (`FSM_STATE_FOR`) |
| 6 | `tlm["yaw"]` · `tlm["ultrasonic"]` · `tlm["estop"]` | **규약에 없는 필드들.** 조용히 `None` 이 되어 IMU 보조가 내내 꺼져 있었다 | `imu.yaw`(deg) · `dist_cm` · `safety_latched` — `TelemetryReceiver` 경유 |
| 7 | `dist_cm < 15` 를 호스트가 판정해 E-STOP | **Tier 1 을 호스트로 옮기는 것**이다 (아키텍처 1.2 불변 규칙). 호스트가 꺼지면 판정이 사라진다 | `flags.obstacle` 을 **따라간다** |
| 8 | 측위 실패 → E-STOP | 자기 위치를 모르는 것은 위험이 아니라 **능력의 상실**이다 | `LOST` + 정지 (FR-6.6) |
| 9 | E-STOP 후 스스로 재개 | 사람 확인 없는 자동 해제 (DR-16) | `RESET_SAFE` + **텔레메트리로 해제 확인** |
| 10 | 자체 10Hz 루프 없음 · 변화 시에만 송신 | 10Hz 고정 송신이 곧 링크 신호다 (규약 1절) | `Commander.tick()` — 변화 없어도 계속 |
| 11 | 모든 수치가 코드 상수 | NFR-3① 매직 넘버 0개 | `config.yaml` |

### `STATE` 사상표

원본의 내부 단계는 유지하고 **내려보내는 값만** 13종으로 사상한다. 로봇은 이
값을 판단에 쓰지 않고 받아적을 뿐이므로 정보 손실이 아니고, 계획과 이동의
구분은 호스트 로그에 남는다.

| 내부 단계 | 내려보내는 `STATE` |
| :--- | :--- |
| `IDLE` | `IDLE` |
| `PLANNING` · `MOVING` | `PATROL` |
| `INSPECT` | `ZONE_INSPECT` |
| `LOST` | `LOST` |
| `HALTED` | `FAILSAFE` |

> ⚠️ **`AVOID` 는 내려보내지 않는다** (ADR-22). 호스트가 내려보내면 로봇이 그 값을
> 되돌려주므로 장애물이 사라진 뒤에도 `state` 가 계속 `AVOID` 로 오고, **해제를
> 알 수 없다.** 해제의 정본은 `flags.obstacle` 의 참→거짓 변화다.
>
> `test_avoid_is_never_announced` 가 이것을 못박는다.

### 안전 판정 주체

| 조건 | 판정 주체 | 이 코드의 대응 |
| :--- | :--- | :--- |
| 초음파 25cm 반사 정지 | **온보드 (Tier 1)** | `flags.obstacle` 을 따라 의도를 정지로 |
| 전도 · 저전압 · 링크두절 | **온보드 (Tier 1)** | `safety_latched` · `state=FAILSAFE` 를 따라 `HALTED` |
| 사용자 E-STOP | 호스트 | `ESTOP` 즉시 |
| **LiDAR 전방 위험거리** | **호스트** | `ESTOP` 즉시 — 아래 각주 |
| 측위 실패 | 호스트 | `LOST` + 정지 (E-STOP 아님) |
| 텔레메트리 침묵 | 호스트가 관측 | 정지 + `FAILSAFE` 표기. **송신은 계속한다** |

> **LiDAR 판정만 호스트인 이유** — LiDAR 는 호스트에 붙은 센서이므로 판정 주체가
> 호스트일 수밖에 없다. Tier 1 을 옮기는 것이 아니라 **온보드가 볼 수 없는 것을
> 보는 것**이다 (초음파는 정면 근거리만 본다 · DR-15). 온보드 판정을 대체하지
> 않고 더하며, 임계를 `obstacle_stop_cm`(25cm)보다 짧은 15cm 로 두어 **온보드가
> 먼저 반응한다.** `test_host_lidar_estop_is_tighter_than_the_onboard_threshold`
> 가 대조한다.

## 3. 리뷰 결과와 남은 Phase 2 전환 조건

### ① 스캔 링크 스키마 — 승인

확정값은 `docs/PROTOCOL_LIDAR.md` 7절에 있다.

### ② 기존 파일에 추가한 두 곳 — 검토 완료

값을 바꾼 곳은 없고, 절과 항목을 뒤에 붙였습니다.

| 파일 | 추가 | 근거 |
| :--- | :--- | :--- |
| `config/config.yaml` | `lidar:` 절 (약 95줄) | *"전 상수를 `config.yaml` 로 분리"* (README 엔지니어링 원칙). 별 파일을 두면 어느 쪽이 쓰이는지 코드를 읽어야 안다 |
| `requirements-dev.txt` | `matplotlib>=3.8` | 런타임이 아니라 개발 도구다. `requirements.txt` 는 건드리지 않았다 |

⚠️ `lidar` 절은 `common/config.py` 의 `REQUIRED_SECTIONS` 에 **넣지 않았습니다.**
넣으면 LiDAR 를 쓰지 않는 Phase 1 운용까지 기동을 막습니다
(`localization.track: none` 이 지금의 정상 상태입니다). 대신
`localization/settings.py` 가 그 절을 검증합니다.

| 설정 | 쓰는 곳 |
| :--- | :--- |
| `zones.ids` | **구역 라벨의 정본.** 좌표 파일이 라벨을 새로 만들지 않는다 |
| `zones.arrival_radius_mm` · `random_after_first_cycle` | 도착 판정 · 무작위 순찰 |
| `localization.settle_delay_ms` · `move_increment_mm` · `pose_timeout_ms` | 정지 후 대기 · 탐색 범위 · `LOST` 임계 |
| `gait.step_length_mm` · `turn_angle_deg` | 호 조향 |
| `safety.cmd_timeout_ms` · `link_loss_failsafe_ms` · `obstacle_stop_cm` | 안전 판정 |
| `fsm.avoid_attempts` | **막힌 구역을 몇 번까지 스스로 다시 확인할지** (5절 ③) |

### ③ `localization.track` 을 언제 `lidar` 로 바꿀지

현재 `none` 입니다 (Phase 1). **실기 모드는 `lidar` 가 아니면 기동을 거부하고**,
`--simulate` 는 거부하지 않습니다 — Phase 1 표준 구성에 LiDAR 가 없으므로
(CONTRIBUTING 1절) 그 값으로 실기 순찰을 돌리면 스캔을 기다리다 정지하고,
그때 원인을 찾기 어렵습니다.

### ④ 새 경로의 `CODEOWNERS` 담당 — 현재 규칙 유지

## 5. 병합 중에 잡은 결함 여섯 개

원본에 없던 문제가 아니라, **규약에 맞추는 과정에서 드러난** 것들이다.

### ① 동적 장애물이 구역을 영구히 봉인했다

원본은 신규 장애물을 마스크에 찍고 **한 번도 지우지 않았다.** 측위가 사이클마다
10~20cm 흔들리는 구간에서 오탐이 열 번 찍히자 통로가 막혀 구역 하나를 매 사이클
건너뛰었고, 로그에는 `zone_unreachable` 만 남아 **지도가 잘못된 것처럼 보였다.**

동적 장애물은 *이번 순찰의 사실이지 공간의 사실이 아니다.* 그래서 ⓐ 사이클
경계에서 표시를 버리고, ⓑ 구역을 포기하기 전에 표시를 버리고 다시 계획한다.

### ② 지도 파일 형식이 `maps/README.md` 와 달랐다

원본은 `slam_map.npy` + `map_meta.json` 을 냈다. 그런데 **`maps/README.md` 는 이
디렉터리에 ROS2 occupancy grid(`*.pgm` + `*.yaml`)를 두라고 이미 정해 두었다**
(ADR-18). 원본을 그대로 뒀으면 지정된 형식과 다른 것이 쌓였을 것이다.

**둘 다 낸다.**

| 파일 | 무엇 | 왜 |
| :--- | :--- | :--- |
| `slam_map.npy` + `map_meta.json` | 로그오즈 float32 | **작업 형식** — 이어서 매핑하고 정합한다 |
| `slam_map.pgm` + `slam_map.yaml` | ROS2 맵 서버 | **`maps/README.md` 가 지정한 형식** |

`.pgm` 만 두지 않는 이유 — **8비트라 로그오즈의 누적 확신을 잃는다.** 그것으로는
다음 세션에 이어서 매핑할 수 없고, **미관측과 반쯤 관측된 셀을 구분하지 못해**
`planner.inflate` 의 판단(*모르는 곳은 빈 곳이 아니다*)도 못 내린다.

PGM(P5)은 헤더 세 줄 + 원시 바이트라 numpy 로 직접 쓴다 — 이미지 라이브러리를
끌어오면 그것이 지도를 저장하는 모든 경로의 요구사항이 된다.

> ⚠️ ROS2 규약 두 가지를 지켜야 한다. **픽셀 255 가 자유, 0 이 점유**이고
> (`negate: 0`), **첫 행이 y 최대**다. 우리 격자는 행 0 이 y 최소이므로 위아래를
> 뒤집는다 — 뒤집지 않으면 지도가 상하 반전으로 로드되어 **벽은 그럴듯한데
> 경로가 전부 틀린다.** 조용한 종류의 오류라서 시험으로 못박았다
> (`test_pgm_rows_are_flipped_so_the_map_is_not_upside_down`).
>
> **`maps/README.md` 는 고치지 않았다.** 팀장 파일이며, 위 표를 반영할지는
> 병합 승인 시 정해 주시면 됩니다.

### ③ ①의 수정이 되돌아가기 루프를 만들었다

표시를 버리고 다시 계획하면 로봇이 그 장애물로 **되돌아간다.** 진짜 장애물이면
다시 찍히고 다시 버려져 되풀이한다 — 그렇게 만들었더니 한 번의 순찰에서
**E-STOP 이 2538회** 났다. 실기라면 서보 기어가 상하는 동작이다.

그래서 재확인 횟수를 **`config.fsm.avoid_attempts` 로 제한했다.** 회피 시퀀스가
같은 문제를 이미 그 값으로 풀었고 근거도 같다 — *"다 쓰고도 못 빠져나오면 멈춘
채로 둔다. 계속 흔들면 기어만 상하고, 갇힌 상황은 사람이 봐야 한다."*

> 시뮬레이터의 `--reset-after-estop` 에도 상한(5회)을 뒀다. 상한이 없으면
> **되풀이하는 실패가 검증을 통과한다** — 2538회를 세고서야 알아챘다.

### ④ 팽창 반경이 E-STOP 거리와 같아서 정상 순찰이 비상정지로 끝났다

**값 하나하나는 그럴듯했다.**

| 설정 | 값 | 뜻 |
| :--- | :--- | :--- |
| `robot_radius_mm` | 150 | 경로 중심선이 벽에서 이만큼 떨어진다 |
| `estop_distance_mm` | 150 | LiDAR 가 이만큼 가까운 것을 보면 E-STOP |

둘이 같으면 **경로를 완벽히 따라 걷는 것만으로 E-STOP 거리를 읽는다.** 추종
오차가 0 이어야 하는데, 호 조향밖에 없는 로봇(DR-11)에 그것을 요구할 수 없다.
한 사이클에 E-STOP 이 6회 나고 구역 하나를 못 갔다.

고친 것 —

* 팽창을 `robot_radius_mm + tracking_margin_mm`(150 + 100)으로 바꿨다.
  이름도 `PlanParams.clearance_m` 로 고쳐 *"로봇 반경"* 이 아니라
  *"경로가 유지할 거리"* 임을 드러냈다.
* `estop_distance_mm` 을 100 으로 낮췄다 (여전히 온보드 250mm 보다 짧아
  **온보드가 먼저 반응한다**).
* **관계를 기동 시에 확인한다** — `settings._validate` 가
  `robot_radius + tracking_margin > estop_distance` 를 검사하고 아니면
  `ConfigError` 로 기동을 막는다.

> 이런 종류는 **값을 하나씩 검토해서는 잡히지 않는다.** 어긋난 것은 값이 아니라
> 값들 사이의 관계이므로, 관계를 검사하는 곳이 있어야 한다. 텔레메트리 규칙
> ⑤(`tipped` 인데 `state != FAILSAFE` 면 폐기)가 *"값이 아니라 레코드 안의
> 모순을 본다"* 고 한 것과 같은 종류의 장치다.

### ⑤ 조향 중에도 최대 보폭으로 걸어 호가 가장 크게 그려졌다

④ 를 고친 뒤에도 한 구간에서 E-STOP 이 남았다. 원인은 `steering_for` 가
**조향만 키우고 보폭을 그대로 두는** 것이었다.

호의 반경은 대략 `step / angle` 이다. 조향은 규약 상한(±30deg)에 걸려 더 키울
수 없으므로, **반경을 줄이는 손잡이는 보폭뿐이다.** 최대 보폭으로 조향하면
로봇이 가장 큰 호를 그리며 방 안쪽 장애물을 돌지 못하고 벽으로 밀려간다.

오차에 비례해 조향을 키우고 **같은 비율로 보폭을 줄이도록** 고쳤다
(`TURN_STEP_REDUCTION = 0.5`). 회피 시퀀스가 후진 거리를 확보하는 것과 같은
이유의 제약이다 (DR-11 · `gait.reverse_distance_mm`).

> `TURN_STEP_REDUCTION` 은 **설정으로 빼지 않았다.** 실제 호 반경은 보행
> 시퀀스가 정하고 `gait_calibration` 이 아직 비어 있어서, 지금 설정 항목으로
> 만들면 **근거 없는 숫자에 설정의 권위가 붙는다.** 실측 후에 옮긴다.

### ⑥ IMU yaw 를 정합의 **중심**으로 써서 측위가 좌표계에 갇혀 있었다

**이것이 가장 찾기 어려웠고 가장 중요하다.**

원본은 `imu.yaw` 를 스캔 정합의 각도 탐색 **중심**으로 썼다 (원본
`estimate_pose` 의 `yaw_hint`, `USE_IMU_AUX`). 그러면 —

> **지도 좌표계의 방위가 IMU 값에서 탐색 범위(±8°) 이상 벗어날 수 없다.**

그런데 **지도 좌표계는 매핑을 시작한 자리가 정하고, IMU 의 0 은 로봇이 부팅한
자리가 정한다.** 둘 사이에는 임의의 옵셋이 있다. 로봇이 지도 기준 90° 를 보고
있는데 IMU 가 0° 를 보고하면 정합은 90° 를 **절대 찾지 못하고** 엉뚱하게 회전된
자세를 최선으로 고른다.

**증상이 원인과 전혀 닮지 않았다.** 자세 오차로 나타나지 않고 —

| 관측된 증상 | 실제 원인 |
| :--- | :--- |
| 지도에 없던 장애물 **30건 오탐** (장애물을 주입하지 않은 순찰에서) | 회전된 자세로 광선을 쏘니 엉뚱한 방향의 지도 벽과 비교되어 실측이 예상보다 가까워 보였다 |
| 구역 하나를 매 사이클 건너뜀 | 오탐이 통로를 막았다 (결함 ①) |
| `zone_unreachable` 로그만 남음 | 지도가 잘못된 것처럼 보였다 |

결함 ①·③ 은 **이것의 증상을 완화한 것**이었다. 근본 원인은 여기였다.

**고친 것** — `match()` 는 이제 절대 yaw 를 받지 않고 **직전 스캔 이후의 회전량**
(`yaw_delta`)만 받는다. 기준은 언제나 지도 좌표계의 이전 방위다. 표류도 이렇게
하면 한 주기분만 들어온다 — 절대값을 쓰면 표류가 누적되어 방이 부채꼴로 휜다.

> 원본 코드의 주석은 *"IMU 는 보조값이며 기준으로 삼지 않는다"* 고 옳게 적어
> 두었는데, **코드가 그것을 지키지 않고 있었다.** 탐색의 중심으로 쓰는 것이
> 곧 기준으로 삼는 것이다.
>
> `test_match_takes_imu_yaw_as_a_delta_not_an_absolute` 가 이것을 못박는다.
> 버그를 되살려 시험이 실제로 실패하는지 확인했다 — 96° 오차로 실패했다.

**실측 (시뮬레이션 · 같은 지도 · 2600틱 · 시드 3개)**

| 시드 | 오탐(재계획) | 구역 방문 | 사이클 | E-STOP |
| :--- | ---: | ---: | ---: | ---: |
| 3 (전) | 45 | 2 | 0 | 0 |
| 3 (후) | **0** | **3** | **1** | 0 |
| 5 (전) | 31 | 2 | 0 | 0 |
| 5 (후) | **0** | **6** | **2** | 0 |
| 11 (전) | 68 | 2 | 2 | 0 |
| 11 (후) | **0** | **5** | 2 | **1** |

> **오탐은 세 시드 전부 0 이 되었다.** 남은 것은 시드 11 의 E-STOP 1회이며,
> 그 사이클에서 구역 하나를 건너뛰었다 — 아래 7절 「아직 하지 않은 것」의
> 경로 추종 정밀도 항목이다. **실측 보행 속도 없이 튜닝할 수 없는 부분이고**,
> 안전 동작 자체는 옳게 걸렸다 (E-STOP → 사람 확인 → `RESET_SAFE`).

> 목업의 IMU 도 함께 고쳤다. **옵셋 0 을 보고하고 있어서 이 버그가
> 시뮬레이션에서 멀쩡해 보였다** — 지금은 임의 옵셋(137°)과 표류
> (0.02°/틱)를 보고하므로, 절대값으로 잘못 쓰는 코드가 다시 들어오면
> 시뮬레이션이 곧 깨진다.

### 규약 준수를 시험이 어떻게 보증하는가

`tests/test_lidar_patrol.py` 는 **컨트롤러가 실제로 내보내는 전문을
`CommandDecoder` 에 물린다.** 의도만 확인하면 "컨트롤러는 옳은데 나가는 전문은
틀린" 상태를 잡지 못한다 — 로봇이 보는 것과 같은 것을 본다.

시뮬레이션에서 나간 전문 **1122건 전량이 폐기 0 · 클램핑 0** 이었고, `seq` 는
단조 증가했고, 첫 전문은 `STOP` seq=1 이었고, 내려보낸 `STATE` 는
`PATROL`·`ZONE_INSPECT` 뿐이었다.

| 항목 | 결과 |
| :--- | :--- |
| 전체 시험 (`pytest -q`) | **871 passed** — 기존 786 + 새 85 |

| 나간 전문의 클램핑 | **0** (규약 범위를 넘겨 잘린 것이 없다) |
