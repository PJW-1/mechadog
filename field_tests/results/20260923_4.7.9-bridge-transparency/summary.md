## 무엇을 확인하려 했나

4.7.9 는 "모듈 마이크 음성을 로봇 경유로 PC 에 보내고, PC 의 응답 음성을 모듈 스피커로 낸다"
였다. 그러려면 로봇 4핀(I²C `0x34`)으로 **음성 파형**이 오가야 한다. 모듈을 USB 로 PC 에 직접
꽂는 구성은 로봇이 돌아다니는 현장에서 쓸 수 없기 때문이다.

## 결과

### 버스 스캔

| 시점 | IIC1 | IIC2 |
|---|---|---|
| 모듈을 IIC1 포트에 연결 | `0x34` `0x6A`(IMU) `0x77`(초음파) | 없음 |
| MP3 모듈로 교체 | `0x6A` `0x77` `0x7B` `0x7E` | 없음 |

⚠️ 로봇의 4핀 포트 가운데 **IIC1 은 하나뿐**이다. 다른 포트에 꽂았을 때는 `0x34` 가 보이지 않았다.

### 0x34 레지스터

| # | 동작 | 결과 |
|---|---|---|
| T0 | 대기 중 `0x00`–`0xFF` 전부 읽기 | 전부 `00` |
| T1 | `0x6E` ← `01` (1바이트) | "I'm going to take a break" 한 번 — 인과 불명(깨움 시간 초과 문구일 수 있다) |
| T1b | `0x6E` ← `02` (1바이트) ×2 | 무음 |
| T1c | `0x6E` ← `FF 05` | **"Obstacle ahead"** 재생 |
| T1d | `0x6E` ← `FF 01` | **"Recyclable waste"** 재생 |
| T2 | `0x70` ← `FF 05` ×2 | 무음 — 쓰기 무시. 바로 뒤 대조군 `0x6E ← FF 05` 는 다시 재생 |
| T3 | "Hello Hiwonder" → "Sit down" 발화 후 `0x64` 읽기 | 첫 읽기 `0C`(SIT-DOWN), 이후 `00` — **읽으면 지워지는 우편함** |

- `0x6E` 는 `[type, id]` 2바이트를 받아 `we_bridge_protocol.c` 매핑표의 고정 문구를 재생한다.
- 1바이트 읽기는 약 462 µs, 4바이트 읽기는 약 790 µs 였다(100 kHz, 안전 버스 IMU·초음파와 공유).

### MP3 모듈(OI-6)

| 동작(`0x7B` 레지스터 ← 값) | 결과 |
|---|---|
| `0C` ← 20(음량), `01` ← 1(1번 곡) | 무음 |
| `0C` ← 30, `05`(재생), `09`(다음 곡), `01` ← 2 | 공장 기본 곡("강남스타일") 재생 — 어느 명령이 재생을 시작했는지는 가리지 못했다 |
| `06`(일시정지) | 멈췄는지 확인하지 못했다 |

## 판정

**4.7.9 원안(음성 파형 중계)은 불가.** 0x34 브리지로는 명령 수준만 오간다.

| 방향 | 되는 것 | 안 되는 것 |
|---|---|---|
| 로봇 → 모듈 | 매핑표의 고정 문구 재생(`0x6E ← type,id`) | 임의 음성·합성 음성 재생 |
| 모듈 → 로봇 | 모듈이 인식한 명령어 id(`0x64`) | 마이크 음성 전달 → PC 에서 STT 불가 |

그래서 듣기는 XIAO 마이크(→ `20260923_xiao-mic`), 말하기는 MP3 모듈(TF 카드에 미리 저장한
문장)로 옮긴다. 결정 근거는 DECISIONS 의 ADR-38 에 있다.

## 남은 것 / 관찰

- `0x6E` 쓰기가 모듈 UART1 을 거치는지는 증명하지 못했다(시험 중 모듈 로그가 비어 있었다).
- `0x64` 우편함이 여러 개를 쌓는지(FIFO 깊이)는 보지 않았다.
- MP3: TF 카드 곡 목록, 어떤 명령이 재생을 시작했는지, 일시정지 동작, `0x7E` 의 정체가 남았다.
- ⚠️ Arduino-ESP32 는 `endTransmission(false)` 를 `requestFrom` 까지 미룬다. 그래서 반복 시작
  읽기의 `tx` 는 늘 0 으로 찍힌다. 판정은 `got` 으로 한다.
- ⚠️ `0x7B` 는 I²C 예약 구간(`0x78`–`0x7F`)에 있다. 스캔 범위를 `0x77` 까지로 두면 보이지 않는다.
