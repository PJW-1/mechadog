## 0. 시작하기 전에 짚을 것

### 이 문서가 카메라 폴더에 있는 이유

XIAO는 PPE를 판정하지 않는다. 비전 노드가 하는 일은 OV3660 영상을 JPEG로 내보내는 것까지이고, 객체 검출과 PPE 판정은 전부 Host PC가 한다.

그런데도 이 문서를 카메라 폴더에 두는 이유는, FR-9의 성패가 카메라 쪽 조건인 화각·해상도·프레임률·장착 방향에 걸려 있기 때문이다. 실제 구현 코드는 `host/vision/ppe_detector.py` 와 `host/behavior/posture.py` 에 들어간다.

### 자주 어긋나는 다섯 가지

아래는 전부 기존 문서 쪽이 맞다.

- XIAO에서 추론을 돌린다고 생각하기 쉽지만, 돌리지 않는다. 스트림 공급 전담이다(아키텍처 1.1).
- `ultralytics` 로 학습하면 안 된다. AGPL-3.0이라 채택하면 팀 코드 전체가 공개 의무에 걸린다(ADR-24). WBS 3.7.2에 남아 있는 "ultralytics" 문구는 정정 대상인 잔재다.
- 판정 거리를 미터로 정하면 안 된다. 거리를 잴 수단이 없으므로 bbox 클리핑으로 직접 판정한다(DR-15, FR-9.2.1).
- Pitch Up은 음수다. 고개를 드는 쪽이 음수이며(2026-09-15 실기 확정), 부호를 뒤집으면 머리가 오히려 더 잘린다.
- 데이터가 모자라도 시뮬레이션으로 채우지 않는다. 합성 데이터는 쓰지 않기로 했다(OI-13, #160).

## 1. 사용 하드웨어

### 비전 노드 — XIAO ESP32S3 Sense

- 센서는 OV3660, PSRAM 8MB, VGA MJPEG 송출 전용이다.
- 장착 높이 15cm, 하향 틸트 약 7도.
- 수평 화각 약 74도, 수직 화각 약 59도, f는 약 424px이다([실측 기록](../docs/measurements/2026-09-13-camera-fov.md)).

### 모션 노드 — MechDog

- ESP32-D0WD, 서보 8개, 초음파 센서(I2C `0x77`), IMU는 QMI8658(`0x6A`)이다.
- FR-9에서 맡는 일은 자세 상승, 눈 LED, 경고 음성, 그리고 온보드 반사 정지다.
- 자세별 몸통 피치 실측값은 `POSE -10/-20/-30` 이 각각 -6.4도, -17.3도, -26.5도이고 `sit`(`ACTION 1`)이 -29.2도다(2026-09-15, `mechdog-01`).

### 전원 — 보조배터리 5,000mAh 2구, USB-C

- XIAO 급전용이며 로봇 본체 2S 배터리와 전원이 분리되어 있다(DR-10).
- 운용 시간의 병목은 보조배터리가 아니라 본체 2S 배터리다. 추정 30~60분이며 OI-4에서 확인한다.

### 추론 — Host PC

- Windows 11 + WSL2, RTX 3080 10GB가 기준 PC다(OI-14).
- `coco.onnx` 와 `ppe.onnx` 추론, 행동 FSM, 대시보드를 전부 여기서 돌린다.
- YOLOX-S 추론 시간은 프레임당 8.2ms로 실측됐다.

### 시연 자재 — 안전모 3개, 안전조끼 3개

팀원 3인이 서로 다른 세 장소에서 촬영하고 시험한다. 장소 단위로 검증셋을 갈라 데이터 누수를 막기 위한 구성이다.

### 주의할 점 두 가지

학습 PC와 추론 기준 PC는 다르다. [MODEL_PLAN 0절](../docs/MODEL_PLAN.md)의 VRAM 예산표는 작성자 PC인 RTX 5070 12GB 기준이고, 성능 판정에 쓰는 기준 PC는 RTX 3080 10GB다. 학습은 오프라인 작업이라 예산 밖이지만, 추론 시간은 반드시 기준 PC에서 잰다.

카메라 장착을 바꾸면 화각을 다시 재야 한다. f값이 장착 높이에 민감해서 몇 cm만 달라져도 화각이 수 도씩 흔들리고, 그 값이 그대로 자세 상승 단계별 최소 판정거리를 바꾼다.

## 2. 데이터 흐름

```text
[XIAO ESP32S3 Sense]                                   [MechDog ESP32]
  OV3660 VGA 640x480                                     HW_MechDog HAL
      | JPEG (상한 25fps)                                   ^        |
      | HTTP MJPEG  :81/stream                              |        | 초음파 25cm
      v                                         UDP :5001   |        v 반사 정지(Tier 1)
+--------------------------------- HOST PC ----------------+-----------+ 10Hz
| StreamReader -> FrameQueue(최신 1장) -> VisionWorker(별도 스레드)     | <- UDP :5101
|                     |                                                |   텔레메트리 10Hz
|                     v  (1) coco.onnx (YOLOX-S)                       |
|                  person 검출 --- 없음 --> PPE 추론하지 않는다          |
|                     | 있음                     (FR-3.1.1 게이팅)      |
|                     v                                                |
|            PersonGate(300ms 안 3히트) -> PersonTracker(IoU 0.3)       |
|                     |                                                |
|                     v  person bbox 상단이 프레임 경계에 닿았나?       |
|              +--- 닿음(클리핑) ---> 자세 상승 시퀀스 -----------------+--> POSE / ACTION / MOVE
|              |                       (대상이 정지 상태일 때만)        |
|              v 안 닿음                                               |
|      person bbox 크롭 -> (2) ppe.onnx (YOLOX-Nano, 4클래스)           |
|                     |                                                |
|                     v  시간 창 누적 판정 -> 위반 확정                 |
|              Escalation L3 -------------------------------------------+--> LED red 2Hz / SOUND
|                     |                                                |
|                     v  스냅샷(원본 JPEG) + 이벤트 -> 대시보드(WS)     |
+----------------------------------------------------------------------+
```

흐름에서 반드시 지켜야 할 것이 넷 있다.

- 추론은 워커 스레드에서만 돌린다. 로봇은 명령이 300ms(`cmd_timeout_ms`) 동안 끊기면 스스로 멈추므로, 메인 루프를 막으면 로봇이 선다(`host/vision/worker.py`).
- PPE 모델에는 풀프레임이 아니라 person bbox를 크롭해서 넣는다. 입력이 작아져 정확도와 속도를 함께 얻는 것이 2단 구조의 취지다.
- 판정 결과는 추적 ID에 귀속시킨다. 적합이거나 미판정이면 그 대상을 다시 붙잡지 않고 순찰로 돌아가야 한다(FR-11.6, WBS 3.7.3).
- 스냅샷은 수신한 JPEG 원본을 그대로 저장한다. 다시 인코딩하면 사건 당시의 실제 입력이 아니게 된다(FR-3.9).

## 3. 학습 데이터셋

확보 방식은 OI-13에서 이미 닫혔다(2026-09-15). 정본은 [`datasets/README.md`](../datasets/README.md) 다.

### 무엇을 어디서 구하나

- 학습용은 공개 PPE 데이터셋을 쓴다. 데이터셋마다 라이선스를 개별 확인하고 비상업(NC) 조건은 제외한다. 다양한 사람·자세·배경을 촬영 없이 확보하기 위해서다.
- 검증과 시험은 XIAO 실기 프레임만 쓰고 장소 단위로 나눈다. 높이 15cm에서 위를 보는 시점은 눈높이 CCTV로 찍은 공개 사진과 전혀 다르므로, 공개 데이터로 잰 성능은 우리 카메라의 성능이 아니다.
- 실사 프레임은 검증 성능이 모자랄 때만 학습에도 섞는다.
- 합성 데이터는 쓰지 않는다(#160). 되살리려면 팀 합의와 WBS 등재가 먼저다.
- `person` 은 학습 대상에서 제외한다. 사람 검출은 COCO 검출기가 담당한다(FR-9.1.1, ADR-12).

공개 데이터 후보는 SHWD(`hat`/`person` 두 클래스를 `helmet`/`no_helmet` 으로 매핑)와 Roboflow Universe의 PPE·조끼 세트들이다. 각각 라이선스를 따로 확인하고, 데이터 카드에 출처·라이선스·이미지 수·클래스 분포를 적는다.

### 검증셋 촬영 조건

팀원 3인이 같은 조건으로 찍는다.

- 장소는 세 곳이며 조명과 배경이 서로 달라야 한다. 장소별로 갈라 누수를 막는다.
- 거리는 1m, 2m, 3m 세 지점을 모두 찍는다.
- 자세는 정면·옆·뒤, 웅크림, 팔 들기, 몸 기울이기를 포함한다.
- 착용 조합 네 가지를 모두 찍는다. 안전모와 조끼 둘 다, 안전모만, 조끼만, 둘 다 없음이다. 이 네 조합이 라벨의 정답지가 된다.
- 경계 사례도 반드시 넣는다. 머리가 프레임 위쪽에서 잘리는 장면(판정 보류 경로 검증용), 역광, 어두운 조명이다.

### 라벨링 규약

- `helmet` 은 머리에 쓴 안전모 영역에 친다. 손에 든 안전모는 라벨하지 않는다. 착용한 것만 센다.
- `no_helmet` 은 안전모를 쓰지 않은 머리에 친다. 후드, 모자, 맨머리는 전부 여기에 들어간다.
- `vest` 는 몸통에 걸친 형광 조끼에 친다. 가방끈이나 하네스는 조끼가 아니다.
- `no_vest` 는 조끼가 없는 몸통에 친다. 반팔, 긴팔, 점퍼가 전부 해당한다.

여기서 가장 흔한 실수가 하나 있다. `no_helmet` 과 `no_vest` 는 그 물건이 없는 신체 부위에 라벨해야 한다. 배경에 라벨하면 아무것도 없는 곳이 위반으로 학습된다.

1차 라벨링은 색상 휴리스틱으로 품을 줄인다. person bbox의 위쪽 25% 구간에서 주황 비율을, 가운데 55% 구간에서 연두 비율을 계산해 초안 라벨을 달고 사람은 검수만 한다. 이 휴리스틱은 대조군으로도 남겨서, 색만으로 어디까지 되고 어디서 깨지는지를 실측으로 기록한다.

데이터셋은 Git에 넣지 않는다. 용량과 라이선스 때문이며 `.gitignore` 의 `datasets/*` 로 막혀 있다.

## 4. 사용 AI 모델

검출기는 2단 구조다. 범용 검출기가 사람을 찾은 프레임에서만 PPE 모델이 돌아간다.

### 1단 — 범용 검출기 (이미 있음)

- 모델은 YOLOX-S이고 파일은 `models/coco.onnx` 다.
- 라이선스는 Apache-2.0, Megvii Inc.
- 공식 배포 ONNX를 `python tools/fetch_models.py` 로 받는다. 학습이 필요 없다.
- COCO 80클래스를 쓰며 매 프레임 돈다.

### 2단 — PPE 검출기 (새로 만들 것)

- 모델은 YOLOX-Nano이고 파일은 `models/ppe.onnx` 다.
- 클래스는 `helmet`, `no_helmet`, `vest`, `no_vest` 네 가지다.
- 입력은 640×640으로 1단과 같고, 실행은 ONNX Runtime에서 DirectML 우선, 안 되면 CPU로 폴백한다.
- 사람이 검출된 프레임에서만 돈다.

YOLOX-Nano를 고른 이유는 1단과 계열이 같아서 전처리와 디코딩 어댑터를 그대로 재사용할 수 있기 때문이다. `host/vision/detector.py` 의 `YoloxAdapter` 가 클래스 수를 `raw.shape[1] - 5` 로 일반화해 두어서 4클래스 출력도 그대로 동작한다. 학습 후 시험으로 확인한다. 클래스가 4개뿐이고 입력도 작으므로 nano 용량이면 충분하고, 2단 구조라 프레임당 비용도 사실상 없다.

### 학습 설정 (시작점)

이 값들은 WBS 3.7.2 산출물에 그대로 기록한다.

- 초기 가중치는 YOLOX-Nano 공식 COCO 가중치에서 fine-tune 한다. 4클래스를 처음부터 학습하기에는 데이터가 모자란다.
- epochs 100, early stop patience 20, batch 16.
- optimizer는 SGD momentum 0.9, lr 0.01, cosine decay, warmup 5 epoch. YOLOX 공식 레시피 그대로다.
- 증강은 HSV(±0.015/0.7/0.4), scale 0.5, translate 0.1, flip 0.5, mosaic 1.0이며 마지막 15 epoch에서 mosaic을 끈다.
- 평가는 mAP50과 함께 클래스별 recall을 본다.

색 채도 증강은 약하게 준다. 주황과 형광이 판정의 단서인데 색을 크게 흔들면 그 특징을 지워 버린다.

### 내보내기와 연동

```bash
python YOLOX/tools/export_onnx.py --output-name ppe.onnx --opset 11 --input 640   # batch 고정 1
```

`config.yaml` 의 `vision.ppe.model_family` 를 `yolox` 로 채운다. 현재는 `null` 이다. 이 값은 기록용 장식이 아니라 어댑터를 고르는 값이라서, 비어 있으면 `Detector.open()` 이 기동을 거부한다. 학습 프레임워크 버전, 학습 날짜, 데이터셋 커밋 해시를 주석으로 함께 남긴다. 재현 가능해야 한다는 것이 요구사항이다(FR-9.1.2).

가중치 파일은 저장소에 넣지 않는다(`.gitignore` 의 `*.onnx`, `models/*`). 배포 방법은 6.3절에 적었다.

## 5. 검출 조건

가장 앞에 오는 것은 모드 게이트다. PPE 모델은 공장 모드에서만 돌고, 경비 모드와 현장지원 모드에서는 아예 돌리지 않는다(FR-11, WBS 3.4.4).

조건은 여섯 가지이며 값은 `config.vision.ppe` 에 있다.

- 사람 게이팅. 사람이 확정된 프레임에서만 추론한다. `detect_window_ms` 300ms 안에 `detect_hits_required` 3회다(FR-3.1.1, ADR-25).
- 머리 가시성. person bbox 상단이 프레임 경계에 닿지 않았을 때만 판정한다. `require_head_visible: true`, `head_margin_px: 8` 이다(FR-9.2.1, DR-15).
- 대상 정지. 자세 상승 시퀀스는 대상이 멈춰 있을 때만 시작한다. `require_target_static: true`, `static_threshold_px: 20`, `static_frames: 5` 다(FR-9.2.0).
- 신뢰도. `conf_threshold: 0.5`, `iou_threshold: 0.45` 로 사람 검출과 같다.
- 위반 확정. 시간 창 1.5초 안에 3회 검출되면 확정한다. 프레임 수가 아니라 시간 창이라는 점이 중요하다(FR-9.4).
- 위반 해제. 창이 완전히 빌 때 푼다. 진입과 해제를 비대칭으로 두어 게이트가 떨리는 것을 막는다.

### 머리 가시성이 왜 핵심인가

카메라가 15cm 높이에 있어서 가까운 거리에서는 사람 머리가 화각을 벗어난다. 그래서 판정 가능 조건과 PPE 검출 가능 조건이 정확히 일치한다. 머리가 보이지 않으면 애초에 안전모를 볼 수 없기 때문이다. 이 때문에 거리를 미터로 재지 않고 bbox 클리핑으로 직접 판정한다.

### 아직 없는 설정값

위반 확정 창 값이 `config.yaml` 에 없다. 사람 게이트의 300ms/3히트를 그대로 쓰면 PPE에는 창이 너무 짧다. `vision.ppe.violation_window_ms: 1500` 과 `violation_hits_required: 3` 을 새로 만들고 값을 코드에 박지 않는다(NFR-3①).

### 성능 판정 기준

판정 기준은 mAP가 아니다.

- `no_helmet` 과 `no_vest` 의 recall이 0.90 이상이어야 한다. 위반을 통과로 읽는 것이 가장 나쁜 오류이기 때문이다. 모자라면 `conf_threshold` 를 0.4까지 내려 다시 잰다.
- mAP50은 학습 리포트용으로 기록만 한다.
- 추론 시간은 기준 PC에서 person 크롭 한 건당 잰다. 1단의 8.2ms와 합쳐 프레임 예산을 확인한다.

## 6. 검출 시 대응 방법

### 6.1 판정이 안 될 때 — 단계적 자세 상승

FR-9.2.2, WBS 3.5.7에 해당한다.

시퀀스는 대상이 정지 상태일 때만 시작한다. 움직이는 사람은 따라갈 수 없기 때문이다. 로봇 Trot 속도가 10~30cm/s인데 사람 보행은 120~150cm/s라 5~15배 차이가 나고, 상향 자세에서는 이동조차 못 한다.

단계는 셋이다.

1. `POSE pitch = -15` 로 시선을 올린다(`posture.pitch_up_deg: -15`). 음수가 고개를 드는 쪽이다.
2. `ACTION 1`(`sit_dowm`)으로 앉는다. 상체가 올라가면서 시선이 크게 상향된다.
3. 후진해서 거리를 벌린다(`posture.back_off_mm: 300`). 전신을 화각 안에 넣기 위해서다.

단계마다 지켜야 할 것은 다음과 같다.

- 각 단계 뒤 `settle_ms` 500ms를 기다린 다음 다시 검사한다.
- 이동이 필요하면 먼저 기본 자세(`ACTION 0`, `stand_four_legs`)로 돌아온 뒤에 움직인다(`return_before_move: true`, FR-9.2.3). 상향 자세에서는 전방 지면이 보이지 않는다.
- 대상이 화각을 벗어나면 즉시 중단하고 복귀한다(`abort_on_target_lost: true`, FR-9.2.4).
- 같은 추적 ID에 대한 재시도는 `max_posture_retries` 2회까지다. 넘어가면 `PPE_UNDETERMINED` 이벤트를 남기고 순찰을 재개한다. 판정 실패도 결과이므로 대시보드에 "미판정, 대상 이동 중"으로 띄운다. 띄우지 않으면 같은 상황이 고장으로 보인다.
- `stand_two_legs` 는 쓰지 않는다. 마스트 때문에 무게중심이 높아 전도 위험이 크다.
- 전도 감지와는 충돌하지 않는다. 자세 상승이 만드는 몸통 피치가 30도 안쪽이고 전도 임계는 60도라, 억제 플래그 없이 임계값 분리만으로 해결된다(DR-16, 2026-09-15 실측).

화각 실측이 준 정량 요구값도 참고한다. 상단 광선이 수평선 위 약 27.5도라서 3m에서 171cm(헬멧이 간신히 들어온다), 2m에서 119cm까지만 덮는다. 헬멧을 판정하려면 2m 기준으로 약 10도, 1.5m 기준으로 약 18도의 자세 상승이 필요하다.

### 6.2 위반이 확정됐을 때 — 에스컬레이션 L3

FR-9.3에 해당하며 네 가지를 한다.

- 경고 방송. `SOUND phrase_id` 로 보내며 값은 `escalation.sound.ppe_violation` 이다. 아직 `null` 이고 WonderEcho 문구를 플래싱한 뒤 실제 ID를 넣는다(OI-10/11).
- 눈 LED 적색 점멸. `LED color=red blink_hz=2` 이며 `escalation.led.l3_alarm` 과 `l3_blink_hz` 를 따른다.
- 스냅샷과 이벤트 기록. 수신 JPEG 원본과 이벤트 로그를 대시보드로 보낸다.
- 단계 상승. `PPE_VIOLATION` 이 `Level.L3` 로 매핑되어 있으며 `host/behavior/escalation.py` 에 이미 등재되어 있다.

여기서 두 가지를 혼동하기 쉽다.

FSM 상태가 함께 바뀌는 것은 아니다. `TRACK` 에서는 `ALERT` 로 전이하지만, `ALERT` 상태에서 위반이 나오면 상태는 그대로 두고 에스컬레이션 단계만 올린다(아키텍처 3.8.3).

L3는 관리자 확인으로만 풀린다. PPE 위반은 다시 인증할 대상이 아니다. 인증 성공으로 풀리는 것은 인증 실패로 들어간 L3뿐이다. 페일세이프 해제 경로와도 분리한다. 하나로 묶으면 비상정지를 눌렀다 푸는 것만으로 경보가 지워진다(ADR-26).

### 6.3 학습된 모델을 팀에 배포하는 방법

`ppe.onnx` 를 저장소에 커밋하지 않는다. `.gitignore` 가 `*.onnx` 와 `models/*` 를 막고 있고, `coco.onnx` 와 똑같은 경로를 쓴다.

1. 릴리스(또는 팀 공용 저장소)에 `ppe.onnx` 를 자산으로 올린다.
2. `tools/fetch_models.py` 의 `WEIGHTS` 에 URL, 바이트 크기, SHA-256, 라이선스 메모를 한 항목 추가한다. 여기가 정본이다.
3. 팀원은 `python tools/fetch_models.py` 한 줄로 받는다. 스크립트가 크기와 해시를 자동으로 검증한다.
4. `models/README.md` 의 표를 사람이 읽을 수 있게 갱신한다. 시험이 정본과 대조한다.

`curl` 로 받으라고 적지 않는다. 그렇게 적어 두면 사람은 다운로드 줄만 복사하고 해시 확인 줄은 건너뛴다. 검증을 건너뛸 수 없도록 스크립트 한 곳에 묶는다.

## 7. 통신 설정

### 7.1 영상 — XIAO에서 Host로, HTTP MJPEG

- 접속은 2.4GHz 공유기 STA 전용이다. AP 모드는 열지 않으며 `wifi_secrets.h` 는 Git에서 제외된다.
- 제어는 `http://<XIAO-IP>:80/` 이고 설정값은 `network.vision_control_port` 다.
- 영상은 `http://<XIAO-IP>:81/stream` 이고 설정값은 `network.vision_stream_port` 다. 스트림이 포트를 오래 점유하므로 제어 포트와 분리해 두었다.
- 해상도는 VGA 640×480이며 `vision.resolution` 값이 `/profile?name=VGA` 로 내려간다.
- 프레임률 상한은 25fps다. `vision.stream_fps_limit` 을 호스트가 기동할 때 `/profile?name=VGA&fps=25` 로 내려보낸다. 펌웨어 기본값은 폴백이다.
- 장착 방향은 `vision.mount_rotation` 이며 `/orient?rot=180` 으로 바꾼다. 재부팅하면 풀리므로 설정 파일이 정본이다.
- 단절 판정은 `vision.stall_timeout_ms` 2초다. 비전 단절은 안전 문제가 아니라 기능 저하이므로, 순찰과 회피는 계속하고 사람 인지만 끈다.

스트림은 한 클라이언트만 받는다. 브라우저로 열어 둔 채 호스트를 돌리면 나중에 붙은 쪽이 한 장도 못 받고 타임아웃으로 끝나는데, 이것은 죽은 스트림과 구분되지 않는다. PPE 검수 중 화면이 검게 나오면 카메라 고장보다 다른 수신자가 붙어 있는지를 먼저 확인한다.

### 7.2 명령과 텔레메트리 — Host와 MechDog 사이, UDP

- 제어 명령은 `network.cmd_port` 5001번으로 10Hz 고정 송신한다. 변화가 없어도 계속 보내며, 그것이 곧 하트비트다.
- 텔레메트리는 `network.telemetry_port` 5101번으로 10Hz 수신한다.

FR-9가 쓰는 명령은 `POSE`, `ACTION`, `MOVE`, `LED`, `SOUND`, `STATE` 여섯 가지다. 모두 한 줄 JSON이며 `seq`(단조 증가), `ts`(epoch 밀리초), `type`(대문자) 세 필드를 공통으로 갖는다.

```json
{"seq": 4101, "ts": 1758153600123, "type": "POSE",   "pitch": -15, "roll": 0, "height": 0, "dur": 300}
{"seq": 4102, "ts": 1758153600623, "type": "ACTION", "id": 1}
{"seq": 4103, "ts": 1758153601123, "type": "LED",    "color": "red", "blink_hz": 2}
{"seq": 4104, "ts": 1758153601223, "type": "STATE",  "state": "ALERT"}
```

`ACTION` 은 블로킹이라는 점을 반드시 기억한다. 벤더의 `action_run` 이 구간마다 `delay()` 로 `loop()` 를 통째로 멈추기 때문에, 그동안 UDP 수신도 300ms 명령 타임아웃 검사도 함께 멈춘다. 그래서 단일 구간 액션만 싣고, 펌웨어가 보행 중에는 `ACTION` 을 거절한다. 자세 상승 2단계를 정지 상태에서만 하는 또 하나의 이유다.

`sit_dowm` 오타는 그대로 둔다. 벤더 `aclist[]` 에 등록된 이름이라 고쳐 적으면 찾지 못하고, 오류도 없이 조용히 아무 일도 일어나지 않는다.

## 8. 테스트 방법

완료 기준은 여기 적지 않는다. 정본은 [WBS](../docs/WBS.md) 의 같은 번호다.

결과는 `python TEST_MECHDOG/run_tests.py` 를 돌려 `TEST_MECHDOG/results/<날짜>_<번호>/` 에 남긴다. 그다음 엑셀 `일정과 업무` 시트에 상태, 실제완료일, 결과 요약, 근거 링크, 확인자 다섯 칸을 채운다. 결과 요약은 합격·불합격이 아니라 숫자로 적는다.

### T1 · 데이터셋 (WBS 3.7.1, PC)

데이터 카드에 출처, 라이선스, 이미지 수, 클래스 분포가 다 있는지 본다. 비상업(NC) 세트가 섞이지 않았는지, 검증셋이 장소 단위로 갈렸는지도 확인한다. 통과 기준은 카드가 빠짐없이 채워져 있고 학습 장소와 검증 장소의 교집합이 0인 것이다.

### T2 · 학습 재현성 (WBS 3.7.2, PC)

학습 로그와 함께 `model_family`, 프레임워크 버전, 데이터셋 해시가 `config.yaml` 주석에 남아 있는지 본다. 같은 값으로 다시 학습했을 때 재현 가능해야 한다(FR-9.1.2).

### T3 · 오프라인 성능 (WBS 3.7.2, PC)

XIAO 실사 검증셋으로 클래스별 recall과 mAP50을 잰다. 통과 기준은 `no_helmet` 과 `no_vest` 의 recall이 0.90 이상인 것이다.

### T4 · 판정기 (WBS 3.7.3, PC)

다섯 가지를 확인하고 pytest 회귀로 고정한다.

1. 사람이 없는 프레임에서 PPE 추론이 돌지 않는가(게이팅).
2. 머리가 잘린 프레임에서 판정이 보류되는가.
3. 웅크린 자세에서도 전신이 보이면 정상 판정되는가.
4. 판정 결과가 추적 ID에 귀속되는가.
5. 경비 모드에서 모델이 아예 돌지 않는가.

### T5 · 자세 상승 (WBS 3.5.7, 실물)

1.5m, 2m, 3m에서 클리핑을 만든 뒤 세 단계가 순서대로 재검사하는지 본다. 이동 전에 기본 자세로 복귀하는지, 대상이 벗어나면 즉시 중단하는지, 2회를 넘기면 `PPE_UNDETERMINED` 를 남기는지도 함께 확인한다. 각 거리에서 몇 단계 만에 판정됐는지를 숫자로 기록하고, IMU 몸통 피치가 60도에 닿지 않는 것을 확인한다.

### T6 · 위반 대응 (FR-9.3, 실물)

위반 확정 뒤 L3 진입, 적색 LED 2Hz 점멸, 경고 방송, 스냅샷과 이벤트 기록이 모두 일어나는지 본다. 관리자 확인 전에는 풀리지 않는 것과, E-Stop을 눌렀다 푸는 것으로 경보가 지워지지 않는 것도 확인한다.

### T7 · 성능 회귀 (PC)

1단과 2단을 합친 추론 시간, 스트림 fps 유지, 메인 루프가 밀리지 않는지(`last_cmd_age_ms`)를 본다. VGA에서 15fps 이상이 유지되고 명령 주기 10Hz가 지켜져야 한다.

### 시험할 때 주의할 것

T5와 T6은 세 장소에서 각자 한 번씩 돈다. 안전모와 조끼를 3세트 준비한 이유가 그것이다. 3절의 같은 조건표로 찍고 결과 수치는 장소를 구분해서 적는다.

T3을 공개 데이터셋 검증셋으로 대신하지 않는다. 그 숫자는 우리 카메라의 성능이 아니다.

잡음 프레임으로 정확도를 시험하지 않는다. `/255` 정규화를 넣어 일부러 고장낸 전처리도 잡음에서는 정상과 똑같이 0건을 냈다. 잡음 시험은 정상과 완전 고장을 구분하지 못한다. 박스를 그려 눈으로 대조하는 절차를 T3과 T4에 포함한다.

## 9. 착수 순서와 남은 결정

### 순서

1. 공개 데이터셋 선정, 라이선스 확인, 라벨 매핑 (WBS 3.7.1). 선행 없음.
2. 세 장소 검증셋 촬영 (WBS 3.7.1). 안전모와 조끼 실물이 있어야 한다.
3. YOLOX-Nano fine-tune과 `ppe.onnx` 내보내기 (WBS 3.7.2). 1, 2번이 선행이다.
4. `ppe_detector.py` 작성 — 게이팅, 클리핑 검사, 시간 창 판정 (WBS 3.7.3). 3번이 선행이다.
5. `posture.py` 작성 — 단계적 자세 상승 시퀀스 (WBS 3.5.7). 실물과 WBS 2.1.4가 선행이다.
6. 공장 모드 게이트에 배선 (WBS 3.4.4). 4, 5번이 선행이다.

### 남은 결정

- `vision.ppe.model_family` 가 `null` 이다. 학습에 착수하면서 `yolox` 로 채운다.
- `escalation.sound.ppe_violation` 이 `null` 이다. WonderEcho 문구를 플래싱한 뒤 ID를 넣는다(OI-10/11).
- `violation_window_ms` 와 `violation_hits_required` 키가 아예 없다. 1.5초와 3히트로 새로 만들자고 제안한다.
- WBS 3.7.2의 "ultralytics" 문구는 ADR-24와 충돌하는 잔재라서 정정해야 한다.
- YOLOX-Nano 채택을 ADR로 승격해야 한다(MODEL_PLAN 6절 1번 항목).
