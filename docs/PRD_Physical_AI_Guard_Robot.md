### 1.1 프로젝트 비전

Hiwonder MechDog은 완성도 높은 **저수준 모션 API**(`move`, `transform`, `set_gait_params`)를 제공하지만, 그 위에는 앱 원격조작과 사전 정의 액션 재생만 존재한다. 본 프로젝트는 그 API를 **HAL(Hardware Abstraction Layer)로 취급**하고, 그 위에 **인지(Perception) → 판단(Behavior FSM) → 항법(Navigation)** 계층을 새로 구축하여 자율 경비·순찰 임무를 수행하는 Physical AI 시스템을 만든다.

> 이는 상용 4족 로봇(예: Boston Dynamics Spot)의 개발 방식과 동일한 구조다. 제조사가 보행·균형을 제공하고, 개발자는 그 위에 자율 스택을 얹는다. **본 프로젝트의 기술적 기여는 IK가 아니라 자율성 계층에 있다.**

### 1.2 문제 정의 및 솔루션

- **Problem** — 교육용 4족 로봇은 (a) 사람이 계속 조종해야 하고, (b) 환경을 인지하지 못하며, (c) 통신이 끊기면 위험한 상태로 방치된다.
- **Solution**
  1. **Thin-Client / Offboard Brain 아키텍처** — 무거운 추론과 SLAM은 Host PC가, 안전에 직결되는 반사 동작은 로봇이 담당하는 3-Tier 레이턴시 분리
  2. **행동 상태 머신(Behavior FSM)** 기반 자율 순찰 · 장애물 회피 · 침입자 인지 및 추종
  3. **Fail-Safe First** — 통신 두절·저전압·전도 시 로봇이 스스로 안전 상태로 진입
  4. **4대 엔지니어링 축 + CI/CD** — 파라미터화 / 예외처리 / 성능 / 로깅을 자동 검증

### 1.3 설계 결정 기록 (Design Decisions & Rejected Alternatives)

본 절은 **검토했으나 채택하지 않은 설계 대안**과 그 이유를 기록한다. 4족 보행 로봇 프로젝트에서 자연스럽게 떠오르는 접근들이지만, 본 하드웨어 구성과 개발 여건에서는 성립하지 않거나 비용 대비 효과가 낮다고 판단한 것들이다.

프로젝트 진행 중 "왜 저렇게 안 했지?"라는 재검토가 반복되는 것을 막고, 전제가 바뀌었을 때 어떤 결정을 다시 열어야 하는지를 명확히 하기 위함이다.

---

#### DR-1. 8-DOF 역기구학(IK) 엔진을 직접 구현하지 않는다

- **검토한 대안** — 링크 구조 4족의 IK를 직접 유도하여 서보 각도를 산출하고, Trot/Walk/Crawl 보행 생성기를 자체 구현
- **채택하지 않은 이유** — Hiwonder가 `HW_MechDog.h` / `mech_base_types.h`를 오픈소스로 제공하며, `move(step_length, angle)` · `transform(pose, duration)` · `set_gait_params(...)` 수준의 API로 IK와 보행 생성이 이미 완비되어 있다. 이를 다시 구현하는 것은 검증된 코드를 미검증 코드로 교체하는 일이며, 프로젝트의 실제 난제(자율 인지·판단·항법)에 쓸 시간을 소모한다.
- **채택안** — 해당 라이브러리를 **HAL로 취급**하고 그 위에 자율 스택을 구축한다. 상용 4족 로봇 개발과 동일한 계층 구조다.
- **재검토 조건** — 라이브러리가 제공하지 않는 보행 패턴이 임무상 필수가 될 경우

#### DR-2. 노드 간 유선 통신 프로토콜(UART + CRC16)을 쓰지 않는다

- **검토한 대안** — 비전 노드와 모션 노드를 UART로 배선하고, `[HEADER][LEN][CMD][PAYLOAD][CRC16]` 형식의 고속 전이중 패킷 프로토콜 구현
- **채택하지 않은 이유** — 비전 노드(XIAO)는 **독립 전원으로 본체에 부착만 하는 구성**이다. 배선을 도입하면 이 구조의 최대 이점인 *본체 무개조 · 노드 간 고장 격리 · 독립 개발*이 모두 사라진다. 또한 두 노드 모두 Wi-Fi를 내장하고 있어 유선 링크가 제공하는 이점이 크지 않다.
  - 부가 정정: CRC16은 오류를 **검출**하는 수단이며 왜곡을 방지하지 못한다. 본 문서는 "검출 후 폐기" 로 명세한다.
- **채택안** — Host PC를 허브로 하는 **Wi-Fi 스타 토폴로지 + UDP/JSON 메시지**(FR-5)
- **재검토 조건** — 메인 ESP32의 Wi-Fi를 쓸 수 없는 것으로 판명될 경우(RISK-01). 이때는 XIAO에서 UART 2가닥만 최소 연결한다.

#### DR-3. 온보드 Edge AI 추론을 하지 않는다

- **검토한 대안** — XIAO ESP32S3에서 경량 사람 검출 모델(FOMO / ESP-DL 계열)을 직접 추론
- **채택하지 않은 이유** — ESP32-S3급에서의 사람 검출은 96×96 그레이스케일 기준 수 FPS 수준이고, MJPEG 스트리밍을 동시에 수행하면 더 낮아진다. 반면 데스크탑 GPU(RTX 3080)에서는 동급 모델이 한 자릿수 ms로 추론되며, 정확도 면에서도 훨씬 큰 모델을 쓸 수 있다. **정확도·속도 양쪽에서 비교가 되지 않는다.**
- **채택안** — XIAO는 **영상 송출만 전담**하고, 객체 검출 추론은 Host PC(Tier 2)에서 수행
- **트레이드오프** — Wi-Fi 단절 시 사람 인지 기능이 정지한다. 이를 NFR-2.6(Graceful Degradation)으로 명세하여, 인지 기능이 죽어도 순찰·회피는 유지되도록 설계한다.
- **재검토 조건** — 무선 환경이 열악하여 오프보드 인지 지연이 NFR-1.1(250ms)을 상시 초과할 경우

#### DR-4. 클라우드에 제어 루프를 올리지 않는다

- **검토한 대안** — 인지·판단 전체를 클라우드 AI로 처리하여 로봇과 PC를 모두 얇게 유지
- **채택하지 않은 이유** — 인터넷 왕복은 지연이 100~300ms에 지터가 크고, 연결이 끊기면 로봇이 제어 불능 상태가 된다. 실시간 제어 루프에 부적합하다.
- **채택안** — **3-Tier 레이턴시 분리**(2.2절). 클라우드는 비실시간 추론(현장 위험요소 판독, 이벤트 리포트)인 Tier 3에만 배치하며, 이 경로의 실패가 주행에 영향을 주지 않도록 격리한다.

#### DR-5. 온보드 SLAM을 시도하지 않는다

- **검토한 대안** — ESP32-S3의 8MB PSRAM에 TinySLAM/CoreSLAM 계열 경량 SLAM을 이식
- **채택하지 않은 이유** — 이론적으로 소형 occupancy grid는 PSRAM에 올릴 수 있으나, 구현·튜닝 난도가 높아 프로젝트 전체를 잠식할 위험이 크다. XIAO는 이미 카메라와 Wi-Fi 스트리밍으로 자원이 포화 상태다.
- **채택안** — 로봇은 스캔 데이터를 중계만 하고, SLAM은 Host PC에서 수행(FR-6.1)

#### DR-6. LiDAR를 MechDog 메인보드에 직결하지 않는다

- **검토한 대안** — LD19를 메인 ESP32의 UART에 연결하고 메인보드가 스캔을 중계
- **채택하지 않은 이유** — ① 확장 포트(I2C 2개)가 비전 모듈·초음파·Wi-Fi 모듈로 이미 점유되어 있다. ② 더 결정적으로, **메인 ESP32의 최우선 실시간 태스크는 8개 서보의 보행 제어**다. 여기에 4,500 pts/s 스트림 수신과 무선 중계를 얹으면 제어 루프에 지터가 발생하고, 4족 보행에서 제어 지터는 곧 전도로 이어진다.
- **채택안** — LiDAR를 **독립 노드**로 분리. **별도 ESP32 DevKit 으로 확정**(OI-7 닫힘, 근거는 [조립 문서](HARDWARE_ASSEMBLY.md) 2.4)

#### DR-7. 보행 중 연속 LiDAR 스캔을 하지 않는다 (Stop-and-Scan 채택)

- **검토한 대안** — 순찰하며 실시간으로 연속 스캔하여 맵을 갱신
- **채택하지 않은 이유** — 2D LiDAR는 스캔 평면이 수평임을 가정하는데, 4족 보행은 매 스텝마다 피치·롤이 변동한다. **피치가 10° 틀어지면 5m 거리에서 스캔 평면이 약 87cm 상하로 쓸려** 바닥·천장을 찍고 맵이 오염된다.
- **채택안** — **정지 → 자세 안정 → 스캔 → 이동**을 반복하는 Stop-and-Scan(FR-6.2) + IMU 기반 스캔 유효성 필터(FR-6.3)
- **재검토 조건** — Stop-and-Scan으로 맵이 안정적으로 생성된 이후, IMU 기반 de-skewing을 적용한 연속 스캔을 차기 과제로 검토

#### DR-8. 위치 추정 수단 없이 "구역 출동"을 명세하지 않는다

- **검토한 대안** — 위험구역 알람 수신 시 해당 좌표로 이동하는 기능을 초기 요구사항에 포함
- **채택하지 않은 이유** — MechDog에는 **엔코더가 없고 SLAM도 없다.** 위치를 알 방법이 없는 상태에서 "좌표로 이동"은 구현 불가능한 명세다.
- **채택안** — 해당 기능을 **FR-6으로 분리하여 Phase 2로 이연**하고, LiDAR SLAM 확보를 전제 조건으로 명시. Phase 2 착수 불가 시(RISK-02) **ArUco 마커 기반 구역 정의**로 대체한다.
- **보완** — 엔코더 부재는 SLAM 도입 후에도 남는 문제이므로, 보행 명령 기반 gait odometry 캘리브레이션(FR-6.4)으로 prior를 공급한다.

#### DR-9. Phase 1에서 ROS2를 쓰지 않으며, Phase 2에서도 nav2를 쓰지 않는다

- **검토한 대안** — 처음부터 ROS2 기반으로 전체 스택을 구성하고 nav2로 경로계획까지 처리
- **채택하지 않은 이유** — ROS2 SLAM의 실패 양상(tf 트리 단절, 타임스탬프 불일치, frame_id 오류, odom 드리프트)은 **원인 파악에 상당한 숙련을 요구**한다. 개발 인력의 ROS2 숙련도가 낮은 현 상황에서 이를 초기부터 도입하면 진행이 정체될 위험이 크다.
- **채택안** — Phase 1(M1~M3)을 **순수 Python 단일 프로세스로 완결**한다. ROS2는 Phase 2에서 `slam_toolbox` 한 가지로 범위를 한정하여 *"스캔을 넣으면 맵과 위치를 반환하는 블랙박스"* 로만 사용하고, 경로 추종은 Python에서 웨이포인트 추적으로 직접 구현한다.
- **rviz2는 예외적으로 채택** — DR-7의 스캔 왜곡 문제는 시각화 없이 진단이 불가능하다. 동등한 시각화를 자체 제작하는 비용이 rviz2 학습 비용보다 크다.

#### DR-10. 전원은 USB 보조배터리 하나로 통합한다 *(v1.1 에서 결정 반전)*

- **v1.0 의 결정** — LiPo 3.7V 1000mAh(약 20g)를 XIAO BAT 패드에 직결. 근거는 **무게**였다 —
  최소형 보조배터리도 60~120g 으로 LiDAR(약 50g)보다 무겁다는 것.
- **결정을 반전한 이유**
  1. **무게 근거가 무너졌다.** 탑재 여력이 약 **600g** 으로 확인되었다(RISK-02, 잠정). 60~70g 짜리
     3,000mAh 급 보조배터리는 여유 안에 들어온다.
  2. **납땜을 0 으로 만든다.** LiPo 직결은 XIAO 뒷면 BAT 패드 납땜을 요구하고, LiDAR 노드 쪽은
     승압 모듈(MT3608)·충전 모듈(TP4056)까지 필요해 **약 12~15 점의 납땜이 발생**한다.
     팀에 인두 경험이 보장되지 않고 **발주 기회가 1회**이므로, 이는 편의가 아니라 리스크 관리다.
  3. **5V 가 바로 확보된다.** LD19 의 공급 전압 허용 범위가 4.5~5.5V 이므로 USB 출력이 그대로 들어간다.
     승압 모듈이 사라지고, "가변저항 출력을 멀티미터로 5V 에 맞춘 뒤 연결" 같은 **파손 위험 절차도 사라진다.**
  4. **무게중심에 유리하다.** 배터리를 둘로 나누면 LiDAR 용 배터리가 마스트 위로 올라간다.
     하나로 통합해 **몸통 하부에 붙이고 선만 올리면** 마스트에는 LiDAR 만 올라간다.
     4족 보행은 절대 무게보다 무게중심 높이에 민감하다.
- **채택안** — **3,000mAh 급 2구 이상 보조배터리 1개**로 XIAO · ESP32 중계 MCU · LD19 를 모두 급전한다.
  LiDAR 전원은 중계 MCU 의 `5V` 핀에서 뽑으므로 **GND 가 자동으로 공통**이 된다.
  상세 배선은 [하드웨어 조립](HARDWARE_ASSEMBLY.md) 2장.
- **대가**
  | | |
  | :--- | :--- |
  | 무게 | LiPo 20g → 보조배터리 60~70g |
  | 고장 격리 | 배터리 하나가 죽으면 전 노드가 함께 멈춘다. 단 10분 시연에서 카메라가 죽으면 어차피 시연이 성립하지 않으므로 실질 손해는 제한적이다 |
- **재검토 조건** — **부하 테스트에서 무게 초과로 판정되면 v1.0 구성(LiPo + MT3608 + TP4056 + 벌크 커패시터)으로
  되돌린다.** 그 경우 납땜이 발생하며, 되돌리는 절차는 [하드웨어 조립](HARDWARE_ASSEMBLY.md) 8절에 있다.

#### DR-11. 제자리 회전(Spot Turn)을 전제하지 않는다

- **검토한 대안** — 제자리에서 몸을 돌려 시야를 바꾸고, 회피·추종·360° 스캔을 수행
- **채택하지 않은 이유** — `HW_MechDog` API는 `move(step_length, angle)`이며 **angle은 −30~30°의 조향각**이다. 즉 **걸어가며 방향을 트는 arc 조향**이고 제자리 회전이 아니다. 내장 액션 16개(`left_foot_kick`, `stand_four_legs`, `rotation_pitch`, `rotation_roll`, `normal_attitude` 등)에도 yaw 회전 액션이 없다.
  - **몸통 yaw도 역학적으로 어렵다.** 다리는 관절 2자유도가 모두 앞뒤 평면에 있어 **발을 좌우로 옮길 수 없고**, 허리 관절도 없다. `mech_pose_t`의 `{roll, pitch, yaw}` 중 yaw 필드는 존재하나 실제 동작 여부가 미검증이다(OI-8).
  - **⚠️ 이는 벤더 라이브러리의 한계가 아니라 기구 구조의 제약이다.** 세 겹으로 막혀 있다.

    | ① | **기하학** — 제자리 회전은 발 접지점이 몸통 중심 주위로 호를 그려야 하며 **측면 변위가 필수**다. 관절이 모두 앞뒤 평면에 있으면 발을 그 호에 올려놓을 수 없다. 발을 들어 다시 놓아도 **같은 평면 안의 전후 위치만 바뀐다** — 한 주기를 돌면 몸통은 회전이 아니라 병진만 한다 |
    | ② | **마찰 의존** — 좌우 다리를 반대 방향으로 밀면 접지 상태에서 **발이 미끄러지며** 거친 회전이 발생할 수는 있다. 그러나 회전량이 바닥 마찰에 전적으로 의존하므로 **재현성이 없고**, 스톨에 가까운 부하가 서보에 걸린다. 개체·바닥마다 결과가 달라 SLAM odometry 로도 쓸 수 없다 |
    | ③ | **API** — `HW_MechDog` 는 `move(step_length, angle)` 만 노출하며 **개별 다리 제어를 제공하지 않는다.** ②를 시도하려면 IK 를 직접 구현해야 하는데, 이는 DR-1 에서 배제한 범위다 |

    **따라서 제자리 회전은 "구현하지 않은 기능" 이 아니라 "이 기구로는 신뢰할 수 없는 동작" 이다.**
- **채택안** — 회전은 **선회 보행(arc)** 으로만 수행한다. FR-2.3·FR-2.4·FR-3.5를 이에 맞게 정의한다.
- **부수 효과 (유리한 점)** — Scan matching은 스캔 간 겹침이 클 때 잘 수렴한다. 제자리 45° 선회는 겹침이 적어 정합이 어려운데, **arc 조향은 조금씩 이동+회전하므로 겹침이 커서 정합에 오히려 유리하다.**
- **부수 효과 (불리한 점)** — **최소 회전 반경**이 생긴다(비홀로노믹 제약). 좁은 공간에서 제자리 선회로 빠져나올 수 없어 후진 활용이 중요해지고, Phase 2 경로 추종이 복잡해진다.
- **재검토 조건** — OI-8에서 `transform()` yaw가 실제 동작함이 확인될 경우, FR-3.5에 몸통 yaw 추종을 추가한다.

#### DR-12. 검출 모델을 하나로 전부 학습하지 않는다 (COCO 범용 + PPE 전용 분담)

- **검토한 대안** — 사람·PPE·일상 물체를 모두 포함한 단일 모델을 직접 학습
- **채택하지 않은 이유** — ① 학습 클래스가 많아질수록 데이터셋 수집·라벨링 비용이 급증한다. ② 특히 FR-8 변화 감지는 시연 환경에 실제로 놓이는 일상 객체(의자·가방·상자·병 등)를 알아야 하는데, 이를 직접 학습하려면 사실상 COCO를 재구축하는 셈이다.
- **채택안** — **2단 구조 + 게이팅**
  | | 담당 | 학습 |
  | :--- | :--- | :--- |
  | ① COCO 사전학습 범용 검출기 | `person` + 79개 일상 객체 (FR-3, FR-8) | **불필요** |
  | ② PPE 전용 모델 | `helmet`/`no_helmet`/`vest`/`no_vest` (FR-9) | 직접 학습 (4클래스) |

  ②는 ①이 `person`을 검출한 프레임에서만 실행하므로 평균 연산량이 1패스 수준으로 유지된다.
- **효과** — 직접 학습 범위가 **4클래스로 축소**되고, 변화 감지 어휘는 **80클래스**를 공짜로 얻는다.
- **재검토 조건** — COCO 검출기의 `person` 검출률이 시연 환경에서 부족할 경우, ①을 자체 학습 모델로 교체하거나 fine-tune을 검토한다.

#### DR-13. TensorRT를 도입하지 않는다

- **검토한 대안** — ONNX Runtime의 TensorRT EP로 전환하여 추론을 가속
- **채택하지 않은 이유**
  1. **이득이 없다.** 추론은 프레임 예산 66.7ms(15fps) 중 약 3.5ms를 쓴다. TensorRT로 2ms를 아껴도 전체의 3%다. 가장 작은 숫자를 최적화하는 일이다.
  2. **엔진을 공유할 수 없다.** TensorRT 엔진은 GPU 아키텍처와 TensorRT 버전에 맞춰 컴파일되므로 팀원 간 산출물 공유가 불가능하고, 각자 빌드해야 한다. 3인 병렬 개발 구조와 충돌한다.
  3. **NVIDIA 전용이다.** 팀원 중 한 명이라도 AMD·Intel 그래픽이면 사용할 수 없다. DirectML은 DX12 GPU 전체에서 동작한다.
  4. CUDA·cuDNN·TensorRT 버전 정합성 문제로 환경 구축 비용이 크다.
- **채택안** — **DirectML EP**(개발 PC) + **CPU EP**(CI). `select_providers()` 로 자동 폴백.
- **재검토 조건**
  1. 로컬 LLM/VLM을 도입하는 경우. 그때는 TensorRT-LLM이 실질적 차이를 만든다. 다만 본 설계는 VLM을 Tier 3 클라우드에 두므로 현재는 해당하지 않는다.
  2. FR-3.1.2에서 **무거운 검출기(개방 어휘 계열 등)를 채택**하여 추론이 프레임 예산의 상당 비율을 차지하게 되는 경우. 단 그때도 **엔진 공유 불가·NVIDIA 종속 문제는 그대로 남으므로**, TensorRT보다 **모델 경량화** 또는 **추론 주기 하향(`vision.inference_fps`)** 을 먼저 검토한다.
#### DR-14. 학습 기반 정책(VLA)을 쓰지 않는다

- **검토한 대안** — OpenVLA · Octo · RT-2 · π0 등 **Vision-Language-Action** 모델로 카메라 영상과 지시문에서 로봇 동작을 직접 생성
- **채택하지 않은 이유**
  1. **학습 도메인 불일치** — 공개 VLA는 대부분 **로봇 팔 조작(manipulation)** 데이터로 학습되어 4족 순찰 임무와 맞지 않는다.
  2. **행동 공간 불일치** — 본 로봇의 액션은 `move(step, angle)` 두 개다. VLA는 고차원 관절 명령을 출력하며 그 정교함이 도달하지 못한다.
  3. **파인튜닝 비용** — 4주 일정에 데이터 수집·학습이 들어갈 여지가 없다.
  4. **설명 가능성 부재** — **왜 그렇게 움직였는지 사후 재구성이 불가능하다.** 경비·안전 임무에서는 치명적이다.
- **채택안** — **규칙 기반 FSM**(DR-9). 상태 전이가 명시적이므로 로그만으로 판단 근거를 재구성할 수 있고, 전이표 전수를 pytest로 검증할 수 있다.
- **포지셔닝** — VLA는 현재 Physical AI 연구의 최전선이다. 본 프로젝트는 이를 **모르고 안 쓴 것이 아니라 안전 설명책임과 일정을 근거로 선택하지 않은 것**이며, 완성된 FSM은 향후 학습 정책을 도입할 때의 **비교 기준선**이 된다.
- **재검토 조건** — 4족 보행·순찰 도메인의 사전학습 정책이 공개되고, 판단 근거를 감사할 수 있는 수단이 함께 제공되는 경우

#### DR-15. 거리 판정에 깊이 모델이나 초음파를 쓰지 않는다

- **검토한 대안** — ① 단안 깊이 추정 모델(Depth Anything V2 등)로 사람까지의 거리를 산출 ② 초음파 센서 재활용 ③ bbox 높이로 미터 거리 환산
- **채택하지 않은 이유**
  - **①** 모델이 하나 늘고 추론 패스가 추가된다. **임계 판정 하나에 신경망을 붙이는 것은 과잉**이다.
  - **②** 초음파의 정격 사거리(300cm)는 크고 평평한 수직면 기준이다. **의복은 초음파를 흡수·산란시켜 사람에 대한 실효 사거리가 1~2m로 줄고**, 약 15° 빔이 3m에서 폭 0.8m로 퍼져 옆의 벽·가구를 잡는다. 10~15cm 높이 전방 지향이라 다리만 스치거나 바닥을 보기도 한다.
  - **③** "사람 키 1.7m" 가정에 의존하여 **웅크리거나 앉은 자세에서 추정이 깨진다.**
- **채택안** — **미터 거리를 구하지 않는다.** 요구사항의 실체는 "머리가 화각에 들어오는가"이므로 **bbox 클리핑 검사**로 직접 판정한다(FR-9.2.1). 추종 거리 유지도 **bbox 높이 비주얼 서보잉**으로 처리한다(FR-3.5.2). 자세와 무관하게 동작한다.
- **초음파의 역할** — 원래 잘하는 일인 **근거리 충돌 회피**(FR-2.2, 25cm)에만 사용한다.
- **재검토 조건** — 검출기가 사람을 빈번히 절단하여 클리핑 검사가 불안정한 경우, 또는 향후 장애물 지도 생성에 밀도 있는 깊이 정보가 필요해지는 경우
#### DR-16. 자동 안전 로직은 기능 동작과 충돌하지 않게 설계한다 (일반 원칙)

> **본 항목은 특정 요구사항이 아니라 프로젝트 전반에 적용되는 설계 원칙이다.** 이후 추가되는 모든 안전 로직에 동일하게 적용한다.

- **전제 (가정 A-13)** — 본 프로젝트는 **상시 인적 감시 하에서 운용되는 시연·연구 목적**이며 무인 상용 배치가 아니다. 사람이 항상 옆에서 지켜보며 **E-Stop을 즉시 누를 수 있다.** 따라서 **자동 안전 로직의 1차 목적은 인적 안전이 아니라 하드웨어 보호와 자율 동작의 성립**이다.

- **핵심 판단** — **안전 로직이 기능을 방해하면 팀은 안전 로직을 끈다.** 임계를 과도하게 좁게 잡으면 결국 누군가 해당 코드를 주석 처리하게 되고, 그 결과 보호 기능이 **완전히** 사라진다. **작동 가능한 수준으로 완화하여 계속 살려두는 것이 실질적으로 더 안전하다.**

- **적용 순서** — 안전 로직이 기능과 충돌할 때 아래 순서로 해결한다.

  | 순위 | 방법 | 이유 |
  | :---: | :--- | :--- |
  | **1** | **임계값·조건을 조정하여 물리적으로 분리** | 로직 간 결합이 생기지 않는다. 설정값 변경으로 끝난다 |
  | 2 | 판정 조건을 더 직접적인 관측량으로 재정의 | 간접 추정을 없애면 충돌 자체가 사라진다 (예: FR-9.2 거리 → bbox 클리핑) |
  | 3 | 해당 안전 로직의 범위를 축소 | 명시적으로 기록하고 재검토 조건을 남긴다 |
  | **✕** | **상태 억제(suppress) 플래그** | **안전 로직에 외부 의존이 생기고, 억제 영구화라는 새 실패 모드를 만든다. 최후 수단으로만** |

- **적용 사례 ①: NFR-2.4 전도 감지** — 앉기 자세(몸통 피치 30~45°)가 임계 45°와 충돌했다. 억제 플래그 대신 **임계를 60°로 상향**하여 해결했다. 의도된 자세(최대 45°)와 실제 전도(약 90°) 사이의 빈 구간을 이용하므로 **두 로직이 서로를 알 필요가 없다.**

- **완화하지 않는 항목** — 기능과 충돌하지 않는 안전 로직은 그대로 유지한다. 특히 아래는 **사람이 지켜봐도 대응할 수 없는 종류**이므로 완화 대상이 아니다.

  | 항목 | 유지 근거 |
  | :--- | :--- |
  | **FR-1.3** 명령 타임아웃 300ms | 통신 단절은 **사람 눈에 보이지 않고 반응 시간도 없다** |
  | **NFR-2.5** 워치독 | 펌웨어 행(hang)은 **사람이 개입할 수 없다** |
  | FR-2.2 초음파 25cm 정지 | 안전이기 이전에 **자율 순찰 기능 그 자체** |
  | NFR-2.3 저전압 | 배터리 보호. 기능 방해 없음 |
  | FR-4.4 E-Stop | **1차 안전망으로 격상** (A-13) |

- **무인 운용으로 확장할 경우** — A-13이 무효화되므로 자동 안전 로직 전반을 재설계해야 한다. 본 결정은 **감시 하 운용 전제에 종속**된다.

#### DR-17. 컨테이너는 Phase 2 ROS2 에만 적용한다

- **검토한 대안** — 호스트 스택 전체(비전·FSM·텔레메트리·대시보드)를 Docker 이미지로 묶고 `compose up` 한 번으로 기동
- **기술적으로는 가능하다** — 이 프로젝트는 컨테이너화에 유리한 조건을 갖췄다. 카메라·IMU·초음파가 모두 **로봇 안에** 있고 PC와는 네트워크로만 연결되므로(2.1 스타 토폴로지), 로보틱스에서 Docker 를 깨뜨리는 최대 원인인 **USB 장치 패스스루가 아예 발생하지 않는다.** 인바운드 텔레메트리도 UDP 포트 퍼블리싱으로 도달한다.
- **채택하지 않은 이유**
  1. **배포 비용이 40초다.** *(v1.2 에서 근거 교체 — 측정 반영)*
     v1.1 은 *"팀이 환경을 통일하지 않으므로 컨테이너의 명분이 없다"* 고 적었으나 **이는 부정확했다.**
     인원 배정(2026-09-03)으로 소프트웨어를 팀장이 전담하게 되면서, **팀장이 만든 호스트 스택을
     나머지 2인이 자기 로봇에서 실행해야 한다** — 즉 배포 대상이 실재한다.
     그래서 추정 대신 **실제로 측정했다.**

     | 단계 | 시간 |
     | :--- | ---: |
     | venv 생성 | 3.9 s |
     | pip 업그레이드 | 3.9 s |
     | 의존성 설치 (33개 패키지, 캐시 없음) | 30.8 s |
     | pytest 59건 | 0.8 s |
     | **합계** | **약 40 s** |

     *(측정 환경: Windows 11 · Python 3.12.10 기존 설치 · `--no-cache-dir`)*

     **배포 비용이 40초이므로 컨테이너로 얻을 것이 없다.** 재현 절차는 `scripts/setup.ps1` 로 스크립트화했다.
     남는 변수는 **Python 설치 자체**뿐이며, **Docker Desktop + WSL2 설치가 Python 설치보다 무겁다** —
     세팅 편의를 목적으로 한 컨테이너는 역효과다.
     실행 프로바이더 자동 폴백(2.5)과 `.onnx` 산출물 공유가 이미 이질적 환경을 전제로 설계되어 있다.
  2. **펌웨어 쪽 절반이 컨테이너에 들어가지 않는다.** Windows 의 COM 포트는 리눅스 컨테이너로 넘어가지 않으므로 펌웨어 빌드·업로드와 WonderEcho 플래싱(`PACK_UPDATE_TOOL.exe`)은 어차피 호스트에서 수행한다. *"컨테이너 하나로 로봇을 작동시킨다"* 는 성립하지 않는다.
  3. **디버깅 변수를 늘린다.** 코드가 아직 없는 시점에 컨테이너를 끼우면, 통신이 되지 않을 때 원인이 **내 코드 · 펌웨어 · 컨테이너 네트워크** 셋으로 갈린다.
  4. **NAT 가 송신자를 가린다.** 포트 퍼블리싱을 거치면 컨테이너는 패킷 출처를 Docker 게이트웨이로 인식하므로, 다중 개체 운용 시 IP 로 로봇을 구분할 수 없다. (FR-5.2 에 `device_id` 를 추가하여 해소했다 — 컨테이너 채택 여부와 무관하게 필요한 필드다.)
- **채택안**
  | 대상 | 컨테이너 | 근거 |
  | :--- | :---: | :--- |
  | Phase 1 호스트 스택 | ✕ | 위 1~3 |
  | 펌웨어 빌드·플래싱 | ✕ | 시리얼 포트 (물리적 제약) |
  | **Phase 2 ROS2** (`slam_toolbox`·`rviz2`) | **○** | 아래 |
  | PPE 모델 학습 | 선택 | 네트워크를 쓰지 않아 부작용이 없다. 담당자 재량 |

  **ROS2 만 채택하는 근거는 환경 통일이 아니다.** ROS2 는 설치 자체가 가장 흔한 실패 지점이고, `apt` 설치가 꼬이면 복구가 어렵다. 공식 `ros:jazzy` 이미지를 쓰면 실패 시 컨테이너를 폐기하고 다시 받으면 된다. 또한 Phase 2 는 **기준기 1대에서만** 동작하므로 도입 비용이 팀 전체가 아니라 담당자 1인에게만 발생한다.
- **재검토 조건**
  1. **팀원 환경에서 `scripts/setup.ps1` 이 크게 지연되는 경우** — 기준값 약 40초를 크게 초과하면
     (예: 반나절) 배포 비용 근거가 무너지므로 호스트 스택 컨테이너화를 재검토한다.
     **측정값을 팀에 공유하는 것이 재검토 트리거다.**
  2. **M1 게이트(제어 링크·페일세이프)를 네이티브에서 통과한 뒤**에는 재검토할 수 있다. 그 시점에는
     통신이 이미 성립해 있으므로, 컨테이너에서 실패하면 원인이 즉시 컨테이너로 확정된다.
     완료 기준은 **"동일한 M1 게이트를 컨테이너에서 다시 통과"** 로 둔다.
     **코드가 0줄인 지금 도입하면 통신 미검증과 컨테이너 미검증이 겹쳐 원인이 넷으로 갈린다.**
  3. 시연을 개발 PC 가 아닌 다른 머신에서 수행하게 되는 경우.

## 2. 시스템 아키텍처

### 2.1 스타 토폴로지 (Star Topology)

본 시스템의 **핵심 설계 원칙은 "로봇 위의 노드끼리 배선하지 않는다"** 이다. 모든 노드는 독립 전원을 가지며 Host PC를 허브로 하는 성형 구조로 통신한다.

```
                    ┌───────────────────────────────────────────┐
                    │            HOST PC  (허브)                 │
                    │  Windows 11 + WSL2 / RTX 3080             │
                    │  · ONNX Runtime 검출기  (사람 인지)        │
                    │  · Behavior FSM         (판단)             │
                    │  · FastAPI + WebSocket  (관제 대시보드)     │
                    │  · [Phase 2] ROS2 slam_toolbox            │
                    └───┬───────────────┬───────────────┬───────┘
        MJPEG(HTTP) ↑   │               │ UDP cmd ↓     │ UDP scan ↑
                        │               │ UDP tlm ↑     │  [Phase 2]
    ┌───────────────────┴──┐   ┌────────┴──────────┐   ┌┴──────────────────┐
    │ VISION NODE          │   │ MOTION NODE       │   │ LIDAR NODE        │
    │ XIAO ESP32S3 Sense   │   │ MechDog ESP32     │   │ (Phase 2 결정)     │
    │ 보조배터리 USB 급전   │   │ 커스텀 Arduino 펌웨어│   │ LD19 + 중계 MCU   │
    │                      │   │                   │   │                   │
    │ · OV2640 → MJPEG     │   │ · HW_MechDog HAL  │   │ · UART 230400 수신 │
    │ · Wi-Fi HTTP 서버     │   │ · Wi-Fi 명령 수신  │   │ · UDP 중계         │
    │ · 추론 없음           │   │ · 초음파 즉시정지   │   │                   │
    │                      │   │ · 하트비트 페일세이프│   │                   │
    └──────────────────────┘   └───────────────────┘   └───────────────────┘
              ✕ ────────── 노드 간 물리 배선 없음 ────────── ✕
```

**이 구조의 이점**

| 항목 | 효과 |
| :--- | :--- |
| 통합 리스크 | MechDog 본체를 개조하지 않음. 비전 노드 고장이 보행에 영향 없음 |
| 개발 병렬성 | 비전 노드와 모션 노드를 독립적으로 개발·테스트 가능 |
| 교체 용이성 | 카메라 노드를 다른 보드로 바꿔도 프로토콜만 맞으면 됨 |
| 전원 격리 | 서보 구동 시 발생하는 전압 강하가 카메라에 영향 없음 |

### 2.2 3-Tier 레이턴시 계층

**어떤 로직을 어디에 둘 것인가**를 레이턴시 요구사항으로 결정한다. 이 표를 위반하는 설계는 반려한다.

| 계층 | 위치 | 담당 로직 | 허용 지연 | 통신 단절 시 |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1 · Reflex** | MechDog ESP32 (온보드) | 초음파 충돌 정지, 하트비트 감시, 저전압 셧다운, 전도 감지, 서보 토크 해제 | **< 50 ms** | **독립 동작 필수** |
| **Tier 2 · Cognition** | Host PC (로컬 Wi-Fi) | 사람 인지 · PPE 판정 · 변화 감지, 행동 FSM, 경로 추종, [P2] SLAM | 100 ~ 200 ms | Tier 1이 안전 정지 |
| **Tier 3 · Reasoning** | 클라우드 (선택) | VLM 현장 판독, 이벤트 요약 리포트, 이상 패턴 분석 | 1 ~ 3 초 | 기능 저하만, 주행 무관 |

> **불변 규칙 (Invariant)**: 안전에 직결되는 판단은 절대 Tier 2/3으로 올리지 않는다. Host PC가 꺼져도 로봇은 스스로 멈춰야 한다.

### 2.4 전원 설계

**MechDog 본체** — 2S 리튬 (7.4V 공칭, 8.4V 2A 충전기 확정)

| 임계값 | 전압 | 동작 |
| :--- | ---: | :--- |
| 정상 | > 7.0 V | 통상 운용 |
| 경고 | ≤ 7.0 V | 대시보드 경고, 순찰 중단 후 대기 |
| 셧다운 | ≤ 6.6 V | `STATE_FAILSAFE` 진입, 엎드린 자세로 서보 토크 해제 |

**보조 노드 전원** — 보조배터리 1개 공용 (DR-10)

XIAO · 중계 MCU · LD19 를 **한 보조배터리에서 급전**한다. LiDAR 는 중계 MCU 의 `5V` 핀에서 받으므로
**GND 가 자동으로 공통**이 된다(UART 성립 조건).

> ⚠️ **용량이 아니라 전류 경로에 주의한다.** LiDAR 가 DevKit 의 `5V` 핀을 거치므로
> **DevKit 의 USB 커넥터와 내부 VBUS 트레이스에 DevKit(200mA) + LD19(200mA) ≈ 400mA 가 몰린다.**
> 보드에 **500mA 폴리퓨즈**가 달린 제품이면 마진이 얇다.
>
> | 증상 | 조치 |
> | :--- | :--- |
> | 스캔 간헐 끊김 · ESP32 리셋 | LiDAR 를 배터리에서 **직접 급전**으로 분리 |
>
> 분리해도 브레드보드 전원 열에 `USB 전원 케이블(낱개선)` 을 꽂으면 되므로 **납땜은 0 을 유지한다.**
> 그래서 해당 케이블을 보험으로 담는다 ([조립](HARDWARE_ASSEMBLY.md) 2.6).

| 부하 | 평균 소비전류 | 순간 피크 |
| :--- | :--- | :--- |
| XIAO 비전 노드 | 200 ~ 250 mA | 300 ~ 500 mA (Wi-Fi TX 버스트) |
| ESP32 중계 MCU | 150 ~ 250 mA | — |
| LD19 [P2] | ~200 mA | — |
| **합계** | **~600 mA** | |

보조배터리 정격은 3.7V 셀 기준이므로, 5V 승압 손실을 감안하면 **실사용은 정격의 60~70%** 다.

| 정격 | 5V 기준 실사용 | 600mA 기준 구동시간 | 무게 |
| ---: | ---: | ---: | ---: |
| 2,000 mAh | ~1,300 mAh | 약 2시간 | 40~50 g |
| 3,000 mAh | ~2,000 mAh | 약 3시간 | 60~70 g |
| **5,000 mAh** ← **보유분 사용** | **~3,300 mAh** | 5시간+ | **100~120 g** |

> **3인이 5,000mAh · 2구 동일 사양으로 통일한다.** 용량 자체는 과하다 — 총 600mA 소비에
> 5.5시간이고 로봇 본체가 30~60분에 방전되므로 5~11배 여유다. **선정 이유는 용량이 아니라 통일이다.**
>
> **전원 구성이 개체마다 다르면 무게차가 개체차에 하나 더 얹힌다.** WBS 8절이 서보 영점과 보행
> 이동량 편차를 관리하고 있는데, 여기에 전원 무게까지 갈리면 변수가 늘어난다.
> **동일 사양이면 기준기에서 한 번 측정한 부하·보행 특성을 개발기에 그대로 적용할 수 있다.**
>
> Phase 1 에서는 XIAO 만 급전하므로(220mA) 용량이 더욱 과하지만, 어차피 구매한다면 통일이 낫다.
>
> **구동시간은 병목이 아니다.** 8개 서보를 구동하는 MechDog 본체가 먼저 방전된다(추정 30~60분, OI-4).
> 시연은 10분이므로 보조배터리는 어느 용량이든 충분하며, **선정 기준은 용량이 아니라 무게**다.
>
> ⚠️ **보조배터리의 USB-C 포트가 입출력 겸용인 제품이 많다.** 그 경우 다른 포트와 배타적이거나 출력이 되지 않는다.
> **보유품으로 두 부하를 동시에 켜보는 것**이 가장 빠른 확인이다. 불가하면 USB 분배 케이블로 늘린다.
>
> **무게 초과 판정 시** LiPo 3.7V 1000mAh + 벌크 커패시터(470~1000µF) 구성으로 되돌린다.
> 그 경우 500mAh 셀은 1C 한계가 500mA 라 Wi-Fi 피크에서 브라운아웃이 발생하므로 **1000mAh 이상**을 쓴다.

### 2.6 음성 및 상태 표시 역할 분담

음성은 **지연 요구가 다른 두 종류**로 나뉜다. 하나의 수단으로 묶으면 즉각성과 표현력 중 하나를 잃는다.

| 용도 | 담당 | 방식 | 지연 | Tier |
| :--- | :--- | :--- | :--- | :---: |
| **암구호 인식** | WonderEcho (CI1302) | **온칩 오프라인 인식.** 네트워크 불필요 | 즉시 | 1 |
| **즉각 경고 방송** | **MP3 모듈 (1순위)** / WonderEcho 내장 스피커 (대안) | 사전 등록된 문구 재생 | **즉시** | 1 |
| **상황 판독 방송** | Host PC + 클라우드 VLM + TTS | 실시간 생성 문장. **관제 센터 방송** 개념 | 1~3초 | 3 |
| **상태 표시** | **초음파 센서 내장 RGB LED** | 에스컬레이션 단계를 색으로 표시 | 즉시 | 1 |

> **인식과 재생을 분리한다.** 둘을 모두 WonderEcho 에 맡기면 재생 문구가 **영어·중국어로 제한되고, 문구를 바꿀 때마다 전용 Windows 도구로 재플래싱**해야 한다.
> 킷에 포함된 **MP3 모듈(TF카드 포함)** 은 SD 카드에 파일만 넣으면 되므로 **한국어가 가능하고 문구 추가가 자유롭다.**
>
> | | 담당 | 얻는 것 |
> | :--- | :--- | :--- |
> | 인식 (암구호 듣기) | WonderEcho 온칩 | 오프라인·즉시. 유지 |
> | **재생 (경고·안내)** | **MP3 모듈** | **한국어 · 재플래싱 불요 · 문구 추가 자유** |
>
> 이렇게 나누면 **착수 전에 확정해야 하는 문구가 암구호 1~2개로 줄어든다.** 방송 문구는 개발 중에 늘리면 된다.
> MP3 모듈의 제어 인터페이스 확인(**OI-6**)이 선행 조건이며, 불가 판정 시 WonderEcho 내장 스피커로 되돌린다.
>
> **상태 표시등은 별도 부품이 필요하지 않다.** 초음파 센서에 RGB LED 가 내장되어 있음을 실물로 확인했다(OI-12 닫힘).

**WonderEcho 제약 (확정)**

| 항목 | 내용 |
| :--- | :--- |
| 커스텀 문구 | **지원.** 웨이크워드·명령어·재생문구를 사용자가 정의 (최대 255~300개) |
| **언어** | **영어 / 중국어만. 한국어 미지원.** 영어 문구는 **대문자 + 하이픈 연결** (예: `ALPHA-SEVEN-CLEAR`) |
| 등록 시점 | **펌웨어 빌드 시 확정.** 런타임에 새 문장을 생성할 수 없다 |
| 인식 거리 | **정숙 환경 5m** / 소음 환경 1m |
| 워크플로우 | 온라인 플랫폼에서 문구 입력 → `.bin` 생성 → `PACK_UPDATE_TOOL.exe`(칩: CI1302)로 USB-C 플래싱 |
| 출력 | 인식 성공 시 **명령 ID 바이트**를 호스트로 전달 (통신 방식 I2C/UART는 OI-10에서 확정) |

> **실시간 AI 음성은 Host PC가 담당한다.** 로봇에 스피커를 추가하지 않고 PC 스피커로 방송한다. 무게 0g·비용 0원이며, 실제 보안 시스템이 관제 센터에서 방송하는 방식과 동일하여 서사상으로도 타당하다.

> **플래싱 리스크** — 커스텀 펌웨어 기록은 되돌리기 어렵다. Advanced Kit 3개로 **WonderEcho 모듈이 3개 확보**되어 있으므로, **1개를 실험용으로 지정**하고 성공한 `.bin`을 나머지에 적용한다.

## 3. 기능 요구사항 (Functional Requirements)

> 표기: **[P1]** = Phase 1 (필수) · **[P2]** = Phase 2 (확장)

### FR-1: 원격 제어 링크 및 페일세이프 [P1]

가장 먼저 구현하고 가장 마지막까지 지켜야 할 요구사항이다. 다른 모든 기능이 이 위에 얹힌다.

- **FR-1.1** MechDog ESP32는 커스텀 Arduino 펌웨어로 Wi-Fi STA 모드에 접속하고, UDP 포트에서 제어 명령을 수신해야 한다.
- **FR-1.2** 수신한 명령을 `HW_MechDog` API 호출로 변환하여 실행해야 한다.
- **FR-1.3 (Command Timeout — 최우선 안전 요구사항)** 마지막 유효 명령 수신 후 **300 ms** 동안 신규 명령이 없으면 즉시 `move(0, 0)`으로 정지해야 한다. 마지막 명령을 계속 실행해서는 안 된다.
- **FR-1.4** 10 Hz 주기로 텔레메트리(상태, 거리, IMU, 배터리)를 Host PC로 송신해야 한다.
- **FR-1.5 (Link Loss)** 3초 이상 통신이 복구되지 않으면 `STATE_FAILSAFE`로 전환하여 안정 자세(엎드림)를 취해야 한다.
- **FR-1.6 (Sequence Guard)** 명령 패킷의 `seq`가 직전 수신값보다 작거나 같으면(UDP 순서 역전·중복) 해당 패킷을 폐기해야 한다.

### FR-2: 자율 순찰 및 장애물 회피 [P1]

- **FR-2.1** `CMD_START_PATROL` 수신 시 Trot 보행으로 자율 전진을 수행한다 (`STATE_PATROL`).
- **FR-2.2 (온보드 반사 정지)** 초음파 측정거리가 **25 cm 미만**이면 **Host PC 판단을 기다리지 않고** 로봇이 즉시 정지해야 한다. (Tier 1)
- **FR-2.3 (회피 기동)** 정지 후 Host PC가 `STATE_AVOID`로 전환하여 **후진 → 선회 보행(arc) → 전방 재확인** 시퀀스를 지시한다. 제자리 회전이 불가하므로 **후진 거리를 충분히 확보**해야 한다(기본 20cm 이상, `config.yaml`). (Tier 2, 근거: DR-11)
- **FR-2.4 (주기 스캔)** 순찰 중 설정 주기(기본 10초)마다 정지하여 `transform()`으로 **상체 피치**를 제어하는 주변 스캔을 3초간 수행하고 순찰을 재개한다 (`STATE_SCAN`). **좌우 시야 확보는 몸통 yaw가 불가하므로 선회 보행으로 수행한다** (근거: DR-11).
- **FR-2.5** 순찰 타이머, 회피 거리, 스캔 주기 등 모든 상수는 하드코딩하지 않고 `config.yaml`에서 로드해야 한다.

### FR-3: 사람 인지 및 경비 대응 [P1]

- **FR-3.1 (영상 파이프라인)** XIAO 비전 노드는 MJPEG over HTTP로 영상을 송출하고, Host PC가 이를 수신하여 **2단 검출 구조**로 처리한다 (근거: DR-12).
  ```
  매 프레임 ─ ① COCO 사전학습 범용 검출기 (학습 불요)
                → person + 79개 일상 객체
                → FR-3 경비 대응 · FR-8 변화 감지
                     │
                     └─ person 검출 프레임에서만
                          └─ ② PPE 전용 모델 (직접 학습)
                                → FR-9 산업안전 판정
  ```
  - **FR-3.1.1 (게이팅)** ②는 ①이 `person`을 검출한 프레임에서만 실행한다. 사람이 없는 프레임에서 PPE 추론을 돌리지 않아 평균 연산량을 1패스 수준으로 유지한다.
  - **FR-3.1.2 (①번 검출기 선정)** ①은 **COCO 사전학습 모델을 기본안**으로 하되, 모델 계열은 M2 착수 시점에 평가하여 확정한다 (OI-15). 프레임 예산에 여유가 크므로(NFR-1.2) **경량 모델을 고집하지 않고 정확도가 높은 쪽을 선택한다.** 특히 FR-8 변화 감지는 시연 환경에 놓이는 임의의 물체를 인식해야 하므로, **개방 어휘(open-vocabulary) 검출기**가 고정 80클래스보다 유리할 수 있다. 선정 결과와 근거는 `config.yaml`과 본 문서에 기록한다.
- **FR-3.2 (Alert 전환)** 신뢰도 임계값(기본 0.5) 이상의 사람이 **연속 3프레임** 검출되면 `STATE_ALERT`로 전환한다. 단발 오검출로 상태가 튀지 않도록 한다.
- **FR-3.3 (Alert Stance)** `transform()`으로 몸체를 전방 상향(Pitch Up 15°)으로 세워 경계 태세를 취한다.
- **FR-3.4 (Warning Broadcast)** 침입자 인지 시 경고 신호를 발령한다. Advanced Kit의 **MP3 모듈 / WonderEcho 음성 모듈**을 활용하며, 미장착 시 대시보드 시각 경보로 대체한다.
- **FR-3.5 (Target Tracking)** 검출 바운딩박스 중심의 화면 내 x축 편차에 비례하여 **선회 보행(arc)** 으로 타겟을 시야 중앙에 유지한다 (`STATE_TRACK`). 데드존을 두어 미세 진동을 억제한다. 제자리 선회가 불가하므로 **로봇이 타겟 방향으로 접근하며 방향을 트는 동작**이 되며, 이는 경비 로봇의 대응 동작으로 타당하다. (근거: DR-11)
- **FR-3.5.1 (조건부)** OI-8에서 `transform()` yaw 동작이 확인되면, 편차가 작을 때는 **발을 고정한 몸통 yaw**로 시선만 돌려 불필요한 이동을 줄인다.
- **FR-3.5.2 (거리 유지)** 추종 시 목표까지의 거리는 **`person` bbox 높이를 목표값 근처로 유지**하는 비주얼 서보잉으로 제어한다. 미터 단위 환산이 불필요하다 (근거: DR-15).
- **FR-3.6 (다중 인원 추적)** 검출 결과에 **추적기(ByteTrack 계열)** 를 적용하여 프레임 간 지속되는 **추적 ID**를 부여한다.
  - **FR-3.6.1** 추적기는 신경망이 아닌 후처리 알고리즘이며 추가 추론 패스를 발생시키지 않는다.
  - **FR-3.6.2 (인증 세션 귀속)** FR-10의 인증 결과는 **추적 ID에 귀속**된다. 인원이 여러 명일 때 누가 인증되었는지 구분하고, 시야를 벗어난 뒤 복귀한 동일 인원에게 재인증을 반복 요구하지 않기 위함이다.
  - **FR-3.6.3** 추적 ID가 소실되면 해당 인증 세션도 만료된다.
- **FR-3.7 (Target Lost)** 5초간 타겟 미검출 시 `STATE_PATROL`로 복귀한다.

- **FR-3.8 (다중 대상 처리)** 추적과 인증은 **개인별**이지만(FR-3.6.2) **에스컬레이션·눈 LED·음향은 로봇 단위**다.
  눈 LED 가 하나, 스피커가 하나이므로 **개인별 병렬 표현이 물리적으로 불가능하다.** 따라서 아래 규칙으로 축약한다.

  - **FR-3.8.1 (인증 축은 최댓값)** **미인증 인원이 한 명이라도 있으면 에스컬레이션을 유지한다.**
    > 인증 상태는 마커·암구호 이벤트로 결정되며 **주 대상 여부와 무관하게 대상별로 집계된다**(FR-3.6.2).
    > 따라서 한 명이 인증되어도 다른 미인증자가 있으면 L2 가 유지된다 — 실제 출입 통제와 같고 안전측이다.
    >
    > ⚠️ **PPE 위반은 이 규칙의 대상이 아니다.** 판정은 주 대상에게만 수행하므로(FR-3.8.2)
    > 비주 대상의 위반 여부는 **알 수 없다**. 비주 대상은 `PPE_UNDETERMINED` 로 기록한다.
  - **FR-3.8.2 (주 대상 = 가장 가까운 대상)** 자세 상승(FR-9.2.2) · 추종(FR-3.5) · 인증 요구(FR-10)는
    **주 대상 1명에게만** 수행하며, **주 대상은 `person` bbox 높이가 가장 큰(가장 가까운) 대상**이다.
    > **판정 결과를 선정 기준으로 쓰지 않는다.** 초기 설계는 *"에스컬레이션 단계가 가장 높은 대상"* 을
    > 1순위로 두었으나 이는 **순환 논리**였다 — 단계는 판정 결과로 올라가고, 판정은 주 대상에게만
    > 수행하므로 **비주 대상의 단계는 영원히 올라가지 않는다.**
    >
    > **bbox 높이는 판정과 무관하게 매 프레임 측정되므로 순환이 없다.** 그리고 가까운 대상이
    > 실제 위협 가능성이 높고 판정 성공률도 높다. **단일 기준이 히스테리시스도 안정적으로 만든다.**
  - **FR-3.8.3 (주 대상 전환 제약)** 두 겹으로 잠근다.

    | 제약 | 내용 |
    | :--- | :--- |
    | **히스테리시스** | 최소 유지 시간(`primary_target_hold_ms`, 기본 2초) 동안 바꾸지 않는다 |
    | **시퀀스 락** | **자세 상승·인증 시퀀스가 진행 중이면 완결 또는 대상 이탈까지 전환하지 않는다.** 히스테리시스 시간이 지나도 마찬가지다 |

    > 프레임마다 바뀌면 로봇이 자세와 방향을 계속 번복하여 어떤 동작도 완결하지 못한다(FR-9.2.4 와 같은 실패 양상).
    > **특히 자세를 올리는 중에 주 대상이 바뀌면 그 시퀀스 자체가 무의미해진다** — 시퀀스 락이 히스테리시스보다 강하다.
  - **FR-3.8.4 (비주 대상 처리)** 주 대상이 아닌 인원은 **기록만 한다** — 스냅샷 · 이벤트 · 추적 ID 유지.
    자세 상승이나 추종을 수행하지 않는다.
  - **FR-3.8.5 (대상 수 상한)** 동시 추적 인원은 `max_tracked_persons`(기본 5)로 제한한다.
    초과 시 bbox 큰 순으로 유지하고 WARN 로그를 남긴다.

  > **시연 전제 — 대상 1명.** 시연은 온라인으로 수행하며 현장 관객이 없고 시연자도 1명이다.
  > 따라서 **FR-3.8 은 시연 성립 조건이 아니다.**
  >
  > 그럼에도 규칙으로 남기는 이유는 **개발·테스트 중 두 명이 화각에 들어올 때 코드가 어느 대상을
  > 고를지 미정의가 되는 것을 막기 위함**이다. 미정의 동작은 재현이 안 되는 버그로 나타난다.
  > 구현 우선순위는 낮다.

- **FR-3.9 (Event Logging)** 탐지 시점의 스냅샷(JPEG), 타임스탬프, 신뢰도, 바운딩박스를 이벤트 로그에 기록하고 대시보드로 실시간 푸시한다.

### FR-4: 웹 미션 대시보드 [P1]

FastAPI + WebSocket 기반 관제 UI를 새로 구현한다.

- **FR-4.1** 실시간 FPV 영상과 검출 바운딩박스 오버레이를 표시한다.
- **FR-4.2** 텔레메트리(배터리 전압, IMU 피치/롤/요, 초음파 거리, 현재 FSM 상태, 링크 지연)를 10 Hz로 스트리밍하여 차트/게이지로 표시한다.
- **FR-4.3 (수동 오버라이드)** 가상 조이스틱 또는 키보드로 자율 모드를 중단하고 수동 조작할 수 있어야 한다. 오버라이드 중에도 **FR-2.2 온보드 반사 정지는 유지**된다.
- **FR-4.4 (E-Stop)** 화면 상시 노출 비상정지 버튼. 클릭 시 즉시 정지 및 `STATE_FAILSAFE` 진입. **상시 인적 감시를 전제하므로(DR-16, A-13) 본 기능은 1차 안전망이다.** 어떤 화면 상태에서도 스크롤 없이 접근 가능해야 하며 키보드 단축키를 함께 제공한다.
- **FR-4.5 (Event Feed)** 사람 감지, 회피, 페일세이프 등 이벤트를 스냅샷과 함께 시간순으로 표시한다.
- **FR-4.6 [P2] (Zone Manager)** SLAM 맵 위에서 순찰 웨이포인트와 위험구역을 지정하고 출동 명령을 트리거한다.

### FR-5: 통신 메시지 스펙 [P1]

> 노드가 물리적으로 배선되지 않는 구조이므로 전송 계층은 Wi-Fi이다. 유선 프로토콜을 채택하지 않은 이유는 DR-2 참조.

#### FR-5.1 제어 명령 (Host PC → MechDog ESP32, UDP)

송신 주기 **10 Hz 고정** (명령 변화가 없어도 계속 송신하여 FR-1.3 타임아웃을 갱신한다).

```json
{"seq": 1234, "ts": 1756800000123, "type": "MOVE",  "step": 60, "angle": 12}
{"seq": 1235, "ts": 1756800000223, "type": "POSE",  "pitch": 15, "roll": 0, "height": 0, "dur": 300}
{"seq": 1236, "ts": 1756800000323, "type": "GAIT",  "lift_time": 120, "ground_time": 180, "height": 25}
{"seq": 1237, "ts": 1756800000423, "type": "STOP"}
{"seq": 1238, "ts": 1756800000523, "type": "ACTION", "id": 7}
{"seq": 1239, "ts": 1756800000623, "type": "LED",    "color": "red", "blink_hz": 2}
{"seq": 1240, "ts": 1756800000723, "type": "SOUND",  "phrase_id": 181}
```

| 필드 | 범위 | HW_MechDog 매핑 |
| :--- | :--- | :--- |
| `step` | −100 ~ 100 (mm) | `move(step, angle)` 제1인자 |
| `angle` | −30 ~ 30 (deg) | `move(step, angle)` 제2인자 |
| `pitch`/`roll` | 라이브러리 허용 범위 | `transform(pose, dur)` |
| `id` | 0 ~ 15 | 내장 액션 그룹 |
| `color` | 색상 이름 (`config.escalation.led`) | 눈 LED. FR-10.4 |
| `blink_hz` | 0 = 상시점등 | 눈 LED 점멸 |
| `phrase_id` | WonderEcho 문구 ID | 사전 등록 문구 재생. FR-3.4 |

**수신측 검증 규칙**

| # | 규칙 |
| :-- | :--- |
| ① | `seq` 역전·중복 패킷 폐기 (FR-1.6) |
| ② | 필드 범위 초과 시 클램핑 |
| ③ | 파싱 실패 시 패킷 폐기. **타임아웃 카운터는 갱신하지 않음** |
| **④** | **미지의 `type` 은 폐기하고 WARN 로그를 남긴다** |

> **④가 스키마 확장 정책의 근거다.** 받는 쪽이 모르는 타입을 안전하게 무시하므로 **새 명령 타입 추가는 항상 하위 호환**이다. 한쪽이 먼저 보내기 시작해도 기존 동작에 영향이 없고, 다른 쪽이 나중에 핸들러를 추가하면 그 시점부터 동작한다.

**스키마 변경 분류**

| 유형 | 예 | 절차 |
| :--- | :--- | :--- |
| **하위 호환 (additive)** | 새 `type` 추가, 옵션 필드 추가 | **자유롭게 진행.** PR 본문에 변경 사실만 기재 |
| **파괴적 (breaking)** | 필드명·단위·의미·범위 변경, 타입 삭제 | 이슈로 알리고 **송·수신 양쪽과 목업·테스트를 함께 수정** |

> 파괴적 변경만 조심하면 된다. 불일치는 **골든 픽스처 기반 CI 테스트**(`tests/fixtures/protocol_samples.jsonl`)가 자동으로 잡는다 — 사람의 규칙 준수에 의존하지 않는다.

#### FR-5.2 텔레메트리 (MechDog ESP32 → Host PC, UDP, 10 Hz)

```json
{
  "seq": 88, "ts": 1756800000500,
  "device_id": "mechdog-b",
  "state": "PATROL",
  "dist_cm": 47,
  "imu": {"pitch": 1.2, "roll": -0.4, "yaw": 183.5},
  "batt_v": 7.62,
  "last_cmd_age_ms": 34,
  "flags": {"lowbatt": false, "tipped": false, "link_ok": true}
}
```

> **`device_id` 는 필수다.** 다중 개체를 동시에 운용할 때 송신자를 IP 로 구분하면 DHCP 변경에 취약하고, 컨테이너를 거치는 경우 출처가 게이트웨이로 보여 아예 구분이 불가능하다 (DR-17). 구조화 로그의 `device_id` 와 같은 값을 쓴다.

#### FR-5.3 영상 (XIAO → Host PC)

- `http://<XIAO_IP>:81/stream` — multipart/x-mixed-replace MJPEG
- 기본 해상도 **VGA 640×480 @ 15 fps**, 대역 부족 시 QVGA 320×240으로 폴백
- Host PC는 스트림 단절 시 **지수 백오프(1s → 2s → 4s, 최대 30s)** 로 자동 재연결해야 한다.

#### FR-5.4 스캔 데이터 [P2]

- LiDAR 노드 → Host PC, UDP. LD19 원시 패킷을 그대로 중계 (약 20 KB/s, UART 230400).
- Host PC 측에서 파싱하여 ROS2 `sensor_msgs/LaserScan`으로 변환한다.

### FR-6: LiDAR SLAM 및 위험구역 출동 [P2]

> 위치 추정 수단이 확보된 전제 위에서만 성립하므로 Phase 2로 분리한다. 근거는 DR-8 참조.
>
> ⚠️ **측위 방식은 미확정이다.** LiDAR SLAM(Track A)과 스마트폰 VIO(Track B) 두 후보를 병행 검토 중이며, 게이트 테스트 결과로 결정한다. 상세 비교와 결정 매트릭스는 **[측위 방식 비교 문서](LOCALIZATION_OPTIONS.md)** 를 따른다. 아래 FR-6은 두 트랙에 공통 적용된다.

- **FR-6.1 (매핑 / 측위)** 선택된 트랙의 센서 입력으로 공간을 인식하고 로봇의 위치·자세를 추정한다. **Track A**: LD19 스캔 + odometry prior → ROS2 `slam_toolbox`가 2D occupancy grid 생성. **Track B**: ARCore VIO가 6자유도 pose를 미터 단위로 제공. ROS2의 역할은 **"스캔을 넣으면 맵과 위치를 반환하는 블랙박스"** 로 한정하며, 경로계획·행동 로직은 Python 계층에 둔다.
- **FR-6.2 (Stop-and-Scan)** 초기 매핑은 **정지 → 자세 안정 대기 → 스캔 취득 → 이동**을 반복하는 방식으로 수행한다. 보행 중 연속 스캔은 차기 과제로 둔다. (근거: RISK-03)
- **FR-6.3 (스캔 유효성 필터)** IMU 기준 |pitch| 또는 |roll|이 임계값(기본 5°)을 초과하는 시점의 스캔은 폐기한다.
  - **FR-6.3.1** **의도된 자세 변경 구간**(FR-3.3 Alert Stance, FR-9.2.2 자세 상승, FR-2.4 스캔 모션)의 스캔도 폐기 대상이다. 마스트 위 센서가 몸통과 함께 기울어지므로, Pitch Up 15°만으로도 5m 거리에서 스캔면이 1.3m 이상 쓸린다.
- **FR-6.4 (Gait Odometry)** 엔코더가 없으므로 "보행 명령 1초당 이동거리"를 실측 캘리브레이션하여 SLAM의 odometry prior로 제공한다. IMU yaw를 회전량 추정에 사용한다.
- **FR-6.5 (Dispatch)** 대시보드에서 지정한 위험구역으로 웨이포인트 추종 이동한다 (`STATE_HAZARD_DISPATCH`). **목표는 반드시 맵 프레임에 고정된 앵커/웨이포인트 객체로 지정하며, 누적 오도메트리 좌표값으로 지정해서는 안 된다** (드리프트 내성 확보). 경로는 **최소 회전 반경을 존중**해야 한다(DR-11).
- **FR-6.6 (Pose Validity)** SLAM pose가 **500 ms** 이상 갱신되지 않거나 추정 신뢰도가 임계값 미만이면 즉시 정지하고 `STATE_LOST`로 전환한다.
- **FR-6.6.1 (센서 상시 장착)** 측위는 주행 중 지속적으로 필요하므로 **측위 센서는 시연·운용 중 탈거할 수 없다.** 매핑만 수행하고 센서를 제거하면 저장된 지도는 활용 불가능한 산출물이 된다.
- **FR-6.7 (Hazard Inspection)** 목표 도달 시 **정지 후 상체 피치 스캔**(FR-2.4 방식)과 **선회 보행(arc)** 을 조합한 주변 스캔을 수행하고, 캡처 이미지를 **Tier 3 클라우드 VLM**에 전송하여 위험요소 판독 리포트를 생성한다. 이 경로는 비실시간이며 주행에 영향을 주지 않아야 한다.

### FR-7: 구역 순찰 및 랜덤 자율주행 [P2]

> 측위 확보를 전제한다. 트랙 확정은 [측위 방식 비교 문서](LOCALIZATION_OPTIONS.md) 참조.

- **FR-7.1 (구역 정의)** 순찰 대상 구역 **A~E(5개)** 를 맵 프레임에 고정된 앵커/웨이포인트 객체로 정의한다. **누적 오도메트리 좌표로 정의해서는 안 된다.**
- **FR-7.2 (순차 순찰)** `A → B → C → D → E` 순서로 순회하며, 각 구역에서 정지 후 FR-2.4 스캔과 FR-8 변화 감지를 수행한다.
- **FR-7.3 (랜덤 순찰)** 순차 순회를 1회 이상 완료한 뒤에는 **방문 순서를 무작위화**한다. 순찰 패턴의 예측 불가성은 침입자의 회피를 어렵게 하므로 경비 로봇의 의도된 특성이다.
- **FR-7.4 (도착 판정)** 목표 앵커로부터 설정 반경(기본 30cm) 이내 진입 시 도착으로 판정한다. 측위 정확도를 고려한 값이며 `config.yaml`에서 관리한다.
- **FR-7.5 (경로 제약)** 경로는 **최소 회전 반경을 존중**해야 한다. 제자리 회전이 불가하므로 좁은 구간에서는 후진을 활용한다 (근거: DR-11).

### FR-8: 사이클 간 변화 감지 (Change Detection) [P1]

> **필요 조건은 "구역 식별"이며 정밀 측위가 아니다.** 어느 구역에 있는지만 알면 성립하므로, 측위 트랙이 확정되지 않아도 Phase 1에서 구현할 수 있다.

- **FR-8.0 (구역 식별 수단)** 각 순찰 구역에 **ArUco 마커를 1장 부착**하고, 카메라로 마커 ID를 읽어 구역 라벨(A~E)을 판정한다. 매핑은 `config.zones.marker_map` 에서 관리한다.
  > ⚠️ **이는 측위가 아니라 라벨 읽기다.** 마커는 *"여기가 C구역이다"* 만 알려주며 좌표를 주지 않는다. 마커가 시야에서 사라져도 변화 감지 기능은 영향받지 않는다 — 도착 시 한 번 읽으면 되기 때문이다.
  > **구역 간 자율 이동(FR-7)은 측위가 필요하므로 Phase 2로 분리되어 있다.** 본 항목은 그 대체가 아니며, LiDAR 도입 여부와 무관하다.
  > 마커 인식은 FR-10.1(사원증 인증)과 동일한 `cv2.aruco` 경로를 재사용하므로 추가 비용이 없다.

- **FR-8.1 (기준 등록)** 각 구역에서 스냅샷과 함께 **검출 객체 목록**(클래스 + 개수 + 화면 내 대략 위치)을 기준값으로 저장한다.
- **FR-8.2 (비교 방식 — 필수 제약)** 비교는 **객체 목록 단위로 수행한다. 픽셀 단위 이미지 차분을 사용해서는 안 된다.**
  - 근거: 로봇이 동일 자세로 복귀하지 못하고(수 cm 이동·수 도 회전), 4족 보행은 매 스텝 몸 높이·피치가 변하며, 조명도 변한다. 픽셀 차분은 오검출이 폭발하여 사용 불가능하다.
- **FR-8.3 (변화 분류)** 비교 대상은 **①번 COCO 범용 검출기의 80클래스**다. 의자·가방·상자·병 등 일상 객체를 포괄하므로 시연 환경에서 실제로 놓이는 물건을 감지할 수 있다. 비교 결과를 아래로 분류하고 대시보드에 표시한다.
  | 분류 | 조건 |
  | :--- | :--- |
  | **물체 반출** | 기준에 있던 객체가 사라짐 |
  | **물체 반입** | 기준에 없던 객체가 추가됨 |
  | **인원 출현** | 기준에 없던 `person` 검출 → FR-3 경비 대응으로 연계 |
- **FR-8.4 (오검출 억제)** 단일 사이클의 변화만으로 경보하지 않고, **연속 2사이클 동일 변화**가 확인될 때 확정한다. 단 `person` 출현은 즉시 처리한다.
- **FR-8.5 (Tier 3 상세 리포트)** 변화 확정 시 기준 이미지와 현재 이미지를 **클라우드 VLM**에 전송하여 *"무엇이 어떻게 달라졌는지"* 문장 리포트를 생성한다. 비실시간이며 이 경로의 실패가 주행에 영향을 주어서는 안 된다.

### FR-9: 산업 안전 관리 (PPE 미착용 감지) [P1]

- **FR-9.1 (모델)** PPE 전용 모델을 **새 데이터셋으로 직접 학습**한다. 학습 클래스는 최소 아래 4종으로 하고, 위반 클래스는 `{no_helmet, no_vest}` 로 한다.
  | 클래스 | 의미 |
  | :--- | :--- |
  | `helmet` / `no_helmet` | 안전모 착용 / 미착용 |
  | `vest` / `no_vest` | 안전조끼 착용 / 미착용 |

  - **FR-9.1.1** `person` 은 학습 대상에서 제외한다. FR-3.1의 ①번 COCO 검출기가 담당하므로 중복 학습이 불필요하다.
  - **FR-9.1.2** 학습 프레임워크 버전(`ultralytics` 및 모델 계열)은 착수 시점에 확정하고 **`config.yaml`에 기록**한다. 재현 가능해야 한다.
- **FR-9.2 (판정 가능 조건 — 물리 제약 대응)** 카메라 높이가 약 15cm이므로 근거리에서는 사람의 머리가 화각을 벗어나 안전모를 판정할 수 없다. 판정 조건을 **거리(미터)가 아니라 화각 포함 여부로 직접 정의**한다 (근거: DR-15).
  - **FR-9.2.1 (판정 조건)** `person` bbox의 **상단이 프레임 경계에 닿지 않았을 때만** PPE를 판정한다. 머리가 잘린 프레임에서는 판정을 보류한다.
    > 이 조건은 자세(직립·웅크림)와 무관하게 성립하며, **판정 가능 조건과 PPE 검출 가능 조건이 정확히 일치**한다. 머리가 보이지 않으면 애초에 안전모를 볼 수 없다.
  - **FR-9.2.2 (단계적 자세 상승 · Posture Escalation)** bbox가 클리핑된 경우 아래 순서로 시야를 확보하고 매 단계마다 재검사한다. 모든 단계는 기존 `HW_MechDog` API와 내장 액션만 사용한다.

    | 단계 | 수단 | 효과 |
    | :---: | :--- | :--- |
    | ① | `transform()` **Pitch Up** (FR-3.3 Alert Stance) | 시선 상향 |
    | ② | 내장 액션 **`sit_dowm`** (앉기) | 상체 상승 + 시선 크게 상향 |
    | ③ | **후진**하여 거리 확보 | 전신을 화각 안으로 |

    > 단계별 최소 판정거리는 **카메라 수직 화각 실측(OI-16)** 후 확정한다. 자세를 세울수록 근거리 판정이 가능해지므로, 침입자를 근거리에서 마주친 상황에도 대응할 수 있어야 한다.
    > `stand_two_legs` 는 **측위 센서 장착 시 무게중심이 높아 전도 위험이 크므로 사용하지 않는다.**
  - **FR-9.2.0 (판정 개시 조건 — 대상이 정지해 있어야 한다)** 자세 상승 시퀀스는 **추적 대상이 정지
    상태일 때만 개시한다.** 추적 bbox 중심의 이동량이 설정 프레임 수 동안 임계 이하일 때 정지로 본다
    (`config.vision.ppe.static_threshold_px` · `static_frames`).
    > **근거 — 이동하는 대상은 추종이 불가능하다.** MechDog Trot 이동 속도는 약 10~30 cm/s 이고
    > 사람 보행은 120~150 cm/s 로 **5~15배 차이**다. 제자리 회전도 불가하므로(DR-11) 방향 전환에도
    > 공간과 시간이 든다. 게다가 **상향 자세에서는 이동할 수 없으므로**(FR-9.2.3) 대상이 움직이면
    > `자세 상승 → 이탈 → 자세 복귀 → 이동 → 재클리핑` 이 반복되는 **루프에 빠지고, 한 바퀴마다
    > 대상은 더 멀어진다.** 로봇은 자세만 오르내리며 아무 결과도 내지 못하고, 관측자에게는 고장으로 보인다.
    >
    > **실제 운용과도 일치한다.** 산업안전 점검의 대상은 *"작업 위치에 있는 작업자"* 이며,
    > 걸어가는 사람을 쫓아가며 보호구를 검사하는 것이 아니다.
  - **FR-9.2.4 (루프 방지)** 자세 상승 중 대상이 화각을 벗어나면 **즉시 시퀀스를 중단하고 기본 자세로
    복귀한다.** 같은 추적 ID 에 대한 자세 상승 재시도는 `max_posture_retries`(기본 2회)로 제한하며,
    초과 시 **`PPE_UNDETERMINED` 이벤트를 기록하고 순찰을 재개한다.**
    > **판정 실패도 결과다.** "미판정 — 대상 이동 중" 을 대시보드에 표시하면 의도된 동작으로 읽힌다.
    > 표시하지 않으면 같은 상황이 고장으로 보인다. 다음 순찰 사이클에서 재시도한다.
  - **FR-9.2.3 (자세 유지 중 제약)** 상향 자세에서는 카메라로 전방 지면을 볼 수 없다. 따라서 이동이 필요하면 **먼저 기본 자세로 복귀한 뒤 이동한다**(자세 → 이동 순서 보장). 초음파 기반 Tier 1 반사 정지는 자세와 무관하게 계속 유효하다.
- **FR-9.3 (위반 처리)** 위반 검출 시 에스컬레이션 **L3**로 진입하여 즉각 경고 방송, 눈 LED 적색, 스냅샷·이벤트 기록을 수행한다.
- **FR-9.4 (오검출 억제)** FR-3.2와 동일하게 **연속 3프레임** 조건을 적용한다.

### FR-10: 경비 인증 (Access Authentication) [P1]

- **FR-10.1 (사원증 인증)** 사원증에 인쇄된 **ArUco 마커**를 카메라로 인식하여 승인 인원을 식별한다. OpenCV `cv2.aruco` 내장 기능을 사용한다.
  - 설계 근거: 로고 템플릿 매칭은 조명·각도에 취약하고 전용 모델 학습은 데이터 수집 비용이 크다. 사원증에 코드가 인쇄된 형태는 현실의 출입 통제와 동일하므로 타당하다.
- **FR-10.2 (암구호 인증)** 사복 착용 등으로 사원증을 확인할 수 없는 경우 **음성 암구호**로 인증한다.
  - **FR-10.2.1** 인식은 **WonderEcho 모듈의 온칩 오프라인 인식**을 기본 수단으로 한다. 오디오 스트리밍이나 호스트 측 음성인식을 사용하지 않는다.
  - **FR-10.2.2** 암구호는 **영어 대문자 + 하이픈 연결** 형식으로 펌웨어에 등록한다 (한국어 미지원, 2.6절).
  - **FR-10.2.3** 로봇은 인식 결과로 전달되는 **명령 ID**만 판정에 사용한다.
  - **FR-10.2.4** 인증 유효 시간은 설정값(기본 60초)이며, 만료 후 재인증을 요구한다.
- **FR-10.3 (인증 실패 처리)** 설정 횟수(기본 2회) 실패 또는 설정 시간(기본 30초) 내 인증이 없으면 에스컬레이션 **L3**로 진입한다.
- **FR-10.4 (상태 표시등)** 에스컬레이션 단계를 **눈 LED 색상**으로 표시한다 (5.1절 표).

| *ANY* `[P2]` | SLAM pose 500 ms 미갱신 | `LOST` | 즉시 정지, 재측위 대기 | 2 |
| `PATROL` | **구역 도착** `[P2]` | `ZONE_INSPECT` | 정지 → 스캔 → **변화 감지**(FR-8) | 2 |
| `ZONE_INSPECT` | 검사 완료 & 변화 없음 | `PATROL` | 다음 구역으로 (순차 또는 랜덤) | 2 |
| `ZONE_INSPECT` | **물체 변화 확정** (FR-8.4) | `ALERT` | 에스컬레이션 **L3**, VLM 리포트 요청 | 2→3 |
| `ALERT` / `TRACK` | **PPE 위반 검출** (FR-9.3) | `ALERT` | 에스컬레이션 **L3**, 경고 방송 | 2 |
| `ALERT` | 미인증 상태 지속 | `AUTH_WAIT` | 에스컬레이션 **L2**, 인증 요구 | 2 |
| `AUTH_WAIT` | **사원증 또는 암구호 인증 성공** | `PATROL` | 에스컬레이션 **L0** 복귀 | 2 |
| `AUTH_WAIT` | 인증 실패 2회 / 30초 초과 | `ALERT` | 에스컬레이션 **L3** | 2 |

> **설계 규칙**: `FAILSAFE`에서 자동으로 빠져나오지 않는다. 원인 해소 후 사용자가 명시적으로 리셋해야 한다.

### 5.1 대응 에스컬레이션 단계 (Escalation Ladder)

위험구역·미확인 인원·안전 위반에 대한 대응 강도를 단계로 정의한다. **FSM 상태와 직교하는 별도 축**이며, 각 상태에서 현재 에스컬레이션 단계에 맞는 표현을 취한다.

| 단계 | 진입 조건 | 눈 LED | 음향 | 자세·기동 | 기록 | Tier |
| :---: | :--- | :---: | :--- | :--- | :--- | :---: |
| **L0** 순찰 | 정상 | 🔵 파랑 | — | 통상 보행 | — | 1 |
| **L1** 관찰 | `person` 연속 3프레임 검출 | 🟡 노랑 | — | 정지 + **Pitch Up 경계 자세** | 스냅샷 | 2 |
| **L2** 인증요구 | L1이 설정 시간 지속 & 미인증 | 🟠 주황 | 비프음 | 경계 유지 + 선회 추종 | 스냅샷 + 이벤트 | 2 |
| **L3** 경보 | 인증 실패 · **PPE 위반** · **물체 변화 확정** | 🔴 빨강 (점멸) | **즉각 경고 방송** (사전 등록 문구) | 추종 | 이벤트 + **VLM 리포트 + 관제 방송** | 2→3 |
| **F** 페일세이프 | 링크두절 · 저전압 · 전도 · E-Stop | ⚪ 흰색 | — | 엎드림, 서보 토크 해제 | 로그 | **1** |

**해제 규칙**

| 전이 | 조건 |
| :--- | :--- |
| L1 → L0 | 타겟 미검출 5초 지속 (FR-3.6) |
| L2 → L0 | **인증 성공** (사원증 또는 암구호) |
| L3 → L0 | **관리자 확인(대시보드 리셋)으로만 해제한다.** 아래 참조 |
| **F → L0** | **자동 복귀 금지.** 원인 해소 후 사용자가 명시적으로 리셋 |

> **⚠️ L3 해제 규칙 정정 (v1.2)** — v1.1 은 `L3 → L0` 조건을 *"인증 성공 + 관리자 확인"* 으로 적었으나,
> 이는 **L3 진입 원인 셋 중 하나(인증 실패)만 보고 쓴 규칙**이었다. 나머지 둘에는 적용되지 않는다.
>
> | L3 진입 원인 | "인증 성공" 이 성립하나 |
> | :--- | :--- |
> | 인증 실패 | ○ |
> | **PPE 위반** | **✕ — 인증할 주체가 없다.** 위반자가 안전모를 써도 "인증"이 아니다 |
> | **물체 변화 확정** | **✕ — 사람이 없다.** 인증할 대상 자체가 존재하지 않는다 |
>
> 그대로 두면 **PPE 위반과 물체 변화로 L3 에 진입한 로봇은 영구히 L3 에서 나올 수 없다.**
>
> **정정 — L3 는 원인과 무관하게 관리자 확인으로만 해제한다.**
> 원인 해소 여부(안전모 재착용, 물건 복귀)는 **대시보드에 표시하되 해제 조건으로 쓰지 않는다.**
> 이유는 둘이다. ① 원인별 자동 해제 조건을 만들면 조건이 셋으로 갈려 버그가 생긴다.
> ② 물건이 돌아왔다고 그것이 정상 상황인지 로봇은 판단할 수 없다 — 사람이 봐야 한다.
> 상시 인적 감시를 전제하므로(A-13) 관리자 확인이 가장 단순하고 안전한 출구다.

> **설계 원칙** — 눈 LED는 장식이 아니라 **관측 가능한 상태 출력**이다. 로봇이 지금 무엇을 판단하고 있는지 관객과 작업자가 즉시 읽을 수 있어야 하며, 이는 디버깅 수단으로도 기능한다.

> **음향 분담** — L3의 즉각 경고는 **WonderEcho가 지연 없이** 재생하고, 상황 설명은 **Host PC가 VLM 판독 후 1~3초 뒤 방송**한다 (2.6절). 즉각성과 표현력을 동시에 확보하기 위한 분리다.

## 6. CI/CD 파이프라인

### 6.1 CI 설계 원칙

임베디드 프로젝트에서 CI가 형식만 갖추고 실질을 잃는 전형적 실패가 있다. 아래 원칙으로 이를 방지한다.

| # | 원칙 | 이유 |
| :-- | :--- | :--- |
| **1** | **정적 분석은 문제를 찾으면 반드시 실패하게 한다** — `cppcheck --error-exitcode=1` | `0` 으로 두면 경고를 출력하고도 잡이 초록불이 된다. 아무도 로그를 읽지 않으므로 분석이 장식이 된다 |
| **2** | **검사 도구는 설치가 아니라 실행이 확인되어야 한다** — `clang-format --dry-run --Werror` | 설치 스텝만 있고 실행 스텝이 없는 구성은 흔한 실수다 |
| **3** | **소스가 없는 잡은 실패가 아니라 스킵한다** — `hashFiles` 조건 | 착수 전 단계에서 빨간불이 상시화되면 팀이 CI를 무시하게 된다. 단 **소스가 추가되면 자동으로 활성화**되어야 한다 |
| **4** | **플랫폼 종속 의존성은 환경 마커로 분기한다** | 리눅스 러너와 Windows 개발 PC가 다르다. `onnxruntime-directml` 은 Windows 전용이므로 마커 없이 선언하면 CI 가 설치 단계에서 죽는다 |
| **5** | **하드웨어 없이 검증 가능한 로직을 최대화한다** | 👇 아래 참조 |
| **6** | **액션 버전을 최신 메이저로 유지한다** | 런타임 deprecation 경고가 매 실행마다 쌓이면 실제 문제를 가린다 |

> **원칙 5가 이 프로젝트 CI의 핵심이다.** 임베디드에서 값싸게 자동화되는 것은 **하드웨어에 의존하지 않는 순수 로직**이다. FSM 전이, 패킷 파싱, 안전 판정, 설정 스키마를 **하드웨어 접근에서 분리하여 설계**하면 CI에서 전수 검증할 수 있다.
>
> 이를 위해 **온보드 코드도 로직 계층과 HAL 호출 계층을 분리**한다 (WBS 0절 3.0/4.0 구분 기준과 동일).

### 6.2 파이프라인 구성

```
[ Git Push / PR ]
      │
      ├─▶ Job 1: Python Quality
      │     · ruff (lint + format check)
      │     · pytest  ← 하드웨어 없이 검증 가능한 순수 로직
      │         - FSM 상태 전이 테이블 전수 검증
      │         - 명령 JSON 직렬화/역직렬화 및 범위 클램핑
      │         - seq 역전·중복 폐기 로직
      │         - 타임아웃/페일세이프 판정 로직
      │         - config.yaml 스키마 검증
      │     · coverage 리포트
      │
      ├─▶ Job 2: Firmware Quality
      │     · clang-format --dry-run --Werror
      │     · cppcheck (--error-exitcode=1)
      │
      ├─▶ Job 3: Firmware Build (matrix)
      │     · arduino-cli 또는 PlatformIO
      │     · [firmware_mechdog_motion] esp32:esp32:esp32
      │     · [firmware_xiao_vision]    esp32:esp32:XIAO_ESP32S3
      │     · 빌드 산출물(.bin/.elf) 아티팩트 업로드
      │
      └─▶ Job 4: Release (tag push 시)
            · Semantic Versioning 태그
            · 펌웨어 바이너리 첨부 릴리스 생성
```

> ⚠️ **선결 과제** — `HW_MechDog` 라이브러리는 GitHub Actions 러너에 없다. 라이브러리를 `third_party/`로 벤더링하거나 CI 캐시에 배치해야 펌웨어 빌드 잡이 성립한다. 라이선스 확인 필요. (RISK-07)

| **OI-16** | **카메라 수직 화각(VFOV) 실측** — FR-9.2.2 자세 단계별 **상하 커버 범위**를 확정하기 위한 선행 측정. ⚠️ *거리 임계를 정하기 위한 것이 아니다* — 판정은 bbox 클리핑으로 하며(FR-9.2.1, DR-15), 이 측정은 **어느 자세 단계에서 머리가 화각에 들어오는가**를 알기 위한 것이다 | **M0** |
| **OI-17** | **앉기 자세의 몸통 피치 실측** — NFR-2.4 임계값(임시 60°) 확정에 필요. 55° 초과 시 자세를 완만하게 조정 (DR-16) | **M0** |
| **OI-19** | **온라인 시연 방식 — 녹화 영상인가 실시간 웹캠인가** — 리스크가 크게 다르다. 녹화는 재시도·편집이 가능하고(WBS 7.2 가 이를 전제한다), 실시간은 한 번에 성공해야 하며 **시연자 1명이 설명과 로봇 조작·복구를 동시에** 해야 한다. 실시간을 택하면 복구 절차와 폴백 시나리오를 추가 정의해야 한다. 부수 영향: ① 눈 LED 가 웹캠 화각에 들어와야 관객에게 전달된다 → 대시보드의 단계 표시 비중 증가 ② 카메라가 3개가 된다(XIAO·웹캠·화면공유) ③ **화면 공유 업로드가 RISK-05 대역 경합에 추가된다** → Host PC 의 5GHz·유선 분리가 선택이 아니라 필수 ④ 로봇 스피커 소리는 웹캠 마이크를 거치므로, 관객에게 들려야 하는 방송은 Host PC 쪽으로 잡는 것이 안전하다 | M3 |
| **OI-18** | **상황별 대응 시나리오 (Response Playbook)** — FSM 전이표(5절)와 에스컬레이션 래더(5.1)는 **"이 상태에서 이 트리거면 이 액션"** 이라는 *점* 을 정의한다. 그러나 **한 상황이 시작부터 종료까지 어떻게 흐르는지**(*선*)는 정의되지 않았다. 예: 사복 인원 출현 → 인증 요구 → 실패 → 최종적으로 로봇은 어떤 상태로 남는가 / 대상이 이탈하면 / PPE 위반자가 무시하고 머무르면 / 인원이 둘인데 한 명만 인증되면. **시연 시나리오(멘토 논의 예정)를 정하면 함께 확정된다** | **M2** |
| OI-5 | `HW_MechDog` 라이브러리 라이선스 및 재배포 가능 여부 | M1 이전 |
| **OI-15** | **①번 범용 검출기 모델 선정** — 판단 기준: ⓐ FR-8 변화감지 어휘(COCO 고정 vs 개방 어휘) ⓑ 기준 PC에서 프레임 예산 내 동작 ⓒ **라이선스** (`ultralytics` = AGPL-3.0 / RT-DETR·MMDetection·YOLOX = Apache-2.0) | M2 |
| OI-6 | **MP3 모듈 제어 인터페이스** (FR-3.4) — 킷에 **MP3 모듈(TF카드 포함)이 별도 포함**되어 있음을 확인. 확인되면 2.6절의 *재생* 담당을 WonderEcho 에서 MP3 모듈로 이관한다 (한국어 가능·재플래싱 불요) | M3 |
| **OI-10** | **WonderEcho 통신 방식** — 실물 모듈의 핀 실크스크린이 `SCL / SDA / GND / 5V` 로 확인됨 → **I2C 로 잠정 판단.** 위키는 인터페이스를 명시하지 않으므로 실물 라벨을 근거로 삼고, 실기에서 확정한다 | M3 |
| **OI-11** | WonderEcho 플랫폼의 재생 문구 입력란이 자유 텍스트인지 (임의 문장 합성 가능 범위) | M3 |
| ~~OI-12~~ | ~~눈 LED 하드웨어~~ — **닫힘.** 초음파 센서에 **RGB LED 가 내장**되어 있음을 실물로 확인(2026-09-03). 별도 부품 불필요. 킷의 Dot Matrix 모듈은 대안으로 보유 | ✅ **닫힘** |
| ~~OI-7~~ | ~~LiDAR 노드 방식~~ — **닫힘. 별도 MCU(ESP32 DevKit)로 결정.** XIAO 겸임은 ① 카메라·Wi-Fi 중 230400 baud 연속 수신의 타이밍 위험 ② LiDAR 모터 부하가 영상에 간섭 ③ 마스트↔몸통 배선 발생 ④ 고장 격리 상실 때문에 배제한다. 비용 차이는 MCU 1개뿐이다. 상세: [하드웨어 조립](HARDWARE_ASSEMBLY.md) 2.4 | ✅ **닫힘** |
