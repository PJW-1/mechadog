# 루프 워치독 실물 검증 절차 (WBS 3.2.4)

2026-09-13 에 실제로 수행해 통과한 절차를 다른 사람이 그대로 따라갈 수 있게 정리한 문서다.
감시기의 **설계와 근거**는 [`firmware_mechdog_motion/README.md`](../firmware_mechdog_motion/README.md)
의 "3.2.4 제어 루프 감시" 절에 있다. 이 문서는 **PC 쪽에서 무엇을 어떤 순서로 실행했는지**를 다룬다.

> **구동 OFF 전용이다.** `MECHADOG_ENABLE_ACTUATORS=1` 과의 조합은 펌웨어가 `#error` 로 막는다.
> 리셋 직후 벤더 시작 코드가 몸체를 움직일 수 있어서, 보행 빌드의 재부팅 거동을 검증하기 전에는
> 켜지 않는다. 이 절차는 다리를 받침에 올린 정지 상태를 전제로 한다.

---

## 1. 준비물

### 하드웨어

| 항목 | 내용 |
| --- | --- |
| 기체 | MechDog 본체 1대, 다리를 받침에 올려 접지시키지 않은 상태 |
| 연결 | 본체 USB(CH340, VID:PID `1A86:7523`)를 PC 에 직결 |
| 전원 | 시험 내내 배터리·USB 유지. 중간에 빠지면 처음부터 다시 한다 |
| 네트워크 | 본체와 PC 가 같은 AP. 본체는 HTTPS 8443, UDP 5001(명령)/5101(상태) |

### COM 포트 구분 — 반드시 먼저 확인한다

본체와 음성 모듈(WonderEcho)이 **둘 다 CH340** 이라 VID/PID 로는 구분되지 않는다.
2026-09-13 기준으로 본체는 `COM8`, 음성 모듈은 `COM5` 였지만 **USB 위치가 바뀌면 달라진다.**

구분 방법: 음성 모듈 USB 를 뽑았다 꽂아 보고, 사라졌다 나타나는 쪽이 음성이다.
스크립트는 전부 본체 포트를 열기 전에 `list_ports` 로 VID/PID 를 확인하지만,
그것만으로는 두 장치를 구분하지 못하므로 **사람이 먼저 확정해야 한다.**
음성 포트를 잘못 열면 다른 작업의 잠금과 충돌한다.

### 소프트웨어

- Python 3.12, `pyserial`, `esptool`
- Arduino CLI + esp32 코어 (`esp-2021r2-patch5-8.4.0` 툴체인의 `xtensa-esp32-elf-objdump`)
- 저장소의 `tools/ota_update.py`, `tools/telemetry_probe.py`, `host/common/protocol.py`
- 배타 실행 잠금과 하드웨어 래퍼 — 두 작업이 동시에 같은 포트를 열지 못하게 한다

## 3. 전체 순서

| # | 단계 | 기기 접촉 | 하는 일 |
| --- | --- | --- | --- |
| 1 | 사전 확인 | 읽기만 | 현재 정상·확정 상태와 UART 확인 |
| 2 | 전체 백업 | 읽기만 | 4 MiB 스냅샷 + 활성 슬롯 확정 |
| 3 | 후보 빌드 | 없음 | probe/final 두 벌 컴파일 + ELF 검사 |
| 4 | 설치 전 검문 | 없음 | 구동 코드가 정말 없는지 기계어로 확인 |
| 5 | 시험본 설치 | OTA | 고장주입 포함 빌드를 정상 OTA 로 설치 |
| 6 | 본 시험 | OTA + UART | 고장 반복 / 전송 중단 / 자동 롤백 |
| 7 | 최종본 설치·부하 | OTA + UDP | 고장주입 없는 최종본 설치 후 120초 부하 |
| — | (사고 시) 복구 | 플래시 쓰기 | 수동 ROM 진입 후 선택영역 4 KiB 만 복원 |

3·4 번을 건너뛰면 안 된다. 실제로 **첫 빌드에서 OTA/센서 옵션이 빠진 적이 있고, 4번의
ELF 검사가 그걸 잡아내 설치를 막았다.** 옵션을 명시한 v2 만 검증·설치했다.

## 4. 단계별 상세

### 1단계 — 사전 확인

무엇을 하나: `/status` 로 `healthy && confirmed && !updating` 을 확인하고,
**DTR/RTS 를 내린 채** UART 를 10초 읽어 센서 줄과 부팅 표식 수를 센다.

왜 DTR/RTS 를 내리나: CH340 은 포트를 여는 것만으로 기체를 리셋시킬 수 있다.
읽기만 하려는데 리셋이 걸리면 그 자체가 시험을 망친다.

통과 기준: 상태 3개 참, 센서 줄이 꾸준히 나옴, 부팅 표식 0개(= 혼자 재부팅하지 않음).
UART 가 128 KiB 를 넘으면 이상 상황으로 보고 멈춘다.

### 2단계 — 전체 백업

무엇을 하나: **수동 ROM 모드** 에서 4 MiB 전체를 읽어 파일로 남기고,
읽은 내용 안에 알고 있는 부트로더·파티션 테이블·정상 앱이 제자리에 있는지 대조한 뒤,
활성 OTA 슬롯이 몇 번인지 확정한다.

- 자동 리셋으로 ROM 에 넣지 않는다. ROM 응답이 없으면 사람이 BOOT 버튼으로 넣는다
- Secure Boot / Flash Encryption 이 켜져 있으면 즉시 중단한다
- 활성 슬롯이 예상과 다르면 **추측하지 말고 멈춘다.** 쓰기 대상을 잘못 고르면 복구 근거가 사라진다

이 백업 없이 5단계 이후로 넘어가지 않는다. 복구는 전적으로 이 파일에 의존한다.

### 3단계 — 후보 빌드

무엇을 하나: 소스를 개인 폴더로 **동결 복사**한 뒤 컴파일하고, 복사본 해시가
컴파일 전후로 같은지 확인하고, ELF 를 역어셈블해 검사하고, 패키지 기술 파일을 만든다.

두 벌을 만든다:

| 빌드 | `MECHADOG_WATCHDOG_FAULT_PROBE` | 용도 |
| --- | --- | --- |
| `probe` | 1 | UART `H` 로 고의 무한루프를 걸 수 있는 시험본 |
| `final` | 0 | 고장주입 경로가 아예 컴파일되지 않은 배포본 |

공통 옵션은 `MECHADOG_ENABLE_OTA=1`, `MECHADOG_ENABLE_SENSORS=1`,
**`MECHADOG_ENABLE_ACTUATORS=0`**, `MECHADOG_ENABLE_TASK_WDT=1` 이다.

ELF 검사 항목:

- `MotionHal::begin` / `move` / `stop` / `actuators_enabled` 에 **`call` 명령이 하나도 없고**
  `retw.n` 이 정확히 한 번 — 즉 전부 빈 함수다
- `actuators_enabled` 가 `movi.n a2, 0` — 항상 false 를 돌려준다
- `begin` 과 `verifyRollbackLater` 가 `movi.n a2, 1`
- 벤더 초기화 심볼 `MechDog_init` 이 바이너리에 **없다**
- 감시 태스크 `mechadog::watchdog_detail::monitorTask` 가 **있다**
- 파티션 테이블 BIN 이 기존 것과 **바이트 단위로 같다**
- 고장주입 문자열 `WDT_FAULT_PROBE H accepted` 가 `probe` 에만 있고 `final` 에는 없다

`verifyRollbackLater` 를 확인하는 이유는 6.3 절을 보라.

### 4단계 — 설치 전 검문

3단계와 같은 검사를 **설치 직전에 한 번 더**, 실제로 설치할 파일에 대해 수행한다.
추가로 앱 이미지 꼬리 32바이트가 본문의 SHA256 과 맞는지, 크기가 슬롯을 넘지 않는지,
`src/task_watchdog.h` 에 `esp_task_wdt_` 호출이 없는지(= SDK 공용 감시를 건드리지 않았는지) 본다.

### 5단계 — 시험본 설치

정상 OTA 경로로 설치한다. **USB 플래시 쓰기가 아니다.**
설치 후 `/status` 로 다음을 전부 확인한다:

```
image_sha256 == 패키지의 image_sha256
healthy == true,  confirmed == true,  updating == false
actuators == false
loop_watchdog_armed == true,  loop_watchdog_deadline_ms == 750
watchdog_fault_probe == true          (final 설치 후에는 false)
```

### 6단계 — 본 시험

#### 6.1 고장 반복 — 이게 DoD 다

UART 로 `H` 한 글자를 보내면 펌웨어가 마지막 진척을 기록한 뒤 의도적으로 무한루프에 들어간다.
PC 는 `H` 를 보낸 시각부터 UART 에 `rst:0x`(ROM 리셋 표식)이 찍힐 때까지를 잰다.

3회 반복하며, 매회 다음을 요구한다:

- `WDT_FAULT_PROBE H accepted` 응답을 받았고 (= 고장이 실제로 주입됨)
- `rst:0x` 를 받았고
- 경과가 **1000 ms 이하**
- 재부팅 후 같은 이미지로 정상·확정 복귀, 감시 재활성
- boot ID 가 매회 달라짐 (= 진짜 재부팅)

> **이 값은 상한이지 보장이 아니다.** PC 의 `H` 전송 시작 → 표식 수신까지의 벽시계이고
> USB·호스트 수신 지연이 포함돼 있다. GPIO 계측이 아니다. 그리고 표식을 못 받은 것을
> "그래도 리셋됐겠지"로 넘기지 않는다 — 그건 실패다.

#### 6.2 전송 중단 복구

전체 길이를 선언해 놓고 **4096 바이트만 보낸 뒤 그 HTTPS 소켓만 닫는다.**
AP 를 내리거나 다른 기기의 네트워크를 끊지 않는다 — 끊는 대상은 이 업로드 연결 하나다.
기존 확정 앱으로 정상 재기동하고 감시가 살아 있으면 통과다.

#### 6.3 자동 롤백

최종본이 돌고 있는 상태에서 시험본을 새로 올리되 **확정 명령을 보내지 않는다.**
`healthy=true / confirmed=false` 를 실제로 확인한 뒤 `H` 를 주입하면,
리셋 후 부트로더가 확정된 최종본으로 되돌린다.

> **주의.** 이 자동 복귀는 `verifyRollbackLater=1` 로 빌드된 OTA 앱에서만 성립한다.
> OTA 를 끈 벤치 빌드에는 승인 지연 override 가 없어서 Arduino 기본값이 앱을 **조기에 VALID 로
> 확정해 버린다.** 2026-09-13 에 그걸 모르고 "NEW 선택만 해두면 다음 리셋에 돌아온다"고
> 가정했다가 시험 앱이 계속 부팅했고, 결국 수동 ROM 진입 + 선택영역 복원으로 되돌렸다.
> **SDK 헤더 설정과 설치된 부트로더의 실제 동작은 별개다.** 3단계 ELF 검사에서
> `verifyRollbackLater` 를 확인하는 이유가 이것이다.

#### 6.4 최종본 설치와 부하

최종본을 설치한 뒤 120초 동안 **STOP 만** 보낸다. 15초 송신 / 5초 중단을 6회 반복해
통신이 끊겼을 때 안전 잠금이 유지되는지도 같이 본다.

통과 기준: STOP 전부 ACK, 상태 프레임 순번 누락 0, boot ID 1개(추가 재부팅 없음),
UART 에 부팅 표식 0개, 송신 중단 구간에서 `link_ok=false` 프레임이 실제로 관측됨.

## 5. 안전 규칙

### 절대 하지 않는 것

- **MOVE / POSE / RESET_SAFE 를 보내지 않는다.** 이 절차에서 보내는 명령은 `STOP` 뿐이다
- 음성 모듈 포트(2026-09-13 기준 `COM5`)를 열지 않는다
- 부트로더·파티션 테이블·NVS·PHY·VFS·정상 슬롯에 쓰지 않는다
- eFuse 변경, 전체 지우기, 일반 Arduino 업로드를 하지 않는다
- 자동 리셋을 반복해서 ROM 진입을 시도하지 않는다. 안 되면 사람이 BOOT 버튼을 누른다
- 시험이 실패했을 때 **마감을 늘리거나 감시 대상을 빼서 통과시키지 않는다.**
  09-12 후보는 공용 TWDT 기한을 5초에서 1초로 바꿨다가 Wi-Fi 기동 중 CPU0 Idle 감시에 걸려
  재부팅을 반복했다. 그때도 임계를 완화하지 않고 구조를 바꿨다

### 쓰기 전후 검사

플래시에 쓰는 단계는 쓰기 대상 **밖** 의 모든 영역을 쓰기 전후로 MD5 대조한다.
하나라도 달라지면 실패로 처리한다.

### 기록

성공한 산출물만 남기지 않는다. **실패 로그와 원본도 그대로 보존한다.**
측정 파일은 새 파일 전용 모드로만 연다 — 기존 파일을 덮어쓸 수 없게 하는 것이다.

## 6. 사고 시 복구

시험 앱이 리셋 후에도 계속 부팅하면(= 자동 롤백이 성립하지 않은 경우) 이렇게 되돌린다.

1. 사람이 BOOT 버튼으로 **수동 ROM 진입**
2. 정상 앱·부트로더·파티션 테이블이 스냅샷과 같은지 먼저 검증
3. 보존돼 있던 VALID 선택 항목이 그대로인지 확인
4. **선택영역 4 KiB(`0x1f0000`) 하나만** 스냅샷의 원본으로 되돌린다
5. 비대상 영역 전체를 쓰기 전후 MD5 로 대조
6. 리셋 후 HTTPS 로 `healthy / confirmed / slot=ota_1 / actuators=false / image_sha256` 을 확인

## 8. 그대로 재실행할 수 없는 부분

당시 쓴 PC 스크립트 중 둘은 **의도적으로 비활성화돼 있다.**

| 스크립트 | 상태 | 이유 |
| --- | --- | --- |
| 비활성 슬롯 직접 설치 helper | 실행 차단 | USB 로 비활성 슬롯에 직접 쓰고 NEW selector 를 세우던 도구. 자동 롤백을 전제로 만들었는데 그 전제가 틀렸다(6.3 참고). 복구는 선택영역 명시 복원이어야 한다 |
| 비 OTA 벤치 부하/고장 시험 | 은퇴 | 기체 식별 검사가 있는 OTA 통합 시험으로 대체됐다 |

나머지도 특정 기체 MAC·특정 빌드 SHA 에 못박혀 있어 **다른 기체에서 그대로 돌아가지 않는다.**
2절의 값을 자기 환경으로 바꾸고, 바꾼 값이 맞는지 1·2단계에서 먼저 확인한 뒤 진행한다.

정지 상태 통신 검증만 필요하다면 일반화·시험된 PC 도구 쪽을 쓰는 편이 낫다.

## 9. 아직 검증되지 않은 것

| 항목 | 상태 |
| --- | --- |
| 보행(`ACTUATORS=1`) 재부팅 안전성 | **미검증.** 컴파일 차단 유지. 이게 풀려야 실전 펌웨어에 켤 수 있다 |
| 리셋 직후 서보 초기화 거동 | 미검증 |
| 장시간 연속 운전 | 미검증 (최장 120초) |
| 인터럽트·스케줄러 자체 정지 | 범위 밖. 그 경우 감시 태스크도 못 돈다 |
| 별도 센서 태스크만 정지 | 범위 밖. 센서 신선도와 300 ms 명령 타임아웃은 별개 기능이다 |
| 다른 기체 2대 | 미검증. 기체 간 값 복사 금지 |

WBS 3.2.4 의 완료 표시는 위 항목들이 정리된 뒤 팀장이 일괄 반영한다.
