## 이 문서를 읽는 방법

**할 일을 잘게 쪼갠 목록이다.** 모든 작업이 `3.1.1` 처럼 번호를 갖고, 그 번호가 브랜치명·커밋·PR 에 그대로 쓰인다.

| 말 | 뜻 |
| :--- | :--- |
| **워크패키지** | 쪼갠 것의 최소 단위. 반나절~하루 반 분량 |
| **M/D** | 1 M/D = 한 사람이 하루(8시간) |
| **DoD** | *"이걸 만족하면 끝"* 의 기준. **"구현 완료" 는 DoD 가 아니다** — 확인할 수 있어야 한다 |
| **R** | 그 일의 책임자. `A`·`B`·`C` 는 작업 성격 분류이고 실제 인원 배정은 4절 |
| **선행** | 이게 끝나야 시작할 수 있는 작업 |
| **게이트 G0~G3** | 단계마다 있는 합격 심사. 통과해야 다음으로 간다 |

> 🙋 **자기 할 일만 보려면 [담당자별 작업 목록](ASSIGNMENTS.md) 을 본다.**
> 이 문서 3절에서 생성되므로 항상 일치한다. 여기는 **산출물 기준**으로 쪼개져 있어
> 한 사람의 일이 7개 대분류에 흩어진다.

## 0. 작성 규칙

| 규칙 | 적용 |
| :--- | :--- |
| **분해 축** | 산출물 기준 7개 대분류. 단계(마일스톤) 정보는 5절 매핑표에서 별도 관리한다 |
| **100% 규칙** | 하위 노드의 합 = 상위 노드. 본 WBS에 없는 작업은 프로젝트 범위 밖이다 |
| **워크패키지 크기** | 0.5 ~ 1.5 M/D (4~12시간). 이를 넘으면 분해한다 |
| **결과물 중심** | 상위 레벨은 명사형 산출물, 최하위 워크패키지만 동사형을 허용한다 |
| **완료 기준 필수** | 모든 워크패키지에 검증 가능한 DoD를 명시한다. "구현 완료"는 DoD가 아니다 |
| **일정과 분리** | 본 문서는 범위 분해다. 시간축 배치는 6절에서 별도로 다룬다 |
| **추적성** | 모든 워크패키지는 PRD의 FR/NFR ID와 연결된다 (사전의 마지막 열) |

### 3.0과 4.0의 구분 기준

두 대분류의 경계가 모호해지기 쉬우므로 아래 기준을 적용한다.

| 대분류 | 판단 기준 | 예시 |
| :--- | :--- | :--- |
| **3.0 판단 로직 및 핵심 기능** | **무엇을 할지 결정하는 규칙과 알고리즘.** 하드웨어·프레임워크에 비의존적이며 단위 시험이 가능함 | 상태 전이 규칙, 안전 판정 조건, 추론 로직, 메시지 규약 |
| **4.0 소프트웨어 및 화면** | **그 결정을 실행하고 표시하는 구현체.** 프레임워크·하드웨어에 의존함 | 펌웨어 골격, UDP 송수신, 대시보드 서버·UI, 로거 |

> 이 구분은 6.2 단위 시험의 대상 범위와도 일치한다. **3.0의 산출물은 하드웨어 없이 pytest로 검증 가능해야 한다.**

## 1. 팀 구성 및 역할 (기능별 수직 분할)

| 역할 | 담당 영역 | 주 기술 스택 | 계획 공수 |
| :--- | :--- | :--- | ---: |
| **A · 임베디드** | 하드웨어 검증, 모션 펌웨어, 온보드 안전 로직, 펌웨어 CI | Arduino / C++17 / ESP32 | **20.5 M/D** |
| **B · 인지·AI** | 비전 노드, 스트림 수신, 객체 검출 추론, 대시보드 화면, 성능 튜닝 | Python / OpenCV / ONNX Runtime | **26.0 M/D** |
| **C · 시스템·통합** | 통신 규약, FSM, 대시보드 서버, CI/CD, 문서·일정 관리 | Python / FastAPI / GitHub Actions | **24.0 M/D** |

> ⚠️ **A/B/C 는 작업 성격 분류이며 인원 배정과 1:1 대응하지 않는다.** 위 공수는 WBS 사전의 `R` 열을
> 실제 합산한 값이다. 실제 인원 배정은 **담당자 기준** 절을 따른다.

> B와 C는 호스트 소프트웨어 작업이 많다. 특히 B가 가장 크므로 3주차 리뷰에서 4.6(화면) 또는
> 6.3~6.4(측정·검수)를 재배분 후보로 본다.
>
> **설계 의도** — 인터페이스의 주인과 통합의 주인을 같은 역할에 둔다. 합류 지점에서 책임 소재가 흐려지는 것을 방지하기 위함이다.

### RACI 표기

| 기호 | 의미 |
| :---: | :--- |
| **R** | Responsible — 실제 수행자 (공수가 집계되는 역할) |
| **A** | Accountable — 최종 승인자 |
| **C** | Consulted — 사전 협의 대상 |
| **I** | Informed — 결과 공유 대상 |

- 1주차 `2.3.1 → 2.3.2 → 2.5`, 2주차 `1.1 → 1.3` 순서다. 1주차에 만든 계획 초안과

- 2주차 `4.3.2 → 4.6.5 → G1` 순서다. 키보드 조종을 3주차 화면 묶음에 포함시키지 않는다.
- 3주차 `3.3.3`과 `4.4.2` 완료 후 `4.4.3 → 4.6.4`, 이어서 화면·성능 항목 완료 후
  `6.4.2 → G2`다. G2는 3주차 **목표**이며 실제 검수 실패·지연 시 통과한 것으로 표시하지 않는다.
- 조건부 항목의 선행은 서로 다르다. `5.4.1`은 `5.3.1`, `3.9.1`은 별도 계획 `8.0`,
  `3.9.2`는 `3.9.1`이 선행이다. G2 통과만으로 SLAM 구현이 끝났다고 간주하지 않는다.

### 이 표를 읽을 때

- ⚠️ **`B` 레인과 `C` 레인은 같은 사람이다.** 나란히 그려져 병렬로 보이지만 팀장이 순차로 처리한다.
  레인 수(3)를 사람 수(3)로 읽으면 **팀장 부하를 실제의 절반으로 오해한다.**
- **주차 배치는 목표이지 실적이 아니다.** 게이트는 실제 검수를 통과해야 통과다.
- 같은 주에 있어도 3절의 **선행 순서**를 지킨다 — 1주차 `2.3.1 → 2.3.2 → 2.5`,
  2주차 `1.1 → 1.3` 및 `4.3.2 → 4.6.5 → G1`, 3주차 `4.4.3 → 4.6.4 → 6.4.2 → G2`.
- `[P2]` 조건부 항목은 **탑재 여력 통과 + G2 통과 + LiDAR 도착 + 계획 승인**이 모두 성립해야 시작한다.
- 이 표는 **이관 전 기준선**이다. 4절 이관이 확정되면 해당 항목을 레인 사이로 옮기고 갱신한다.

### 병목은 FR-8 변화 감지다

`3.3.3 → 3.6.1 → 3.6.2` 뒤로 `3.6.3`(오검출 억제)과 `4.8.1 → 4.8.2`(VLM·TTS)가 갈라진다.
**6개 전부 팀장 담당이고 합계 4.5 M/D 가 3주차에 들어간다.** FR-8 은 과제 주제의 핵심이라
**여기가 밀리면 주제 자체가 흔들린다.**

| 완화 수단 | 효과 |
| :--- | :--- |
| `3.3.3` 을 2주차로 당긴다 | 체인 전체가 한 주 앞당겨진다. 다만 `4.3.5 → 3.3.2 → 3.3.3` 세 항목을 2주차에 압축해야 한다 |
| `4.8` VLM·TTS 를 축소 대상으로 둔다 | 체인 뒤 2단(1.5 M/D)이 떨어져 나가고 FR-8 본체(`3.6`)는 유지된다 |

**어느 것을 택할지는 M1 리뷰(1.4)에서 정한다.** 여기서는 제약만 드러낸다.

**1주차에 반드시 끝내야 하는 둘** — `2.1.1` Wi-Fi 검증(실패하면 아키텍처가 바뀐다)과
`3.1.1` 메시지 스키마 공유(모든 노드가 여기에 의존한다).

## 7. 다중 개체 운용 계획

### 전제 — MechDog 3대 (팀원 각 1대 보유)

하드웨어 점유 경합이 없어 **3인이 각자 실기 테스트를 병렬 수행**할 수 있다. 다만 개체가 늘면 별도 문제가 생기며, 관리하지 않으면 "내 로봇에서는 되는데"로 통합 단계에서 시간을 잃는다.

### 개체차 대응

| 문제 | 원인 | 대응 |
| :--- | :--- | :--- |
| **서보 영점 편차** | 개체마다 `MechDog_offset[9]` 값이 다름 | **2.4.1** 개체 프로파일로 분리 |
| **보행 이동량 편차** | 조립 공차·바닥 마찰 | 개체 프로파일에 gait odometry 계수 포함 (Phase 2 FR-6.4 직결) |
| **배터리 상태 편차** | 충전 이력·셀 노화 | 저전압 임계는 공통 유지. 잔량 추정은 보수적으로 판정 |
| **검수 재현성 상실** | 3대 각각 통과 ≠ 통합 통과 | 👇 기준기 규칙 |

### 기준기(Reference Unit) 규칙

| 규칙 | 내용 |
| :--- | :--- |
| **기준기 지정** | **Phase별로 서로 다른 2대를 지정한다.** `phase1_reference` = P1 표준 구성(LiDAR 미장착) / `phase2_reference` = LiDAR 장착 2대 중 측위 검수용 1대. 2.4.1에서 결정하고 물리적으로 표시한다 |
| **왜 1대가 아닌가** | 기준기를 1대로 고정하면 LiDAR 장착 전후의 물리 조건이 달라져 Phase 1 NFR과 Phase 2 측위 검수의 기준이 섞인다. Phase별 표준 구성을 분리하되, 나머지 LiDAR 장착 1대도 개발·재현 시험에 사용한다 |
| **검수는 기준기에서만** | G1~G3 게이트 검수(6.4.1 / 6.4.2 / 6.4.3)는 **반드시 `phase1_reference` 에서**, Phase 2 측위·매핑 검수는 **`phase2_reference` 에서** 수행한다. 개발기 통과는 검수로 인정하지 않는다 |
| **개체 프로파일 필수** | 모든 실기 실행은 `--device <unit-id>`로 자신의 프로파일을 명시한다 (4.4.1) |
| **개체 ID 로깅** | 구조화 로그에 `device_id`를 포함한다 (4.4.2) |
| **성능 수치의 출처** | Phase 1 NFR은 **`phase1_reference`**, Phase 2 측위 성능은 **`phase2_reference`** 실측값으로 문서화한다. 나머지 개체 값은 편차·재현성 자료로 병기하며, 각 기체 보정값은 따로 유지한다 |

### 기준 PC 규칙 — 성능 수치의 출처를 하나로 고정한다

**추론 부하가 팀장 한 사람에게 모였으므로 팀 내 가장 강한 GPU 를 팀장이 쓰고 그 PC 를 기준으로 삼는다.**
다른 두 명은 GPU 사양이 성능에 영향을 주지 않는다 — `slam_toolbox` 는 CPU 연산이다.

| 항목 | 규칙 |
| :--- | :--- |
| **기준 PC** | 팀장 PC (RTX 3080, 사양 확인만 남음 — OI-14) |
| **NFR 측정은 기준 PC 에서만** | NFR-1.1(E2E 250ms) · NFR-1.2(추론) · NFR-1.3(15fps). 타 PC 값은 참고치로 병기 |
| **환경 기록 의무** | 성능 리포트(6.3.1)에 GPU 모델 · EP · 드라이버 버전을 함께 기록 |
| **재검토** | LiDAR 파트 조기 종료로 1명이 소프트웨어로 이동해 추론을 돌리게 되면 그 PC 에서도 재측정 |

> **GPU 는 병목 순위 최하위다** (사람 공수 → 탑재중량 → Wi-Fi 대역 → … → GPU).
> 가장 무거운 조합을 골라도 프레임 예산 66.7ms 안에 들어온다.

### 네트워크 동시 운용

| 항목 | 규칙 |
| :--- | :--- |
| IP 할당 | 개체별 고정 IP 또는 DHCP 예약. 2.4.2 할당표에 기록 |
| 포트 할당 | 명령·텔레메트리 포트를 개체별로 분리 (예: `500X` / `510X`, X = 개체번호) |

| **A-13** | **상시 인적 감시 하에서 운용된다** (시연·연구 목적, 무인 배치 아님) | **DR-16의 전제.** 자동 안전 로직의 1차 목적이 인적 안전이 아니라 하드웨어 보호와 자율 동작 성립이 된다. E-Stop이 1차 안전망. **무인 운용으로 확장 시 안전 로직 전반 재설계 필요** |
| **A-14** | **팀 3대 PC 가 모두 NVIDIA 이며 RTX 3060급 이상이다** | ⚠️ **가정이며 확인 전이다** (OI-14). 이 가정은 **개발 착수 조건이 아니다** — 팀은 환경을 통일하지 않으므로(DR-17) 각자 자신의 GPU 로 시작한다. 영향 범위는 **기준 PC 선정과 NFR 측정치의 출처**뿐이다. 비NVIDIA 가 있어도 DirectML EP 로 동작하므로 재설계는 발생하지 않는다 |

### 제외 범위 (Out of Scope)

- **8.0 SLAM 코어 구현** — 2.2.1 부하 테스트 통과를 조건으로 하는 별도 계획. 착수 전 **V-9(LiDAR 시야 확보·2대 상호 간섭)** 을 수행한다. 3.9와 5.4.1의 2.5 M/D는 P2 승인 시 사용할 조건부 예약 공수이며, 미승인 시 다른 우선 작업으로 재배정한다

- **다개체 협동 동작 구현은 현재 기준선 밖이다.** 다만 협동을 무엇으로 충족할지 결정하는 작업은 1.4와 OI-21에 포함한다. M2에서 시나리오를 채택하면 구현 전에 공수·담당·6절 일정을 다시 승인하고, 보류하면 이벤트 공유와 3대 개별 운용까지만 기준선으로 유지한다

- **한국어 음성 인식** — WonderEcho 미지원. 암구호는 영어 문구로 한다 (아키텍처 1.6)
