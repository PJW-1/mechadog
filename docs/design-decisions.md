## 1. 노드를 선으로 잇지 않고 Host PC 를 허브로 둔다

[ADR-2](DECISIONS.md#adr-2) · 관련 [ADR-3](DECISIONS.md#adr-3)

- **문제**: 카메라 노드(XIAO ESP32S3)와 구동 노드(MechDog ESP32)를 어떻게 연결할 것인가.
- **검토한 대안**: 두 노드를 UART 로 배선하고 CRC16 패킷 규약을 구현한다.
- **결정**: Host PC 를 허브로 하는 Wi-Fi 스타 토폴로지를 쓰고, 명령과 텔레메트리는 UDP 한 줄 JSON 으로 주고받는다.
- **근거**: 카메라 노드는 독립 전원으로 본체에 붙이기만 하는 구성입니다. 배선을 넣으면 본체 무개조, 고장 격리, 독립 개발이라는 이점이 사라집니다. 추론도 ESP32 가 아니라 Host PC GPU 에서 합니다.
- **대가**: Wi-Fi 가 끊기면 인지가 멈춥니다. 그래서 충돌 정지와 링크 두절 페일세이프는 로봇 온보드에 두고, Host 가 꺼져도 로봇이 스스로 멈추게 했습니다.

<a id="d2"></a>
## 2. Phase 1 은 ROS2 없이 단일 Python 프로세스로 완결한다

[ADR-9](DECISIONS.md#adr-9)

- **문제**: 처음부터 ROS2 로 전체 스택을 구성할 것인가.
- **검토한 대안**: 전체를 ROS2 노드로 만들고 경로 계획까지 nav2 로 처리한다.
- **결정**: Phase 1 은 순수 Python 단일 프로세스로 완결합니다. Phase 2 에서는 ROS2 를 `slam_toolbox` 하나로 한정하고, 스캔을 넣으면 지도와 위치를 돌려주는 블랙박스로만 씁니다.
- **근거**: 노드 셋 중 둘이 마이크로컨트롤러라 ROS2 노드가 될 수 없습니다. 특히 온보드 안전 로직은 Host 없이도 돌아야 하므로 미들웨어에 의존시킬 수 없습니다. 넣어도 Host 한 대 안의 함수 호출을 토픽으로 바꾸는 일이 됩니다.
- **대가**: 시각화 도구를 직접 만들어야 하는 부담이 생깁니다. 그래서 `rviz2` 는 예외로 채택했습니다.

<a id="d3"></a>
## 3. CUDA·TensorRT 대신 DirectML 로 추론한다

[ADR-13](DECISIONS.md#adr-13)

- **문제**: ONNX 추론 실행 공급자(Execution Provider)를 무엇으로 할 것인가.
- **검토한 대안**: CUDA EP, TensorRT 엔진.
- **결정**: 개발 PC 는 DirectML EP, CI 는 CPU EP 를 쓰고, `select_providers()` 가 자동으로 폴백합니다.
- **근거**: 프레임당 예산 40ms 가운데 검출이 차지하는 시간은 몇 ms 이므로, CUDA 로 아낄 수 있는 몫이 작습니다. DirectML 은 GPU 제조사와 무관하게 설치 한 줄로 돌고, CUDA 는 버전이 어긋나면 오류 없이 CPU 로 떨어집니다. TensorRT 엔진은 GPU 세대마다 다시 빌드해야 해서 팀원끼리 모델 파일을 주고받을 수 없습니다.
- **재검토 조건**: 속도가 실제로 병목이 되면 TensorRT 가 아니라 CUDA EP 를 먼저 봅니다. CUDA EP 는 같은 `.onnx` 파일을 그대로 씁니다.

<a id="d4"></a>
## 4. 범용 검출기는 라이선스로 골라 YOLOX-S 로 정한다

[ADR-24](DECISIONS.md#adr-24)

- **문제**: 사람 검출에 쓸 범용 검출기를 고른다. 기준은 검출 어휘, 프레임 예산, 라이선스입니다.
- **검토한 대안**: `ultralytics` YOLOv8/11.
- **결정**: YOLOX-S(Apache-2.0)를 씁니다.
- **근거**: 기준 PC(RTX 3080)에서는 어느 후보든 예산 안이라 성능은 변별력이 없었습니다. `ultralytics` 는 AGPL-3.0 이고, FastAPI·WebSocket 으로 관제 화면을 내보내는 이 구조가 AGPL 이 겨냥하는 형태 그대로입니다. 모델 하나를 고르는 일이 팀 전체 코드의 라이선스를 정하는 일이 됩니다. 라이선스는 원본 저장소의 `LICENSE` 파일로 직접 확인했습니다.
- **결과**: 기준 PC·DirectML 에서 전처리부터 후처리까지 평균 8.2ms, p95 8.6ms(n=50)를 실측했습니다.

<a id="d5"></a>
## 5. 사람 확인은 연속 프레임이 아니라 고정 시간 창의 히트 수로 센다

[ADR-25](DECISIONS.md#adr-25) · 관련 [ADR-23](DECISIONS.md#adr-23)

- **문제**: 요구사항이 사람 확인을 «연속 3프레임»으로 정의했습니다. 그런데 프레임 수로 정의하면 같은 3프레임이 7fps 에서는 429ms, 25fps 에서는 120ms 가 됩니다. 추론률을 바꾸면 오검출 억제 강도와 확인 지연이 함께 움직입니다.
- **검토한 대안**: 연속 N 프레임을 유지하고 추론률만 조정한다.
- **결정**: 판정을 «고정 시간 창(300ms) 안에 3회 검출»로 바꾸고, 추론률은 실측으로 25fps 로 정했습니다.
- **근거**: 실기 343프레임을 분석하니 진짜 검출 구간과 단발 오검출이 깨끗하게 나뉘었습니다(길이가 2인 연속 구간이 하나도 없었습니다). 진짜 구간 10개 중 10fps 는 4개, 25fps 는 10개를 인정했습니다.
- **한계**: 시간 창은 히트를 인정할 최대 간격만 고정합니다. 필요한 히트 수가 횟수이므로 확인 지연은 여전히 추론률에 따라 달라지고, 그래서 25fps 도 이 결정에 포함합니다. 창 안에 필요한 횟수가 들어갈 수 없는 설정(예: 300ms 창에 200ms 주기)은 로더가 기동 전에 거부합니다.
- **교훈**: 한 값에 두 가지 의미(억제 강도와 지연)가 묶여 있으면, 한쪽을 바꿀 때 다른 쪽이 조용히 바뀝니다.

<a id="d6"></a>
## 6. 페일세이프 해제는 로봇이 보고하는 래치만 보고 판단한다

[ADR-21](DECISIONS.md#adr-21) · 관련 [ADR-16](DECISIONS.md#adr-16)

- **문제**: Host 가 `FAILSAFE` 에서 벗어날 때 로봇도 실제로 풀렸는지 확인해야 합니다. 확인하지 않으면 Host 는 `IDLE` 인데 로봇은 잠긴 채로 남고, 관제 화면이 거짓을 보여 줍니다.
- **검토한 대안**: 텔레메트리의 `state` 가 `FAILSAFE` 인 동안 해제를 막는다.
- **결정**: 로봇의 자체 래치 `safety_latched` 만 봅니다. 사람이 확인하면 Host 가 `RESET_SAFE` 를 보내고, 로봇이 원인이 없음을 확인해 래치를 풀고 `safety_latched=false` 를 보고한 다음에야 Host 가 해제를 확정합니다.
- **근거**: `state` 는 Host 가 알려 준 값을 로봇이 되돌려 주는 반향일 수 있습니다. 반향을 근거로 잠그면 링크 두절 한 번으로 Host 가 스스로를 영구히 잠급니다. 막는 것은 나가는 문(해제) 하나이고, 들어가는 사건(비상정지, 온보드 페일세이프)은 막지 않습니다.

<a id="d7"></a>
## 7. 경비와 산업안전 점검을 운용 모드로 나눈다

[ADR-33](DECISIONS.md#adr-33)

- **문제**: 두 기능이 같은 사람 검출에서 출발하지만, 사람을 만난 뒤 로봇이 할 일이 부딪힙니다. 경비는 그 사람을 침입자 후보로 보고 따라가며 신원을 확인하고, 점검은 작업자로 보고 멈춰 선 채 자세를 세워 보호구를 확인합니다.
- **검토한 대안**: 한 순찰에서 두 판정을 동시에 수행하고 우선순위 규칙을 둔다.
- **결정**: 순찰 하나는 운용 모드 하나(`guard` 또는 `factory`)로 돕니다. 모드는 로봇이 멈춰 있을 때만 바꿀 수 있고, 바꿔도 경보와 페일세이프는 풀리지 않습니다.
- **근거**: 우선순위 규칙은 결국 일하는 작업자에게 순찰마다 사원증을 요구하거나, 인증을 기다리는 중에 추종을 멈추게 합니다. 시험 조합도 인증 결과 × 보호구 결과 × 자세 단계로 불어납니다.

<a id="d8"></a>
## 8. 음성은 규칙만 쓰고 음성 LLM 을 넣지 않는다

[ADR-38](DECISIONS.md#adr-38) · 관련 [ADR-31](DECISIONS.md#adr-31)

- **문제**: 로봇이 돌아다니면서 듣고 말하려면 음성 모듈을 로봇에 달아야 합니다. 계획은 로봇이 I²C 로 음성 파형을 왕복 중계하는 것이었습니다.
- **실측**: 로봇의 I²C 브리지로는 음성 파형이 오가지 않았습니다. 로봇에서 모듈로는 매핑된 고정 문구만, 모듈에서 로봇으로는 인식한 명령 id 만 전달됐습니다.
- **결정**: 말하기는 미리 넣어 둔 문장만 재생하는 로봇의 MP3 모듈로 옮깁니다. 그 자리에서 문장을 만들어 말하는 기능(음성 LLM 자유 대화, 운영 정보 질의응답, 임의 문장 방송)은 넣지 않습니다. 음성 인식은 Host PC 에서 로컬로 하고, 정해진 규칙(웨이크워드, 명령, 암구호)에 걸린 말에만 정해진 문장으로 답합니다.
- **근거**: 말할 경로가 고정 문장만 허용하는데 자유 생성 기능을 유지하면, 기능은 있지만 로봇 위에서는 쓸 수 없는 상태가 됩니다. 인식 결과는 판정 입력으로만 쓰고 명령으로 실행하지 않습니다.
