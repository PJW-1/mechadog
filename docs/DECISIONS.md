# 설계 결정 기록 (ADR)

> **"왜 저렇게 안 했지?"** 에 답하는 문서. 검토했으나 채택하지 않은 대안과 그 근거를 남긴다.
> 같은 논의를 반복하지 않기 위함이고, **전제가 바뀌면 해당 항목만 다시 연다.**
>
> 기능 요구사항은 [PRD](PRD_Physical_AI_Guard_Robot.md), 구조는 [아키텍처](ARCHITECTURE.md),

## ADR-1 · 역기구학(IK) 엔진을 직접 구현하지 않는다

**대안** — 링크 구조 4족의 IK 를 직접 유도해 서보 각도를 산출하고 보행 생성기를 자체 구현.

**근거** — Hiwonder 가 `HW_MechDog.h` 를 오픈소스로 제공하며 `move(step, angle)` · `transform(pose, dur)` ·
`set_gait_params(...)` 수준으로 IK 와 보행 생성이 완비돼 있다. 다시 구현하는 것은 **검증된 코드를
미검증 코드로 교체하는 일**이고, 실제 난제(자율 인지·판단·항법)에 쓸 시간을 소모한다.

**채택** — 벤더 라이브러리를 **HAL 로 취급**하고 그 위에 자율 스택을 올린다. 상용 4족 로봇 개발과
같은 계층 구조다.

**재검토** — 라이브러리가 제공하지 않는 보행 패턴이 임무상 필수가 될 경우.

## ADR-2 · 노드 간 유선 통신(UART + CRC16)을 쓰지 않는다

**대안** — 비전 노드와 모션 노드를 UART 로 배선하고 CRC16 패킷 프로토콜을 구현.

**근거** — 비전 노드는 **독립 전원으로 본체에 부착만 하는 구성**이다. 배선을 도입하면 이 구조의 최대
이점인 *본체 무개조 · 고장 격리 · 독립 개발* 이 모두 사라진다. 두 노드 모두 Wi-Fi 를 내장하고 있어
유선의 이점도 크지 않다.

**채택** — Host PC 를 허브로 하는 **Wi-Fi 스타 토폴로지 + UDP/JSON**(FR-5).

**재검토** — 메인 ESP32 의 Wi-Fi 를 쓸 수 없는 것으로 판명될 경우(RISK-01). 그때는 UART 2가닥만 최소 연결.

## ADR-3 · 로봇에서 AI 추론을 하지 않는다

**대안** — XIAO ESP32S3 에서 경량 사람 검출 모델을 직접 추론.

**근거** — ESP32-S3 급의 사람 검출은 96×96 그레이스케일 기준 **수 FPS** 이고 MJPEG 스트리밍을 동시에
하면 더 낮아진다. 데스크탑 GPU 는 동급 모델을 **한 자릿수 ms** 에 추론하며 훨씬 큰 모델도 쓸 수 있다.
정확도·속도 양쪽에서 비교가 되지 않는다.

**채택** — XIAO 는 영상 송출만, 검출은 Host PC(Tier 2).

**트레이드오프** — Wi-Fi 단절 시 인지 기능이 정지한다. NFR-2.6 으로 명세해 **인지가 죽어도 순찰·회피는
유지**되도록 설계했다.

**재검토** — 무선 환경이 나빠 오프보드 인지 지연이 NFR-1.1(250ms)을 상시 초과할 경우.

## ADR-4 · 클라우드에 제어 루프를 올리지 않는다

**대안** — 인지·판단 전체를 클라우드로 처리해 로봇과 PC 를 모두 얇게 유지.

**근거** — 인터넷 왕복은 지연 100~300ms 에 지터가 크고, **연결이 끊기면 로봇이 제어 불능**이 된다.

**채택** — 3-Tier 분리. 클라우드는 비실시간 추론(Tier 3)에만 두고 **그 경로의 실패가 주행에 영향을 주지
않도록 격리**한다.

## ADR-5 · 로봇 안에서 지도를 만들지 않는다

**대안** — ESP32-S3 의 PSRAM 에 경량 SLAM 을 이식.

**근거** — 이론적으로 작은 점유격자는 올릴 수 있으나 구현·튜닝 난도가 높아 **프로젝트 전체를 잠식할
위험**이 크다. XIAO 는 이미 카메라와 스트리밍으로 자원이 포화 상태다.

**채택** — 로봇은 스캔을 중계만 하고 SLAM 은 Host PC 에서 수행(FR-6.1).

## ADR-6 · LiDAR 를 로봇 메인보드에 직결하지 않는다

**대안** — LD19 를 메인 ESP32 의 UART 에 연결하고 메인보드가 중계.

**근거** — ① 확장 포트가 이미 점유돼 있다 ② 더 결정적으로 **메인 ESP32 의 최우선 실시간 태스크는 8개
서보의 보행 제어**다. 여기에 4,500 pts/s 스트림 수신과 무선 중계를 얹으면 제어 루프에 지터가 생기고,
**4족 보행에서 제어 지터는 곧 전도**다.

**채택** — LiDAR 를 **독립 노드**로 분리하고 별도 ESP32 DevKit 을 중계로 쓴다.

## ADR-7 · 걸으면서 **지도를 만들지** 않는다 (Stop-and-Scan)

**대안** — 순찰하며 연속 스캔으로 맵을 갱신.

**근거** — 2D LiDAR 는 스캔 평면이 수평임을 가정하는데 4족 보행은 매 스텝 피치·롤이 변한다.
**피치가 10° 틀어지면 5m 거리에서 스캔 평면이 약 87cm 상하로 쓸려** 바닥·천장을 찍고 맵이 오염된다.

**채택** — **정지 → 자세 안정 → 스캔 → 이동** 반복(FR-6.2.1) + IMU 기반 스캔 유효성 필터(FR-6.3).

⚠️ **범위를 좁혔다 (2026-09-08).** 원래 제목이 *"걸으면서 스캔하지 않는다"* 였는데 그것은
**매핑과 운용 중 측위를 한데 묶은 표현**이었다. 요구 품질이 자릿수로 다르다 — 나쁜 스캔 하나가
지도에 섞이면 **영구히** 남지만, 측위에서는 그 한 번의 보정만 건너뛰면 된다. 이미 아는 지도와
맞추는 일이고 직전 위치라는 사전정보가 있기 때문이다.

따라서 **이 결정은 매핑에만 적용된다.** 지도가 있는 상태의 순찰·출동은 게이팅된 보행 중 스캔과
주기적 짧은 정지 앵커로 **멈추지 않고 수행한다**(FR-6.2.2~3). 앵커는 새로 만들지 않고 이미 멈추는
자리(FR-2.4 주기 스캔)를 겸용한다.

**재검토** — 각도 구간 단위 게이팅(FR-6.3.2)과 걸음 위상 동기(FR-6.2.5)는 ①②로 부족할 때 착수한다.
가능 여부는 **보행 중 피치·롤 진폭 실측**(`OI-24`·`2.2.3`)에 달렸다.

## ADR-8 · 위치 추정 수단 없이 "구역 출동"을 명세하지 않는다

**대안** — 위험구역 알람 수신 시 좌표로 이동하는 기능을 초기 요구사항에 포함.

**근거** — MechDog 에는 **엔코더가 없고 SLAM 도 없다.** 위치를 알 방법이 없는 상태에서 "좌표로 이동" 은
구현 불가능한 명세다.

**채택** — FR-6 으로 분리해 Phase 2 로 이연하고 LiDAR SLAM 확보를 전제로 명시.

⚠️ **착수 불가 시(RISK-02) ArUco 마커 기반 구역 정의로 축소하지만, 그것은 대체가 아니라 최후 예비다.**
마커는 *"지금 어느 구역인가"* 만 답한다 — 좌표도 점유격자도 주지 않으므로 **경로 계획이 성립하지 않고
자율주행이 사라진다.** 남는 것은 구역 식별뿐이다. 본선은 Track A(2D LiDAR SLAM)이며 OI-9 에서 확정됐다.

## ADR-9 · Phase 1 에 ROS2 를, Phase 2 에 nav2 를 쓰지 않는다

**대안** — 처음부터 ROS2 로 전체 스택을 구성하고 nav2 로 경로계획까지.

**근거 ① — 구조가 맞지 않는다. 이것이 주된 이유다.**

ROS2 의 값어치는 **여러 노드가 같은 미들웨어로 말할 때** 나온다. 그런데 이 시스템의 노드는 셋이고
**그중 둘이 마이크로컨트롤러**다.

| 노드 | 무엇으로 도는가 | ROS2 노드가 될 수 있나 |
| :--- | :--- | :--- |
| MechDog ESP32 | Arduino / C++17 | **안 된다.** Tier 1 안전 로직은 **호스트가 꺼져도 혼자 돌아야** 한다(아키텍처 1.2 불변 규칙). 미들웨어에 의존시키면 그 전제가 깨진다 |
| XIAO ESP32S3 | Arduino / C++17 | **안 된다.** HTTP MJPEG 을 내보내는 것이 전부이고 추론도 하지 않는다 |
| Host PC | Python | 된다 |

즉 ROS2 를 넣어도 **호스트 한 대 안에서 혼자 도는 껍데기**가 된다. 한 프로세스 안의 함수 호출을
토픽·서비스로 바꾸는 일이고, 얻는 것 없이 tf 트리·타임스탬프·수명주기가 더해진다. **노드 간 통신은
이미 UDP 한 줄 JSON 으로 규약이 서 있다**(PROTOCOL.md) — 그것을 DDS 로 바꿔야 할 이유가 없다.

**근거 ② — 실패 양상이 조용하다 (보조 근거).**

ROS2 SLAM 의 대표적 실패(tf 트리 단절 · 타임스탬프 불일치 · frame_id 오류 · odom 드리프트)는 **넷 다
죽지 않고 조용히 이상해진다.** 크래시는 추적이 쉽지만 이것은 경험이 필요하다. ⚠️ **이것은 ①을 보강하는 관찰이지 결정의 근거가 아니다.**

**채택** — Phase 1 을 **순수 Python 단일 프로세스로 완결**. ROS2 는 Phase 2 에서 `slam_toolbox` 하나로
범위를 한정해 *"스캔을 넣으면 맵과 위치를 반환하는 블랙박스"* 로만 쓴다.

**예외** — `rviz2` 는 채택한다. ADR-7 의 스캔 왜곡 문제는 시각화 없이 진단할 수 없고, 동등한 시각화를
자체 제작하는 비용이 학습 비용보다 크다.

## ADR-10 · 전원을 USB 보조배터리 하나로 통합한다 *(v1.1 에서 반전)*

**v1.0 결정** — LiPo 3.7V 를 XIAO 에 직결. 근거는 **무게**였다.

**반전 근거** — ① **무게 근거가 무너졌다.** 탑재 여력이 약 600g 으로 확인됐고 60~70g 보조배터리는 여유
안에 든다 ② **납땜이 12~15점에서 0 이 된다.** 팀에 인두 경험이 보장되지 않고 발주 기회가 1회이므로
편의가 아니라 리스크 관리다 ③ LD19 허용 범위가 4.5~5.5V 라 USB 출력이 그대로 들어가 승압 모듈이
사라진다 ④ 배터리를 몸통 하부에 붙이면 **무게중심이 낮아진다.**

**재검토** — 부하 테스트에서 무게 초과로 판정되면 v1.0 구성으로 되돌린다.

> *실측이 판단을 뒤집은 사례다. 이래서 M0 하드웨어 검증을 먼저 한다.*

## ADR-11 · 제자리 회전을 전제하지 않는다

⚠️ **2026-09-22 실측이 전제 ①을 깼다 — 제자리 회전은 «불가» 가 아니라 «신뢰할 수 없다» 다.**
`MOVE step=0 angle=±30` 은 **실제로 몸통을 제자리에서 돌린다**(아래 실측 · 육안 확인).
그러나 같은 명령이 낸 각속도가 **5.11~9.34 도/s** 로 최대·최소 차가 **82%** 다 — 근거 ②가
예고한 «재현성 없음» 그대로다. **그래서 결정은 유지하고 문장만 고친다.** 방향을 바꾸는
표준 수단은 여전히 **자동차처럼 원호를 그리는 것**이다.

**근거 — 원래 세 겹으로 막혀 있다고 보았다.**

| # | 층위 |
| :-- | :--- |
| ① | ❌ **반증 (2026-09-22)** — ~~**기하학** — 제자리 회전은 발 접지점이 몸통 중심 주위로 호를 그려야 하며 **측면 변위가 필수**다. 관절이 모두 앞뒤 평면에 있으면 발을 그 호에 올려놓을 수 없다~~ → 실기는 양방향 모두 돌았다. 관절 배치가 막는 것은 **«깨끗한 선회»이고 «회전 자체»가 아니다** |
| ② | ✅ **확증 (2026-09-22)** — **마찰 의존** — 좌우 다리를 반대로 밀면 미끄러지며 거친 회전이 나올 수는 있으나 **재현성이 없고** 서보에 스톨에 가까운 부하가 걸린다. **실측 산포 82% 가 이것이다** |
| ③ | **API** — `move(step, angle)` 만 노출하며 개별 다리 제어가 없다. ②를 시도하려면 IK 를 직접 구현해야 하는데 ADR-1 에서 배제한 범위다. ⚠️ **다만 벤더 `move` 자체가 `step=0` 에서 ②를 일으킨다** — 우리가 IK 를 쓰지 않아도 마찰 회전에 도달한다. 즉 이 층위는 «막는 장치» 가 아니었다 |

**따라서 제자리 회전은 "구현하지 않은 기능" 도 "불가능한 동작" 도 아니라 "이 기구로는 신뢰할 수 없는 동작" 이다.**

**채택** — 회전은 **선회 보행(arc)** 으로만. FR-2.3 · FR-2.4 · FR-3.5 를 이에 맞게 정의했다.

**부수 효과** — 유리: scan matching 은 겹침이 클 때 잘 수렴하는데 arc 조향은 조금씩 이동+회전하므로
겹침이 크다. 불리: **최소 회전 반경**이 생긴다(비홀로노믹). 좁은 공간에서 후진 활용이 중요해지고
경로 추종이 복잡해진다. **그 반경의 실측값은 아직 없다 (OI-22).**

**재검토** — OI-8 에서 `transform()` yaw 가 실제 동작함이 확인될 경우.

**실측 (2026-09-22 · `mechdog-01` · 무하중 · 배터리 8.40 → 8.18 V)** — 절차·원자료·정정 경위는 [docs/measurements/2026-09-22-inplace-rotation.md](measurements/2026-09-22-inplace-rotation.md)

`MOVE step=0 angle=±30` 을 `MANUAL` 에서 4초씩 8회. 매 시행마다 `accepted=True` 와
`state=MANUAL` 을 확인해 **조용히 거부된 시행이 결과로 위장하지 못하게** 했다 —
전날 `-30` 4회가 전부 무효 시행이었고 그것을 «안 돈다» 로 읽었다.

| 항목 | 값 |
| :--- | :--- |
| IMU 정지 바이어스 | **+2.90 도/s** (n=6 · +2.30~+3.68) — **반드시 빼야 한다** |
| 좌회전 `angle=+30` | **+6.63 도/s** (n=3 · 표준편차 2.23) |
| 우회전 `angle=-30` | **-6.79 도/s** (n=3 · 표준편차 1.16) |
| 크기 전체 | **7.37 도/s** (n=8 · 5.11~9.34 · 표준편차 1.81) |
| 180도 / 360도 선회 | 약 **24초** / **49초** |

좌우 크기 차가 2.4% 로 대칭이고 **부호가 명령을 그대로 따른다** — 우연한 미끄러짐이
아니라 지령에 반응하는 동작이다.

⚠️ **이 수치를 제어에 쓰지 않는다.** ① 표준편차가 평균의 25% 다 ② 바이어스 2.90 이
신호 7.37 의 **39%** 라 신호대잡음이 나쁘다 ③ IMU yaw 는 적분값이라 같은 창에서
드리프트와 신호를 분리할 수 없다. 제어에 쓸 값이 필요하면 **바닥 표식 + 외부 절대
각도 측정**으로 다시 재야 한다.

⚠️ **각속도가 호 선회와 사실상 같다** — [ADR-29](#adr-29) 가 잰 `move(±60, +20)` 이
6.8 / 6.6 도/s 다. **제자리 회전을 써도 더 빨리 돌지 못한다.** 얻는 것은 속도가 아니라
«이동을 동반하지 않는다» 뿐이고, 그 대가가 82% 산포와 스톨 부하다. 회피·추종을
제자리 회전으로 바꿀 공학적 이득이 실측으로는 보이지 않는다.

## ADR-12 · 검출 모델을 하나로 전부 학습하지 않는다

**대안** — 사람·보호구·일상 물체를 모두 포함한 단일 모델을 직접 학습.

**근거** — ① 학습 클래스가 늘수록 데이터셋 수집·라벨링 비용이 급증한다 ② 특히 변화 감지는 시연
환경의 일상 객체를 알아야 하는데 직접 학습하면 **사실상 COCO 를 재구축하는 셈**이다.

**채택 — 2단 구조 + 게이팅**

| | 담당 | 학습 |
| :--- | :--- | :--- |
| ① COCO 사전학습 범용 검출기 | `person` + 79개 일상 객체 (FR-3, FR-8) | **불필요** |
| ② 보호구 전용 모델 | `helmet`/`no_helmet`/`vest`/`no_vest` (FR-9) | 직접 학습 (4클래스) |

②는 ①이 `person` 을 검출한 프레임에서만 실행하므로 평균 연산량이 1패스 수준이다.
직접 학습 범위가 **4클래스로 축소**되고 변화 감지 어휘 **80클래스**를 공짜로 얻는다.

**재검토** — COCO 검출기의 `person` 검출률이 시연 환경에서 부족할 경우.

## ADR-13 · CUDA·TensorRT 대신 DirectML 을 쓴다

**한 줄로** — **더 빠른 쪽이 아니라 협업이 편한 쪽을 골랐다.** 예산이 넉넉해서 그 선택이 공짜다.

### 근거 ① 속도로는 승부가 안 난다

추론률을 25fps 로 잡았으므로 한 프레임에 쓸 수 있는 시간이 **40ms** 다(ADR-23·25). 검출은 그중
**몇 ms~십몇 ms** 를 쓴다. CUDA 로 바꿔서 아끼는 것은 **예산의 몇 %** 다. 가장 작은 숫자를
최적화하는 일이다.

### 근거 ② DirectML 이 협업에서 이득이다

| | |
| :--- | :--- |
| 누구 PC 에서든 돈다 | NVIDIA·AMD·Intel 무관, GPU 가 없으면 CPU 로 떨어진다 → **팀원 사양을 물어볼 필요가 없다** |
| 설치가 한 줄 | `onnxruntime-directml` 하나. CUDA 는 CUDA·cuDNN·onnxruntime 버전을 **3대에 각각** 맞춰야 한다 |
| 조용한 고장이 없다 | 버전이 어긋난 CUDA 는 **에러 없이 CPU 로 떨어진다.** 느려진 이유를 찾는 데 반나절이 든다 |
| CI 에서 같은 코드가 돈다 | GitHub 러너에 GPU 가 없다 → CPU 경로는 어차피 필요하고 매 PR 마다 검증된다 |

### 근거 ③ TensorRT 는 한 단계 더 나쁘다 — **모델 파일을 주고받을 수 없다**

TensorRT 엔진은 **GPU 아키텍처마다 다시 빌드**해야 한다. `3080`(Ampere)에서 만든 파일이
`5070`(Blackwell)에서 안 돌아간다. **팀원이 전부 RTX 여도 해결되지 않는다** — 세대가 다르면
공유가 안 되기 때문이다. 3인 병렬 개발과 정면으로 충돌한다.

**CUDA EP 는 이 문제가 없다.** `.onnx` 파일을 그대로 쓴다. 그래서 나중에 속도가 정말 필요해지면
**TensorRT 가 아니라 CUDA 를 먼저 본다.**

**채택** — **DirectML EP**(개발 PC) + **CPU EP**(CI). `select_providers()` 로 자동 폴백.
GPU 를 안 쓰는 결정이 아니라 **아무 GPU 나 쓰겠다는 결정**이다.

**재검토** — `3.3.1` 검출 실측이 **30ms 를 넘을 때**(예산 100ms 에서 PPE 2단·전후처리 자리가
사라지는 선). 순서는 **모델 경량화 → 추론 주기 하향 → CUDA EP** 다. TensorRT 는 근거 ③이
살아 있는 한 보지 않는다. 로컬 LLM/VLM 도입 시에는 이 결정 전체를 다시 연다.

## ADR-14 · 학습 기반 정책(VLA)을 쓰지 않는다

**대안** — OpenVLA · Octo · RT-2 등으로 영상과 지시문에서 동작을 직접 생성.

**근거** — ① **학습 도메인 불일치** — 공개 VLA 는 대부분 로봇 팔 조작 데이터로 학습됐다 ② **행동 공간
불일치** — 본 로봇의 액션은 `move(step, angle)` 둘뿐이다 ③ **파인튜닝 비용** — 4주에 데이터 수집·학습이
들어갈 여지가 없다 ④ **설명 가능성 부재** — **왜 그렇게 움직였는지 사후 재구성이 불가능하다.**
경비·안전 임무에서는 치명적이다.

**채택** — **규칙 기반 FSM.** 상태 전이가 명시적이라 로그만으로 판단 근거를 재구성할 수 있고,
전이표 전수를 pytest 로 검증할 수 있다.

**포지셔닝** — VLA 는 현재 Physical AI 연구의 최전선이다. **모르고 안 쓴 것이 아니라 안전 설명책임과
일정을 근거로 선택하지 않은 것**이며, 완성된 FSM 은 향후 학습 정책 도입 시의 비교 기준선이 된다.

## ADR-15 · 거리 판정에 깊이 모델이나 초음파를 쓰지 않는다

⚠️ **이 로봇은 "몇 미터 앞"을 모른다. 알 필요도 없게 만들었다.**

**대안** — ① 단안 깊이 추정 모델 ② 초음파 재활용 ③ bbox 높이로 미터 환산.

**근거** — ① 모델이 하나 늘고 추론 패스가 추가된다. **임계 판정 하나에 신경망을 붙이는 것은 과잉**이다
② **의복이 초음파를 흡수·산란시켜 사람에 대한 실효 사거리가 1~2m 로 줄고**, 빔이 부채처럼 퍼져 옆의
벽·가구를 잡는다 ③ "사람 키 1.7m" 가정에 의존해 **웅크리거나 앉은 자세에서 깨진다.**

**채택** — **미터 거리를 구하지 않는다.** 요구사항의 실체는 *"머리가 화각에 들어오는가"* 이므로
**bbox 클리핑 검사**로 직접 판정한다(FR-9.2.1). 추종 거리 유지도 상자 크기로 처리한다(FR-3.5.2).

> **요구사항을 다시 읽어 문제를 없앤 사례다.**

**초음파의 역할** — 원래 잘하는 일인 근거리 충돌 회피(FR-2.2, 25cm)에만 쓴다.

## ADR-16 · 안전 로직에 상태 억제 플래그를 쓰지 않는다 *(일반 원칙)*

**전제** — 본 프로젝트는 **상시 인적 감시 하의 시연·연구 목적**이며 무인 상용 배치가 아니다. 따라서
자동 안전 로직의 1차 목적은 인적 안전이 아니라 **하드웨어 보호와 자율 동작의 성립**이다.

**핵심 판단** — **안전 로직이 기능을 방해하면 팀은 안전 로직을 끈다.** 임계를 과도하게 좁게 잡으면
누군가 그 코드를 주석 처리하게 되고 보호 기능이 **완전히** 사라진다. **작동 가능한 수준으로 완화해
계속 살려두는 것이 실질적으로 더 안전하다.**

**충돌 시 해결 순서**

| 순위 | 방법 | 이유 |
| :---: | :--- | :--- |
| **1** | **임계값·조건을 조정해 물리적으로 분리** | 로직 간 결합이 생기지 않는다. 설정값 변경으로 끝난다 |
| 2 | 판정 조건을 더 직접적인 관측량으로 재정의 | 간접 추정을 없애면 충돌 자체가 사라진다 (ADR-15) |
| 3 | 해당 안전 로직의 범위를 축소 | 명시적으로 기록하고 재검토 조건을 남긴다 |
| **✕** | **상태 억제 플래그** | **억제 영구화라는 새 실패 모드를 만든다. 최후 수단** |

**적용 사례** — 앉기 자세(피치 30~45°)가 전도 임계 45° 와 충돌했다. 억제 플래그 대신 **임계를 60° 로
상향**해 해결했다. 의도된 자세(최대 45°)와 실제 전도(약 90°) 사이의 빈 구간을 쓰므로 **두 로직이
서로를 알 필요가 없다.**

> **그 스위치가 켜진 채로 남으면 안전장치가 조용히 죽는다. 그리고 아무도 모른다.**

## ADR-17 · 컨테이너는 Phase 2 ROS2 에만 적용한다

**대안** — 호스트 스택 전체를 Docker 로 묶고 `compose up` 한 번으로 기동.

**기술적으로는 가능하다** — 카메라·센서가 모두 로봇 안에 있고 PC 와는 네트워크로만 연결되므로,
로보틱스에서 Docker 를 깨뜨리는 최대 원인인 **USB 장치 패스스루가 발생하지 않는다.**

> 없다")는 부정확했고 그것을 기록에 남겼다 — 배포 대상은 실재한다.*

## ADR-19 · LiDAR 중계 보드는 현재 WROOM 기준을 유지한다

**상태** — 기존 발주 기준 유지. 새 하드웨어 선정이나 C3 사용 불가 판정이 아니다.

현재 배선은 ESP32-WROOM-32E 기반 38핀 DevKitC 호환 보드의 GPIO16 수신을 기준으로 한다.
핀헤더가 장착된 구매 옵션을 선택해야 무납땜 연결이 가능하다. C3 SuperMini로 바꾸면
정확한 보드의 노출 핀·플래시 점유·전원 경로와 UART 설정을 다시 검증해야 하므로 즉시 교체하지 않는다.

### 칩 사양과 판매 보드 옵션을 구분한다

- **ESP32-C3에는 UART 컨트롤러가 2개 있다.** GPIO16이 칩에 아예 없다는 설명은 틀리다.
  GPIO12~17의 플래시 사용 제약과 실제 보드의 핀 노출 여부는 별도로 확인해야 한다.
  UART2가 없다는 사실만으로 UART→UDP 중계 자체가 불가능하다고 결론 내리지 않는다.
- 핀헤더 납땜 여부·USB 커넥터·보드 무게는 판매 제품과 옵션에 따라 달라진다.
  ‘C3는 반드시 납땜’, ‘DevKitC는 항상 USB-C’, ‘차이는 정확히 7g’으로 일반화하지 않는다.
- **Espressif 공식 DevKitC V4는 Micro-USB다.** 프로젝트에서 USB-C 호환 보드를 구매한다면
  판매 페이지와 실물로 그 옵션 및 전원 핀을 확인한다. 이름만 보고 폰 케이블 호환을 가정하지 않는다.

**재검토 조건** — H3 탑재 시험에서 변경 필요성이 확인되면 정확한 후보 제품의 질량·배선·전원·
통신을 검증하고 변경 승인을 받는다. 이번 정리는 기존 구성·담당·Phase 범위를 변경하지 않는다.

**출처 (2026-09-06 확인)**

- [ESP32-C3 공식 데이터시트 — GPIO 및 UART](https://documentation.espressif.com/esp32-c3_datasheet_en.html)
- [Espressif DevKitC V4 공식 가이드 — Micro USB 포트](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32/hw-reference/esp32/get-started-devkitc.html)

로컬에 남아 있던 ADR 초안의 취지를 보존하되, 미확인 제품 수치와 칩/보드 혼동을 정정했다.
## ADR-20 · 벤더 라이브러리를 저장소에 넣지 않는다 (라이선스 표기 부재)

빌드가 되게 하고, CI 에서도 서보를 초기화하는 빌드까지 검증한다. `5.1.2` DoD 가 원래 이것이었다.

**확인했다 (2026-09-08).** `MechDog V1.3` 공식 설치본에서 추출한 파일을 직접 열어 보았다.

**재검토** — Hiwonder 가 라이선스를 명시하거나 문의에 재배포를 서면으로 허용하는 경우.

## ADR-21 · 페일세이프 해제는 로봇의 래치 보고로만 막는다

**문제** — 호스트가 `FAILSAFE` 를 떠날 때 로봇도 함께 풀렸는지 확인해야 한다. 확인하지 않으면
조작자가 리셋을 누른 뒤 **호스트만 `IDLE` 이고 로봇은 잠긴 채**가 된다. 로봇은 명령을 무시하니
위험하지는 않지만 **관제 화면이 거짓을 말하고**, 같은 상태의 반복 보고는 사건을 재발행하지
않으므로 그 뒤 어떤 텔레메트리도 그 어긋남을 고치지 못한다.

**대안** — 텔레메트리의 `state` 가 `FAILSAFE` 인 동안 `RESET_CONFIRMED` 를 막는다. 한 줄이고
추가 필드도 필요 없다.

**왜 틀렸나** — **`FAILSAFE` 는 `STATE` 명령으로도 내려간다.** 로봇은 호스트 전용 상태를
받아적어 되돌려주는데(`STATE` 절), `FAILSAFE` 는 온보드가 스스로 아는 셋 중 하나이기도 하다.
따라서 되돌아온 `state="FAILSAFE"` 가 **우리가 알려준 것의 반향인지 로봇 자신의 판정인지
구분할 수 없다.** 반향을 근거로 잠그면 호스트가 스스로를 영구히 잠근다 — 링크 두절로 한 번
`FAILSAFE` 에 들어가면 로봇이 멀쩡해도 나올 방법이 사라진다.

**채택** — 규약이 이미 답을 두었다. *"패킷 수락과 실제 안전 해제는 다르므로 송신측은 텔레메트리의
`state=IDLE`, `safety_latched=false` 를 확인해야 한다"* (PROTOCOL 2절). `safety_latched` 는
**로봇의 자체 래치이며 반향되지 않는다.** 그래서 이것만 본다.

```python
LATCH_GUARDED: frozenset[Event] = frozenset({Event.RESET_CONFIRMED})
```

막는 것은 **나가는 문 하나**다. 들어가는 사건(`ESTOP`·`ONBOARD_FAILSAFE`)을 막으면 위험한 쪽으로
틀린다.

**해제 절차** — 사람이 확인 → 호스트가 `RESET_SAFE` 송신 → 로봇이 원인 없음을 확인하고 래치 해제
→ 로봇이 `safety_latched=false` 보고 → **그때** 호스트가 `RESET_CONFIRMED`. 호스트가 먼저 풀지
않는 것이 요점이다.

**래치를 보고하지 않는 펌웨어** — 막지 않는다. 알 수 없는 것을 근거로 잠그면 해제 수단이 사라진다.
그 조합은 규약이 *"실기 운용 전 송수신을 함께 갱신한다"* 로 이미 금지했고, 호스트는 대신
**로봇이 명령을 받아들이고 있는지**(`last_cmd_age_ms`)를 감시해 소리를 낸다.

**재검토** — 텔레메트리에 온보드 판정의 출처(전도·저전압·링크)가 분리되어 들어오는 경우. 그때는
무엇 때문에 잠겼는지까지 화면에 낼 수 있다.

## ADR-22 · 온보드 반사 상태는 `state` 가 아니라 플래그로 보고한다

**문제** — 회피가 끝났는지를 호스트가 알아야 한다. 로봇이 `AVOID` 를 벗어나 `PATROL` 을 보고하면
끝난 것으로 보는 규칙을 `4.3.6` 에 두었고, 단위 시험은 통과했다.

**실기에서 성립하지 않았다.** 목업 상대 실행에서 회피 시퀀스가 **3회 전부 돌고도 빠져나오지
못했다.** 후진으로 장애물이 실제로 멀어졌는데도 `state` 는 계속 `AVOID` 로 왔다.

**원인** — `STATE` 명령이다. 호스트 FSM 이 `AVOID` 로 가면 그 상태를 로봇에게 알려주고, 로봇은
호스트 전용 상태를 받아적어 되돌려준다. 그런데 `AVOID` 는 **온보드가 스스로 아는 셋 중
하나이기도** 하다. 그래서 되돌아온 `state="AVOID"` 가 *로봇의 센서 판정*인지 *우리 말의 반향*인지
구분할 수 없다. **ADR-21 과 정확히 같은 형태이며 대상이 `FAILSAFE` 에서 `AVOID` 로 바뀐 것이다.**

**대안 ⓐ — 호스트가 온보드 상태를 `STATE` 로 알려주지 않는다.** 반향 자체를 없애는 방향이라
매력적이다. 그러나 로봇의 폴백은 *"마지막으로 받은 호스트 상태"* 이므로, 순찰·회피를 알려주지
않으면 **기동 시의 `IDLE` 같은 낡은 값이 되돌아온다.** 해제를 알 수 없는 것은 그대로다.

**대안 ⓑ — 호스트가 `dist_cm` 을 보고 판정한다.** Tier 1 을 호스트로 옮기는 것이므로 배제한다
(아키텍처 1.2). 호스트가 꺼지면 판정이 사라지는 구조를 처음부터 피했다.

**채택** — 텔레메트리 `flags` 에 **`obstacle`**(bool)을 더한다. *"온보드 반사 정지가 지금 걸려
있는가"* 이며 **반향되지 않는다.** 참→거짓 변화가 곧 로봇이 말하는 *"전방이 비었다"* 다.

```python
if previous is True and reading.obstacle is False:
    return (Event.AVOID_CLEARED,)
```

거짓→참은 사건을 내지 않는다 — `state` 의 `AVOID` 가 이미 같은 것을 말하므로 중복이다.

**호스트는 여전히 판정하지 않는다.** 거리를 보지 않고 **로봇이 보고한 플래그의 변화**만 옮긴다.
`safety_latched` 와 같은 성질이며, 두 번 같은 문제를 만난 뒤 이것이 규약의 패턴이 됐다.

**선택 필드로 둔 이유** — 보내지 않는 펌웨어에서도 레코드가 폐기되면 안 된다. 없으면 예전
규칙(`AVOID → PATROL` 상태 짝)으로 폴백하며, 그 조합은 호스트가 `AVOID` 를 알려주지 않는
경우에만 동작한다는 한계를 함께 적어 두었다.

**함께 고친 것** — 근거리 반사 정지가 **전진만 막아야 한다.** 전부 막으면 *"정지 후 후진"*
(FR-2.3)이 실행 불가가 되어 회피 자체가 성립하지 않는다. 초음파는 정면만 보므로 물러나는 것이
유일한 탈출 경로이고, 후진 거리는 설정으로 제한된다. 목업을 그렇게 고치고 `3.2.6` DoD 에
펌웨어 요구사항으로 적었다.

**재검토** — 텔레메트리에 온보드 판정 근거가 종류별로 들어오는 경우(전도·저전압·링크·장애물).
그때는 플래그 여러 개 대신 하나의 구조로 묶는 것이 나을 수 있다.

## ADR-23 · 인지 추론률을 사건 대기로 정한다 (7 → 10 → 25fps)

> ⚠️ **이 결정의 값은 두 번 바뀌었다.** 아래 본문은 2026-09-09 에 7→10fps 로 올린
> 기록이며, **2026-09-10 실기 측정으로 10 → 25fps 가 됐다** — 근거는
> [ADR-25](#adr-25) 다.
> 아래의 *"10fps"* 와 *"연속 3프레임 = 200ms"* 는 **그때의 값**이다.

**문제** — 7fps는 GPU 부하가 작지만 사건이 추론 직후 발생하면 다음 판정까지 최대
143ms를 기다린다. 사람은 연속 3프레임으로 확인하므로 이 대기와 별도로 첫 양성 뒤
약 286ms가 필요해 체감 반응과 NFR-1.1 예산을 불필요하게 소모한다.

**실측** — XIAO VGA 25fps 200프레임을 받으며 메인 ESP32에 명령을 보냈을 때 UDP RTT는
평균 3.2ms·최대 15.4ms·손실 0%였다. 25fps 수신·7fps 소비·JPEG 디코드와 `STOP` ACK를
연결한 구간도 평균 31.2ms·p95 69ms였다. 현재 공유기 환경에서는 통신이 병목이 아니다.

**대안** — 7fps를 유지하면 연산 여유는 가장 크지만 반응 대기를 줄이지 못한다. 15fps는
대기를 더 줄이지만 검출 모델이 정해지기 전에 GPU 예산을 소비한다. 25fps 전 프레임 추론은
드롭 정책의 의미가 없어지고 PPE 2단 추론까지 들어왔을 때 여유가 작다.

**채택** — `vision.inference_fps=10`. FSM의 10Hz 틱과 맞추고 다음 추론의 최악 대기를
100ms로 줄인다. 연속 3프레임 확인은 첫 양성 뒤 200ms가 된다. 최신 프레임 우선 큐는
유지해 25fps 입력 중 쌓인 과거 프레임을 처리하지 않는다.

**측정 경계** — NFR-1.1은 단일 프레임의 촬영→검출→명령 적용 ACK이고, 연속 3프레임
확인과 물리 서보 반응은 별도로 기록한다. 통합하지 않으면 어느 구간이 병목인지 숨는다.

**재검토 — 실제로 열렸다 (2026-09-10).** 실기 343프레임에서 **10fps 가 진짜 검출 구간
10개 중 4개만 확정**하는 것이 드러나 **25fps(수신률과 동일)로 올렸다.** 그리고 확인 조건을
프레임 수에서 시간 창으로 바꿔 **히트를 인정할 최대 간격**을 300ms로 고정했다. 다만
확인 지연과 히트 기회는 추론률에 따라 달라지므로 25fps도 실측 결정에 포함한다
([ADR-25](#adr-25)).

**여기서 배운 것** — 이 결정은 *"연산 여유"* 로 값을 정했는데, 실제로 값을 정한 것은
**정보를 얼마나 버리는가**였다. 10fps 는 25fps 수신에서 프레임 60%를 버리고 있었고
(큐 드롭 185/20초), 그중에 짧은 검출이 들어 있었다. **부하 계산만으로는 보이지 않았다.**

## ADR-24 · 범용 검출기를 YOLOX-S 로 정한다 (라이선스가 결정했다)

**문제** — ①번 검출기를 골라야 한다(OI-15). 기준은 셋이었다 — ⓐ FR-8 변화 감지 어휘,
ⓑ 기준 PC 프레임 예산, ⓒ 라이선스.

**ⓑ 는 사실상 제약이 아니었다.** (당시 추론률 10fps · 프레임당 100ms), 이미
실측된 구간(도착→디코드→ACK p95 69ms)을 빼도 검출에 쓸 수 있는 시간이 넉넉하다. 기준 PC
가 RTX 3080 10GB 이므로 이 급 모델은 어느 것이든 예산 안이다.

**그래서 ⓒ 가 결정했다.** `ultralytics`(YOLOv8/11)는 **AGPL-3.0** 이다. 우리는 대시보드를
FastAPI + WebSocket 으로 띄우므로 AGPL 이 겨냥하는 형태 그대로이고, 채택하면 **팀 3인의
코드 전체**가 공개 의무에 걸린다. 저장소에 `LICENSE` 파일조차 없는 상태여서 의무를
이행할 형식도 갖춰지지 않는다. **모델 하나를 고르는 일이 팀 전체 코드의 라이선스를
정하는 일이 된다** — 그건 혼자 정할 사안이 아니다.

**채택** — **YOLOX-S** (Apache-2.0, Copyright (c) 2021-2022 Megvii Inc.)

| 판단 | 근거 |
| :--- | :--- |
| 라이선스 | **Apache-2.0** — 원본 저장소 `LICENSE` 파일로 직접 확인했다(기억이 아니라 파일) |
| 이름값 | **YOLO 계열이다.** AGPL 문제는 "YOLO"가 아니라 "Ultralytics"의 문제였다 |
| 착수 비용 | 공식 릴리스에 **`yolox_s.onnx` 가 이미 배포**되어 있다 — export 툴체인이 필요 없다 |
| EP 위험 | **순수 CNN** 이라 DirectML 이 연산을 조용히 CPU 로 내려보낼 위험이 없다 |
| 예산 | **실측 — 기준 PC · DirectML 에서 mean 8.2ms · p95 8.6ms** (전처리+추론+후처리, n=50). 프레임 예산 100ms 의 **8%** |

**버린 대안**

| | 이유 |
| :--- | :--- |
| YOLOv8 / YOLO11 (`ultralytics`) | **AGPL-3.0.** 정확도·생태계는 최상이지만 팀 코드 전체를 물들인다 |
| RT-DETR-R18 | Apache 이고 정확도가 더 높으며(**COCO AP 약 46 대 40**) **NMS 가 없어** 후처리가 줄지만, 트랜스포머 연산이 DirectML 에서 CPU 로 떨어질 위험이 있고 export 손이 더 간다 |
| RTMDet-s | Apache, CNN, 정확도 중간. 다만 ONNX 를 얻으려면 **MMDeploy** 가 필요해 하루 작업에 위험이 크다 |
| 개방 어휘 (Grounding DINO·OWL-ViT·YOLO-World) | 프레임당 수백 ms 로 예산 초과이고 라이선스도 불리하다. **FR-8 은 시연 소품을 COCO 80 안에서 고르는 쪽으로 푼다** — 우리가 물체를 놓는 쪽이므로 어휘를 우리가 정할 수 있다 |

**대가로 무엇을 잃었나** — 정확도 약 4~6 AP 다. 다만 **간판 기능인 사람 검출은 영향이
거의 없다**(`person` 은 COCO 에서 가장 잘 학습된 클래스다). 격차는 작고 드문 물체에서
벌어지므로 **FR-8 변화 감지**에서 보인다. 그쪽은 소품을 크고 명확한 것으로 고르는 것으로
완화한다.

**갈아 끼울 수 있게 만들었다** — 이 결정을 되돌릴 가능성이 실재하므로
`host/vision/detector.py` 를 세 겹으로 나눴다. 모델 고유 부분(전처리 규약·출력 디코딩)은
`DetectorAdapter` 뒤에 있고, 세션 관리·억제·좌표 복원·게이팅은 모델을 모른다.
`vision.coco.model_family` 가 어댑터를 고르며 **모르는 이름은 거부한다** — 조용히
기본값으로 넘어가면 설정을 고쳐도 아무 일이 안 일어난다(해상도 정본이 둘이어서 겪은
그 형태다).

**실측이 드러낸 것 둘** (2026-09-10, 기준 PC)

| 발견 | 내용 |
| :--- | :--- |
| **GPU 가 없으면 성립하지 않는다** | CPU EP 로는 mean **61.9ms** — 예산 100ms 의 62% 라 PPE 2단을 얹을 자리가 없다. DirectML 로 **8.2ms**(8%). ADR-13 이 *"속도로는 승부가 안 난다"* 고 한 것은 **GPU 를 쓴다는 전제 위에서만** 맞았다 |
| **첫 프레임 비용의 주범이 추론이 아니었다** | 첫 프레임 122ms 를 쪼개니 **전처리 78.8ms + 추론 5.2ms** — OpenCV 의 첫 호출 초기화가 지배했다. 세션만 미리 돌렸을 때 108ms 로 거의 그대로였고, **전처리까지 흘려야** 8.8ms 가 됐다 |

두 번째는 **원인을 재기 전에 고쳤다가 절반만 데운 사례**다. "첫 추론이 느리다"는 그럴듯한
설명이었고 실제로 GPU 커널 준비도 있었지만, **크기가 1/15 였다.** 구간을 쪼개 보기 전까지
그것을 알 수 없었다.

**⚠️ 검출 정확도는 아직 검증되지 않았다.** 위 8.2ms 는 **잡음 프레임**으로 잰 것이고,
CNN 의 연산량은 입력 내용과 무관하므로 **속도로는 유효하지만 정확도로는 아무것도 말하지
않는다.** 실제로 확인했다 — `/255` 정규화를 넣어 일부러 고장낸 전처리도 잡음에서 정상과
**똑같이 0건**을 냈다. **잡음 시험은 정상과 완전 고장을 구분하지 못한다.**

전처리 규약은 그래서 다른 방법으로 확인했다 — **원본 `yolox/data/data_augment.py` 의
`preproc()` 과 한 줄씩 대조**했다(여백 114 · 좌상단 정렬 · 정규화 없음 · BGR 유지 ·
`swap=(2,0,1)`). 그 과정에서 **축소를 반올림으로 쓴 것을 발견해 버림으로 고쳤다** —
VGA·QVGA 는 비율이 정수라 차이가 없지만 다른 해상도에서 1픽셀 어긋나면 모델이 학습 때 본
것과 다른 그림이 된다.

**정확도 확인 (2026-09-10 · 공개 사진 3장)** — `datasets/coco_samples`.

| 확인 | 결과 |
| :--- | :--- |
| 사람 검출 (간판 기능) | 7명 사진에서 `person` **7건 · 0.83~0.92**, `tennis racket` 0.82 |
| **박스 위치** | 그려서 **눈으로 대조** — 사람마다 정확히 얹혔다 |
| **letterbox 되돌리기** | 500x375(ratio **1.28**)에서 `chair` 0.92 · `tv` 0.92 — 좌표 정상 |
| 변화감지 어휘 | 실내 사진에서 `chair`·`person`·`refrigerator`·`potted plant` |

**숫자만 보는 것으로는 부족했다.** "검출 4건" 은 무언가 나왔다는 뜻일 뿐이고, **박스가
그 물체에 얹혔는지는 그려서 봐야** 안다. 그리고 대부분의 COCO 사진은 긴 변이 640 이라
**비율이 1.0** 이다 — letterbox 경로를 검증하려면 그렇지 않은 사진을 일부러 골라야 했다.

⚠️ **이것은 "동작한다"의 확인이고 성능 평가가 아니다.** mAP 를 재지 않았고 3장은 표본이
아니다. **실기(XIAO) 프레임 검증은 여전히 남아 있다**(`3.3.3`) — 조명·화질·화각·JPEG
압축률이 다르다.

**재검토** — ① FR-8 변화 감지가 COCO 80 어휘로 부족할 때 ② 사람 검출률이 시연 환경에서
부족할 때(ADR-12 재검토 조항과 같다). 둘 다 **어댑터 하나를 더 쓰는 일**이고, 그때 첫
후보는 RT-DETR-R18 이다. 예산에 92% 가 남아 있으므로 **정확도를 더 사는 여지가 크다.**

<a id="adr-25"></a>
## ADR-25 · 연속 프레임 대신 **고정 시간 창 안의 히트 수**로 판정한다

**문제** — `FR-3.2` 가 *"연속 3프레임"* 으로 적혀 있었다. 프레임 수로 정의하면 **의미가
추론률에 종속된다.**

| | 7fps | 10fps | 20fps | 25fps |
| :--- | :--- | :--- | :--- | :--- |
| 같은 "3프레임" 이 | **429ms** | 300ms | 150ms | **120ms** |

즉 **오검출 억제 강도와 확인 지연이 한 값에 묶여**, 추론률을 바꾸면 둘이 같이 움직인다.
[ADR-23](#adr-23) 에서 7→10fps 로 올렸을 때 *"확인 시간이
286→200ms"* 라고 적었는데, **그것이 검출 성공률까지 바꾼다는 것은 몰랐다.**
결정 22번(*"상태 하나로 두 가지를 표현하지 않는다"*)과 같은 형태다.

**실측이 그것을 드러냈다** (2026-09-10 · 실기 343프레임 · 사람이 걸어서 왕복 · 25fps 수신).
임계 0.5 를 넘은 연속 구간 길이가 이랬다.

```
[52, 38, 29, 15, 12, 6, 6, 5, 3, 3,  1, 1, 1, 1, 1, 1, 1, 1]
 └──────── 진짜 10개 ────────┘  └─── 단발 8개 ───┘
                                    ↑ 2연속이 0개 = 깨끗한 분리
```

| 추론률 | 진짜 인정 | 단발 차단 | 추론 부하 |
| ---: | ---: | ---: | ---: |
| 10fps | **4 / 10** | 2 | 8.2% |
| 20fps | 8 / 10 | 5 | 16.4% |
| **25fps** | **10 / 10** | 8 | 20.5% |

**`inference_fps: 10` 은 진짜 검출의 절반 이상을 놓쳤다.** 짧은 구간(3~6프레임 =
120~240ms)이 건너뛰기에 사라지기 때문이다 — 화면 가장자리를 빠르게 지나가는 경우다.

**채택** — 둘을 함께 바꾼다.

```yaml
detect_window_ms: 300        # 이 시간 안에
detect_hits_required: 3      # 이만큼 검출되면 사람
inference_fps: 25            # 수신률과 동일 — 프레임을 버리지 않는다
```

| 판단 | 근거 |
| :--- | :--- |
| **시간 창** | 히트를 인정할 최대 간격을 300ms로 고정한다. 추론률을 바꾸면 검출률·오검출률은 다시 잰다 |
| **연속을 요구하지 않는다** | 실기에서 통과율이 52% 였다 — 깜빡임 하나가 확인을 처음부터 다시 시작하게 만들면 안 된다 |
| **25fps** | 부하 20.5% 로 예산 안이고 진짜 10개를 전부 인정한다 |
| **해제는 비대칭** | 창이 **완전히 빌 때**만 게이트 확정을 해제해 후속 추적 판단의 떨림을 줄인다. ALERT 복귀는 FR-3.7의 5초 타이머가 맡는다 |

> **정확한 경계** — 시간 창은 히트를 인정할 **최대 관측 간격**을 고정한다. 하지만
> `detect_hits_required`가 횟수인 이상 확인 지연과 히트 기회는 여전히 추론률의 영향을
> 받는다(실측상 7fps 286ms · 25fps 80ms). 따라서 25fps도 이 결정의 일부이며 값을
> 바꾸면 검출률과 오검출률을 다시 잰다. “추론률과 완전히 독립적”이라고 해석하지 않는다.

> **게이트 해제와 대상 상실은 다른 시계다.** 창이 빈 300ms 시점에는 확정만 풀고,
> `TARGET_LOST`는 마지막 실제 검출부터 FR-3.7의 5초가 지난 뒤 FSM이 낸다. 둘을 바로
> 연결하면 사람 검출이 한 번 흔들릴 때마다 `ALERT`와 `PATROL`이 왕복한다.

**설정으로 막은 함정** — 창 안에 필요한 횟수가 들어갈 수 없으면 **영원히 확정되지 않는다**
(`300ms 창에서 200ms 주기라 양 끝 포함 최대 2회 < 3회`). 추론률과 창 길이가 함께 정하는 상한이라 둘 중 하나만 봐서는
잡히지 않으므로, 로더가 기동 전에 거부한다.

**실기 검증** — 같은 343프레임을 게이트에 통과시키니 **원자료 18개 구간(단발 8 포함)이
깨끗한 4개로** 정리됐다(41·72·73·14프레임). **1~2프레임짜리 떨림이 하나도 없었다.**
그리고 실제 스트림으로 20초 운용해 `PATROL↔ALERT` 전이 6회를 확인했으며 틱 간격은
max 101ms 로 `cmd_timeout_ms` 초과 0회였다.

**남은 것** — 해제 후 **200ms 만에 재확정**되는 사례가 한 번 있었다. 사람이 300ms 이상
실제로 사라졌다 돌아온 것이므로 게이트는 옳게 동작했지만, 그 왕복이 로봇에게는 한 걸음이
된다.

> **정정 (2026-09-10)** — 위 문장은 *"`primary_target_hold_ms` 가 있는 `3.8.3` 에서 함께 본다"* 로
> 적혀 있었다. **둘을 잘못 묶었다** — `primary_target_hold_ms` 는 `FR-3.8.3`(여러 명 중 **주 대상**을
> 언제 바꾸는가)의 값이고 추적기(`3.3.4`) 소관이다. WBS `3.8.3`(에스컬레이션 단계)과는 번호만 같다.
>
> 그리고 **에스컬레이션 축은 이 떨림에 이미 영향받지 않는다** ([ADR-26](#adr-26)) — 게이트 확정이
> 풀려도 단계는 L1 에 남고, 내려가는 것은 *마지막 실제 검출* 로부터 5초일 때다. 남은 문제는
> **자세·추종 시퀀스가 왕복하는 것**이며 `3.3.4` 추적기에서 본다.

**재검토** — ⓐ 검출 모델을 바꿔 추론 시간이 늘면 25fps 가 예산을 넘을 수 있다 ⓑ 역광 등
악조건에서 통과율이 52% 보다 크게 낮아지면 `detect_hits_required` 를 2 로 내리는 것을
검토한다(실기 데이터에서 **2연속 구간이 0개**였으므로 2 로 내려도 단발 8개는 전부 막힌다).

## ADR-26 · 대응 단계의 **내려오는 길**을 정한다 (확인 경로를 둘로 나눈다)

**문제** — `3.8.3` 을 만들면서 표를 코드로 옮기니 **올라가는 길만 있었다.** 아키텍처 3.1
표에는 `L3 → L0` 이 *"관리자 확인으로만"* 이라고 적혀 있는데, **관리자가 확인할 수단이
저장소 어디에도 없었다.** 운용 런타임(`python -m host.runtime`)에는 입력 경로가 하나도
없고 대시보드는 `4.6` 이며, `teleop` 은 자기 `Behavior` 를 따로 만들어 쓰므로 비전·인증이
없어 **L3 에 도달할 수 없다.**

즉 *"관리자 확인으로만 해제"* 는 **문서에서는 정책이고 코드에서는 함정**이었다. 시연에서
경보가 한 번 울리면 프로세스를 죽여야 끝난다.

### ① 확인 사건을 하나로 두지 않는다

| 대안 | 왜 버렸나 |
| :--- | :--- |
| `RESET_CONFIRMED` 하나로 L3·F 를 함께 해제 | **비상정지를 눌렀다 푸는 것으로 경보가 지워진다.** 침입자가 `X`·`R` 을 누르면 기록만 남고 경보는 끝난다 |
| 경보 확인이 F 도 함께 해제 | 로봇이 **넘어진 채로 다시 움직인다.** 경보를 끄려는 조작이 물리 안전을 풀면 안 된다 |

**확인해야 하는 것이 다르다.**

| | 무엇을 확인하나 | 경로 |
| :--- | :--- | :--- |
| **F** | **물리 상태** — 넘어졌나 · 배터리 · 링크 | `RESET_SAFE` 송신 → **로봇이 `safety_latched=false` 를 보고**할 때 해제 ([ADR-21](#adr-21)) |
| **L3** | **상황 판단** — 침입자가 갔나 · 안전모 · 물건 | 관리자 확인. **로봇에 보낼 것이 없다** |

**채택** — 둘을 나누고, **F 로 올라갈 때 경보 여부를 기억한다.** F 를 풀면 `L0` 이 아니라
`L3` 로 돌아온다. 경보가 없었다면 `L0` 으로 간다 — 없던 경보를 만들지 않는다.

**진입점** — `Runtime.confirm_alarm()` 과 `Runtime.request_reset()`. 사람이 누르는 자리는
콘솔 `c`(경보 확인)·`r`(페일세이프 해제 요청)이며 **stdin 이 tty 일 때만** 붙는다.
`4.6` 대시보드 버튼도 같은 두 진입점을 쓴다.

> **한 글자 즉시 입력이 아니라 Enter 를 받는다.** `teleop` 이 즉시 입력을 쓰는 것은 조종이
> 연속 동작이기 때문이고, 확인은 *"경보를 껐다"* 는 기록을 남기는 조작이라 지나가다 키가
> 눌리는 것으로 일어나지 않는 편이 낫다.

> **누른 즉시 풀지 않는다.** 콘솔·대시보드는 운용 루프와 다른 스레드다. 거기서 단계나
> 송신기를 직접 만지면 루프가 전문을 만드는 중간에 바뀌어 **그 틱의 명령이 어느 단계의
> 것인지 말할 수 없게 된다.** 요청만 세워 두고 다음 틱이 꺼낸다 — 급한 것은 `ESTOP`
> 하나뿐이다([ADR-16](#adr-16) 과 같은 원칙).

### ② L2 도 함정이었다

표에는 `L2 → L0` 이 *"인증 성공"* 뿐이었다. 그러면 **인증을 요구받은 사람이 그냥 걸어가
버릴 때 로봇이 주황 눈으로 영구히 남는다** — `AUTH_WAIT` 30초 타이머는 FSM 이 그 상태에
들어가 있을 때만 돌고, 사람이 사라지면 그 상태로 가지 않는다.

| 대안 | 왜 버렸나 |
| :--- | :--- |
| 미검출 5초로 `L2 → L0` | **인증을 무시하고 지나가는 것이 가장 이득인 정책**이 된다. 서 있으면 경보, 지나가면 무사 |

**채택** — 미검출 5초로 **`L2 → L3`** 로 올린다. 미인증 통과는 경비 대응 대상이며
`AUTH_WAIT` 30초 초과가 `AUTH_FAILED` → L3 로 가는 것과 같은 결론이다(FR-10.3).
**두 경로의 시간이 다른 것은 의도다** — 사라진 경우 5초, 서 있는 경우 30초. 서 있는
사람에게는 인증할 시간을 줘야 하지만 이미 사라진 사람에게 줄 시간은 없다.

### ②-보충 · **정정 (2026-09-11)** — 인증은 `L1` 을 내리지 않는다

처음 구현은 `note_authenticated()` 가 `L1` 과 `L2` 를 함께 `L0` 으로 내렸다. 그런데
런타임은 추론마다 `note_person()` 과 `note_authenticated()` 를 **둘 다** 부르므로,
인증된 사람이 앞에 서 있는 동안 **10Hz 로 `L0↔L1` 이 진동했다** — 관측이 올리고
인증이 곧바로 내린다. 실기에서 **초당 20줄**씩 로그가 쏟아지고 눈 LED 가 파랑/노랑으로
깜빡이는 것으로 드러났다. **시험 786건이 놓쳤다** — 두 호출을 번갈아 반복하는 시험이
없었기 때문이다.

**정정** — 단계 표의 `L1` 해제 조건은 *미검출 5초* 하나뿐이고 *인증 성공*은 `L2` 줄에만
있다. **표가 맞았고 구현이 표를 넘었다.** 인증된 사람 앞에서 `L1`(관찰)에 머무는 것이
옳다 — 로봇은 그 사람을 실제로 보고 있고, 승격만 하지 않는다.

### ③ 미검출 5초를 단계기가 스스로 잰다

FSM 의 `TARGET_LOST` 를 얻어 쓰려 했으나 **그 사건은 `ALERT`·`TRACK` 에서만 전이를
만들어 전이표에 걸러진다.** 사람이 보이는 동안 조작자가 수동(`MANUAL`)으로 전환하면
사건이 오지 않아 **L1 이 영구히 남는다.** 같은 설정 키(`fsm.target_lost_timeout_s`)를
읽으므로 **숫자는 여전히 하나다** — 두 개의 5초를 만들지는 않았다.

**함께 고친 것** — 사건을 단계 축에 넣을 때 **FSM 이 받아들였는지를 함께 넘긴다.**
올리는 것은 전이 여부와 무관하지만(`ALERT` 의 PPE 위반은 전이가 없다) **내리는 것은
그렇지 않다** — 로봇 래치가 걸려 있으면 `RESET_CONFIRMED` 가 거부되는데(`LATCH_GUARDED`)
그때 F 를 풀면 **로봇은 잠긴 채 호스트만 풀려** [ADR-21](#adr-21) 이 막으려던 그 상태가
된다.

**재검토** — ⓐ 대시보드(`4.6`)가 붙으면 콘솔 키는 보조 수단이 된다 ⓑ 무인 운용으로
확장하면 *"관리자 확인"* 자체를 다시 정의해야 한다(A-13 이 전제다) ⓒ 여러 명을 동시에
다루게 되면(`multi_target_policy: max` · FR-3.8.1) 단계는 대상별로 계산한 뒤 최댓값을
로봇 단계로 쓰므로, 추적기(`3.3.4`) 뒤에 이 파일이 대상별로 확장된다.

## ADR-27 · 추적은 **겹침 결합 + 시간 기반 소실 버퍼**로 한다 (예측·2단계 결합 미채택)

**문제** — `FR-3.6` 은 *"추적기(ByteTrack 계열)"* 를 요구한다. 그런데 원본
ByteTrack 을 그대로 옮기려면 두 가지를 함께 들여와야 하고, 둘 다 우리 구조와
어긋난다.

### ① BYTE 2단계 결합 — **쓸 재료가 없다**

그 알고리즘의 구별점은 *임계 미달의 낮은 점수 검출*로 가려진 대상을 되살리는
것이다. 그런데 **우리 검출기는 임계 미달을 반환하지 않고 버린다**
(`Detector._finalize` 의 `scores >= conf`).

| 대안 | 왜 버렸나 |
| :--- | :--- |
| `coco.conf_threshold` 를 내려 낮은 밴드를 얻는다 | **실기로 검증한 경로를 흔든다.** 임계 0.5 는 실측으로 고른 값이고(`conf 0.3` 에서 `book` 오검출 3건), 게이트가 그 목록을 그대로 받으므로 판정 강도까지 함께 바뀐다 |
| 검출기가 두 밴드를 나눠 반환하고 워커가 쪼갠다 | 얻는 것이 대체로 **박스의 연속성**이고 **ID 의 연속성은 소실 버퍼가 이미 지킨다.** 실측으로 확인했다(아래) |

**재검토 조건** — 사람이 서로를 가려 박스가 사라지는 시연 배치가 되면, 그때는
검출기가 두 밴드를 나눠 반환하게 만든다. 지금 시연은 방 하나에 1~3명이다.

### ② 칼만 예측 — **ID 를 억지로 잇는 것은 인증을 억지로 잇는 것이다**

예측의 목적은 긴 공백을 건너 같은 ID 를 이어 붙이는 것이다. 그런데 **인증
결과가 ID 에 귀속되므로**(FR-3.6.2) 그것은 *인증을 이어 붙이는 것*과 같다.
공백 뒤에 돌아온 것이 같은 사람인지 로봇은 모르고, 틀렸을 때의 대가가
**미인증자가 인증 세션을 물려받는 것**이다.

**ID 재발급은 재인증을 뜻하고 그것이 안전측이다**(FR-3.6.3). 그래서 예측하지
않는다 — 못 하는 것이 아니라 **하지 않는 편이 안전한 방향**이다.

짧은 공백은 예측 없이도 겹침으로 이어진다. 25fps 에서 120ms 공백은 사람이
18cm 움직인 정도이고, 실측 프레임 간 공백의 **중앙값이 47ms** 였다.

### ③ 소실 버퍼는 **프레임 수가 아니라 시간**이다

원본은 `track_buffer=30 프레임` 으로 정의한다. 그러면 **의미가 추론률에
종속된다** — 같은 30프레임이 10fps 에서 3초, 25fps 에서 1.2초다.
[결정 22](#adr-22)·[25](#adr-25) 와 같은 형태이므로 `track_lost_ms` 로 둔다.
**같은 실수를 세 번 하지 않기 위한 것이다.**

설정 검증이 `track_lost_ms >= 추론 주기` 를 강제한다 — 그보다 짧으면 **한 번만
놓쳐도 ID 가 바뀌고**, 실기 통과율이 52% 였으므로(ADR-25) 한 프레임 공백은
예외가 아니라 일상이다.

### ④ 헝가리안 대신 탐욕 결합

동시 추적 상한이 5명(FR-3.8.5)이라 최적 할당과 결과가 갈리는 경우가 드물고,
갈리는 상황은 **두 사람의 박스가 서로 비슷하게 겹칠 때**인데 그때는 어느 쪽을
골라도 옳다고 말할 수 없다. `scipy` 를 그것 때문에 들이지 않는다.

⚠️ **다만 "가장 겹치는 짝부터" 는 지켜야 한다.** 트랙 순서대로 훑으며 *임계를
넘는 첫 검출*을 집으면 가까이 선 두 사람이 서로 바뀐다 — 교차 짝도 임계를
넘기 때문이다. 시험(`test_best_overlap_wins_not_the_first_acceptable_one`)이
그 구현을 실제로 걸러낸다.

### 실측이 뒷받침한 것 (2026-09-10 · 실기 724 추론 / 30초 · 2인)

| 확인 | 값 |
| :--- | :--- |
| 2개 ID 동시 | **129 / 724 프레임** |
| 최장 유지 | **16.61초 · 288프레임** (점수 0.50~0.93 을 오가는 동안) |
| 프레임 간 공백 | 중앙 **47ms** · 최대 **969ms** · 유지된 트랙 안에서 **1초 초과 0회** |
| 추적 비용 | 5명 기준 갱신당 **27.8µs** — 추론(8.2ms)의 **0.34%** (FR-3.6.1) |

**검출 순서 역전에도 ID 가 유지되는 것을 실기에서 봤다.** 검출기는 점수
내림차순으로 주는데 두 대상의 점수가 엎치락뒤치락해 순서가 매 프레임 뒤바뀌었고
(`(2,0.60),(1,0.59)` → `(1,0.60),(2,0.56)` → `(2,0.60),(1,0.51)`), 그래도 ID 는
높이 272px / 337px 로 각자 유지됐다.

> ⚠️ **최대 공백 969ms 는 소실 버퍼 1초와 여유가 31ms 다.** 그 구간은 검출률이
> 25프레임 중 4~8 로 떨어져 있었고(대상 하나가 폰 화면의 사진이라 점수가 0.50~0.73
> 이었다), 실제 사람만 있던 앞선 측정에서는 30초 동안 **ID 하나가 706프레임
> 유지**되며 재발급이 없었다. **값을 올리지 않는다** — 올리면 ID 와 함께 인증
> 세션도 오래 살고, 그 방향의 오류가 더 비싸다(위 ②). 대신 이 경계를 기록한다.
>
> **재검토** — 시연 배치에서 1초 넘는 공백이 반복되면 `track_lost_ms` 를 올리기
> 전에 **왜 검출이 끊기는지**를 먼저 본다. 버퍼를 늘리는 것은 검출 실패를
> 가리는 일이지 고치는 일이 아니다.

## ADR-28 · 사원증은 **읽는 것이지 배우는 것이 아니다** (학습 모델 미채택)

`FR-10.1` 은 *"전용 모델 학습은 데이터 수집 비용이 크다"* 며 ArUco 를 골랐다.
`3.8.1` 을 만들면서 그 근거가 실제로 값을 하는 지점과, 반대로 **학습으로는 풀리지
않는 지점**을 함께 확인했다.

### ① 학습이 없다 — 그리고 그것이 이 설계의 값이다

`DICT_4X4_50` 은 OpenCV 소스에 상수로 박힌 **400바이트 고정 표**다 (50코드 ×
16비트, 해밍 거리가 최대가 되도록 수학적으로 고른 것). 판독은 *사각형 후보 →
정면 정렬 → 칸 이진화 → 16비트 조회 → 오류 정정(1비트)* 의 결정론적 절차다.

| | ArUco (채택) | 학습 방식 |
| :--- | :--- | :--- |
| 사원증 추가 | **`config.yaml` 한 줄** | 데이터 수집 + 재학습 |
| 공수 | 0.5 M/D | 3.0 M/D 급 (`3.7.1`+`3.7.2` 와 같은 규모) |
| 추론 부하 | **0** — 알고리즘이다 | 추가 패스. `FR-3.6.1` 이 피한 것이고 40ms 예산을 PPE 와 다툰다 |
| 인원 증가 | 비용 0 | 인원마다 데이터·재학습 |

### ② **오늘의 실패는 학습으로 풀리지 않는다**

폰 화면으로 8회, 1,100프레임 이상에서 **해독 0건**이었다. 원인은 대비다.

| | 검은 칸 | 흰 칸 | 결과 |
| :--- | ---: | ---: | :--- |
| 정답 | 0 | 255 | 깨끗한 2분할 |
| 카메라가 받은 값 | **131** | 255 | 2:1 미만 → **흰 칸 세 개가 하나로 붙었다** |

검출기 파라미터 5종(코너 보정·다각형 근사·적응 이진화 창·오류 정정 완화), 사전
4종, CLAHE, 샤프닝, 2배 확대를 모두 시도해도 0건이다. **정보가 사라진 것이므로
복원되지 않는다** — 없는 비트는 어떤 모델도 만들어 내지 못한다.

> **크기는 제약이 아니었다.** 검출 하한을 재 보니 **변 12px** 이고 JPEG 품질 12
> 압축 후에도 같다. 14cm 마커는 1.5m 에서 47px 다. 처음에 *"너무 작다"* 로 진단했고
> 그것은 틀렸다 — 재고 나서 정정했다.

### ③ 화면이 필요해지면 답은 학습이 아니라 **코드 종류**다

| | ArUco 4×4 | QR |
| :--- | :--- | :--- |
| 오류 정정 | 1비트 / 16비트 | **최대 30%** |
| 화면 표시 | 위와 같이 실패 | 원래 노리는 용도 |
| 거리·각도 | 강함 (채택 이유) | 상대적으로 약함 |
| 학습 | 없음 | **없음** (`cv2.QRCodeDetector` 내장) |

**재검토** — 시연 진행상 화면으로 보여 줄 수밖에 없어지면 QR 을 검토한다(반나절).
학습은 그때도 마지막 선택지다.

### ④ 인증 표시는 **사건이 아니라 상태에서 읽는다**

| 대안 | 왜 버렸나 |
| :--- | :--- |
| `AUTH_OK` 사건만으로 인증 상태를 유지 | **사건이 없는 변화를 놓친다** — 60초 유효 시간 만료(FR-10.2.4)와 **미인증자가 새로 합류한 것**(FR-3.8.1)에는 사건이 없다. 그러면 한 번 인증한 사람 앞에서 영원히 승격되지 않는다 |

**채택** — 추론마다 *"보이는 전원이 인증됐나"* 를 물어 에스컬레이션에 반영한다.
`all_authenticated()` 가 **한 명이라도 미인증이면 False** 인 것이 FR-3.8.1 이며,
인증된 사람 뒤에 따라 들어오는 것을 막는다.

### ⑤ 시도 횟수는 **마커 ID 집합**으로 센다

25fps 로 도는데 프레임마다 세면 `max_attempts: 2` 가 **80ms 에 소진된다** —
사원증을 한 번 들어 보이는 것이 곧 *"2회 실패"* 가 된다. **프레임 수로 무언가를
세다 실패한 것이 이 저장소에 이미 세 번 있다**([22](#adr-22)·[25](#adr-25)·[27](#adr-27)).

**채택** — 본 마커 ID 의 **집합** 크기를 시도 횟수로 쓴다. 프레임률과 무관하며,
*다른* 사원증을 두 번째로 보이는 것이 두 번째 시도다. 같은 사원증을 계속 들고
있는 경우는 이 규칙으로 잡히지 않지만 **`AUTH_WAIT` 의 30초 타이머가 그 경로를
덮는다** — 두 장치가 서로를 보완하므로 새 시간 상수를 만들지 않는다.

## ADR-29 · 회피는 **후진하며 선회**한다 (물러난 뒤 전진 선회 미채택)

**상태:** 채택 (v1.4 · 2026-09-11) · **관련:** ADR-11 · FR-2.3 · WBS 2.2.3 / 3.5.1

제자리 회전을 전제하지 않으므로([ADR-11](#adr-11)) 선회는 **반드시 이동을 동반한다.**
원래 회피 구간표는 `정지 → 후진 200mm → 전진 선회 30도 → 전방 재확인` 이었고,
실측 전까지 남은 문제는 *"거리·각도를 몇 초로 바꾸는가"* 뿐이라고 봤다.
**실측이 그 전제를 깼다.**

| 조합 (`move(step, angle)`) | 선회 | 동반 이동 | 각도당 이동 |
| :--- | :--- | :--- | :--- |
| 전진 선회 `move(+60, +20)` | 6.8 도/s | **+84.3 mm/s 전진** | 12.4 mm/도 |
| 후진 선회 `move(-60, +20)` | 6.6 도/s | **-69.7 mm/s 후퇴** | 10.5 mm/도 |

선회 속도는 사실상 같다(3% 차). 다른 것은 **여유의 부호**다.

    후진 구간        +200mm
    전진 선회 30도   4.41s x 84.3 = -372mm
    -------------------------------------
    순 여유          **-170mm**

즉 지금까지의 구간표는 **회피가 아니라 접근이었다.** 시간 계산이 맞아도 결과가
틀렸고, 시험 709개가 이것을 잡지 못했다 — **시험은 시간을 검증했고 거리를
검증하지 않았다.** 여유 산수를 하는 주체가 없었던 것이 원인이다.

| 대안 | 왜 버렸나 |
| :--- | :--- |
| **후진 거리를 늘린다**(200 → 600mm) | **뒤를 보지 않는다.** LiDAR·카메라가 전방이므로 후진량을 늘리는 것은 관측되지 않는 방향으로 더 들어가는 것이다. 여유를 벌려고 더 위험한 곳으로 간다 |
| **선회 각도를 줄인다** | 30도 미만이면 같은 장애물이 화각에 남아 **시도 횟수만 소진**된다. 각도를 줄여 얻는 것은 시간뿐이고 잃는 것은 회피 자체다 |
| **후진과 전진 선회를 번갈아 여러 번** | 구간·주기만 늘고 순 여유는 같다 — 전진 선회는 도당 12.4mm 를 그대로 낸다 |
| 제자리 회전 | [ADR-11](#adr-11) — 2026-09-22 실측으로 **동작하기는 한다.** 그래도 버린다: 각속도가 호 선회와 같은 6.63~6.79 도/s 라 **여유를 벌지 못하고**, 산포 82% 를 회피 구간표에 넣을 수 없다 |

**채택** — 구간을 하나로 합쳐 `move(-step_length_mm, +turn_angle_deg)` 를 유지한다.
유지 시간은 **각도 목표와 여유 목표 중 오래 걸리는 쪽**이다(30도 4.55s vs 200mm
2.87s → **4.55s**). 결과는 30도 선회 + **317mm 후퇴**, 구간은 4개에서 3개로 줄고
순 여유는 -170 → **+317mm** 가 된다.

⚠️ **두 값이 다 있어야 적용한다.** 하나만 재고 쓰면 시간을 무엇으로 나눌지
임의가 되므로, 미실측 개체는 옛 구간표로 돈다 — **그 개체에서는 위의 음수 여유가
그대로 남아 있으므로 `2.2.3` 을 먼저 재야 한다.**

⚠️ **남는 위험: 후방은 여전히 관측되지 않는다.** 이 결정은 그것을 해결하지 않고
**후진량을 200 → 317mm 로 늘린다.** 옛 구간표도 이미 후진했으므로 위험의 종류가
새로 생기지는 않지만 크기는 커졌다. 시연장에서 로봇 뒤 1m 를 비워 두는 것이
운용 전제이며, 후방 센서는 Phase 1 범위가 아니다.

## ADR-30 · 배터리 상한에 **측정 여유 0.2V** 를 둔다 (평균만 내기 · 상한만 넓히기 미채택)

**상태** — **확정 · 실기 확인 완료** (2026-09-13). 만충 직후 `mechdog-01` 에서 폐기 0 · 텔레메트리 180/180 · 10Hz · 최대 간격 0.11초.

**문제** — 2S 만충이 8.4V 이고 규약의 폐기 상한도 8.4V 였다. 그래서 **충전을 마친 로봇이
보내는 정상 레코드가 폐기된다.** 2026-09-12 공중 보행 실기에서 정지 중 34건 중 9건이 8.4V 를
넘었다(7.72~8.46V, 중앙값 8.25V). 폐기는 레코드 단위여서 배터리 값만이 아니라 `state`·
`dist_cm`·`imu`·`last_cmd_age_ms` 가 함께 사라진다. 호스트는 그 줄로 **리셋 해제를 확인**하고
링크 생존을 판단하므로, 순찰이 열리지 않거나 폐기가 이어져 링크 두절 FAILSAFE 에 들어간다.
⚠️ **시연 직전에 충전할수록 확률이 높아진다** — 가장 중요한 순간에 가장 잘 터진다.

**결정** — 둘을 함께 한다.

- **펌웨어가 ADC 를 9회 읽어 중앙값을 싣는다.** 지금은 `analogRead` 한 발이라 서보 전류에
  그대로 흔들린다. 9회는 100ms 주기에서 1ms 도 쓰지 않는다.
- **폐기 상한을 8.6V 로 올린다.** 여유 0.2V 의 근거는 ADC 보정·분압 저항 오차 합 ±2~3% 와
  실측 최댓값 8.46V 다.

**저전압 판정(경고 7.0V · 셧다운 6.6V)은 건드리지 않는다.** 이 결정이 답하는 질문은
*"측정이 가능한 값인가"* 이고 그것은 *"안전한가"* 다. 둘을 섞으면 보호가 느슨해진다.

**대안**

- **ⓐ 평균만 낸다** — 흔들림은 줄지만 **만충은 그대로 8.4 를 넘는다.** 문제의 절반만 푼다.
- **ⓑ 상한만 넓힌다** — 튀어 오른 한 발을 그대로 믿게 되어, 8.46 이 진짜 만충인지 잡음인지
  구분할 수단이 없다. 값을 믿을 수 있게 만드는 것이 여유를 주는 것보다 먼저다.
- **ⓒ 배터리 값만 버리고 나머지 필드는 살린다** — 규약은 레코드 단위 폐기이며(FR-5.1 규칙 ④)
  필드별 예외를 만들면 **부분적으로 거짓인 레코드**가 생긴다. 그것을 믿고 대시보드를 갱신하는
  쪽이 더 위험하다.

⚠️ **이전 판단을 뒤집는 것이다.** 2026-09-11 기록에는 *"`[6.0, 8.4]` 를 넓히거나 측정값을
가짜 정상값으로 바꾸지 않았다"* 고 적혀 있다. 그때는 근거가 8.20V 측정 하나뿐이어서 **상한을
넘는 것이 관측되지 않았고**, 넓히면 고장을 정상으로 덮을 위험이 더 컸다. 지금은 만충이 상한에
닿는다는 것이 34건 표본으로 관측됐다. **근거가 바뀌었으므로 결정도 바뀐다.**

## ADR-31 · 암구호 인식을 **Host PC 로컬 음성 인식**으로 옮긴다 (온칩 명령 ID 미채택)

**상태** — **확정** (2026-09-14 · 팀장 결정). 근거 실물은 PR #83 — WonderEcho 에서 안내 재생 →
5초 녹음 → PC 한국어 인식 → 이름 추출까지 실물로 통과했다(`"사원 홍길동입니다."` · `no_speech_prob 0.042`).

**문제** — FR-10.2 는 인식을 **모듈 온칩 오프라인 인식**으로 정하고 *"오디오 스트리밍이나 호스트 측
음성인식을 사용하지 않는다"* 고 적었다. 온칩 인식은 **영어·중국어만** 되고, 암구호를 **대문자 + 하이픈**
문구로 **펌웨어 빌드 때 확정**해야 하며, 문구를 바꿀 때마다 재플래싱해야 한다. 한국어로 말하는 경비
시연에 맞지 않는다.

**결정**

- WonderEcho 는 **마이크·스피커**로만 쓴다. 음성은 Speex 로 압축(약 3 KB/s)해 PC 로 보낸다.
- PC 는 **로컬** faster-whisper(medium · CUDA)로 한국어 텍스트를 만든다. **클라우드로 보내지 않는다.**
- 인증은 인식 결과를 **등록 목록과 대조해 일치할 때만** 성립한다. 대조 대상은 `3.8.2` 에서 정한다.

**지키는 선**

- ⚠️ **이름은 비밀이 아니다.** 말한 이름을 받아 적는 것만으로는 누구나 통과한다 — #83 도
  `identity_verified: false` 로 두었다. 대조 규칙 없이 인증으로 쓰지 않는다.
- **인식 텍스트를 명령으로 실행하지 않는다.** 판정 입력으로만 쓴다.
- Whisper 는 무음에서 그럴듯한 문장을 지어낸다(실측 `"오늘도 시청해 주셔서 감사합니다."` ·
  `no_speech_prob 0.753`). 그 값을 함께 보고 판정에서 거른다.

**대가**

- **GPU 가 시연 조건이 된다.** VRAM 8 GB 이상, **시연 PC 는 RTX 50 시리즈**(CUDA 12.8 이상 빌드 필요).
  성능 수치의 기준 PC(`OI-14` · RTX 3080)와 시연 PC 가 달라진다.
- **모델 약 15 GB 를 각자 받는다.** 저장소에 싣지 않는다. 시연 중 실시간으로 도는 것은 인식 모델(약 1.5 GB)
  뿐이고, 안내 음성 합성(Orpheus 3B)은 미리 음원을 만들어 두는 오프라인 작업이다. Orpheus 는 게이트
  저장소라 재배포할 수 없다.
- **즉시가 아니다.** 녹음 5초 + 인식 시간이 든다. 즉각 경고 방송(FR-3.4)과는 경로가 다르다.

**대안**

- **ⓐ 온칩 명령 ID (원래 FR-10.2)** — 네트워크·GPU 가 필요 없고 즉시다. 그러나 한국어가 안 되고 문구가
  펌웨어에 묶인다.
- **ⓑ 암구호를 이번 일정에서 제외** — 사원증 인증만으로 시연한다. 가장 가볍지만 사복 인원 시나리오를
  잃는다.

**열린 것** — 모듈을 USB 대신 로봇 I²C(`0x34`)로 붙이면 벤더 I²C 소유권 규칙(`MP3Sensor` 등 금지)과
부딪힌다. 지금은 USB 시리얼로 둔다(OI-10). *(2026-09-23 정정 — 처음에 주소로 적은 `0x64` 는 장치 주소가 아니라
0x34 모듈의 명령 id 우편함 레지스터다.)*

### 개정 (2026-09-23) — 로봇 I²C 음성 경로는 닫혔고, 입력 마이크는 XIAO 로 옮겨 간다

**결정(PC 로컬 인식 · 등록 목록 대조 · 클라우드 미사용)은 그대로다.** 바뀐 것은 소리가 들어오고 나가는
길이다([ADR-38](#adr-38)).

- **위 «열린 것» 은 불가로 닫혔다.** `4.7.9` 실측(2026-09-23)에서 0x34 브리지로는 명령 id 만 오가고 음성
  파형은 오가지 않았다. 모듈 마이크 음성을 로봇 경유로 PC 에 보낼 수 없다.
- **입력 마이크는 XIAO ESP32S3 Sense 의 PDM 마이크**(비전 펌웨어 포트 82 `/audio`)로 옮긴다. USB 단독 인식
  6/6, 영상과 동시 전송에서 음성 누락 0. 파이프라인 연결은 `4.7.19`(미착수)다.
- **말하기는 로봇 I²C 의 MP3 모듈(`0x7B`)** 이 TF 카드에 미리 넣은 문장을 재생한다(`4.7.20` · `4.7.21`).
- 그때까지 WonderEcho USB 시리얼 링크는 **시제품 · 임시 경로**로만 남는다. 위 «결정» 첫 줄은 이 임시
  경로의 서술이다.
- 파이프라인의 음성 합성은 **Piper** 다 — `--tts orpheus` 선택지는 지웠다. TF 카드 문장도 Piper 로 미리
  합성한다(`4.7.21`). 위 «대가» 의 Orpheus 3B 는 오프라인 스크립트(`synth_prompt_orpheus.py`)로만 남아 있다.

## ADR-32 · FPV는 **판정에 사용한 JPEG와 박스를 함께** 그린다 (원본 MJPEG 위 별도 오버레이 미채택)

**상태** — **확정 · 실기 확인 완료** (2026-09-14). **관련:** FR-4.1 · WBS 4.5.2 / 4.6.1.

**문제** — XIAO 원본 영상은 25fps로 도착하지만 PC 추론은 그보다 늦게 끝난다. 브라우저가 원본 MJPEG를
계속 재생하면서 별도 채널의 *최신 박스*를 얹으면, 박스가 계산된 장면은 이미 지나갔다. 사람이 움직일수록
박스가 몸에서 벗어나며, 화면은 부드러워 보여도 **시스템이 실제로 무엇을 판정했는지 재현할 수 없다.**

**결정** — 서버가 추론 결과 하나를 `[JSON 길이][JSON 헤더][판정에 사용한 JPEG]`인 단일 WebSocket
메시지로 보낸다. 브라우저는 그 메시지 안의 사진을 먼저 그리고 같은 메시지의 박스를 같은 캔버스에 그린다.
사람은 지속 ID가 붙은 추적 박스로 한 번만, 나머지 객체는 검출 박스로 표시한다.

디코딩 중 새 장면이 오면 완료된 옛 장면까지 버리고 **가장 최신 한 장만** 그린다. 모든 장면을 순서대로
보여 주면 처리량이 순간적으로 떨어질 때 영상 지연이 계속 누적되기 때문이다. 새 결과가 2초 없으면 마지막
장면은 증거로 남기되 `실시간` 표시를 `영상 멈춤`으로 바꾼다.

**대안**

- **ⓐ 원본 MJPEG + 별도 박스 WebSocket** — 전송은 단순하지만 두 채널의 프레임을 정확히 결합할 공통
  키와 브라우저 버퍼 제어가 필요하다. 결합에 실패하면 그럴듯한 오답 화면을 만든다.
- **ⓑ 서버에서 박스를 JPEG에 구워 전송** — 브라우저는 단순해지지만 서버가 매 프레임 다시 인코딩해
  CPU와 지연을 더 쓴다. 지금 형식은 JPEG를 복사하고 브라우저가 선만 그린다.
- **ⓒ 받은 장면을 전부 순서대로 표시** — 누락은 줄지만 관제 화면이 과거를 따라가게 된다. 이 시스템의
  목적은 녹화 재생이 아니라 현재 상황 관측이다.

**실기 근거** — XIAO OV3660 VGA 25fps 설정에서 카메라 수신 24~27fps, PC 추론 20~24fps,
브라우저 WebSocket **22.62fps**(272장 / 11.982초)였다. 순서 역전·JPEG 오류·화면 밖 박스는 0건이었고,
640×480 실제 화면에서 사람 박스와 신뢰도가 몸에 맞게 붙었다. 호스트 종료 시 마지막 장면을 유지하며
`연결 중`으로 바뀌고, 재기동 뒤 별도 조작 없이 `실시간 수신 중`으로 복귀했다.

**재검토** — 원격망 전송이나 다수 동시 관제 때문에 JPEG 대역폭이 병목이 되면 프레임 ID가 있는
WebRTC/H.264 경로와 서버 합성을 비교한다. 그때도 **영상과 판정의 프레임 동일성**은 유지한다.

## ADR-33 · 경비와 산업안전 점검을 **운용 모드로 나눈다** (한 순찰 동시 수행 미채택)

**상태** — **확정** (2026-09-16 · 팀장 결정) · **구현됨** (2026-09-19 · `3.4.4` ·
`host/behavior/mission.py`). **관련:** FR-11 · FR-3.8 · FR-8 · FR-9 ·
FR-10 · 아키텍처 3 / 3.1 · WBS 3.4.4 / 3.7 / 3.8 / 6.4.3.

> **2026-09-17 확장** — [ADR-34](#adr-34)가 `assist`를 세 번째 모드로 추가했다. 이 ADR의 두 모드 비교와
> 비용은 당시 경비·안전점검 분리 결정의 기록이며, 현재 정본은 FR-11과 ADR-34를 함께 본다.
>
> **2026-09-23 개정** — `assist` 는 폐기했다([ADR-38](#adr-38) · ADR-34 폐기). 모드는 다시 **`guard` · `factory`
> 두 개**다(`mission.MODES`). 아래 개정 절의 `assist` 서술은 기록으로만 남는다.

**문제** — README 와 PRD 는 *"한 번의 순찰에서 경비와 산업안전 점검을 동시에 수행한다"* 고 적었다. 두 판정이
같은 `person` 검출에서 출발하므로 한 프레임에서 둘 다 낼 수 있다는 것 자체는 맞다. 그러나 **사람을 만난 뒤
로봇이 할 일이 서로 부딪힌다.**

| | 경비가 요구하는 것 | 점검이 요구하는 것 |
| :--- | :--- | :--- |
| 그 사람은 | 침입자 후보 — 신원을 확인해야 한다 | 작업자 — 신원은 전제다 |
| 로봇 몸 | 선회 추종으로 따라간다(FR-3.5) | 대상이 멈춰 있을 때 자세를 세운다(FR-9.2.0) — 세운 자세로는 움직이지 못한다(FR-9.2.3) |
| 시간 | 10초 뒤 인증 요구, 30초 뒤 경보 | 자세 상승 3단계 × 재시도 2회 |
| 경고 방송 | *"신원을 확인하십시오"* | *"안전모를 착용하십시오"* |

주 대상은 한 명이고(FR-3.8.2) 눈 LED·스피커도 하나라서, 둘을 한 순찰에 넣으면 **어느 쪽을 먼저 할지 규칙을
새로 만들어야 한다.** 그 규칙은 결국 ⓐ 일하고 있는 작업자에게 순찰이 지날 때마다 사원증을 요구하거나 ⓑ 인증을
기다리는 중에 자세를 세워 추종을 멈추게 한다. 시험도 *인증 결과 × PPE 결과 × 자세 단계* 조합으로 불어난다.

그리고 **지금 구현된 것은 경비 쪽뿐이다.** 사람 검출·추적(`3.3`) · FSM(`3.4.1~3.4.3`) · 에스컬레이션
L0~L3(`3.8.3`) · 사원증 인증(`3.8.1`)은 들어가 있지만 PPE 는 모델도 판정기(`vision/ppe_detector.py`)도 없고
(`3.7.1~3.7.3` · `3.5.7` 미착수) FSM·단계기에 `PPE_VIOLATION → L3` 자리만 있다. README 의 *"같은 카메라
프레임에서 두 판정이 함께 나온다"* 는 **지금 사실이 아니었다.**

**결정** — 로봇은 **순찰 하나를 운용 모드 하나로** 돈다.

| | 경비 모드 `guard` (기본) | 공장 모드 `factory` |
| :--- | :--- | :--- |
| 가정한 운용 상황 | 출입이 없어야 할 시간·구역 (야간·휴무) | 작업자가 있는 시간 (주간·작업 중) |
| 사람을 보면 | **침입자 후보** — L1 관찰 → 미인증 지속 시 L2 인증 요구 → 실패·미인증 이탈 시 L3 | **작업자** — L1 관찰 → **쓰러졌는지 먼저 보고** 보호구 판정 |
| FR-10 인증 | 켠다 | **요구하지 않는다** — L2·`AUTH_WAIT` 가 없다 |
| FR-8 변화 감지 | 끈다 | **켠다** — 확정 시 L3 |
| FR-9 PPE 판정 | **끈다** — PPE 모델을 돌리지 않는다 | 켠다 — FR-9.2.2 자세 상승, 위반 확정 시 L3 |
| L3 원인 | 인증 실패 · 미인증 이탈 | PPE 위반 확정 · **물체 변화 확정 · 사람 쓰러짐** |
| 판정 뒤 순찰 복귀 | 인증 성공 또는 대상 미검출 5초 | 보호구 판정 종료(적합 · `PPE_UNDETERMINED`) 또는 대상 미검출 5초 |
| 경고 방송 | 침입 경고 문구 | 보호구 착용 안내 · 위반 경고 문구 |

**두 모드에 공통** — 순찰 · 주기 스캔 · 장애물 회피 · 온보드 근거리 정지 · 페일세이프 F · 수동 조작 ·
비상정지 · 음성 명령 · 사람 검출과 추적 · 사건 기록 · 관제 화면. **모드는 판단 층(Tier 2)의 선택이며 Tier 1
안전 반사에는 닿지 않는다.** 모드 이름이 가정한 운용 상황은 설명일 뿐 **무인 운용 허가가 아니다** — Phase 1 은
두 모드 모두 상시 인적 감시(`A-13`) 아래 운용한다.

운용 규칙:

1. **모드는 순찰을 시작하기 전에 정한다.** 기본값은 `config.yaml` 의 `mission.mode`(기본 `guard`), 기동 때는
   `python -m host.runtime --mode`, 운용 중에는 관제 화면에서 바꾼다.
2. **멈춰 있을 때만 바꾼다** — `IDLE`·`MANUAL` 에서만 받는다. 그 밖의 상태에서 온 요청은 **거부하고 사유를
   돌려준다.** 대응 중에 판정 규칙이 바뀌면 진행 중인 인증·자세 시퀀스가 의미를 잃는다(FR-3.8.3 시퀀스 락과
   같은 이유).
3. **모드 전환은 L3·F 를 풀지 않는다.** 모드를 바꿨다고 경보가 사라지면 *"모드 바꾸기"* 가 확인 없는 해제
   경로가 된다 — ADR-26 이 비상정지로 경보를 지우지 못하게 한 것과 같다. L1·L2 는 대기에 들어설 때
   이미 L0 으로 내려가 있다(아키텍처 3.1 잠정 규칙).
4. **공장 모드의 판정 결과는 추적 ID 에 귀속한다.** 적합 또는 미판정으로 끝난 ID 앞에서는 L0 으로 내리고
   순찰로 돌아가며 같은 ID 에 다시 멈추지 않는다. ID 가 소실되면 만료된다(FR-3.6.2~3.6.3 인증 세션과 같은
   구조). 이 규칙이 없으면 **보호구를 제대로 쓴 작업자가 서 있는 동안 로봇이 떠나지 못한다.**
5. **사건 · 블랙박스 · 구조화 로그에 `mode` 를 남긴다.** 같은 `person` 검출이 모드에 따라 다른 결과를 낳으므로
   모드 없이 기록을 읽으면 판단 근거를 되짚을 수 없다(PRD 1.2 ②).
6. **관제 화면은 현재 모드를 항상 보여 준다.** 공장 모드인 줄 모르고 보면 *"사람이 지나갔는데 인증을
   요구하지 않는다"* 가 고장으로 읽힌다.
7. **PPE 판정기가 없으면 `safety` 선택을 거부한다.** 판정기 없이 켜면 로봇이 사람 앞에 서서 아무 판정도 내지
   못한다. `3.7.3` 이 끝나기 전까지는 경비 모드만 고를 수 있다.

**대안**

- **ⓐ 동시 수행 + 우선순위 규칙** — 예: *인증 먼저, 인증되면 PPE*. 작업자에게 **순찰이 지날 때마다 사원증을
  요구**하게 되고, 인증을 기다리며 PPE 자세를 세우면 추종이 멈춘다. 규칙이 하나 늘 때마다 FSM·단계기의 조합
  시험이 곱으로 늘어 9/30 동결 전에 닫을 수 없다.
- **ⓑ 사원증이 보이면 PPE, 안 보이면 경비** — 분기가 사원증 판독에 걸린다. 판독 하한이 변 12px 이고 대비에
  약해서(FR-10.1.2 · A-15 · A-16) **멀리서·역광에서 판독에 실패하면 작업자가 침입자로 처리된다.** 판독이
  흔들리면 같은 사람이 프레임마다 두 규칙을 오간다.
- **ⓒ 시간대에 따라 자동 전환** — 설정이 하나 더 늘고 순찰 중 전환 금지(규칙 2)와 부딪히며, 운용자가 지금 어느
  모드인지 예측하기 어렵다. 필요해지면 규칙 1 위에 나중에 얹을 수 있다.

**치르는 대가**

- *"한 번에 둘 다"* 라는 설명을 잃는다. 대신 **각 결과가 어느 규칙에서 나왔는지 설명할 수 있다**(ADR-14 와
  같은 가치).
- **공장 모드는 외부인 침입을 잡지 않는다.** 작업 시간의 출입 통제는 현장의 출입 관리가 맡는다고
  전제한다(`A-17`).
- 구현 공수 `3.4.4` **1.0 M/D** 가 늘어난다(총 89.5 → 90.5).
- 시연이 두 장면이 된다. **G3(`6.4.3`)는 경비 모드로 한다.** PPE 장면은 `3.7.3` 이 끝난 뒤 공장 모드로
  따로 기록한다.

**재검토** — 작업 시간에도 외부인 출입 통제가 요구될 때. 그때 ⓐ·ⓑ 를 다시 보되 **사원증 원거리 판독이 먼저
확보돼야 한다** — ⓑ 가 떨어진 이유가 그것이다.

### 개정 (2026-09-17) — `safety` 를 `factory` 로 넓히고 변화 감지를 옮긴다

**두 번 고쳤다.** ① `assist`(현장지원)가 세 번째 모드로 들어왔다([ADR-34](#adr-34)). ② 남은 두 모드의
경계를 다시 그었다.

| 바꾼 것 | 왜 |
| :--- | :--- |
| `safety` **안전점검** → `factory` **공장** | 이름이 «보호구 점검» 만 가리켜 범위를 좁게 만들었다. 작업 현장을 도는 로봇은 보호구만 보는 것이 아니라 **쓰러진 사람·무너진 물건·없어진 물건**을 함께 본다 — 그 전부가 한 순찰의 일이다 |
| **FR-8 변화 감지를 공장 모드로** | 처음에는 경비에 두었다. 그런데 이 기능의 주된 쓰임은 *"물건이 없어졌다"* 보다 **"물건이 무너졌다"** 이고, 판독 경로도 PPE 와 같은 카메라·같은 모델을 쓴다. 경비 모드는 **침입 대응에 집중**한다 |
| 공장 모드에 **쓰러짐 판정** 추가 | 사람을 보면 보호구보다 **먼저** 본다. 쓰러진 사람에게 보호구를 묻는 것은 순서가 틀렸다 |

⚠️ **경비 모드가 도난을 못 잡게 되는 것을 받아들인다.** 야간 무인 순찰에서 물건이 없어져도 경비 모드는
표시하지 않는다. 필요해지면 «경비 + 변화 감지» 조합을 다시 열되, **그때는 모드가 아니라 옵션으로** 둔다 —
모드를 늘리면 시험 조합이 다시 곱으로 늘어난다.

**모드는 적재 프로파일이기도 하다 (2026-09-17 실측).** GPU 가 10GB 뿐이라 전부 올릴 수 없다.

| 모드 | 올리는 것 | 합계 |
| :--- | :--- | ---: |
| `guard` | 검출기 1.0 + STT 1.5 | ~2.5 GB |
| `factory` | 검출기 1.0 + STT 1.5 + **VLM 4.1** | ~6.6 GB |
| `assist` | 검출기 1.0 + STT 1.5 + **LLM 4.9** | ~7.4 GB |

⚠️ **`factory` 와 `assist` 는 같이 못 켠다** — 그것이 모드를 나누는 또 하나의 이유가 됐다. 전환할 때
모델을 내렸다 올리며, 실측 적재는 **5.5초**다(해제는 즉시). 전환은 어차피 멈춰 있을 때만 받으므로
(규칙 2) 문제가 되지 않는다. ⚠️ **이 5.5초는 낡았다 — 2026-09-20 재측정에서 3회 모두 14.5초였다**
(아래 재검토). 결론은 그대로이고 «멈춰 있을 때만 전환» 이라는 근거만 더 세진다. ⚠️ **LLM 을 내려도 음성 명령은 살아 있다** — 화이트리스트 대조는 STT 만
쓰고 LLM 을 쓰지 않는다(`4.7.11`). 비상정지·순찰 정지는 공장 모드에서도 말로 걸 수 있다.

> **개정 (2026-09-23)** — 위 표의 `assist` 행과 «`factory` 와 `assist` 는 같이 못 켠다» 는 기록으로만 남는다.
> 현장지원 모드와 음성 LLM 을 함께 폐기했다([ADR-38](#adr-38)). 이제 음성 경로는 어느 모드에서든 **STT + 규칙**
> 뿐이라 LLM 적재가 없다. 모드가 적재 프로파일이라는 성질은 `factory` 의 VLM 하나로 남는다.

## ADR-34 · 운영정보 안내는 **현장지원 모드 + 구조화 조회**로 둔다 (상시 자유 RAG 미채택) *(폐기 · 2026-09-23 · ADR-38)*

> ⚠️ **폐기 (2026-09-23 · 사용자 결정 · [ADR-38](#adr-38))** — 현장지원 모드(`assist`)와 운영정보 경로를 없앤다.
> 운용 모드는 `guard` · `factory` 둘이다.
>
> - **지운 것** — `host/factory_ops/` 전체, `tools/factory_ops_seed.py`, `tests/test_factory_ops*.py`, `mission.py` 의
>   `assist` 모드, 관제 화면의 모드 버튼·이름, `config.yaml` 의 `factory_ops:` 절, 음성 쪽 `factorylink.py` ·
>   `factory_mes.py`(가상 MES) · `test_factorylink.py`, 음성 규칙의 `factory_rules` 섹션.
> - **왜** — 말하기가 **미리 녹음한 문장만** 내는 로봇 MP3 모듈로 옮겨 간다. 생산량·납기·설비 상태처럼 **계속
>   바뀌는 값**은 미리 녹음할 수 없다. 규칙 3 이 전제한 음성 LLM 도 함께 폐기했다. 이 ADR 스스로 «부가기능이라
>   일정이 밀리면 `assist` 만 제외» 라 적어 둔 기능이다.
> - **잃는 것** — `4.7.15~4.7.17`(가상 MES 원본 · 질의 라우터 · 신선도 계약)은 2026-09-22 에 구현을 마쳤던 것을
>   지운다. `4.7.18` 실기는 하지 않았다. WBS `4.7.15~4.7.18` 행을 지웠고(-3.0 M/D), `3.4.4` 는 1.5 → 1.0 M/D 다.
>
> 아래 본문은 당시 결정의 기록으로 남긴다. 상태 줄의 «운영정보 경로는 구현 전» 은 작성 시점의 서술이다.

**상태** — **확정** (2026-09-17 · 팀장 결정) · **모드 축은 구현됨** (2026-09-19 · `3.4.4`) ·
**운영정보 경로는 구현 전** (`4.7.15~4.7.18`). 그래서 `assist` 는 아직 고를 수 없다 (FR-11.7).
**관련:** FR-11 · FR-12 · ADR-31 · ADR-33 · WBS 3.4.4 / 4.7.6 / 4.7.10 / 4.7.15~4.7.18.

**문제** — 음성 파이프라인에는 이미 `knowledge/*.txt`를 찾아 LLM 프롬프트에 넣는 경량 RAG가 있고,
합성 작업현황·출하 일정·식단·안전 문서를 한 폴더에서 다룬다. 안전 규정과 매뉴얼은 문서가 정본이라 이 방식이
맞지만, 생산량·납품일·설비 가동 상태는 시간이 지나면 바뀐다. 시작 때 한 번 읽은 텍스트를 최신 운영값처럼
답하면 **문장 자체는 자연스럽지만 값의 시각과 출처를 증명할 수 없다.**

또 경비·공장 모드에서 만난 사람에게 자유 대화를 자동으로 시작하면, 같은 `person`을 침입자·PPE 점검 대상·질의
사용자로 동시에 다루게 된다. ADR-33이 분리한 충돌을 음성 경로에서 다시 만든다. 반대로 모든 모드에서 운영정보
질의를 항상 허용하면 부가기능 때문에 핵심 경비 시퀀스와 시연 설명이 흐려진다.

**결정** — `assist`를 세 번째 **현장지원 모드**로 추가한다. 이 모드는 현장 근로자가 웨이크워드로 안전 문서,
로봇 상태, 합성 공장 운영정보를 묻는 부가기능이다.

| 질문 종류 | 정본 | 답변 규칙 |
| :--- | :--- | :--- |
| 안전 규정·설비 매뉴얼 | 버전이 관리되는 `knowledge/` 문서 | 검색 근거를 LLM에 주고 **문서 범위 안에서만** 절차를 설명한다 |
| 로봇 배터리·상태 | 기존 텔레메트리 API | 실측값을 그대로 읽는다. LLM이 수치를 만들지 않는다 |
| 생산량·출하·작업 일정·설비 상태 | 로컬 가상 MES(SQLite) 읽기 전용 어댑터 | 결정론적 질의로 가져온 값만 설명하고 `source`·`updated_at`을 표시한다 |
| 자료 없음·오래된 운영값 | 없음 | 추정하지 않고 **최신 정보를 확인할 수 없다고** 답한다 |

운용 규칙:

1. **사람 검출만으로 대화를 시작하지 않는다.** `assist`에서도 웨이크워드 또는 관제 요청이 있어야 한다.
2. **자동 경비·PPE 사건을 만들지 않는다.** 사람은 질의 사용자이며 인증 요구, 자세 상승, 추종을 하지 않는다.
   장애물 회피·명령 타임아웃·저전압·E-Stop 같은 Tier 1 안전은 세 모드 공통이다.
3. **LLM은 조회 결과를 설명만 한다.** SQL·API 인자, 숫자, 날짜, 상태, 신선도 판정은 규칙 코드가 결정한다.
   LLM 자유 텍스트는 명령·인증·PPE 판정·L3/F 해제로 연결하지 않는다.
4. **운영값에는 출처와 갱신 시각이 필수다.** 항목별 최대 수명(TTL)을 넘긴 값은 실패로 취급한다.
5. **`assist`는 선행 기능이 완성되기 전 선택을 거부한다.** DB/어댑터, 질의 라우터, 신선도 검사 중 하나라도
   없으면 정상 모드처럼 켜지지 않는다. 모드 전환 안전 규칙은 ADR-33과 같다.
6. **데모 데이터는 합성한다.** 실제 직원 개인정보, 생산 실적, 암구호를 저장하지 않는다. 고장 질문은 진단이
   아니라 매뉴얼에 적힌 점검 순서 안내로 표현한다.

**데이터 범위** — 1차 구현은 `production_status`, `shipment_schedule`, `work_schedule`,
`equipment_status` 네 운영 테이블만 만든다. 기존 사건 JSONL·블랙박스·순찰 리포트는 이미 목적에 맞게 동작하므로
SQLite로 복제하지 않는다. 과거 사건 검색이 실제 요구가 될 때 `incidents`·`mission_runs` 색인을 별도 결정한다.

**대안**

- **ⓐ 경비·공장 모드 모두에서 항상 Q&A 허용** — 화면 기능은 늘지만 대응 중 음성 상호작용이 끼어들고 모드별
  설명이 흐려진다. 필요하면 나중에 *대응 중이 아닐 때만* 공통 기능으로 승격할 수 있다.
- **ⓑ 운영값도 `knowledge/*.txt`에 유지** — 구현은 이미 되어 있지만 파일 복사 시각을 모르면 최신값이라고
  말할 수 없다. DB를 쓴다는 사실보다 **동적 값의 정본과 신선도를 분리하는 것**이 이 결정의 핵심이다.
- **ⓒ LLM이 자연어를 SQL로 변환** — 데모 질문은 유연해지지만 잘못된 필드·범위·집계가 그럴듯한 답으로 나온다.
  이번 범위는 질문 종류가 네 가지라 명시적 라우터가 더 작고 시험 가능하다.

**치르는 대가** — 모드 구현 확장 0.5 M/D와 운영정보 경로 3.0 M/D, 합계 **3.5 M/D**가 늘어난다. 총 계획
공수는 90.5 → **94.0 M/D**다. 부가기능이므로 일정이 밀리면 `assist`만 제외하고 G1~G3 핵심 검수는 유지한다.

**재검토** — 실제 MES/API가 제공되거나 현장지원이 핵심 요구로 승격될 때. 그때 SQLite 어댑터를 실제 API
어댑터로 교체하되 `source`·`updated_at`·TTL·읽기 전용 계약은 유지한다.

## ADR-35 · 상황 판독은 **로컬 VLM**으로, 공장 모드에서만 올린다 (클라우드·상시 구동 미채택)

**상태** — **확정** (2026-09-17 · 팀장 결정 · 실측 근거) · **구현 전**. **관련:** FR-8 · FR-9 · FR-11
공장 모드 · WBS `3.6` · `4.8.1` · [ADR-33](#adr-33) 개정 · ADR-15 · ADR-31.

**문제** — 요구사항은 *"위험구역 감지 및 변화"* 인데, 우리가 가진 것은 **COCO 80클래스 객체 목록 비교**뿐이다.
목록으로는 *"사람이 쓰러져 있다"*·*"소화기가 무너져 있다"* 를 말할 수 없다. FR-8.3 이 이미 적어 두었듯
**소화기·사다리·공구함·상자는 COCO 80 에 아예 없다** — 넘어졌는지 이전에 물건 자체가 보이지 않는다.
어휘 밖을 읽으려면 사진을 그대로 해석하는 모델이 필요하다.

**실측 (2026-09-17 · RTX 3080 · `Qwen2-VL-2B-Instruct`)**

| 사진 | 사람 판정 | 넘어진 물건 |
| :--- | :--- | :--- |
| 쓰러진 작업자 (참고 사진) | ✅ **"누워 있다"** | ❌ 안전모를 못 봄 |
| 넘어진 페트병 (참고 사진) | ✅ 없음 | ✅ **"옆으로 누운 병"** |
| 우리 카메라 — 방 전경 | ✅ 서 있음 | ✅ 없음 |
| 우리 카메라 — 침대·의자 | ✅ 앉아 있음 | ✅ 없음 |
| 우리 카메라 — 책상 | ✅ 앉아 있음 | ✅ 없음 |

**정상 장면을 위험하다고 말한 적은 0건이다.** 질문당 **0.2~0.9초**(평균 0.4초), 적재 5.5초, VRAM 4.1GB.

같은 두 사진을 우리 검출기(YOLOX-S)에 넣으면 **쓰러진 사람은 `person` 0.89 로 잡히지만**(박스가 가로로
납작하다 — 세로 88 · 가로 286), **넘어진 페트병은 `snowboard` 0.51** 로 나온다. 즉 **사람은 검출기가
트리거할 수 있고 물건은 못 한다.**

**결정**

1. **로컬 VLM 을 쓴다. 클라우드는 쓰지 않는다.** 사진이 PC 를 떠나지 않는다 — 음성을 클라우드로 보내지
   않기로 한 것([ADR-31](#adr-31))과 같은 기준이다. 목소리를 안 보내면서 얼굴 사진을 보내는 것은 앞뒤가 맞지 않는다.
2. **판정은 VLM 이 하지 않는다.** ⚠️ 실측에서 *"위험한가?"* 라는 **열린 질문에는 쓰러진 작업자에게도
   `NORMAL` 이라고 답했다.** 항목별로 쪼개 물으면(*"사람이 누워 있나?"*) 정확히 맞힌다. 그래서 **질문은
   고정 항목으로 두고, 사건 생성은 FSM 이 한다** — 모델은 관찰자다([ADR-14](#adr-14) 와 같은 선).
3. **영어로 묻고 한국어는 LLM 이 쓴다.** 같은 사진에 한국어로 물었더니 *"정상입니다"* 라고 답했다. 2B
   모델의 한계다. 관제 화면·방송 문장은 이미 있는 로컬 LLM 이 만든다. *(2026-09-23 개정 — 아래)*
4. **부르는 때는 둘** — ① `person` 검출 시(쓰러짐 확인, 급한 쪽) ② **스캔 정지마다 1회**(사람이 없어도
   물건·통로를 본다). ②가 없으면 사람 없는 구역의 무너짐을 영영 못 잡는다. 걷는 동안 부르지 않는 이유는
   흔들려서 판독이 나빠지기 때문이다 — 멈춰서 재는 [ADR-7](#adr-7) 과 같은 논리다.
5. **공장 모드에서만 올린다.** VRAM 이 10GB 뿐이라 음성 LLM(4.9GB)과 동시에 못 올린다. 모드가 곧 적재
   프로파일이며 전환은 정지 중에만 한다(ADR-33 개정). *(2026-09-23 개정 — 아래)*
6. **실패는 기능 저하로 기록하고 주행에 영향을 주지 않는다** — Tier 3 규칙 유지.

**대안**

- **ⓐ 4bit 양자화로 VRAM 을 줄인다** — ❌ **실측에서 무너졌다.** 2.3GB 로 줄지만 쓰러진 작업자를 *"사람이
  없다"*, 넘어진 병을 *"없다"*, 멀쩡한 책상 사진을 *"줄무늬 셔츠가 옆으로 누워 있다"* 로 답했다. 미탐지와
  오경보가 동시에 생긴다.
- **ⓑ 클라우드 VLM** — 품질은 확실히 낫고 열린 질문도 답할 것이다. 그러나 ① 얼굴이 담긴 사진이 외부로
  나가고 ② 호출마다 과금되며 ③ 인터넷이 시연의 실패 지점이 된다. **사건이 확정된 뒤 1회 서술**에는 여전히
  선택지로 남긴다(FR-8.5 의 원래 자리).
- **ⓒ 제어 루프에 VLM 감독자를 둔다** (1초마다 방향 제안) — 판단 근거를 설명할 수 없고 시험 조합이 늘어난다.
  Tier 구분을 다시 그려야 한다. 넣지 않는다.
- **ⓓ 규칙만으로 쓰러짐 판정** (박스 종횡비) — **버리지 않는다.** 즉시·무료·설명 가능하므로 VLM 과 **함께**
  둔다. 사람이 쓰러진 것은 가장 급한 사건인데 0.4초짜리 경로 하나에만 맡길 이유가 없다.

**치르는 대가** — 모델 4.1GB 적재와 모드 전환 5.5초. 공장 모드에서는 자유 대화가 안 된다(화이트리스트
음성 명령은 유지). 구현 공수는 별도 산정한다.

**재검토** — 2B 판독이 실기 프레임(15cm 높이·VGA·JPEG 압축)에서 부족하다고 판명될 때. 그때는 ⓑ 를 사건
확정 시 1회 호출로 다시 본다. ⚠️ **아직 우리 카메라로 찍은 «진짜 위험 장면» 으로는 시험하지 않았다** —
위 두 장은 참고 사진이고, 조명·높이·해상도가 우리 조건과 다르다.

**재측정 (2026-09-20 · `4.8.0` 구현 중)** — 원자료
`TEST_MECHDOG/results/20260920_4.8.0-vlm-compare/`.

| 항목 | 09-17 | 09-20 | |
| :--- | ---: | ---: | :--- |
| VRAM | 4.1 GB | **4.11 GB** | 일치 |
| 질문당 | 0.2~0.9초 | **0.20~0.22초** | 일치 (첫 질문만 0.89초 — 워밍업) |
| 적재 | 5.5초 | **14.5초** | ⚠️ **어긋난다.** 3회 모두 14.5초로 편차가 없어 디스크 캐시 탓이 아니다 |

⚠️ **두 장 비교는 안 된다 — 이 ADR 이 쓰지 않은 길이지만 확인해 두었다.** 기준·현재를 나란히
넣으면 **같은 파일 두 장을 «동일하지 않다»** 고 답하고, 장면이 통째로 달라도 «변화 없음» 이라
답한다. 한 장이면 `yes` 도 나오는데 두 장이면 `no` 로 쏠린다. 그래서 FR-8.5 의 *"기준 이미지와
현재 이미지를 VLM 에 전송"* 은 **로컬 2B 로 실현할 수 없다** — 그 조항은 «클라우드 VLM» 을
전제로 쓰였고, 로컬로 내리면서 그 능력이 함께 빠졌다. FR-8.5 문서 갱신이 따로 필요하다.

**개정 (2026-09-23 · [ADR-38](#adr-38))** — **음성 LLM 이 없어졌다.** 이 ADR 이 기댄 «이미 있는 로컬 LLM» 두
군데를 고친다.

- **결정 3** — 한국어 문장은 LLM 이 아니라 **규칙 템플릿**이 만든다. `4.8.1` 은 VLM 항목 결과와 객체 목록
  차이를 고정 틀에 채운다. 영어 고정 항목으로 묻는다는 부분은 그대로다.
- **결정 5** — «음성 LLM(4.9GB)과 동시에 못 올린다» 는 상대가 없어졌다. **공장 모드에서만 올린다는 결정은
  유지한다** — VLM 을 쓰는 쓰러짐·변화 감지가 공장 모드의 기능이다(ADR-33 개정).
- **치르는 대가** 의 «공장 모드에서는 자유 대화가 안 된다» — 이제 어느 모드에도 자유 대화가 없다.

## ADR-36 · 전도 감지(NFR-2.4)를 **폐기한다** (Phase 2 이연 철회)

**상태** — **확정** (2026-09-20 · 팀장 결정 · 실측 근거). **관련:** NFR-2.4 · NFR-2.4.1 ·
`A-13` · [ADR-16](#adr-16) · WBS `3.2.3`(이연 철회) · `2.1.4` ② · `3.5.7` · OI-17 · OI-23.

**문제** — 2026-09-10 에 전도 감지를 *"버리는 것이 아니라 Phase 2 로 미룬다"* 고 적었다.
근거는 ① `A-13` 상시 인적 감시 ② QMI8658 드라이버가 선행이라 실질 2 M/D ③ 시연 환경의
전도 확률이 낮음 이었고, **IMU 드라이버가 `FR-6.3` 때문에 어차피 만들어지면 반나절이 된다**
는 전망 위에 서 있었다. 그 전망이 오늘 무너졌다.

**실측 (2026-09-20 · `mechdog-01`)** — **이 기체의 IMU 자세각을 믿을 수 없다.**

| 관측 | 값 | 기대 |
| :--- | :--- | :--- |
| `FAILSAFE` 로 **정지한** 로봇의 1초 평균 피치 | **2.47 ~ 83.01°** 사이를 배회 | 0° 근처 고정 |
| `POSE` 0 → -30 스윕의 IMU 피치 변화 | **2.3°** (2.85 → 0.55) | 약 -23° |
| 같은 스윕의 **카메라** 각도 변화 | **22.7°** (`y1` 85.3 → 269.8px) | — |
| 정지 중 롤 | **38°** | 0° 근처 |
| 정지 중 `yaw_rate_deg_s_avg` | **55 ~ 91 °/s** | 0 근처 (09-19 추종 런은 1.5~4) |

**즉 서 있는 로봇이 임계 60°를 혼자서 넘는다.** 전도 감지를 얹으면 **정상 보행 중에 서보
토크를 해제**한다 — 넘어지지 않은 로봇을 넘어뜨리는 기능이 된다. 2초 지속 조건도 막지
못한다(83° 구간이 1초 평균으로 여러 번 연속 찍힌다).

⚠️ **2026-09-18 에는 정상이었다** (`POSE -15` → IMU `-11.5`, 1:0.77 축척). **되던 것이 안
된다.** 원인은 미확인이며 이 ADR 은 그 원인을 규명하지 않는다 — 규명하더라도 아래 결정은
바뀌지 않기 때문이다.

**결정**

1. **NFR-2.4 전도 감지를 폐기한다. 이연이 아니다.** Phase 2 목록에서도 뺀다.
2. **2차 손상 방지는 `A-13`(상시 인적 감시) 아래 사람의 `ESTOP` 이 맡는다.** 이는 새 설계가
   아니라 **2026-09-10 이후 실제로 동작해 온 방식**이다 — 펌웨어는 `Fall detection is not
   implemented` 이고 `safety_monitor` 판정에도 전도가 없다. 이 ADR 은 **코드를 바꾸지 않고
   문서가 달고 다니던 숙제를 끊는다.**
3. **`safety.tip_angle_deg: 60` · `tip_duration_ms: 2000` 은 설정에 남긴다.** ⚠️ **전도 감지를
   위해서가 아니다** — `tools/mock_mechdog.py` 와 시험 5곳이 이 값으로 **«로봇이 `ONBOARD_
   FAILSAFE` 를 보고했을 때 호스트가 어떻게 처리하는가»** 를 검증한다. 그 경로는 링크두절·
   저전압으로 살아 있어야 한다. 지우면 시험 다섯 파일을 건드리고 얻는 것이 없다.
4. **딸린 숙제를 함께 닫는다** — `NFR-2.4.1`(임계값 산정 근거) 폐기, `OI-17`(앉기 자세 몸통
   피치 실측) 닫음, WBS `2.1.4` ② 의 목적 소멸, `3.5.7` 의 **«전도 감지와 충돌하지 않음»
   실기 확인 의무 해제**(충돌할 상대가 없다).

**대안**

- **ⓐ IMU 축 문제를 고친 뒤 원래대로 Phase 2 에 둔다** — ❌ 고쳐도 남는 것은 2026-09-10 의
  근거 셋이 그대로인 상태다. **오늘 실측은 「미루는 이유」 를 하나 더한 것이지 「해야 할
  이유」 를 더하지 않았다.** 목록에 남겨 두면 매 검토마다 다시 판단해야 한다.
- **ⓑ 임계를 60°에서 올린다** (예: 85°) — ❌ 값의 문제가 아니다. 정지 중 83°가 나오는 센서는
  **어떤 임계로도 의도된 자세와 전도를 가르지 못한다.** NFR-2.4.1 이 기대한 «빈 구간» 자체가
  존재하지 않는다.
- **ⓒ 박스 종횡비로 «쓰러진 로봇» 을 보는 시각 판정** — ❌ 카메라가 로봇 자신에게 달려 있다.
  넘어지면 카메라도 같이 넘어간다. [ADR-35](#adr-35) ⓓ 의 종횡비 판정은 **화면 안의 사람**에
  대한 것이고 여기에 쓸 수 없다.

**치르는 대가** — **넘어진 로봇의 서보가 사람이 `ESTOP` 을 누를 때까지 스톨 상태로 최대
토크·최대 전류를 쓴다.** 기어 톱니 파손·권선 과열·배터리 급방전의 위험이 남는다. 받아들이는
근거는 `A-13` 하나뿐이다 — **사람이 항상 보고 있다.**

**재검토** — **`A-13` 이 깨질 때.** 무인 운용으로 확장하는 논의가 나오면 이 ADR 을 `A-13` 과
**함께** 다시 연다. PRD `A-13` 이 이미 *"무인 운용으로 확장하면 안전 로직 전반을 재설계해야
한다"* 고 적어 두었고, 그 재설계 목록의 첫 줄이 이 항목이다.

## ADR-37 · 인증 창은 **말을 받았을 때만 · 상한 안에서 한 번** 늘린다 (타이머 정지 · 무조건 연장 미채택)

**상태** — **확정** (2026-09-22 · 실측 근거). **관련:** FR-10.3 · `auth.timeout_s` ·
`auth.verdict_grace_s` · [ADR-31](#adr-31) · WBS `3.8.2` · `4.5.3`.

**문제** — **방문객이 말하는 도중에 눈이 빨개진다.**

`AUTH_WAIT` 의 30초는 *상태에 머문 시간*만 잰다 (`fsm.TIMERS`). 그런데 음성 인증은
**말이 끝난 시각**과 **판정이 도착한 시각**이 다르다 — 파이프라인이 녹음(최대 15초) →
무음 1초 → 전사를 **직렬로** 하기 때문이다. 창이 열린 뒤에 말을 걸어도 판정이 30초를
넘겨 도착할 수 있고, 그때는 이미 `AUTH_FAILED` 가 나가 L3 다.

**실측 (2026-09-22 · `mechdog-01` · 실제 음성)**

| 관측 | 값 |
| :--- | :--- |
| 창이 열린 뒤 **통과 판정이 도착하기까지** (1회차) | **24.3초** |
| 같은 값 (2회차) | **18초** |
| 창(`auth.timeout_s`) | **30초** |
| 남은 여유 | **5.7 ~ 12초** |
| 같은 날 관측된 L3 2건의 원인 | **둘 다 시도 소진이 아니라 순수 30초 만료** |

시도 횟수 문제(창 밖의 발화가 시도로 세어지던 것)는 앞서 닫았지만, **창 자체가 짧다는
것은 손대지 않은 채였다.** 조금 길게 말하거나 GPU 가 조금 느리면 곧바로 경보다.

**결정**

1. **«판정이 오는 중» 을 별도 신호로 받는다** — `POST /api/command/auth` `{"result":
   "pending"}`. 파이프라인은 **첫 발화 프레임에서** 보낸다(`capture_pcm(on_speech=...)`).
   판정이 아니라 **창의 수명**만 건드린다 — 시도를 세지도, 사건을 내지도 않는다.
2. **상한을 둔다** — `auth.verdict_grace_s: 10`, 그리고 **대기 한 번에 1회만.** 같은
   신호를 계속 보내도 마감은 한 번만 밀린다.
3. **창 밖에서 시작된 발화는 유예를 사지 못한다** — 창이 열린 시각보다 앞선
   `captured_at_ms` 는 거절한다. 그렇지 않으면 앞서 막은 길이 옆문으로 되살아난다.
4. **엔진은 이유를 모른다** — `Behavior.defer_timer(by_ms, cap_ms)` 는 «얼마나 미룰 수
   있는가» 만 알고 어느 상태인지 묻지 않는다. 상태 이름이 엔진으로 돌아오면 `TIMERS`
   표를 둔 이유가 사라진다. 정책은 `Runtime.note_voice_listening` 에 있다.

**대안**

- **ⓐ `timeout_s` 를 30 → 45초로 늘린다** — ❌ **말이 없는 방문객에게도 45초가 된다.**
  아무 말 없이 서 있는 사람 앞에서 경보가 15초 늦어진다. 문제는 «창이 짧다» 가 아니라
  «말을 받아 둔 채 기다리는 시간이 창 밖에 있다» 이므로, 그 경우에만 늘리는 것이 맞다.
- **ⓑ 판정이 올 때까지 타이머를 멈춘다** — ❌ **경보를 영영 막는 길이 된다.** 침입자가
  소리만 계속 내면 로봇이 L2 에 붙박인다. **경보가 늦는 것보다 오지 않는 것이 나쁘다.**
  상한과 «창마다 1회» 가 이 결정의 본론이다.
- **ⓒ 파이프라인이 녹음을 짧게 끊는다** — ❌ 암구호를 끝까지 못 듣는다. 무음 1초 조건은
  이미 최소값에 가깝고, 전사 시간은 파이프라인이 줄일 수 있는 것이 아니다.
- **ⓓ 파이프라인이 «지금 `AUTH_WAIT` 인가» 를 먼저 보고 보낸다** — ❌ 같은 규칙이 두
  곳에 생긴다. 파이프라인이 물어본 순간과 창이 열리는 순간이 어긋나면 어느 쪽도 맞지
  않는다. **상태 판정은 호스트만 한다** — 파이프라인은 «말을 받았다» 는 사실만 보낸다.

**치르는 대가** — 최악의 경우 **경보가 10초 늦는다.** 창 안에서 말을 건 사람이 있을
때뿐이고 대기 한 번에 한 번뿐이지만, 그 10초는 실제로 늦는 시간이다. `A-13`(상시 인적
감시) 아래에서 받아들인다.

**재검토** — **전사 지연이 줄거나 늘 때.** 통과까지의 실측이 창의 절반 아래로 내려오면
유예를 줄이고, 반대로 유예까지 다 쓰고도 늦는 일이 관측되면 **유예를 늘리기 전에
파이프라인의 직렬 구조**(녹음이 끝나야 전사가 시작되는 것)를 먼저 본다.

**개정 (2026-09-23 · [ADR-38](#adr-38))** — ⚠️ **재측정 필요.** 위 실측(24.3초 · 18초)은 WonderEcho 녹음
(최대 15초 + 무음 1초 + 전사) 기준이다. 입력이 XIAO `:82` 스트림으로 바뀌면(`4.7.19`) 녹음·전사 시간이
달라진다. 결정 자체는 유지하고, 창의 여유는 `4.7.19` 에서 다시 잰다.

<a id="adr-38"></a>
## ADR-38 · 음성은 **규칙만** 쓰고, 듣기는 XIAO 마이크 · 말하기는 로봇 MP3 모듈로 옮긴다 (음성 LLM · 현장지원 · 로봇 경유 PCM 중계 미채택)

**상태** — **확정** (2026-09-23 · 사용자 결정 · 실측 근거) · **폐기와 규칙 전환은 코드에 반영됨** · **새 음성
경로는 XIAO `:82` 펌웨어만 완료**(`4.7.19~4.7.21` 미착수). **관련:** FR-10.2 · FR-11 · FR-12 ·
[ADR-20](#adr-20) · [ADR-31](#adr-31) · [ADR-33](#adr-33) · [ADR-34](#adr-34)(폐기) · [ADR-35](#adr-35) ·
[ADR-37](#adr-37) · WBS `3.4.4` · `3.5.5` · `3.5.6` · `4.7.4` · `4.7.6` · `4.7.8` · `4.7.9` · `4.7.14` ·
`4.7.19~4.7.21` · `4.8.1` · OI-6 · OI-10.

**문제** — `4.7.9` 는 WonderEcho 를 로봇 4핀에 다시 달고, 로봇이 I²C 로 PCM 을 왕복 중계해 **로봇에 달린
마이크·스피커**를 만들 계획이었다. 모듈을 USB 로 PC 에 꽂은 지금 구성은 **로봇이 돌아다니면 쓸 수 없다.**
2026-09-23 에 그 전제를 실측했더니 **0x34 브리지로는 음성 파형이 오가지 않았다.**

그래서 말하기는 로봇 I²C 의 MP3 모듈로 옮겨 가는데, 이 모듈은 **TF 카드에 미리 넣어 둔 문장만** 재생한다.
그러면 **그 자리에서 문장을 만들어 말하는 기능**이 전부 말할 길을 잃는다 — 음성 LLM 자유 대화, 현장지원
모드의 운영값 답변([ADR-34](#adr-34)), 로봇 상태 수치 답변(`4.7.10`), 타자로 친 임의 문장 방송(`4.7.14`).

**실측 ① 0x34 브리지 (2026-09-23 · `mechdog-01` · 로봇 IIC1)** — 원자료
`TEST_MECHDOG/results/20260923_4.7.9-bridge-transparency/`.

| 시험 | 결과 |
| :--- | :--- |
| 대기 중 `0x00`–`0xFF` 전부 읽기 | 전부 `00` |
| `0x6E` ← `FF 05` / `FF 01` | 매핑표의 고정 문구 **"Obstacle ahead"** / **"Recyclable waste"** 재생 |
| `0x70` ← `FF 05` ×2 | 무음 — 쓰기 무시. 바로 뒤 대조군 `0x6E ← FF 05` 는 다시 재생 |
| "Hello Hiwonder" → "Sit down" 발화 뒤 `0x64` 읽기 | 첫 읽기 `0C`(SIT-DOWN), 이후 `00` — **읽으면 지워지는 우편함** |
| 다른 4핀 포트에 연결 | `0x34` 가 보이지 않는다 — **IIC1 은 하나뿐** |
| MP3 모듈로 교체 | IIC1 에 `0x7B` · `0x7E`. 공장 기본 곡 재생은 확인했지만 어느 명령이 재생을 시작했는지는 가리지 못했다 |

**판정: 원안 불가.** 로봇 → 모듈은 매핑표의 고정 문구만, 모듈 → 로봇은 모듈이 인식한 명령어 id 만 오간다.
⚠️ **`0x64` 는 장치 주소가 아니다** — 0x34 모듈의 명령 id 우편함 레지스터다. 여러 문서가 «로봇 I²C(`0x64`)»
로 적었던 것을 이번에 정정한다. ⚠️ `0x7B` 는 I²C 예약 구간(`0x78`–`0x7F`)에 있어 스캔을 `0x77` 까지만 하면
보이지 않는다.

**실측 ② XIAO PDM 마이크 (2026-09-23 · GPIO42 CLK / GPIO41 DATA · 16 kHz)** — 원자료
`TEST_MECHDOG/results/20260923_xiao-mic/`.

| 조건 | 결과 |
| :--- | :--- |
| USB 단독 · 30 cm · 1 m | Whisper 인식 **6/6** — 이름 「김민수」 정확, 무음에서 빈 문자열 |
| Wi-Fi · 영상(`:81`)과 동시 | 음성 누락 **0**, 샘플률 15,925–16,068, DMA 넘침 **0**, 가장 긴 전송 정지 **218 ms**(DMA 여유 256 ms 안) |
| 같은 조건 · 30 cm 네 문장 연속 | **4/4** |

⚠️ **영상은 음성과 무관하게 약 2.5 Mbps 에서 막힌다.** 영상만 보낸 구간에서도 프레임이 31 KB 로 커지면
9.4 fps 까지 내려갔다. `4.2.2` 의 «VGA ≥ 15 fps» 는 음성과 별개로 재측정이 필요하다. ⚠️ 1 m 에서 rms(233~249)
가 무음(209)과 가깝다. 로봇 탑재(서보 소음) · 1 m 초과 · 공장 소음은 보지 않았다.

**결정**

1. **음성 LLM 을 폐기한다.** 로컬 LLM(EXAONE GGUF · llama.cpp) 적재와 답변, `SYSTEM` 프롬프트, `--model` ·
   `--tts orpheus` · `--dry-llm-only`, «기계 답변» 고지(`machine_guard`)를 코드에서 지웠다. 음성 경로는 **전부
   결정론적 규칙**(명령 · 시나리오 · 비상 · 암구호)이다. 규칙에 걸리지 않은 발화에는 **고정 문구 한 줄**로
   답한다 — `phrases.py` 의 `not_understood` 「잘 못 들었습니다. 다시 말씀해 주세요.」
2. **현장지원 모드(`assist`)를 폐기한다** — [ADR-34](#adr-34) 폐기. 운용 모드는 `guard` · `factory` 둘이다.
   지운 목록은 ADR-34 머리의 폐기 상자에 있다.
3. **로봇 상태 음성 응답(`4.7.10`)을 폐기한다.** 「메카독 배터리/거리 어때」 라우트(`robotlink.fetch_status` ·
   `is_status_query`), 상태 호출어(`status` 종류), `robot_briefing` 시나리오와 「상태보고」 트리거를 지웠다.
   상태 질문은 `not_understood` 로 간다.
4. **임의 문장 방송을 없앤다(`4.7.14` 축소).** `POST /say`, 관제 화면 음성 화면의 방송 입력칸 · 「말하기」 ·
   「긴급 방송」 버튼, `voice-link.js` 의 `say()` 를 지웠다. 발화 로그 · 대기/깨우기 · 시나리오 실행 · 문구
   라이브러리 · `/report` · `/status` · `/transcript` 는 남는다. ⚠️ **say 큐는 남았다** — `3.5.6` 단계 경고가
   `Hub.enqueue_say(urgent=True)` 로 계속 쓴다. 없앤 것은 외부 입구(`/say`)뿐이다. 그래서 `admin` 역할 라벨은
   「관제 방송」 → 「경고 방송」, 상태 칸은 「방송 대기」 → 「경고 대기」다.
5. **듣기와 말하기를 나눈다 (목표 구조).**

   | | 수단 | 상태 |
   | :--- | :--- | :--- |
   | 듣기 | XIAO ESP32S3 Sense 의 PDM 마이크 → 비전 펌웨어 포트 82 `/audio`(HTTP chunked, `audio/L16;rate=16000;channels=1`, PCM16LE 모노, `?gain=0..4` 기본 2) → PC Whisper | 펌웨어 완료(2026-09-23) · 파이프라인 입력은 `4.7.19` |
   | 판단 | PC 의 규칙 → 로봇 API(화이트리스트 명령만) | 동작 중 |
   | 말하기 | 로봇 IIC1 의 MP3 모듈(`0x7B`)이 TF 카드의 문장 트랙을 재생. 음원은 Piper 로 미리 합성 | `4.7.20` · `4.7.21` |

   ⚠️ **지금 코드는 아직 WonderEcho USB COM 링크(임시)** 로 Piper 음성을 실시간 합성해 재생한다. 목표 경로가
   붙을 때까지의 시제품 경로다.
6. **MP3 드라이버는 자체 코드로, 센서 HAL 을 거쳐 만든다.** IIC1 은 IMU(`0x6A`) · 초음파(`0x77`)와 공유하는
   안전 버스다. 벤더 SDK 의 `MP3Sensor` 예제는 쓰지 않는다([ADR-20](#adr-20)).

**남는 제약** — 기록만 한다. 이번에 고치지 않는다.

- **동적 문장** — MP3 는 미리 녹음한 문장만 낸다. 코드에 남은 동적 문장은 둘이다: `scenarios.sc_guard` 의
  `"{hit} 님, ..."`(명단 이름 되읽기), `scenarios.sc_emergency_response` 의 `"{answer} 위치로 접수했습니다..."`
  (위치 되읽기). 지식 문서 본문을 붙이는 공지·안내 시나리오(교대 · 식사 · 설비 점검 · 길안내 등)는 본문이 정적
  파일이라 미리 합성할 수 있다. 처리 방침은 `4.7.21` 이 정한다.
- **`3.5.6` 과 트랙 번호** — `3.5.6` 은 문구 ID(정수)를 버리고 `config.escalation.sound.l3_warning` 에 한국어
  문장을 두었다. MP3 는 **트랙 번호**로 재생한다. 방향: 한국어 문장이 계속 정본이고, `4.7.21` 이 **문장 →
  트랙 번호 표**를 만들어 재생 직전에 바꾼다. 호스트 ↔ 음성 프로세스 사이 계약은 문장 그대로다. 표에 없는
  문장은 재생할 수 없으므로 제작 도구가 누락을 검사한다.
- **[ADR-37](#adr-37) 의 실측 근거는 WonderEcho 녹음 기준**(최대 15초 + 무음 1초 + 전사)이다. XIAO 스트림
  입력으로 바뀌면 재측정한다. 결정은 유지한다.

**대안**

- **ⓐ 음성 LLM 유지 (자유 대화)** — ❌ MP3 는 미리 녹음한 문장만 내므로 **생성 문장을 말할 수 없다.** 시연
  범위에 자유 대화가 필요한 장면도 없다. 결정론적 규칙만 남기면 **모든 응답을 시험으로 고정할 수 있다** —
  LLM 이 있던 동안에는 규칙에 안 걸린 발화가 LLM 으로 새서, 거리를 물었는데 지어낸 거리가 나간 일이 있었다
  (`4.7.10` 실기 기록).
- **ⓑ 로봇 I²C 경유 PCM 중계 (`4.7.9` 원안)** — ❌ 실측 ① 로 불가 판정. 0x34 브리지는 명령 id 만 오간다.
- **ⓒ WonderEcho 를 USB 로 PC 에 직결한 채 운용** — ❌ 로봇이 돌아다닌다. 케이블이 로봇을 PC 옆에 묶는다.
  목표 경로가 붙을 때까지의 임시 링크로만 둔다.
- **ⓓ 0x34 모듈의 고정 문구만 쓴다** (`0x6E ← type, id`) — ❌ 매핑표의 문구는 "Obstacle ahead" 같은 **영어
  고정 문구**다. 한국어 문장이 없다.
- **ⓔ 현장지원 모드 유지** — ❌ 생산량 · 납기 · 설비 상태는 **계속 바뀌는 값**이라 미리 녹음할 수 없고,
  [ADR-34](#adr-34) 규칙 3 이 전제한 음성 LLM 도 없어졌다. ADR-34 스스로 부가기능이라 적었다.
- **ⓕ 상태 음성 응답 유지** — ❌ 거리 · 배터리 실측값은 미리 녹음할 수 없다. 시연에서 말로 보여 줄 이유도
  없다(사용자 판단) — 배터리와 전방 거리는 관제 화면 텔레메트리에 이미 나온다.
- **ⓖ 임의 문장 방송 유지** — ❌ 타자로 친 문장은 TF 카드에 없다. 관제자가 낼 문장은 문구 라이브러리와
  시나리오로 미리 만든다. 단계 경고는 내부 큐로 남는다(결정 4).

**치르는 대가**

- **자유 대화를 잃는다.** 규칙 밖 발화에는 모두 같은 한 줄로 답한다.
- **끝냈던 일을 지운다** — `4.7.10`(실기 완료 2026-09-23) · `4.7.15~4.7.17`(구현 완료 2026-09-22).
- **문장을 바꾸려면 TF 카드를 다시 만든다.** 문구 라이브러리를 고치면 합성과 복사가 따른다(`4.7.21`).
- **목표 경로가 아직 없다.** 이번에 들어간 것은 XIAO `:82` 펌웨어뿐이다. 문제에 적은 «로봇이 돌아다니면 못
  쓴다» 는 `4.7.19~4.7.21` 이 끝나야 풀린다.
- **WBS** — 번호와 공수는 WBS 가 정본이다.

  | 항목 | 변경 | M/D |
  | :--- | :--- | ---: |
  | `3.4.4` 운용 모드 | 현장지원 제거 | 1.5 → **1.0** |
  | `4.7.9` 로봇 탑재 오디오 중계 | 불가 판정 완료 | 3.0 → **0.5** |
  | `4.7.10` 로봇 상태 음성 응답 | 폐기 (행 삭제) | 1.0 → 삭제 |
  | `4.7.14` 관제 음성 콘솔 | 방송 제거 | 2.0 → **1.5** |
  | `4.7.15~4.7.18` 현장지원 | 폐기 (행 삭제) | 3.0 → 삭제 |
  | `4.7.19` XIAO 음성 입력 전송층 | 신규 | **1.0** |
  | `4.7.20` 로봇 MP3 모듈 드라이버(`0x7B`) | 신규 | **1.5** |
  | `4.7.21` TF 카드 문장 제작 | 신규 | **0.5** |

  총 95.0 → **90.5 M/D** (현장지원 폐기 -3.5 · 음성 재편 -1.0). `4.7.4` · `4.7.6` · `4.7.8` · `4.8.1` 은
  공수를 그대로 두고 서술만 바꾼다 — 로컬 LLM 을 빼고, `4.8.1` 은 규칙 템플릿 문장으로 만든다.

**재검토**

- **MP3 모듈로 필요한 문장을 낼 수 없다고 판명될 때** — 재생 시작 명령 · 트랙 선택이 `4.7.20` 에서 확정되지
  않거나, 단계 경고와 시나리오 문장을 TF 카드 트랙으로 다 담지 못할 때. 그때는 말하기 수단부터 다시 고른다.
- **로봇에 스피커로 음성을 스트리밍할 수단이 생길 때.** 그때 생성 문장이 필요한지 다시 보되, **규칙 밖 발화가
  명령 · 인증 · 해제로 이어지지 않는다**는 선은 유지한다.
- **XIAO 마이크가 로봇 탑재 소음에서 암구호 · 명령을 못 알아들을 때** (`4.7.19` 실측) — 듣기 수단을 다시 본다.

<a id="adr-39"></a>
## ADR-39 · 명령 타임아웃(FR-1.3)을 **300ms → 600ms** 로 늘린다 (시연·개발 운용 한정)

**상태** — **확정** (2026-09-23 · 실측 근거). **관련:** FR-1.3 · NFR-2.1 · `safety.cmd_timeout_ms` ·
펌웨어 `kCommandTimeoutMs` · FR-1.5(링크 두절 3초는 그대로).

**문제** — **호스트가 제때 보내는데도 로봇이 스스로 래치한다.** 2026-09-23 17:38 이후
`mechdog-01` 이 `ONBOARD_FAILSAFE` 를 반복했다 — 해제 1초 안에 다시 걸린 적도 있다.
시리얼(`COM8`)로 사유를 확정했다:

    19:47:09.980 CMD: seq=89880 STOP
    19:47:10.278 FAILSAFE: command timeout >= 300 ms
    19:47:10.362 CMD: seq=89881 STOP      ← 382ms 만에 도착

- 호스트 송신 간격은 그 초에 최대 103ms 였다 (`cmd_gap_ms_max`). **호스트는 늦지 않았다.**
- `seq` 가 끊기지 않았다. **유실이 아니라 무선 구간 지연**이다.
- 로봇이 래치돼 서 있을 때도 ping 이 튄다 — 40회 평균 12ms · **최대 292ms**. 보행·카메라
  (`--no-vision` 으로 끊어도 재현)·WonderEcho 모듈(빼도 재현)과 무관하다.
- 호스트 PC 는 유선이고 로봇만 무선이다. 로봇 Wi-Fi 절전은 이미 꺼져 있다(`WiFi.setSleep(false)`).

10Hz 송신에 300ms 기준이면 **연속 두 주기**만 늦어도 걸린다. 이 현장의 2.4GHz 는 그만큼의
지연 스파이크를 수시로 낸다.

**결정** — `cmd_timeout_ms` 와 펌웨어 `kCommandTimeoutMs` 를 **600ms** 로 올린다. 설정 검증의
상한(`config.py`)도 600 으로 옮긴다. 링크 두절 3초(FR-1.5)와 «명령 정지가 링크 페일세이프보다
먼저» 라는 순서 제약은 그대로다.

**대가** — 송신이 정말 멈췄을 때 로봇이 **최대 0.3초 더** 마지막 보행 명령으로 걷는다.
보폭 60mm · 약 3.3 걸음/s 기준으로 **약 6cm** 더 나간다. 온보드 25cm 장애물 정지와 사람의
`ESTOP`(A-13 상시 인적 감시)은 그대로 살아 있다.

**미채택**
- *송신을 20Hz 로 올린다* — 지연이 한 패킷이 아니라 **구간 단위**(수백 ms)로 오므로 촘촘히
  보내도 같은 구멍에 함께 갇힌다.
- *공유기 채널·위치로 푼다* — 현장마다 다르고 시연장에서 통제할 수 없다. 가능하면 병행한다.

**범위** — 이 프로젝트는 시연·개발용이다(PRD `A-13` 상시 인적 감시 전제). **무인 운용으로
확장하면 이 값부터 다시 연다** — 그때는 링크 품질 자체(전용 AP·5GHz·유선 중계)로 푼다.

**재검토** — 600ms 에서도 무선 지연 래치가 관측되면 값을 더 올리기 전에 **링크를 먼저** 본다.
