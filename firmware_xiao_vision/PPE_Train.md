3. no_helmet 검출력이 낮은 원인으로 유력하며 다음 학습에서 제거한다
4. no_vest 가 vest 의 두 배다. 조끼 오알람의 원인으로 의심된다

## 2. 학습 모델 엔진과 검출 조건

### 2.1 모델

1. YOLOX-Nano, Apache-2.0, Megvii Inc.
2. ultralytics 계열은 쓰지 않는다. AGPL-3.0 이라 팀 코드 전체가 공개 의무에 걸린다(ADR-24)
3. 1단 COCO 검출기와 같은 계열이라 전처리와 디코딩 어댑터를 그대로 재사용한다

### 2.2 학습 설정

1. 사전학습 가중치 yolox_nano.pth (릴리스 0.1.1rc0) 에서 fine-tune
2. 입력 640x640. 호스트 어댑터가 640 격자로 디코드하므로 바꿀 수 없다
3. 100 epoch, batch 16, fp16
4. SGD momentum 0.9, lr 0.01, cosine decay, warmup 5 epoch
5. mosaic 은 마지막 15 epoch 에서 끈다
6. HSV 채도 게인을 30 에서 15 로 낮췄다. 주황과 형광이 판정 단서라 색을 크게 흔들면 특징이 지워진다
7. Google Colab T4 에서 약 3시간

### 2.3 산출물

1. models/ppe.onnx, 3,677,797 bytes (릴리스 태그 ppe-v2)
2. sha256 ff78802506e07dfcf89961374900486d363e558fff4fe81ce6053c3330d4a1c4
3. 입력 images [1, 3, 640, 640], 출력 output [1, 8400, 10]
4. 10 은 중심 오프셋 2, 크기 2, objectness 1, 클래스 5 의 합이다
   ⚠️ v2(2026-09-23)부터 5클래스(person_down 포함)다. 데이터셋 구성은
   아래 §1과 다르다 — 자체 시뮬+Construction-PPE+SHWD (`models/NOTICE` §3)
5. 디코드 전 원시 출력이다. 격자 디코드는 호스트 어댑터가 한다
6. config.yaml 의 vision.ppe.model_family 를 yolox 로 채우고 학습 정보를 주석으로 남겼다

### 2.4 전처리 규약

1. 0~255 값을 그대로 넣는다. 0~1 정규화를 하면 검출이 전부 사라진다
2. BGR 순서를 유지한다
3. letterbox 는 좌상단 정렬이고 여백은 114 로 채운다

### 2.5 실행 구조

1. 1단 COCO 검출기가 사람을 찾은 프레임에서만 PPE 모델이 돈다
2. 사람이 없으면 PPE 추론을 하지 않는다. 배경 오검출을 원천 차단한다
3. PPE 모델 입력은 풀프레임이 아니라 person bbox 크롭이다
4. 판정 단위는 사진이 아니라 추적 ID 다

### 2.6 판정 세 갈래

1. 확인불가를 먼저 판정하고 나머지를 적합과 위반으로 가린다
2. 확인불가는 머리 박스 없음, 몸통 박스 없음, 머리 박스 상단이 프레임 상단 8px 이내 중 하나다
3. 위반은 머리와 몸통이 모두 보이고 no_helmet 또는 no_vest 가 검출된 경우다
4. 적합은 머리와 몸통이 모두 보이고 helmet 과 vest 만 있는 경우다
5. 근거 없이 위반으로 보내면 L3 경보가 뜨고 관리자 확인으로만 풀린다. 그래서 확인불가를 포괄 범주로 둔다
6. 확인불가는 자세 상승으로 재시도하고 2회를 넘기면 PPE_UNDETERMINED 를 기록하고 순찰을 재개한다

### 2.7 검출 임계값

1. conf_threshold 0.5, iou_threshold 0.45
2. head_margin_px 8
3. 위반 확정은 1,500ms 안에 3회다. 프레임 수가 아니라 시간 창이다
4. 알람은 하나다. 안전모만 미착용이든 조끼만이든 둘 다든 같은 PPE_VIOLATION 이벤트로 L3 에 진입한다

## 4. 네크 포인트: ESP32-S3 전원 유지 불가

### 4.1 증상

1. 보조배터리에 연결하면 몇 초 뒤 XIAO 전원이 끊긴다
2. 보조배터리의 저전류 자동 차단이다. 부하가 50~100mA 아래로 떨어지면 출력을 끊는다
3. XIAO 는 카메라를 돌려도 150~250mA 수준이고 Wi-Fi 접속 전에는 더 낮아 그 경계에 걸린다

### 4.2 전원 차단 이후 카메라 무응답

1. 전원이 끊긴 이후 카메라 센서가 SCCB 에 응답하지 않는다
2. 차단 이전에는 같은 코드로 CHIP_ID 0x3660 을 읽고 VGA 프레임 13,606바이트를 받았다
3. 차단 이후에는 주소 0x3C 가 한 번도 응답하지 않는다
4. XCLK 20MHz, 16MHz, 10MHz, 8MHz 를 모두 시도했고 전부 실패했다
5. I2C 속도와 클럭 유무를 바꿔도 결과가 같다

### 4.3 배선 단계 측정

1. SDA 와 SCL 은 내부 풀업에서 HIGH 로 읽힌다
2. 데이터선 D0 부터 D7 까지 여덟 개가 내부 풀업에도 전부 LOW 다
3. VSYNC, HREF, PCLK 도 LOW 다
4. 리본이 완전히 빠졌다면 이 핀들은 풀업으로 HIGH 가 되어야 한다
5. 신호 경로는 연결되어 있고 센서에 전원이 공급되지 않는 상태로 해석된다

### 4.4 현재 상태

1. 리본 재장착과 전원 재인가로는 복구되지 않았다
2. 2026-09-18 21시 기준 미해결이다
3. USB 연결이 잡히지 않아 추가 진단도 중단된 상태다

### 4.5 부수적으로 확인한 펌웨어 문제

1. 카메라가 살아 있을 때도 esp_camera_init 이 간헐적으로 실패했다
2. 코어 2.0.17 에서는 0x105 ESP_ERR_NOT_FOUND, 3.3.11 에서는 0x106 ESP_ERR_NOT_SUPPORTED 가 나온다
3. 두 오류 모두 배선 불량과 구분되지 않아 멀쩡한 하드웨어를 의심하게 만든다
4. OV3660 은 XCLK 가 돌기 시작한 뒤에야 SCCB 에 답하는데 드라이버는 클럭을 켜자마자 ID 를 읽는다
5. 초기화 전에 XCLK 를 200ms 돌리고 SCCB 를 한 번 열어 두면 통과한다
6. warmUpSensorClock 함수로 펌웨어에 반영했고 초기화 재시도를 3회 넣었다
7. 부팅마다 SENSOR_PROBE chip_id 를 찍는다. 0x3660 이면 센서 정상, 0x0000 이면 연결 문제다

### 4.6 다음 조치

1. 멀티미터로 카메라 모듈 전원 핀 전압을 측정한다
2. 0V 에 가까우면 확장 보드 전원부 문제, 정상 전압이면 센서 자체 문제다
3. 여분 카메라 모듈이 있으면 교체해 원인을 확정한다
4. 실기 테스트에서는 보조배터리 대신 PC USB 나 벽 충전기로 급전한다
5. 보조배터리를 쓸 경우 저전류 모드를 켜거나 다른 기기를 함께 물려 부하를 올린다

## 6. 향후 테스트 절차

ESP32-S3 카메라 전원이 유지되는 것을 전제로 한다. 위에서부터 순서대로 진행한다.

### 6.1 카메라 복구 확인

1. XIAO 를 USB-C 데이터 케이블로 PC 에 연결한다. 보조배터리는 저전류 차단 때문에 쓰지 않는다
2. 시리얼 115200 으로 부팅 로그를 읽는다
3. SENSOR_PROBE chip_id=0x3660 이 나오면 센서가 살아난 것이다
4. CAMERA_READY, WIFI_READY, HTTP_READY 세 줄이 모두 나오는지 확인한다
5. PC 에서 curl http://192.168.0.22/ 로 상태 API 가 응답하는지 확인한다
6. sensor 가 OV3660 으로 찍히면 준비 완료다

### 6.2 카메라 장착 조건 맞추기

1. 카메라를 실제 운용 조건인 높이 15cm 에 고정한다
2. 하향 7도로 기울인다
3. 장착 방향이 뒤집혔으면 /orient?rot=180 으로 바로잡고 config 의 mount_rotation 에 기록한다
4. 장착을 바꾸면 화각이 달라지므로 자세 상승 단계별 최소 판정거리도 다시 재야 한다

### 6.3 실기 판정 관찰

1. 브라우저로 카메라 주소를 직접 열지 않는다. 스트림은 한 클라이언트만 받는다
2. tools/ppe_live_check.py 를 실행한다. 이 도구는 로봇에 명령을 보내지 않는다
3. 브라우저로 http://127.0.0.1:8088/ 을 열어 판정이 그려진 화면을 본다
4. 초록이 적합, 빨강이 위반, 주황이 확인불가다
5. 이 개발 PC 는 0.5fps 라 위반 확정 창을 20초로 늘려서 관찰한다
6. 종료 시 MD 보고서가 생성되며 알람 이력과 프레임별 판정이 기록된다

### 6.4 네 조합 시험

1. 안전모와 조끼를 모두 착용하고 적합이 나오는지 본다
2. 안전모만 착용하고 위반이 나오는지 본다
3. 조끼만 착용하고 위반이 나오는지 본다
4. 둘 다 미착용하고 위반이 나오는지 본다
5. 각 조합을 1m, 2m, 3m 세 거리에서 반복한다
6. 웅크린 자세, 팔 들기, 몸 기울이기도 포함한다

### 6.5 경계 조건 시험

1. 1m 안쪽으로 접근해 머리가 화면 위로 잘리는 상태를 만든다
2. 확인불가 판정과 머리 클리핑 사유가 뜨는지 확인한다
3. 이 경로는 실기에서 자세 상승으로 이어지는 지점이라 반드시 확인한다
4. 프레임에서 사람이 완전히 빠진 배경 상태를 몇 분 유지한다
5. 배경에서 위반 클래스가 뜨는 비율을 잰다. 공개 데이터 검증에서 재지 못한 항목이다
6. 역광과 어두운 조명에서도 같은 조합을 반복한다

### 6.6 검증셋 촬영

1. 서로 다른 세 장소에서 같은 조건표로 촬영한다
2. 거리 세 종류, 착용 조합 네 종류를 모두 포함한다
3. 머리가 프레임 상단에 잘리는 샷을 20장에서 30장 확보한다
4. 사람 없는 배경 프레임을 장소당 100장에서 200장 확보한다
5. 장소 단위로 분리해 데이터 누수를 막는다
6. 촬영한 프레임에 라벨을 달아 검증셋을 만든다

### 6.7 성능 판정

1. 촬영한 XIAO 실사 검증셋으로 3분류 판정을 다시 잰다
2. no_helmet 과 no_vest 의 recall 을 본다. 통과 기준은 0.90 이다
3. 정상 착용자에게 알람이 뜨는 오알람률을 함께 잰다
4. 배경 프레임에서 위반이 뜨는 비율을 잰다
5. 추론 속도는 기준 PC 인 RTX 3080 에서 측정한다
6. 이 결과가 FR-9 의 확정 판정이다. 공개 데이터 수치는 참고값이다

### 6.8 결과에 따른 분기

1. 통과하면 ppe_detector.py 구현으로 넘어간다
2. no_helmet recall 이 부족하면 안전모만 미착용 조합의 학습 데이터를 보강한다
3. 오알람이 높으면 정상 착용 사진을 늘려 vest 와 no_vest 비율을 맞춘다
4. 머리 라벨이 없는 544장을 제거한 데이터셋으로 재학습한다
5. 재학습은 기존 가중치에서 이어서 40 epoch 만 돌리면 약 100분이다
6. 재학습 후 같은 검증셋으로 다시 재서 개선 여부를 비교한다
