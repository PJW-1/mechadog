## 무엇이 빠져 있었나

펌웨어는 `LED` 명령을 받아 적용할 수 있었고(#208), `escalation.presentation()` 은 단계별
색과 점멸을 **이미 계산하고 있었다.** 그런데 그 값이 **로그에만** 쓰였다 — 호스트 전체에
`once("LED", ...)` 호출이 **하나도 없었다**(시험 파일 제외).

결과적으로 순찰 중 눈은 펌웨어 기본값 `{0,0,255}` = **파랑에 머물렀다.** L0 이 파랑이라
겉보기에는 맞아 보이지만, L1~L3 에서 색이 바뀌지 않는다.

## 판정 — 5단계 전부 통과

에스컬레이션 전이는 `escalation_log.txt` 에 있고, **색은 운용자가 눈으로 확인**했다.

| 단계 | 색 | 로그 | 육안 |
| :--- | :--- | :--- | :---: |
| L0 순찰 | blue 상시점등 | `F → L0 failsafe_confirmed led=blue` (02:44:48) | ✅ |
| L1 관찰 | yellow 상시점등 | `L0 → L1 person_present led=yellow` (03:02:53) | ✅ |
| L2 인증요구 | orange 상시점등 | `L1 → L2 unauthenticated_hold led=orange` (02:56:08) | ✅ |
| L3 경보 | red **2Hz 점멸** | `L2 → L3 AUTH_FAILED led=red` (02:56:38) | ✅ 점멸 확인 |
| F 페일세이프 | white 상시점등 | `L0 → F ONBOARD_FAILSAFE led=white` (03:02:17) | ✅ |

**결정적인 것은 노랑·주황·빨강이다.** 펌웨어 기본값이 파랑이므로 **호스트가 보내지 않으면
나올 수 없는 색**이고, 배선 전 실기에서는 실제로 계속 파랑이었다.

### 해제 후 복귀

`RESET_SAFE` 로 래치를 푼 뒤 눈이 **파랑(L0)** 으로 돌아오는 것을 확인했다(02:44:48 · 03:02:37).
래치 중 흰색은 **온보드가 덮는다** — 링크가 끊겨 `F` 로 갔다면 호스트는 색을 보낼 수 없기
때문이며, 호스트는 그 자리에서 흰색을 만들지 않는다.

### 미등록 색 거부

[#208 보고서](../20260918_4.7.3-eye-led/report.md) 가 `magenta` 로 확인했다(`applied=false`).
`4.7.3` 의 완료 기준 밖이라 여기서 다시 하지 않았다.

## 관찰됐으나 이번 범위 밖

**검출 공백이 대상 상실 임계를 넘을 수 있다.** 운용자가 *"bbox 가 자주 깜빡이는데 한 번
깜빡였다고 바로 빨강이 되면 안 되지 않나"* 고 지적했다. 확인 결과 **유예는 이미 5초**이고
(`fsm.target_lost_timeout_s` · FR-3.7), 기준이 게이트 확정이 아니라 **실제 검출 시각**이라
단발 깜빡임으로는 걸리지 않는다.

다만 09-18~19 로그의 공백 분포는 **43회 · 중앙값 1,441ms** 이고 그중 **5초를 넘긴 것이
일곱**이다(8.7 · 10.7 · 14.2 · 16.1 · 17.5 · 28.8 · 31.5초). 이것이 *"깜빡임"* 인지 *"정말
자리를 떴다"* 인지는 **이 데이터로 가르지 못한다.**

공백의 알려진 원인은 카메라가 바닥을 보는 자세와 **몸이 프레임에 잘리는 것**이며, 후자는
`3.5.7` 단계적 자세 상승이 다루는데 아직 미구현이다. **임계를 늘리는 것은 대가가 있다** —
`fsm.target_lost_timeout_s` 는 FSM 의 대상 상실과 같은 키이고, 늘리면 오경보는 줄지만
미인증자가 빠져나갈 시간도 함께 늘어난다. `3.5.7` 로 공백이 줄어든 뒤 다시 본다.
