## 1. 이 시스템의 구성

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **호스트 PC** (Host PC) | 여러분의 노트북. 시스템의 **머리** | 카메라 영상 분석, 다음 행동 결정, 대시보드. `host/` 폴더 코드가 전부 여기서 돈다 |
| **모션 노드** | 로봇 몸통의 ESP32. 시스템의 **몸** | 다리를 움직이고, 초음파로 벽을 보고, 배터리를 감시한다 |
| **비전 노드** | 로봇에 붙인 카메라(XIAO). 시스템의 **눈** | 영상만 Wi-Fi 로 쏜다. 판단은 하지 않는다 |
| **온보드** (onboard) | **로봇 안에서** 도는 것 | 반대말은 "호스트에서" 다. 안전 판정은 온보드에 있어야 한다 |
| **HAL** (Hardware Abstraction Layer) | 하드웨어를 부르는 **창구**를 한 곳으로 모은 층 | 벤더 라이브러리(`HW_MechDog`)를 감싸서, 위쪽 코드가 하드웨어를 직접 만지지 않게 한다 |
| **Tier 1 / 2 / 3** | 판단을 **얼마나 급한지**로 나눈 3단 | Tier 1 = 로봇이 즉시(안전), Tier 2 = 노트북이(판단), Tier 3 = 클라우드가(리포트) |
| **기준기** (REF) | 팀의 **표준 로봇 1대** | 3대의 개체차 때문에 검수는 항상 이 한 대로 한다 |
| **기준 PC** | 성능 수치를 재는 **표준 노트북** | 팀장 PC. "빠른 PC 에서만 되는 것"을 성능 달성으로 세지 않기 위함 |

## 2. 로봇이 무엇을 하는지

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **FSM** (유한 상태 기계) | 로봇이 **지금 뭐 하는 중인지**를 이름표로 관리하는 방식 | `PATROL`(순찰) · `ALERT`(경계) 처럼 13가지. 조건이 맞으면 다음 이름표로 넘어간다 |
| **상태 전이** | 이름표가 **바뀌는 것** | "순찰 중에 사람을 3프레임 연속 발견하면 경계로" 같은 규칙. 표로 정리해 뒀다 (PRD 5절) |
| **에스컬레이션** | 대응을 **얼마나 세게 할지**의 단계 | L0(정상) → L1(관찰) → L2(인증요구) → L3(경보). 눈 LED 색으로 보인다 |
| **페일세이프** (fail-safe) | 문제가 생기면 **스스로 안전한 쪽으로** | 통신 끊김·저전압·넘어짐 → 멈추고 힘을 뺀다. 사람이 리셋해야 다시 움직인다 |
| **E-Stop** | 비상정지 버튼 | 대시보드에 항상 보이게 둔다. 어떤 상태에서든 최우선 |
| **PPE** | 안전 보호구 (안전모·조끼) | 미착용을 카메라로 잡는 것이 이 프로젝트의 산업안전 기능이다 |
| **워치독** (watchdog) | 프로그램이 멈추면 **자동으로 재시작**시키는 감시견 | ESP32 기능. 무한루프에 빠져도 1초 내 리셋된다 |

## 3. 노트북과 로봇이 대화하는 방식

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **프로토콜** (규약) | 서로 알아들을 **말의 규칙** | 정본은 [PROTOCOL.md](PROTOCOL.md). 한 줄 JSON 을 주고받는다 |
| **텔레메트리** | 로봇이 보내는 **상태 보고서** | 0.1초마다 1줄. 배터리·거리·기울기·상태. **로봇은 파일 로그를 안 남기므로 이게 곧 로그다** |
| **UDP** | 빠르지만 **도착을 보장하지 않는** 전송 방식 | 순서가 뒤바뀌거나 사라질 수 있어서 `seq` 로 걸러낸다 |
| **`seq`** | 보낸 순서를 세는 **번호표** | 이전보다 작은 번호가 오면 옛 패킷이므로 버린다 |
| **클램핑** (clamping) | 범위를 벗어난 값을 **잘라서** 쓰기 | `step: 500` → `100`. 버리지 않는 이유는 "명령이 조용히 사라지는 것보다 낫기" 때문 |
| **폐기 + WARN** | 버리되 **경고 기록은 남기기** | 모르는 명령이 왔을 때. 죽지 않고 넘어가므로 새 기능 추가가 안전해진다 |
| **additive / breaking** | **더하기 변경 / 깨뜨리는 변경** | 새 명령 추가는 안전(모르면 무시). 이름·단위 변경은 양쪽을 동시에 고쳐야 한다 |
| **MJPEG** | 사진을 연달아 보내 영상처럼 보이게 하는 방식 | 카메라가 `:81/stream` 으로 15fps 송출 |

## 4. 로봇이 어디 있는지 아는 방법

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **측위** (localization) | 로봇이 **자기 위치를 아는 것** | Phase 1 에서는 안 쓴다. 방식이 아직 미결 (LiDAR vs 스마트폰) |
| **SLAM** | 돌아다니며 **지도를 만들고 동시에 자기 위치를 찾는** 기술 | Phase 2. LiDAR 를 달면 시도한다 |
| **LiDAR** | 레이저로 **주변 거리를 한 바퀴 재는** 센서 | FHL-LD19. 발주 대기 중 |
| **VIO** | 카메라 흔들림으로 **움직인 거리를 추정**하는 방식 | 스마트폰을 얹는 대안 경로 |
| **ArUco 마커** | 흑백 사각형 **인쇄 코드** (QR 사촌) | 사원증 인증과 구역 표시에 쓴다. A4 로 출력하면 비용 0 |
| **웨이포인트** | 지나가야 할 **좌표 점** | Phase 2 구역 순찰 경로 |

## 5. 카메라로 사람을 찾는 방법

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **추론** (inference) | 학습된 모델에 사진을 넣어 **답을 얻는 것** | "이 사진에 사람이 있나" 를 노트북이 판단한다 |
| **bbox** (바운딩 박스) | 찾아낸 대상을 감싼 **네모 상자** | 좌표만 있고 거리(미터)는 없다. 그래서 판정을 상자 크기·위치로 한다 |
| **클리핑** | 대상이 화면 밖으로 **잘린 상태** | 카메라가 지면 15cm 에 있어 머리가 잘린다. 그때 자세를 올려 다시 본다 |
| **ONNX** | 여러 프레임워크에서 **공통으로 쓰는 모델 파일 형식** | 학습은 어디서 하든 실행은 이 형식으로 통일한다 |
| **실행 프로바이더** (EP) | 모델을 **어느 장치로 돌릴지** 고르는 설정 | DirectML(GPU) → CUDA → CPU 순으로 되는 것을 쓴다 |
| **DirectML** | 윈도우에서 **어느 회사 GPU 든** 쓰게 해주는 층 | 팀원 GPU 가 NVIDIA·AMD·Intel 로 달라서 이걸 골랐다 |
| **NMS** | 같은 대상에 겹쳐 잡힌 상자를 **하나로 정리** | 검출 후처리 단계 |
| **추적** (tracking) | 프레임이 바뀌어도 **같은 사람임을 유지** | 각 사람에게 `track_id` 를 붙인다. 인증을 그 ID 에 귀속시킨다 |
| **개방 어휘** (open-vocabulary) | 학습하지 않은 물체도 **이름을 말하면 찾는** 모델 | 변화 감지 후보 기술. 선정 미결 (OI-15) |

## 6. 개발·품질 관리

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **WBS** | 할 일을 **잘게 쪼갠 목록** | 이 프로젝트의 모든 작업이 번호로 있다 (`3.1.1` 처럼) |
| **워크패키지** | 쪼갠 것의 **최소 단위** (0.5~1.5 M/D) | PR 하나가 워크패키지 하나에 대응한다 |
| **DoD** (Definition of Done) | **"이걸 만족하면 끝"** 의 기준 | "구현 완료" 는 DoD 가 아니다. 검증 가능해야 한다 |
| **M/D** (인일) | 한 사람이 **하루(8시간)** 일한 양 | 공수 단위 |
| **마일스톤 / 게이트** | 중간 목표 / 그 목표의 **합격 심사** | M0~M3 과 G0~G3. 게이트를 통과해야 다음으로 간다 |
| **FR / NFR** | **기능** 요구사항 / **품질** 요구사항 | "사람을 검출한다"(FR) vs "250ms 안에"(NFR) |
| **DR** (Design Decision) | **왜 그렇게 정했는지**의 기록 | 특히 *채택하지 않은 대안*과 그 이유. 같은 논의를 반복하지 않기 위함 |
| **OI** (Open Issue) | **아직 안 정해진 것** | 번호로 관리하고 닫히는 시점을 정해 둔다 |
| **RISK** | **잘못될 수 있는 것**과 대비책 | 등록해 두고 추적한다 |
| **골든 픽스처** | 정답을 적어 둔 **답안지 파일** | Python 과 C++ 이 같은 답안지로 채점받아, 서로 어긋날 수 없게 만든다 |
| **회귀 시험** (regression test) | 한 번 고친 버그가 **다시 생기지 않게** 두는 시험 | 버그를 잡으면 그 케이스를 테스트로 남긴다 |
| **커버리지** | 테스트가 코드의 **몇 %를 실제로 실행**했는지 | 70% 미만이면 CI 가 실패한다 |
| **CI** (지속적 통합) | PR 을 올리면 **자동으로 검사**하는 장치 | 린트·테스트·펌웨어 빌드. 통과해야 머지된다 |
| **린트** (lint) | 문법·스타일을 **자동으로 지적**하는 도구 | `ruff`. 규칙을 어기면 CI 가 실패한다 |
| **목업 / 목** (mock) | 실물인 **척하는 대역** | `mock_mechdog.py` 가 로봇 역할을 한다. CI 러너에는 로봇이 없기 때문 |
| **주입** (injection) | 시계·하드웨어를 **밖에서 넣어주기** | 그래야 300ms 타임아웃을 실제로 기다리지 않고 시험할 수 있다 |
| **엣지 트리거** | 값이 **변할 때만** 기록하기 | 10Hz 를 매번 남기면 중요한 사건이 묻힌다 |
| **블랙박스** | 사건 순간의 **스냅샷 보관함** | 로그는 지워지지만 이건 남긴다 |
| **프로파일** (dev/prod) | 개발용·실전용 **설정 묶음** | 같은 코드로 다른 값을 쓴다 |

## 7. 헷갈리기 쉬운 짝

| 짝 | 차이 |
| :--- | :--- |
| **`AVOID` vs `FAILSAFE`** | 앞은 **정상 동작**(벽을 피하는 중), 뒤는 **비정상**(문제가 생겨 멈춤) |
| **`ALERT` vs `AUTH_WAIT`** | 앞은 사람을 **발견**한 상태, 뒤는 **인증을 요구하고 기다리는** 상태 |
| **폐기 vs 클램핑** | 앞은 **버린다**, 뒤는 **잘라서 쓴다** |
| **유실 vs 파싱 실패** | 앞은 **도착조차 안 함**, 뒤는 도착했지만 **못 읽음** |
| **저전압 판정 임계 vs 물리 범위** | 앞은 *"안전한가"*(6.6V), 뒤는 *"측정이 가능한 값인가"*(6.0~8.4V) |
| **구역 식별 vs 구역 이동** | 앞은 마커를 **읽는 것**(Phase 1), 뒤는 **찾아가는 것**(Phase 2, 측위 필요) |
| **ArUco 마커 vs ARCore 앵커** | 앞은 **인쇄물**, 뒤는 **가상 좌표** |
| **에스컬레이션 vs FSM 상태** | **서로 직교한다.** "무엇을 하는 중"(FSM) 과 "얼마나 세게 대응"(에스컬레이션) 은 별개 축 |
