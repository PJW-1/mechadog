## 1. 시스템 아키텍처

### 1.1 스타 토폴로지 (Star Topology)

**원칙은 한 줄이다 — 로봇 위의 장치끼리 선을 연결하지 않는다.**

카메라도, 나중에 붙일 LiDAR 도 **자기 배터리로 켜지고 Wi-Fi 로만 말한다.** 서로 직접
대화하지 않고 전부 노트북을 거친다. 자전거 바큇살처럼 가운데(노트북)에서 뻗어 나가는
모양이라 **성형(星形, star) 구조**라고 부른다.

```
                    ┌───────────────────────────────────────────┐
                    │            HOST PC  (허브)                 │
                    │  Windows 11 + WSL2 / RTX 3080             │
                    │  · ONNX Runtime 검출기  (사람 인지)        │
                    │  · Behavior FSM         (판단)             │
                    │  · FastAPI + WebSocket  (관제 대시보드)     │
                    │  · [Phase 2] ROS2 slam_toolbox            │
                    └───┬───────────────┬───────────────┬───────┘
        MJPEG(HTTP) ↑   │               │ UDP cmd ↓     │ UDP scan ↑
                        │               │ UDP tlm ↑     │  [Phase 2]
    ┌───────────────────┴──┐   ┌────────┴──────────┐   ┌┴──────────────────┐
    │ VISION NODE          │   │ MOTION NODE       │   │ LIDAR NODE        │
    │ XIAO ESP32S3 Sense   │   │ MechDog ESP32     │   │ (Phase 2 결정)     │
    │ 보조배터리 USB 급전   │   │ 커스텀 Arduino 펌웨어│   │ LD19 + 중계 MCU   │
    │                      │   │                   │   │                   │
    │ · OV2640 → MJPEG     │   │ · HW_MechDog HAL  │   │ · UART 230400 수신 │
    │ · Wi-Fi HTTP 서버     │   │ · Wi-Fi 명령 수신  │   │ · UDP 중계         │
    │ · 추론 없음           │   │ · 초음파 즉시정지   │   │                   │
    │                      │   │ · 하트비트 페일세이프│   │                   │
    └──────────────────────┘   └───────────────────┘   └───────────────────┘
              ✕ ────────── 노드 간 물리 배선 없음 ────────── ✕
```

**얻는 것 네 가지** — 요약하면 *"카메라가 죽어도 로봇은 걷는다"* 다.

| 항목 | 효과 |
| :--- | :--- |
| 통합 리스크 | 로봇 본체를 **개조하지 않는다.** 카메라가 고장 나도 보행에 영향이 없다 |
| 개발 병렬성 | 카메라 담당과 모션 담당이 **서로를 기다리지 않는다** |
| 교체 용이성 | 카메라를 다른 보드로 바꿔도 **말이 통하면(프로토콜) 그대로 쓴다** |
| 전원 격리 | 다리 모터가 전기를 왈칵 당겨 전압이 떨어져도 **카메라는 흔들리지 않는다** |

### 1.2 3-Tier 레이턴시 계층

**어떤 판단을 어디에 둘지는 "늦으면 얼마나 위험한가"로 정한다.**

*벽이 가까우면 멈춘다* 는 판단이 0.2초 늦으면 로봇이 벽에 부딪힌다. 반면 *이 사람이
안전모를 썼는지* 는 0.2초 늦어도 아무 일도 일어나지 않는다. **급한 것은 로봇 안에,
생각이 필요한 것은 노트북에, 여유 있는 것은 클라우드에** 둔다.

> 이 표를 위반하는 설계는 반려한다.

| 계층 | 쉽게 말하면 | 위치 | 담당 로직 | 허용 지연 | 통신 단절 시 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Tier 1 · Reflex** | **반사** — 뜨거운 걸 만지면 손을 떼는 것 | MechDog ESP32 (온보드) | 초음파 충돌 정지, 하트비트 감시, 저전압 셧다운, 전도 감지, 서보 토크 해제 | **< 50 ms** | **독립 동작 필수** |
| **Tier 2 · Cognition** | **생각** — 보고 판단해서 다음 행동을 정하는 것 | Host PC (로컬 Wi-Fi) | 사람 인지 · PPE 판정 · 변화 감지, 행동 FSM, 경로 추종, [P2] SLAM | 100 ~ 200 ms | Tier 1이 안전 정지 |
| **Tier 3 · Reasoning** | **보고서** — 나중에 정리해서 남기는 것 | 클라우드 (선택) | VLM 현장 판독, 이벤트 요약 리포트, 이상 패턴 분석 | 1 ~ 3 초 | 기능 저하만, 주행 무관 |

> **불변 규칙 (Invariant)**: 안전에 직결되는 판단은 절대 Tier 2/3으로 올리지 않는다.
> **Host PC가 꺼져도 로봇은 스스로 멈춰야 한다.**
>
> 사람도 그렇다 — 뜨거운 것에서 손을 떼는 것은 뇌까지 갔다 오지 않는다. 척수에서 끝낸다.
> 신호가 뇌를 왕복하는 동안 이미 화상을 입기 때문이다. **Tier 1 이 그 척수다.**

>
> ⚠️ 단 **측정 조건이 기록되지 않았다.** 아래 네 조건에서 재확인해야 한다 — **① 마스트 높이(무게중심 상승) ② 배터리 반방전 ③ 직진 외 선회 ④ 10분 연속(서보 발열로 토크 저하)**. (RISK-02)

### 1.4 전원 설계

**MechDog 본체** — 2S 리튬 (7.4V 공칭, 8.4V 2A 충전기 확정)

| 임계값 | 전압 | 동작 |
| :--- | ---: | :--- |
| 정상 | > 7.0 V | 통상 운용 |
| 경고 | ≤ 7.0 V | 대시보드 경고, 순찰 중단 후 대기 |
| 셧다운 | ≤ 6.6 V | `STATE_FAILSAFE` 진입, 엎드린 자세로 서보 토크 해제 |

**보조 노드 전원** — 보조배터리 1개 공용 (DR-10)

XIAO · 중계 MCU · LD19 를 **한 보조배터리에서 급전**한다. LiDAR 는 중계 MCU 의 `5V` 핀에서 받으므로
**GND 가 자동으로 공통**이 된다(UART 성립 조건).

> ⚠️ **배터리 용량이 문제가 아니다. 전기가 지나가는 길이 문제다.**
>
> LiDAR 전기를 중계 보드의 `5V` 핀에서 뽑아 쓰는데, 그러면 **보드의 USB 단자 하나로
> 두 장치 몫의 전기가 몰린다.**
> LiDAR 가 DevKit 의 `5V` 핀을 거치므로
> **DevKit 의 USB 커넥터와 내부 VBUS 트레이스에 DevKit(200mA) + LD19(200mA) ≈ 400mA 가 몰린다.**
> 보드에 **500mA 폴리퓨즈**가 달린 제품이면 마진이 얇다.
>
> **여기 달린 보호 부품(폴리퓨즈)은 딱 끊어지지 않고 서서히 저항이 커진다.** 그래서 증상이
> *"가끔 리셋되고 이유 없이 불안정하다"* 로 나타난다 — **가장 찾기 어려운 형태의 고장이다.**
> 증상을 기다리지 말고 **조립 직후 멀티미터로 전압을 재서 판정한다.**
>
> | 조건 | 판정 |
> | :--- | :--- |
> | LiDAR 연결 후 `5V` 핀이 **4.5V 이상** | 통합 유지 |
> | **4.5V 미만** | LiDAR 를 배터리에서 **직접 급전**으로 분리 |
>
> LD19 허용 하한이 4.5V 이므로 숫자로 갈린다. 분리해도 브레드보드 전원 열에
> `USB 전원 케이블(낱개선)` 을 꽂으면 되므로 **납땜은 0 을 유지한다.**
> 절차는 [하드웨어 2절](HARDWARE.md).

| 부하 | 평균 소비전류 | 순간 피크 |
| :--- | :--- | :--- |
| XIAO 비전 노드 | 200 ~ 250 mA | 300 ~ 500 mA (Wi-Fi TX 버스트) |
| ESP32 중계 MCU | 150 ~ 250 mA | — |
| LD19 [P2] | ~200 mA | — |
| **합계** | **~600 mA** | |

보조배터리 정격은 3.7V 셀 기준이므로, 5V 승압 손실을 감안하면 **실사용은 정격의 60~70%** 다.

| 정격 | 5V 기준 실사용 | 600mA 기준 구동시간 | 무게 |
| ---: | ---: | ---: | ---: |
| 2,000 mAh | ~1,300 mAh | 약 2시간 | 40~50 g |
| 3,000 mAh | ~2,000 mAh | 약 3시간 | 60~70 g |
| **5,000 mAh** ← **보유분 사용** | **~3,300 mAh** | 5시간+ | **100~120 g** |

> **3인이 5,000mAh · 2구 동일 사양으로 통일한다.** 용량 자체는 과하다 — 총 600mA 소비에
> 5.5시간이고 로봇 본체가 30~60분에 방전되므로 5~11배 여유다. **선정 이유는 용량이 아니라 통일이다.**
>
> **전원 구성이 개체마다 다르면 무게차가 개체차에 하나 더 얹힌다.** WBS 8절이 서보 영점과 보행
> 이동량 편차를 관리하고 있는데, 여기에 전원 무게까지 갈리면 변수가 늘어난다.
> **동일 사양이어도 개체차가 있으므로 기준기 수치를 다른 기체에 그대로 복사하지 않는다.** 기준기 값은 게이트 판정의
> 공통 기준이고, 각 기체의 서보 오프셋·보행 계수·탑재 후 안정성은 개체별 프로파일에 따로 기록한다.
>
> Phase 1 에서는 XIAO 만 급전하므로(220mA) 용량이 더욱 과하지만, 어차피 구매한다면 통일이 낫다.
>
> **구동시간은 병목이 아니다.** 8개 서보를 구동하는 MechDog 본체가 먼저 방전된다(추정 30~60분, OI-4).
> 시연은 10분이므로 보조배터리는 어느 용량이든 충분하며, **선정 기준은 용량이 아니라 무게**다.
>
> ⚠️ **보조배터리의 USB-C 포트가 입출력 겸용인 제품이 많다.** 그 경우 다른 포트와 배타적이거나 출력이 되지 않는다.
> **보유품으로 두 부하를 동시에 켜보는 것**이 가장 빠른 확인이다. 불가하면 USB 분배 케이블로 늘린다.
>
> **무게 초과 판정 시** LiPo 3.7V 1000mAh + 벌크 커패시터(470~1000µF) 구성으로 되돌린다.
> 그 경우 500mAh 셀은 1C 한계가 500mA 라 Wi-Fi 피크에서 브라운아웃이 발생하므로 **1000mAh 이상**을 쓴다.

**추론 실행 프로바이더 (EP) 선택**

| EP | 대상 | 용도 | 판단 |
| :--- | :--- | :--- | :--- |
| **DirectML** | **모든 DX12 GPU** (NVIDIA·AMD·Intel) | 개발 PC 전체 | ⭐ **채택** — 팀원 GPU가 달라도 동작 |
| CPU | 모든 환경 | **CI 러너**(리눅스), 단위 시험 | 채택 |
| CUDA | NVIDIA 전용 | — | 미채택 (이식성 손실, 이득 미미) |

> 실제로는 그 PC 에서 쓸 수 있는 것과의 교집합을 취한다.

### 1.6 음성 및 상태 표시 역할 분담

음성은 **지연 요구가 다른 두 종류**로 나뉜다. 하나의 수단으로 묶으면 즉각성과 표현력 중 하나를 잃는다.

| 용도 | 담당 | 방식 | 지연 | Tier |
| :--- | :--- | :--- | :--- | :---: |
| **암구호 인식** | WonderEcho (CI1302) | **온칩 오프라인 인식.** 네트워크 불필요 | 즉시 | 1 |
| **즉각 경고 방송** | **MP3 모듈 (1순위)** / WonderEcho 내장 스피커 (대안) | 사전 등록된 문구 재생 | **즉시** | 1 |
| **상황 판독 방송** | Host PC + 클라우드 VLM + TTS | 실시간 생성 문장. **관제 센터 방송** 개념 | 1~3초 | 3 |
| **상태 표시** | **초음파 센서 내장 RGB LED** | 에스컬레이션 단계를 색으로 표시 | 즉시 | 1 |

> **인식과 재생을 분리한다.** 둘을 모두 WonderEcho 에 맡기면 재생 문구가 **영어·중국어로 제한되고, 문구를 바꿀 때마다 전용 Windows 도구로 재플래싱**해야 한다.
> 킷에 포함된 **MP3 모듈(TF카드 포함)** 은 SD 카드에 파일만 넣으면 되므로 **한국어가 가능하고 문구 추가가 자유롭다.**
>
> | | 담당 | 얻는 것 |
> | :--- | :--- | :--- |
> | 인식 (암구호 듣기) | WonderEcho 온칩 | 오프라인·즉시. 유지 |
> | **재생 (경고·안내)** | **MP3 모듈** | **한국어 · 재플래싱 불요 · 문구 추가 자유** |
>
> 이렇게 나누면 **착수 전에 확정해야 하는 문구가 암구호 1~2개로 줄어든다.** 방송 문구는 개발 중에 늘리면 된다.
> MP3 모듈의 제어 인터페이스 확인(**OI-6**)이 선행 조건이며, 불가 판정 시 WonderEcho 내장 스피커로 되돌린다.
>
> **상태 표시등은 별도 부품이 필요하지 않다.** 초음파 센서에 RGB LED 가 내장되어 있음을 실물로 확인했다(OI-12 닫힘).

**WonderEcho 제약 (확정)**

| 항목 | 내용 |
| :--- | :--- |
| 커스텀 문구 | **지원.** 웨이크워드·명령어·재생문구를 사용자가 정의 (최대 255~300개) |
| **언어** | **영어 / 중국어만. 한국어 미지원.** 영어 문구는 **대문자 + 하이픈 연결** (예: `ALPHA-SEVEN-CLEAR`) |
| 등록 시점 | **펌웨어 빌드 시 확정.** 런타임에 새 문장을 생성할 수 없다 |
| 인식 거리 | **정숙 환경 5m** / 소음 환경 1m |
| 워크플로우 | 온라인 플랫폼에서 문구 입력 → `.bin` 생성 → `PACK_UPDATE_TOOL.exe`(칩: CI1302)로 USB-C 플래싱 |
| 출력 | 인식 성공 시 **명령 ID 바이트**를 호스트로 전달 (통신 방식 I2C/UART는 OI-10에서 확정) |

> **실시간 AI 음성은 Host PC가 담당한다.** 로봇에 스피커를 추가하지 않고 PC 스피커로 방송한다. 무게 0g·비용 0원이며, 실제 보안 시스템이 관제 센터에서 방송하는 방식과 동일하여 서사상으로도 타당하다.

> **플래싱 리스크** — 커스텀 펌웨어 기록은 되돌리기 어렵다. Advanced Kit 3개로 **WonderEcho 모듈이 3개 확보**되어 있으므로, **1개를 실험용으로 지정**하고 성공한 `.bin`을 나머지에 적용한다.

### 3.1 대응 에스컬레이션 단계 (Escalation Ladder)

위험구역·미확인 인원·안전 위반에 대한 대응 강도를 단계로 정의한다. **FSM 상태와 직교하는 별도 축**이며, 각 상태에서 현재 에스컬레이션 단계에 맞는 표현을 취한다.

| 단계 | 진입 조건 | 눈 LED | 음향 | 자세·기동 | 기록 | Tier |
| :---: | :--- | :---: | :--- | :--- | :--- | :---: |
| **L0** 순찰 | 정상 | 🔵 파랑 | — | 통상 보행 | — | 1 |
| **L1** 관찰 | `person` 연속 3프레임 검출 | 🟡 노랑 | — | 정지 + **Pitch Up 경계 자세** | 스냅샷 | 2 |
| **L2** 인증요구 | L1이 설정 시간 지속 & 미인증 | 🟠 주황 | 비프음 | 경계 유지 + 선회 추종 | 스냅샷 + 이벤트 | 2 |
| **L3** 경보 | 인증 실패 · **PPE 위반** · **물체 변화 확정** | 🔴 빨강 (점멸) | **즉각 경고 방송** (사전 등록 문구) | 추종 | 이벤트 + **VLM 리포트 + 관제 방송** | 2→3 |
| **F** 페일세이프 | 링크두절 · 저전압 · 전도 · E-Stop | ⚪ 흰색 | — | 엎드림, 서보 토크 해제 | 로그 | **1** |

**해제 규칙**

| 전이 | 조건 |
| :--- | :--- |
| L1 → L0 | 타겟 미검출 5초 지속 (FR-3.6) |
| L2 → L0 | **인증 성공** (사원증 또는 암구호) |
| L3 → L0 | **관리자 확인(대시보드 리셋)으로만 해제한다.** 아래 참조 |
| **F → L0** | **자동 복귀 금지.** 원인 해소 후 사용자가 명시적으로 리셋 |

> **⚠️ L3 해제 규칙 정정 (v1.2)** — v1.1 은 `L3 → L0` 조건을 *"인증 성공 + 관리자 확인"* 으로 적었으나,
> 이는 **L3 진입 원인 셋 중 하나(인증 실패)만 보고 쓴 규칙**이었다. 나머지 둘에는 적용되지 않는다.
>
> | L3 진입 원인 | "인증 성공" 이 성립하나 |
> | :--- | :--- |
> | 인증 실패 | ○ |
> | **PPE 위반** | **✕ — 인증할 주체가 없다.** 위반자가 안전모를 써도 "인증"이 아니다 |
> | **물체 변화 확정** | **✕ — 사람이 없다.** 인증할 대상 자체가 존재하지 않는다 |
>
> 그대로 두면 **PPE 위반과 물체 변화로 L3 에 진입한 로봇은 영구히 L3 에서 나올 수 없다.**
>
> **정정 — L3 는 원인과 무관하게 관리자 확인으로만 해제한다.**
> 원인 해소 여부(안전모 재착용, 물건 복귀)는 **대시보드에 표시하되 해제 조건으로 쓰지 않는다.**
> 이유는 둘이다. ① 원인별 자동 해제 조건을 만들면 조건이 셋으로 갈려 버그가 생긴다.
> ② 물건이 돌아왔다고 그것이 정상 상황인지 로봇은 판단할 수 없다 — 사람이 봐야 한다.
> 상시 인적 감시를 전제하므로(A-13) 관리자 확인이 가장 단순하고 안전한 출구다.

> **설계 원칙** — 눈 LED는 장식이 아니라 **관측 가능한 상태 출력**이다. 로봇이 지금 무엇을 판단하고 있는지 관객과 작업자가 즉시 읽을 수 있어야 하며, 이는 디버깅 수단으로도 기능한다.

> **음향 분담** — L3의 즉각 경고는 **WonderEcho가 지연 없이** 재생하고, 상황 설명은 **Host PC가 VLM 판독 후 1~3초 뒤 방송**한다 (1.6절). 즉각성과 표현력을 동시에 확보하기 위한 분리다.

## 4. CI/CD 파이프라인

### 4.1 CI 설계 원칙

임베디드 프로젝트에서 CI가 형식만 갖추고 실질을 잃는 전형적 실패가 있다. 아래 원칙으로 이를 방지한다.

| # | 원칙 | 이유 |
| :-- | :--- | :--- |
| **1** | **정적 분석은 문제를 찾으면 반드시 실패하게 한다** — `cppcheck --error-exitcode=1` | `0` 으로 두면 경고를 출력하고도 잡이 초록불이 된다. 아무도 로그를 읽지 않으므로 분석이 장식이 된다 |
| **2** | **검사 도구는 설치가 아니라 실행이 확인되어야 한다** — `clang-format --dry-run --Werror` | 설치 스텝만 있고 실행 스텝이 없는 구성은 흔한 실수다 |
| **3** | **소스가 없는 잡은 실패가 아니라 스킵한다** — `hashFiles` 조건 | 착수 전 단계에서 빨간불이 상시화되면 팀이 CI를 무시하게 된다. 단 **소스가 추가되면 자동으로 활성화**되어야 한다 |
| **4** | **플랫폼 종속 의존성은 환경 마커로 분기한다** | 리눅스 러너와 Windows 개발 PC가 다르다. `onnxruntime-directml` 은 Windows 전용이므로 마커 없이 선언하면 CI 가 설치 단계에서 죽는다 |
| **5** | **하드웨어 없이 검증 가능한 로직을 최대화한다** | 👇 아래 참조 |
| **6** | **액션 버전을 최신 메이저로 유지한다** | 런타임 deprecation 경고가 매 실행마다 쌓이면 실제 문제를 가린다 |

> **원칙 5가 이 프로젝트 CI의 핵심이다.** 임베디드에서 값싸게 자동화되는 것은 **하드웨어에 의존하지 않는 순수 로직**이다. FSM 전이, 패킷 파싱, 안전 판정, 설정 스키마를 **하드웨어 접근에서 분리하여 설계**하면 CI에서 전수 검증할 수 있다.
>
> 이를 위해 **온보드 코드도 로직 계층과 HAL 호출 계층을 분리**한다 (WBS 0절 3.0/4.0 구분 기준과 동일).

## 부록. 용어

문서를 읽다 막히면 여기를 본다. 정확한 규정은 각 정본 문서에 있다.

### 1. 이 시스템의 구성

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **호스트 PC** (Host PC) | 여러분의 노트북. 시스템의 **머리** | 카메라 영상 분석, 다음 행동 결정, 대시보드. `host/` 폴더 코드가 전부 여기서 돈다 |
| **모션 노드** | 로봇 몸통의 ESP32. 시스템의 **몸** | 다리를 움직이고, 초음파로 벽을 보고, 배터리를 감시한다 |
| **비전 노드** | 로봇에 붙인 카메라(XIAO). 시스템의 **눈** | 영상만 Wi-Fi 로 쏜다. 판단은 하지 않는다 |
| **온보드** (onboard) | **로봇 안에서** 도는 것 | 반대말은 "호스트에서" 다. 안전 판정은 온보드에 있어야 한다 |
| **HAL** (Hardware Abstraction Layer) | 하드웨어를 부르는 **창구**를 한 곳으로 모은 층 | 벤더 라이브러리(`HW_MechDog`)를 감싸서, 위쪽 코드가 하드웨어를 직접 만지지 않게 한다 |
| **Tier 1 / 2 / 3** | 판단을 **얼마나 급한지**로 나눈 3단 | Tier 1 = 로봇이 즉시(안전), Tier 2 = 노트북이(판단), Tier 3 = 클라우드가(리포트) |
| **기준기** (Reference Unit) | 특정 Phase의 성능을 재는 **표준 로봇** | `phase1_reference`(LiDAR 미장착 P1 표준 구성)와 `phase2_reference`(LiDAR 장착 측위 검수용)를 따로 지정한다 |
| **기준 PC** | 성능 수치를 재는 **표준 노트북** | 팀장 PC. "빠른 PC 에서만 되는 것"을 성능 달성으로 세지 않기 위함 |

### 2. 로봇이 무엇을 하는지

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **FSM** (유한 상태 기계) | 로봇이 **지금 뭐 하는 중인지**를 이름표로 관리하는 방식 | `PATROL`(순찰) · `ALERT`(경계) 처럼 13가지. 조건이 맞으면 다음 이름표로 넘어간다 |
| **상태 전이** | 이름표가 **바뀌는 것** | "순찰 중에 사람을 3프레임 연속 발견하면 경계로" 같은 규칙. 표로 정리해 뒀다 (아키텍처 3절) |
| **에스컬레이션** | 대응을 **얼마나 세게 할지**의 단계 | L0(정상) → L1(관찰) → L2(인증요구) → L3(경보). 눈 LED 색으로 보인다 |
| **페일세이프** (fail-safe) | 문제가 생기면 **스스로 안전한 쪽으로** | 통신 끊김·저전압·넘어짐 → 멈추고 힘을 뺀다. 사람이 리셋해야 다시 움직인다 |
| **E-Stop** | 비상정지 버튼 | 대시보드에 항상 보이게 둔다. 어떤 상태에서든 최우선 |
| **PPE** | 안전 보호구 (안전모·조끼) | 미착용을 카메라로 잡는 것이 이 프로젝트의 산업안전 기능이다 |
| **워치독** (watchdog) | 프로그램이 멈추면 **자동으로 재시작**시키는 감시견 | ESP32 기능. 무한루프에 빠져도 1초 내 리셋된다 |

### 3. 노트북과 로봇이 대화하는 방식

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **프로토콜** (규약) | 서로 알아들을 **말의 규칙** | 정본은 [PROTOCOL.md](PROTOCOL.md). 한 줄 JSON 을 주고받는다 |
| **텔레메트리** | 로봇이 보내는 **상태 보고서** | 0.1초마다 1줄. 배터리·거리·기울기·상태. **로봇은 파일 로그를 안 남기므로 이게 곧 로그다** |
| **UDP** | 빠르지만 **도착을 보장하지 않는** 전송 방식 | 순서가 뒤바뀌거나 사라질 수 있어서 `seq` 로 걸러낸다 |
| **`seq`** | 보낸 순서를 세는 **번호표** | 이전보다 작은 번호가 오면 옛 패킷이므로 버린다 |
| **클램핑** (clamping) | 범위를 벗어난 값을 **잘라서** 쓰기 | `step: 500` → `100`. 버리지 않는 이유는 "명령이 조용히 사라지는 것보다 낫기" 때문 |
| **폐기 + WARN** | 버리되 **경고 기록은 남기기** | 모르는 명령이 왔을 때. 죽지 않고 넘어가므로 새 기능 추가가 안전해진다 |
| **additive / breaking** | **더하기 변경 / 깨뜨리는 변경** | 새 명령 추가는 안전(모르면 무시). 이름·단위 변경은 양쪽을 동시에 고쳐야 한다 |
| **MJPEG** | 사진을 연달아 보내 영상처럼 보이게 하는 방식 | 카메라가 `:81/stream` 으로 15fps 송출 |

### 4. 로봇이 어디 있는지 아는 방법

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **측위** (localization) | 로봇이 **자기 위치를 아는 것** | Phase 1 에서는 안 쓴다. 방식이 아직 미결 (LiDAR vs 스마트폰) |
| **SLAM** | 돌아다니며 **지도를 만들고 동시에 자기 위치를 찾는** 기술 | Phase 2. LiDAR 를 달면 시도한다 |
| **LiDAR** | 레이저로 **주변 거리를 한 바퀴 재는** 센서 | FHL-LD19. 발주 대기 중 |
| **VIO** | 카메라 흔들림으로 **움직인 거리를 추정**하는 방식 | 스마트폰을 얹는 대안 경로 |
| **ArUco 마커** | 흑백 사각형 **인쇄 코드** (QR 사촌) | 사원증 인증과 구역 표시에 쓴다. A4 로 출력하면 비용 0 |
| **웨이포인트** | 지나가야 할 **좌표 점** | Phase 2 구역 순찰 경로 |

### 5. 카메라로 사람을 찾는 방법

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **추론** (inference) | 학습된 모델에 사진을 넣어 **답을 얻는 것** | "이 사진에 사람이 있나" 를 노트북이 판단한다 |
| **bbox** (바운딩 박스) | 찾아낸 대상을 감싼 **네모 상자** | 좌표만 있고 거리(미터)는 없다. 그래서 판정을 상자 크기·위치로 한다 |
| **클리핑** | 대상이 화면 밖으로 **잘린 상태** | 카메라가 지면 15cm 에 있어 머리가 잘린다. 그때 자세를 올려 다시 본다 |
| **ONNX** | 여러 프레임워크에서 **공통으로 쓰는 모델 파일 형식** | 학습은 어디서 하든 실행은 이 형식으로 통일한다 |
| **실행 프로바이더** (EP) | 모델을 **어느 장치로 돌릴지** 고르는 설정 | DirectML(GPU) → CUDA → CPU 순으로 되는 것을 쓴다 |
| **DirectML** | 윈도우에서 **어느 회사 GPU 든** 쓰게 해주는 층 | 팀원 GPU 가 NVIDIA·AMD·Intel 로 달라서 이걸 골랐다 |
| **NMS** | 같은 대상에 겹쳐 잡힌 상자를 **하나로 정리** | 검출 후처리 단계 |
| **추적** (tracking) | 프레임이 바뀌어도 **같은 사람임을 유지** | 각 사람에게 `track_id` 를 붙인다. 인증을 그 ID 에 귀속시킨다 |
| **개방 어휘** (open-vocabulary) | 학습하지 않은 물체도 **이름을 말하면 찾는** 모델 | 변화 감지 후보 기술. 선정 미결 (OI-15) |

### 6. 개발·품질 관리

| 용어 | 쉬운 말 | 우리 프로젝트에서 |
| :--- | :--- | :--- |
| **WBS** | 할 일을 **잘게 쪼갠 목록** | 이 프로젝트의 모든 작업이 번호로 있다 (`3.1.1` 처럼) |
| **워크패키지** | 쪼갠 것의 **최소 단위** (0.5~1.5 M/D) | PR 하나가 워크패키지 하나에 대응한다 |
| **DoD** (Definition of Done) | **"이걸 만족하면 끝"** 의 기준 | "구현 완료" 는 DoD 가 아니다. 검증 가능해야 한다 |
| **M/D** (인일) | 한 사람이 **하루(8시간)** 일한 양 | 공수 단위 |
| **마일스톤 / 게이트** | 중간 목표 / 그 목표의 **합격 심사** | M0~M3 과 G0~G3. 게이트를 통과해야 다음으로 간다 |
| **FR / NFR** | **기능** 요구사항 / **품질** 요구사항 | "사람을 검출한다"(FR) vs "250ms 안에"(NFR) |
| **DR** (Design Decision) | **왜 그렇게 정했는지**의 기록 | 특히 *채택하지 않은 대안*과 그 이유. 같은 논의를 반복하지 않기 위함 |
| **OI** (Open Issue) | **아직 안 정해진 것** | 번호로 관리하고 닫히는 시점을 정해 둔다 |
| **RISK** | **잘못될 수 있는 것**과 대비책 | 등록해 두고 추적한다 |
| **골든 픽스처** | 정답을 적어 둔 **답안지 파일** | Python 과 C++ 이 같은 답안지로 채점받아, 서로 어긋날 수 없게 만든다 |
| **회귀 시험** (regression test) | 한 번 고친 버그가 **다시 생기지 않게** 두는 시험 | 버그를 잡으면 그 케이스를 테스트로 남긴다 |
| **커버리지** | 테스트가 코드의 **몇 %를 실제로 실행**했는지 | 70% 미만이면 CI 가 실패한다 |
| **CI** (지속적 통합) | PR 을 올리면 **자동으로 검사**하는 장치 | 린트·테스트·펌웨어 빌드. 통과해야 머지된다 |
| **린트** (lint) | 문법·스타일을 **자동으로 지적**하는 도구 | `ruff`. 규칙을 어기면 CI 가 실패한다 |
| **목업 / 목** (mock) | 실물인 **척하는 대역** | `mock_mechdog.py` 가 로봇 역할을 한다. CI 러너에는 로봇이 없기 때문 |
| **주입** (injection) | 시계·하드웨어를 **밖에서 넣어주기** | 그래야 300ms 타임아웃을 실제로 기다리지 않고 시험할 수 있다 |
| **엣지 트리거** | 값이 **변할 때만** 기록하기 | 10Hz 를 매번 남기면 중요한 사건이 묻힌다 |
| **블랙박스** | 사건 순간의 **스냅샷 보관함** | 로그는 지워지지만 이건 남긴다 |
| **프로파일** (dev/prod) | 개발용·실전용 **설정 묶음** | 같은 코드로 다른 값을 쓴다 |

### 7. 헷갈리기 쉬운 짝

| 짝 | 차이 |
| :--- | :--- |
| **`AVOID` vs `FAILSAFE`** | 앞은 **정상 동작**(벽을 피하는 중), 뒤는 **비정상**(문제가 생겨 멈춤) |
| **`ALERT` vs `AUTH_WAIT`** | 앞은 사람을 **발견**한 상태, 뒤는 **인증을 요구하고 기다리는** 상태 |
| **폐기 vs 클램핑** | 앞은 **버린다**, 뒤는 **잘라서 쓴다** |
| **유실 vs 파싱 실패** | 앞은 **도착조차 안 함**, 뒤는 도착했지만 **못 읽음** |
| **저전압 판정 임계 vs 물리 범위** | 앞은 *"안전한가"*(6.6V), 뒤는 *"측정이 가능한 값인가"*(6.0~8.4V) |
| **구역 식별 vs 구역 이동** | 앞은 마커를 **읽는 것**(Phase 1), 뒤는 **찾아가는 것**(Phase 2, 측위 필요) |
| **ArUco 마커 vs ARCore 앵커** | 앞은 **인쇄물**, 뒤는 **가상 좌표** |
| **에스컬레이션 vs FSM 상태** | **서로 직교한다.** "무엇을 하는 중"(FSM) 과 "얼마나 세게 대응"(에스컬레이션) 은 별개 축 |
