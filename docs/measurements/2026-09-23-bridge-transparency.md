# 0x34 브리지 투명성과 MP3 모듈 0x7B — 2026-09-23

**로봇 4핀(I²C `0x34`) 뒤의 WonderEcho 브리지로는 명령 id 만 오간다.** 음성 파형(PCM)은
어느 방향으로도 지나가지 않는다. 그래서 WBS 4.7.9 원안(모듈 마이크 음성을 로봇 경유로 PC 에
보내고, PC 의 응답 음성을 모듈 스피커로 낸다)을 **불가로 판정**했다. 같은 시험에서 MP3 모듈이
I²C 예약 구간의 **`0x7B`** 에 있다는 것을 찾았다. 듣기는 XIAO 마이크로, 말하기는 이 MP3 모듈로
옮긴다([ADR-38](../DECISIONS.md#adr-38)).

| 항목 | 값 |
| --- | --- |
| 기체 | **`mechdog-01`** (`3c:8a:1f:33:32:08`) · USB COM8 · 배터리 전원 |
| 음성 모듈 | WonderEcho CI1302 · 로봇 4핀 중 **IIC1 포트**(SDA22/SCL23, 100 kHz) |
| 로봇 펌웨어 | 진단 스케치 `firmware_mechdog_motion/diagnostics/i2c_bridge_probe` 를 app0 에만 올려 시험하고, 끝난 뒤 원래 app0 로 되돌렸다(백업 SHA256 `1084ab8d…`, 되돌린 뒤 쓰기 해시 일치) |
| 일시 | 2026-09-23 18:15–18:50 |
| 원자료 | [summary](../../TEST_MECHDOG/results/20260923_4.7.9-bridge-transparency/summary.md) · `robot_probe.log` · `module_uart0.log` (로그는 git 미추적) |

> ⚠️ **`0x64` 는 장치 주소가 아니다.** 모듈이 인식한 명령 id 를 담는 `0x34` 안의 레지스터다.
> 모듈의 I²C 주소는 `0x34` 하나다. 문서에 "로봇 I²C(`0x64`)" 처럼 주소로 적힌 곳은 이 측정을
> 근거로 정정한다.

---

## 1. 왜 쟀나

4.7.9 는 "모듈 마이크 음성을 로봇 경유로 PC 에 보내고, PC 의 응답 음성을 모듈 스피커로 낸다"
였다. 그러려면 로봇 4핀(I²C `0x34`)으로 **음성 파형**이 오가야 한다. 모듈을 USB 로 PC 에 직접
꽂는 구성은 로봇이 돌아다니는 현장에서 쓸 수 없기 때문이다.

그래서 물음은 하나다. **`0x34` 브리지가 임의 바이트를 그대로 넘기는가, 아니면 정해진 명령만
받는가.**

## 2. 재는 법

진단 스케치는 모터·Wi-Fi·벤더 라이브러리가 없고, USB 시리얼(115200) 줄 단위 명령으로 버스를
직접 찌른다. 주소·레지스터·데이터는 16진이다.

1. 파티션 표를 읽고 기존 app0 을 백업한 뒤 스케치를 **app0 에만** 기록한다.
2. `scan` 으로 IIC1·IIC2 를 `0x08`–`0x7F` 전부 훑는다. **`0x77` 에서 멈추지 않는다** — MP3 모듈은
   예약 구간의 `0x7B` 에 있다.
3. 대기 중 `0x34` 의 레지스터 `0x00`–`0xFF` 를 전부 읽어 기준을 잡는다(`map 34`).
4. 쓰기(`w 34 6EFF05` 꼴)마다 스피커를 귀로 확인한다. 무음이 나오면 **바로 뒤에 재생되던 쓰기를
   대조군으로 넣어** 모듈이 살아 있는지 확인한다.
5. 모듈에 명령어를 말한 뒤 `0x64` 를 거듭 읽어(`drain`) 값이 남는지 지워지는지 본다.
6. 모듈을 MP3 모듈로 바꿔 꽂고 `0x7B` 레지스터에 써 본다.
7. 끝나면 백업한 app0 을 되돌리고 쓰기 해시를 확인한다.

⚠️ **반복 시작 읽기의 `tx` 는 늘 0 으로 찍힌다.** Arduino-ESP32 는 `endTransmission(false)` 를
`requestFrom` 까지 미루기 때문이다. 판정은 `got` 으로 한다.

## 3. 결과

### 버스 스캔

| 시점 | IIC1 | IIC2 |
|---|---|---|
| 모듈을 IIC1 포트에 연결 | `0x34` `0x6A`(IMU) `0x77`(초음파) | 없음 |
| MP3 모듈로 교체 | `0x6A` `0x77` `0x7B` `0x7E` | 없음 |

⚠️ 로봇의 4핀 포트 가운데 **IIC1 은 하나뿐**이다. 다른 포트에 꽂았을 때는 `0x34` 가 보이지 않았다.

### 0x34 레지스터

| # | 동작 | 결과 |
|---|---|---|
| T0 | 대기 중 `0x00`–`0xFF` 전부 읽기 | 전부 `00` |
| T1 | `0x6E` ← `01` (1바이트) | "I'm going to take a break" 한 번 — 인과 불명(깨움 시간 초과 문구일 수 있다) |
| T1b | `0x6E` ← `02` (1바이트) ×2 | 무음 |
| T1c | `0x6E` ← `FF 05` | **"Obstacle ahead"** 재생 |
| T1d | `0x6E` ← `FF 01` | **"Recyclable waste"** 재생 |
| T2 | `0x70` ← `FF 05` ×2 | 무음 — 쓰기 무시. 바로 뒤 대조군 `0x6E ← FF 05` 는 다시 재생 |
| T3 | "Hello Hiwonder" → "Sit down" 발화 후 `0x64` 읽기 | 첫 읽기 `0C`(SIT-DOWN), 이후 `00` — **읽으면 지워지는 우편함** |

- `0x6E` 는 `[type, id]` 2바이트를 받아 `we_bridge_protocol.c` 매핑표의 고정 문구를 재생한다.
- 1바이트 읽기는 약 462 µs, 4바이트 읽기는 약 790 µs 였다(100 kHz, 안전 버스 IMU·초음파와 공유).

### MP3 모듈

| 동작(`0x7B` 레지스터 ← 값) | 결과 |
|---|---|
| `0C` ← 20(음량), `01` ← 1(1번 곡) | 무음 |
| `0C` ← 30, `05`(재생), `09`(다음 곡), `01` ← 2 | 공장 기본 곡("강남스타일") 재생 — 어느 명령이 재생을 시작했는지는 가리지 못했다 |
| `06`(일시정지) | 멈췄는지 확인하지 못했다 |

레지스터 뜻은 1=곡 번호, 5=재생, 6=일시정지, 9=다음 곡, 12(`0x0C`)=음량으로 두고 시험했다.

## 5. 판정

**4.7.9 원안(음성 파형 중계)은 불가.** `0x34` 브리지로는 명령 수준만 오간다.

| 방향 | 되는 것 | 안 되는 것 |
|---|---|---|
| 로봇 → 모듈 | 매핑표의 고정 문구 재생(`0x6E ← type,id`) | 임의 음성·합성 음성 재생 |
| 모듈 → 로봇 | 모듈이 인식한 명령어 id(`0x64`) | 마이크 음성 전달 → PC 에서 STT 불가 |

그래서 듣기는 XIAO 마이크([측정](2026-09-23-xiao-mic.md)), 말하기는 MP3 모듈(TF 카드에 미리
저장한 문장)로 옮긴다. WBS 4.7.9 는 이 판정으로 완료 처리했고 남은 예산은 4.7.19~21 로 옮겼다.
MP3 드라이버는 벤더 `MP3Sensor` 를 쓰지 않고 센서 HAL 경유 자체 코드로 만든다(4.7.20, 미착수).

## 6. 남은 것

- `0x6E` 쓰기가 모듈 UART1 을 거치는지는 증명하지 못했다(시험 중 모듈 로그가 비어 있었다).
- `0x64` 우편함이 여러 개를 쌓는지(FIFO 깊이)는 보지 않았다.
- MP3: TF 카드 곡 목록, 어떤 명령이 재생을 시작했는지, 일시정지 동작, `0x7E` 의 정체가 남았다.
  4.7.20 에서 확정한다.
- ⚠️ `0x7B` 는 I²C 예약 구간(`0x78`–`0x7F`)에 있다. 스캔 범위를 `0x77` 까지로 두면 보이지 않는다.
