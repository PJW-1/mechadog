# 정지 상태 ESP32 센서 코어 비교

AI 모델은 Host PC에서 실행하고 PC와 메크독 ESP32가 통신한다. 이 시험은
ESP32의 센서 처리·통신 지연을 비교하며 PC 모델 추론 속도를 측정하지 않는다.

## 변경 범위

- `MECHADOG_SENSOR_CORE=0`은 기존 배치, `=1`은 비교 후보다. 기본은 0이다.
- 두 빌드 모두 센서 ON, 구동 OFF, 센서 우선순위 3, 주기 40ms,
  신선도 200ms와 기존 결함 래치를 유지한다. HTTPS 배치도 동일하다.
- 동일한 누적 시간 계측과 재부팅 예약 수정이 양쪽 빌드에 들어간다.
- 실제 소스 파일의 SHA-256 목록을 비교하여 코어·버전 이외 차이가 없는지
  확인한다. 비밀 설정을 포함한 BIN/ELF/인증 파일은 로컬 private 폴더에 둔다.

## 실물 시험 절차

1. PC와 로봇을 같은 Wi-Fi에 연결하고 인증서 pin·MAC·실행 이미지와
   `healthy`, `confirmed`, `actuators=false`를 확인한다.
2. 검토된 OTA 패키지로 코어 0(A1) → 코어 1(B) → 코어 0(A2) 순서로 설치한다.
   모든 설치 시 UART 부팅 로그와 OTA 결과를 별도 원본으로 보존한다.
3. 각 실행에서 같은 위치·전원·네트워크를 유지한다. STOP 확인 후 STATE IDLE을
   10Hz로 보내고 HTTPS 상태를 별도 PC 작업자에서 1Hz로 조회한다.
   보행·서보 활성화·센서 임계 완화는 하지 않는다.
4. 각 90초를 수집하고 첫 10초는 준비 구간으로 구분한다. 명령 응답,
   텔레메트리 연속성, 센서 유효성, loop 간격, 메모리, 재부팅을 함께 본다.
   실패한 실행도 원본과 결과를 남기고 정상 표본에서 임의로 제외하지 않는다.

```text
python tools/runtime_compare.py capture --config PRIVATE_CLIENT.json --pc-ip PC_IPV4 --device DEVICE_ID --expected-image-sha256 IMAGE_SHA256 --expected-core 0 --duration 90 --warmup 10 --output NEW_CAPTURE.jsonl --uart-output NEW_UART.log
python tools/runtime_compare.py summarize NEW_CAPTURE.jsonl
```

캡처는 설치/리셋을 하지 않는다. 실제 PC 설치에서는 기존 USB/OTA 도구와
동일한 작업 잠금을 잡은 전용 wrapper를 통해 중복 조작을 방지한다.

## 계측 해석

`Perf`는 사이클·시작 지연·IMU/필터·초음파·ADC 중 한 종류씩 매초 출력한다.
따라서 각 종류는 약 5초에 한 번 관찰된다. count/sum/max와 고정 histogram은
부팅 이후 누적값이며 `at_us`는 센서 snapshot 시각이다.

준비 구간을 제외하려면 종류별로 수신 시각 10초에 1초 여유를 더한 뒤 첫
snapshot과 마지막 snapshot의 count/sum/histogram을 차분한다. UART 수신 시각과
장치 시각이 정확히 동기화된 것은 아니므로 준비 구간 경계는 근사다.
종류별 실제 장치 측정 시작/끝 시각도 결과에 기록한다.
최댓값은 차분할 수 없으므로 부팅 누적 최대라고 표시한다. p95/p99는
histogram 구간 상한을 이용한 근사이며 CPU 사용률이 아니다. 사이클 시간은
센서 읽기·드라이버 대기·선점과 기존 snapshot 전달을 포함하고 계측 통계
집계와 주기 대기는 제외한다.

두 빌드 모두 같은 계측 비용을 부담한다. 원래 계측 없는 펌웨어 대비
절대 성능 변화나 특정 지연의 스케줄러 원인을 이 비교만으로 확정하지 않는다.

## 채택 기준과 한계

후보에 센서 결함·재부팅·통신 연속성 또는 제어 응답의 악화가 있으면
기본 배치를 유지한다. 세 실행 모두 정상이고 후보의 센서 지연 감소가
앞뒤 기준 실행에 비해 일관되게 확인될 때만 제한된 시험 조건에서 개선으로
판단한다. 분포 차이가 작거나 앞뒤 기준 변화와 비슷하면 우열 미확정이다.
10Hz 송신, ACK 구동 OFF/SAFE ON, 센서 유효성 유지가 필수다.

이 시험은 무선 장애 재현, 장시간 내구성, 실제 보행, 최종 센서·구동 통합
펌웨어와 PC 모델의 종단 지연을 검증하지 않는다. 최종 결과와 실패 기록은
로컬 작업일지 및 날짜별 실물 측정 폴더에 기록한다.

## 2026-09-12 실물 결과

코어 1은 채택하지 않았다. 두 번의 후보 설치 모두 정상성 확인을 통과하지
못했고, 기존 코어 0 이미지의 정상·확정 상태로 자동 복귀했다.

- 첫 후보는 센서 유효 상태로 Wi-Fi 연결 이벤트를 냈지만, 기록 구간에서
  IP 획득과 정상 OTA 응답을 확인하지 못했다. 원인이 코어 배치인지는 미확정이다.
- 동일 후보 재시도는 새 부팅 1.522초에 시작 지연 48ms로 IMU 오류가
  래치됐다. 기존 40ms 기준을 완화하지 않았고 PC도 승인을 보내지 않았다.
  이후 IMU 처리 count가 22에서 멈춘 구간의 낮은 사이클 시간은 속도 개선이 아니다.
- 첫 기준 배치의 90초 수집은 준비 구간 뒤 센서 80행 모두 유효했다.
  실제 관측 구간 약 74.68초의 사이클 평균은 4.882ms였고,
  p95/p99 histogram 상한은 12ms였다. 정지 상태 명령 800개 중 ACK 794개를
  관측했다. 원인이 무선인지 PC인지 ESP32인지는 분리하지 못했다.
- 마지막 복귀 후 90초 기준 재점검에서도 사이클 평균 4.831ms,
  p95/p99 상한 12ms였다. 정지 상태 명령 800개 중 ACK 799개를 관측했다.
  센서/OTA 정상 상태와 별개로 ACK 누락 및 텔레메트리 미수신 때문에
  전체 통신 시험 통과로 표시하지 않는다. 후보의 90초 정상 비교 구간은
  확보하지 못했다.
- 배터리 ADC 환산 보고가 약 8.5V여서 현재 규약의 8.4V 상한을 초과했다.
  UART의 `Telemetry unavailable: battery outside [6.0,8.4]`와 encoder의
  거부 조건을 대조했다. 텔레메트리 미수신을 네트워크 손실이라고 판단하지 않는다.
  실제 전압은 외부 계측기로 검증하지 않았으며 임의 보정·상한 변경도 하지 않았다.
- HTTPS 응답은 약 2초여서 단일 요청 방식의 실제 부하는 약 0.5Hz였다.
  1Hz 목표와 실제 실행률을 구분한다. 텔레메트리 송신도 중단돼 계획했던
  전체 통신 부하를 검증하지 못했다.

초기 파일 `a1`은 snapshot busy를 고장으로 잘못 분류한 PC 도구가 중단한
예비 실행이다. 세 센서가 모두 `snapshot_busy`인 정확한 경우만 조회 불가로
따로 집계하도록 고쳤다. 실제 오류와 데이터 부족은 계속 실패로 판정하며
예비 실행도 보존했다. 후보 실패와 전체 통신 미검증 때문에 코어 변경의
성능 개선을 주장하지 않는다. 기본 코어 0, 재부팅 예약 수정, 진단 계측을 유지한다.
