# 2026-09-15 — WBS 4.1.2 실기: HAL 에 POSE·ACTION 붙이기

기체 `mechdog-01` · 펌웨어 `MECHADOG_ENABLE_ACTUATORS=1 MECHADOG_ENABLE_SENSORS=1` ·
`app0` 만 기록(`esptool write_flash -u 0x10000`, 해시 검증 통과).

⚠️ **두 번 확인했다.** 처음 확인한 빌드는 806,781 B 였고, `dev` 의 `#136`(SERVICE 모드)을 리베이스로 합친 뒤 바이너리가 807,173 B 로 바뀌어 **합친 것을 다시 올려 재확인했다** — 액션 6/6 실행, `failsafe_count` 0 유지. 두 변경은 같은 `switch` 에 서로 다른 분기를 더한 것이라 겹치지 않는다.

## 결론

**DoD 충족 — 닫는다.** MOVE·POSE·ACTION 세 경로가 모두 실물에서 동작한다. 다만 **실기가
아니었으면 못 봤을 결함 세 개**가 나왔고 전부 이 PR 에서 고쳤다.

| 항목 | 결과 |
| :--- | :--- |
| `MOVE` | 기존 경로, 회귀 없음 |
| `POSE` pitch·roll·height | 적용·복귀 모두 확인 (IMU 로 교차 확인) |
| `ACTION` 0·1·2 | 벤더 이름 실재 확인 (`sit_dowm` 오타 포함) |
| 보행 가드 | 걷는 중 `applied=false`, 정지 후 `applied=true` |
| 표에 없는 id | `ACTION 9` → `applied=false` |

## 실기가 잡은 결함 셋

### ① `transform` 은 복귀하지 않는다 — 벤더 매핑은 `set_pose`

규약에 `transform(pose, dur)` 이라고 적혀 있었으나 **검증되지 않은 가정**이었다.
`pitch=15` 뒤 `pitch=0` 을 보내도 **돌아오지 않았다** — 절대 자세가 아니었다.
벤더 자신은 `transform` 을 한 번도 부르지 않고 `normal_attitude`·`rotation_pitch`·
`rotation_roll` 이 전부 `set_pose` 를 쓴다. HAL 을 `set_pose` 로 바꾸니 복귀한다.

### ② `pitch` 부호가 뒤집혀 있었다

| 명령 | IMU `pitch` | 눈으로 본 것 |
| :--- | ---: | :--- |
| 중립 | 1.01 | — |
| `pitch=+15` | **17.37** | **앞이 내려감** |
| 중립 | 1.91 | 복귀 |
| `pitch=-15` | **-11.61** | **앞이 올라감** |

`config` 의 `alert_pitch_up_deg`·`posture.pitch_up_deg` 는 이름이 *"위로"* 인데 값이
`+15`, 즉 **바닥을 보게 만드는 값**이었다. `-15` 로 고치고 `alert_pitch_deg` 로 이름도
고쳤다. `3.5.2`·`3.5.3`·`3.5.7` 이 미착수라 코드에 들어가기 전에 잡혔다.

### ③ 로봇이 제 낮잠 때문에 스스로 래치했다

벤더 `action_run` 은 구간마다 `delay()` 로 블로킹한다(실측 1,062ms). 그동안 `loop()` 가
멈춰 **UDP 수신도 300ms 명령 타임아웃 검사도 함께 멈춘다.** 깨어난 watchdog 은 자기가
눈감은 시간을 «호스트 침묵» 으로 읽고 FAILSAFE 를 걸었다.

측정(고치기 전) — 호스트는 10Hz 송신을 **한 번도 끊지 않았다**:

```
  1461ms  <- STOP   seq= 15 latched=False fc=9      ← 여기까지 정상
  1520ms  -> ACTION 송신
  2523ms  <- ACTION seq= 16 latched=False fc=9      ← 1,062ms 공백 (블로킹)
  2527ms  <- STOP   seq= 17 latched=True  fc=10     ← 깨자마자 자기 래치
  2529ms  <- STOP   seq= 18 latched=True  fc=10     ← 밀렸던 전문이 10ms 안에 몰림
```

밀렸던 패킷이 한꺼번에 처리된 것이 증거다 — **침묵한 것은 호스트가 아니라 우리였다.**

고친 뒤 같은 조건 26회 연속 액션에서 `failsafe_count` 가 한 번도 오르지 않았다.

> 대안이던 «그냥 래치한다» 는 더 나쁘다 — 액션마다 호스트가 `RESET_SAFE` 를 보내게 되어
> **안전 래치를 자동으로 푸는 습관**을 가르친다. 호스트가 정말 죽었다면 액션이 끝난 뒤
> 300ms 안에 그대로 래치된다(최악 약 1.3초). 그 사이 동작은 서기·앉기·엎드리기뿐이라
> 몸이 이동하지 않는다.

## 실기가 잡은 것 하나 더 — `applied` 가 거짓말을 하고 있었다

벤더 `act_run_func` 는 이름을 못 찾거나 건너뛰어도 **오류를 내지 않고 조용히 돌아온다.**
같은 이름을 같은 조건으로 보냈는데 **43회 중 6회가 아무 일도 하지 않았다.** 원인은 벤더
안쪽이라 소스 없이는 더 볼 수 없다(ADR-20). 다음 가설은 실기로 **배제**했다:

- «이미 그 자세면 건너뛴다» → `ACTION 1` 3연속이 모두 1,004~1,006ms 로 실행됐다. 아니다.
- «자리(순번)의 문제» → 무동작이 1·3·4회차에 흩어져 나왔다. 아니다.

고칠 수 없는 대신 **숨기지 않게** 만들었다. 실행과 무동작은 걸린 시간으로 깨끗이 갈린다:

| | 표본 | 걸린 시간 |
| :--- | ---: | :--- |
| 실제 실행 | 37 | 1,003~1,006ms |
| 조용한 무동작 | 6 | 3~6ms |

두 무리가 겹치지 않으므로 100ms 에 선을 그어 `applied` 를 판정한다. 고친 뒤 확인:
무동작 2회는 `applied=false`, 실행 24회는 `applied=true` — **오탐 없음.**

재시도는 온보드에서 하지 않는다. 또 1초를 블로킹하는 판단은 호스트 몫이다.

## 남는 것 (이 PR 범위 밖)

- **FR-1.5 의 «엎드림» 을 온보드가 스스로 하지 않는다.** 현재 `latchFailsafe()` 는
  `move(0,0)` 만 한다. 링크가 끊긴 상황에서는 호스트가 `ACTION 2` 를 보낼 수 없으므로
  온보드가 해야 한다. `3.2.5` 에 FR-1.5 가 걸려 있으나 그 항목은 래치 우선순위 얘기다.
- **`2.1.4` ②** (앉은 자세 IMU pitch) 는 이제 `POSE`·`ACTION` 이 열렸으니 측정 가능하다.
