# NFR-1.1 E2E 단일 프레임 사슬 실측 — 2026-09-15

**한 프레임을 촬영부터 명령 ACK 까지 끊지 않고 따라간 첫 측정이다.** 지금까지는 구간을
따로 재서 더했고, 그 합산에 오류가 있었다(아래 3절).

| 항목 | 값 |
| --- | --- |
| 기체 | `mechdog-01` · `192.168.1.101` · 배터리 8.4~8.6V |
| 카메라 | XIAO ESP32S3 · OV3660 · VGA · 상한 25fps · RSSI −37dBm · `192.168.1.102` |
| 도구 | `python tools/latency_probe.py chain` (WBS 6.1.2 확장) |
| 원자료 | `TEST_MECHDOG/results/20260915_nfr1.1-chain/` |

## 1. 재는 방법

`NFR-1.1` 의 정의는 **촬영 → 검출 → 명령 적용 ACK** 다(아키텍처 2절). 세 구간을 한
프레임에서 이어 잰다.

| 구간 | 어떻게 |
| --- | --- |
| ① 촬영 → 호스트 도착 | 호스트 화면의 카운터를 카메라가 찍는다. 도착 시각 − 프레임에 찍힌 값. **같은 시계라 동기가 필요 없다** |
| ② 도착 → 검출 완료 | `completed_ms − frame_received_ms`. 디코드와 추론이 모두 들어간다 |
| ③ 검출 → 명령 ACK | 추론이 끝나면 **즉시** `STOP` 을 보내고 그 `seq` 의 ACK 를 기다린다 |

⚠️ **로봇은 움직이지 않는다.** `STOP` 은 `move(0,0)` 이고 서 있는 로봇에게는 아무 일도
일어나지 않는다. 2026-09-09 기준선도 같은 방식이었다.

⚠️ **표본이 아닌 프레임에도 `STOP` 을 보낸다.** 표본만 보내면 간격이 온보드 300ms 명령
타임아웃을 넘겨 측정 도중에 로봇이 잠긴다. 전 표본 `applied=true` 를 확인했다.

⚠️ **ACK 를 `seq` 로 고른다.** 같은 소켓으로 10Hz 텔레메트리가 함께 들어오므로, 첫 전문을
ACK 로 세면 **텔레메트리 도착 시각을 지연이라고 적게 된다.**

## 2. 결과

2차 실행(`--count 16 --every 7`)에서 16 표본을 받았고 그중 **카운터를 확정할 수 있는 4장**으로
사슬을 닫았다. ②③ 은 16 표본 전부 있다.

| 구간 | min | mean | p95 / max |
| --- | ---: | ---: | ---: |
| ① 촬영 → 도착 | 67 | 78.2 | 88 |
| ② 도착 → 검출 완료 | 10 | 15.8 | 29 |
| ③ 검출 → 명령 ACK | 3 | 4.5 | 6 |
| **합계 (프레임마다 먼저 더한 값)** | **81** | **98.5** | **121** |

**최악 프레임 121ms / 예산 250ms → 충족.**

같은 날 1차 실행(n=6)은 합계 **87~132ms · 평균 98.0ms** 였다. **두 판의 평균이 98ms 로
일치**하는 것이 이 값의 가장 강한 근거다. ⚠️ 1차의 프레임 원본은 2차 실행 전에 지워서
남아 있지 않다 — 재현은 2차 자료로 한다.

### ⚠️ 여기에 틱 대기가 빠져 있다

이 도구는 추론이 끝나면 **틱을 기다리지 않고 즉시** 보낸다. 실제 런타임은 명령을 10Hz
틱에 실으므로 **최악 100ms** 가 더 붙는다.

```
측정 최악          121 ms
+ 틱 대기 최악     100 ms
───────────────────────────
런타임 경로 최악   221 ms   (예산 250ms · 여유 29ms)
```

**줄일 수단이 있다** — 인지 반응(`ALERT` 진입)을 `ESTOP` 처럼 즉시 송신으로 빼면 그 100ms
가 사라진다. 규약상 10Hz 고정 송신은 하트비트이므로 사이에 한 건 더 보내도 문제없다.

## 3. 2026-09-14 기록의 278ms 정정

이전 문서는 구간 합산 상한을 **278ms** 로 적고 *"상한 조합이 이미 250ms 를 넘는다"* 고
남겼다. **세 가지가 함께 틀렸다.**

| # | 무엇이 틀렸나 |
| --- | --- |
| ① | **겹치는 구간을 두 번 더했다.** `69ms` 의 원래 정의는 아키텍처 2절의 *"프레임의 **호스트 도착**부터 JPEG 디코드와 `STOP` 적용 ACK 까지"* 인데 *"판정 → 명령 적용 ACK"* 로 적었고, 그 위에 *"호스트 도착 → 판정 완료 35ms"* 를 따로 더했다. 디코드 구간이 중복 계상됐다 |
| ② | **서로 다른 날·조건의 p95 를 더했다.** 실제로는 일어나지 않는 경로다. 합은 **프레임마다 먼저 더한 뒤** 분포를 봐야 한다 |
| ③ | **물리 구동을 예산에 넣었다.** `NFR-1.1` 은 명령 적용 ACK 에서 끝나고 물리 구동은 `NFR-1.4`(명령 → 서보 ≤50ms) 소관이다. 아키텍처가 *"세 값을 섞어 250ms 하나로 판정하면 통신·인지·기계 응답 중 어디를 고쳐야 하는지 알 수 없다"* 고 미리 적어 두었다 |

그리고 `69ms` 로 잡고 있던 자리(③)의 실측은 **3~6ms** 다. 20배 차이다.

## 4. 이 측정의 한계

- **사슬을 닫은 표본이 4장이다.** 칸이 꽉 찬 순간이 **자릿수가 넘어가는 순간과 겹쳐** 숫자에
  잔상이 생기고, 그런 프레임은 버렸다. 카운터에서 고칠 수 있다 — 자릿수 갱신 위상을 반 칸
  밀면 칸이 꽉 찰 때 숫자가 안정된다. **다음 측정 전에 고친다.**
- 숫자·칸은 **눈으로 읽는다.** 칸 단위라 ±10ms 다. OCR 을 넣지 않은 이유는 인식 실패가
  측정 오차로 섞이기 때문이다.
- 모니터 양자화 ±16.7ms(60Hz).
- 단일 기체·단일 AP·실내·정지 상태다. **보행 중 측정이 아니다.**
- 물리 구동(`NFR-1.4`)은 여전히 미계측이다. 로봇 구동 승인이 필요하다.

## 5. 판정에 미치는 영향

`M2` 검수 기준 ③(*"E2E 인지 지연 250ms 이하 측정치 제시"*)은 **충족**으로 본다.
근거는 위 표와 두 판의 일치이며, 틱 대기를 더한 런타임 경로(최악 221ms)도 예산 안이다.

⚠️ **여유가 29ms 뿐이다.** 해상도·추론 모델·AP 환경이 바뀌면 다시 잰다.
