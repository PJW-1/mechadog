## ① 양방향 보정 — 기각

배터리가 두 구간에서 **7.59V / 7.56V** 로 같아 좌우 비교가 성립한다.

| | **우측** (02:22:15~23) | **좌측** (02:24:00~06) |
| :--- | ---: | ---: |
| 편차 | 109.4px | 168.2px |
| 보정 전 raw 각 | 4.96° | 9.16° |
| **실제 나간 명령** | **9.96°** (2.01배 증폭) | **4.16°** (0.45배 감쇠) |
| 실제 회전 | **−4.02 °/s** | **+1.49 °/s** |
| 영점(−5.0)에서 거리 | 4.96° | 9.16° |
| **이득** (회전 ÷ 영점거리) | **0.811** | **0.163** |

**5.0배 비대칭.** 좌측은 편차가 **더 큰데(168 vs 109) 회전은 더 느리다.** 실제로
**7초 동안 편차가 163~175px 에 붙박여** 수렴하지 않았다.

### 계산이 왜 틀렸나

곡선 대입(2026-09-18)은 **«명령 → 회전율»** 만 봤다. 양방향은 그 **앞단에서 명령
자체를 가른다** —

```
좌  raw 9.16  + (-5.0) = 4.16   (0.45배)
우  raw -4.96 + (-5.0) = -9.96  (2.01배)
                          ↑ 명령 단계에서 이미 2.4:1
```

명령에서 벌어진 것을 곡선이 다시 벌린다. **모델의 입력을 틀리게 넣은 것이지 곡선이
틀린 것이 아니다.**

### 지금 코드가 낫다는 것도 같은 데이터가 말한다

우선회는 **두 방식이 완전히 같은 명령**(−9.96)을 낸다 — 보정 부호가 같아 어차피
더해지기 때문이다. 좌선회만 9.16 vs 4.16 으로 갈린다. 즉 **양방향은 우측을 전혀
개선하지 못하면서 좌측만 깎는다.**

→ `host/behavior/tracker.py` 원복. 커밋할 것 없음.

## ⚠️ 곡선과 추종이 안 맞는다 — 새로 열린 물음

영점 기준으로 정규화한 이득을 비교하면:

| | 곡선 (지속 조향 · 8.6~7.6V) | 오늘 추종 (7.56V) |
| :--- | ---: | ---: |
| 우 | 0.269 ~ 0.343 | **0.811** |
| 좌 | 0.280 ~ 0.334 | **0.163** |

**곡선은 «영점 기준 좌우 거의 대칭» 이라고 말하는데 추종에서는 5배가 벌어진다.**
짚이는 것 둘 — **모두 미확인이다**:

- **배터리** — 곡선은 8.6→7.6V, 오늘은 **7.56V 로 바닥**. 서보 토크가 방향별로 다르게
  죽을 수 있다.
- **지속 vs 과도** — 곡선은 한 각도를 수 초 유지하며 쟀고, 추종은 100ms 마다 각이
  바뀌어 걸음이 자리를 못 잡는다. 09-18 기록의 *"선회율은 창 길이에 따라 커진다"* 와
  같은 현상일 수 있다.

⚠️ **오늘 좌측은 «양방향» 으로만 쟀다 — 지금 코드(우선회만)의 좌측 숫자가 없다.**
다음에 잴 것은 **bias 값이 아니라 그 숫자**다 (아래 6절).

## ② coast / `track_gap_ms` — 1000ms 유지

```
n=37 (1초 평균)   중앙값 100ms   최소 77   최대 1382
77 77 77 79 80 83 84 89 90 91×6 99 100×10 109 110 111×3 112 114 │ 167  297  807  1382
└────────── 정상 대역 (비전 유효 ~10Hz) ──────────┘             └──── 공백 ────┘
```

추적기가 실제로 끊은 지점은 **1001 ~ 1123ms** — coast 상한 직후 정확히 끊긴다.
상한이 **807ms 는 살리고 1382ms 는 버린다.** 807ms 구간에서 추종이 이어진 것을
확인했으므로 그 선이 맞다.

⚠️ **1초 평균이라 진짜 최악값은 여전히 가려진다.** 지금 지표로 아는 것은 *"어떤 1초의
평균이 1382ms"* 까지다. 최악값이 필요하면 요약에 `max` 를 함께 실어야 한다.

## ③ 순찰 시작 시 사람 인지 — 구멍이었다

첫 판(`run.log`)이 통째로 무효가 된 이유다.

```
02:07:16 [IDLE]   person_gate · present=True       ← 사람이 이미 보임
02:07:18 [PATROL] fsm_transition · IDLE → PATROL   ← 게이트가 이미 True
                                                      상승엣지 없음 → PERSON_FOUND 안 나감
02:07:18~46                                        ← 검출 초당 10~40건인데 ALERT 0회
```

`PERSON_FOUND` 는 게이트의 **상승 엣지**로만 나간다(`runtime.py`). 전이표에
`PATROL --PERSON_FOUND--> ALERT` 가 멀쩡히 있어도 **사건이 안 가면 도달하지 못한다.**
2026-09-18 의 `ALERT` 33초 갇힘과 **같은 종류의 엣지 기억 문제**다.

고침 뒤 재확인 —

```
02:23:51 [PATROL] fsm_transition · IDLE → PATROL   trigger=START_PATROL
02:23:51 [ALERT]  fsm_transition · PATROL → ALERT  trigger=PERSON_FOUND    ← 같은 초
```

사람이 화면 중앙(편차 **1.56px**)에 선 채로 시작했는데 같은 초에 잡았다.

⚠️ **재장전은 임무 밖(`STANDBY`)에서 들어올 때만이다.** 모든 `PATROL` 진입에서
재장전하면 **인증을 통과한 사람이 곧바로 다시 경보를 올린다** — `AUTH_WAIT → PATROL`
복귀 틱에 그 사람이 아직 화면에 있기 때문이다. 시험이 잡았다.

## 다른 기체를 위한 절차 (일반화)

이 판에서 쓴 방법은 기체와 무관하게 재사용된다.

1. **좌우를 한 런에서 이어서 잰다.** 배터리가 구간 사이에 0.1V 이상 떨어지면 비교가
   흐려진다. 오늘은 7.59 / 7.56 이라 성립했다.
2. **이득은 «명령» 이 아니라 «영점에서 떨어진 거리» 로 정규화한다.**
   `이득 = |yaw| / |명령 − yaw_zero_angle_deg|`. 영점이 0 이 아닌 기체에서 명령 그대로
   나누면 좌우가 가짜로 비대칭하게 보인다.
3. **교차 구간을 잘라낸다.** 대상이 화면 중앙을 지나는 동안은 명령이 0 근처라 평균에
   섞으면 이득이 희석된다. 편차·명령이 안정된 창만 쓴다(오늘은 각 7~9초).
4. **모델을 바꿀 때는 «명령 단계» 와 «회전율 단계» 를 나눠 본다.** 오늘 계산이 틀린
   이유가 정확히 이것이다 — 곡선만 보고 명령 변화를 빼먹었다.
5. **게이트가 엣지인지 레벨인지 확인하고 시작한다.** 순찰 전에 대상이 이미 보이면
   엣지 사건은 영영 안 온다. 실기 전에 *"대상이 없는 상태에서 시작하는가"* 를 정해 둔다.
