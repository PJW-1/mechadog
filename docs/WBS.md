## 이 문서를 읽는 방법

**이 문서는 "할 일을 잘게 쪼갠 목록"이다.** 프로젝트의 모든 작업이 `3.1.1` 처럼 번호로 있고,
그 번호가 브랜치명·커밋·PR 에 그대로 쓰인다.

| 여기 나오는 말 | 뜻 |
| :--- | :--- |
| **워크패키지** | 쪼갠 것의 **최소 단위.** 반나절~하루 반 분량. 이보다 크면 더 쪼갠다 |
| **공수 · M/D** | 일이 얼마나 드는지. **1 M/D = 한 사람이 하루(8시간)** |
| **DoD** | *"이걸 만족하면 끝"* 의 기준. **"구현 완료" 는 DoD 가 아니다** — 확인할 수 있어야 한다 |
| **R** | 그 일의 **책임자** (A · B · C 는 작업 성격 분류. 실제 인원 배정은 4절) |
| **선행** | 이게 끝나야 시작할 수 있는 작업 |
| **롤업** | 쪼갠 것들을 **다시 합쳐 총량을 보는 것** (4절) |
| **게이트 (G0~G3)** | 단계마다 있는 **합격 심사.** 통과해야 다음으로 간다 |

> **어디를 봐야 하나** — 내가 맡은 일이 궁금하면 **4절 담당자 기준**, 언제 하는지는 **6절 일정**,
> 무엇을 만들면 되는지는 **3절 사전(Dictionary)**. 모르는 용어는 [용어 사전](GLOSSARY.md).

## 0. 작성 규칙

| 규칙 | 적용 |
| :--- | :--- |
| **분해 축** | 산출물 기준 7개 대분류. 단계(마일스톤) 정보는 5절 매핑표에서 별도 관리한다 |
| **100% 규칙** | 하위 노드의 합 = 상위 노드. 본 WBS에 없는 작업은 프로젝트 범위 밖이다 |
| **워크패키지 크기** | 0.5 ~ 1.5 M/D (4~12시간). 이를 넘으면 분해한다 |
| **결과물 중심** | 상위 레벨은 명사형 산출물, 최하위 워크패키지만 동사형을 허용한다 |
| **완료 기준 필수** | 모든 워크패키지에 검증 가능한 DoD를 명시한다. "구현 완료"는 DoD가 아니다 |
| **일정과 분리** | 본 문서는 범위 분해다. 시간축 배치는 6절에서 별도로 다룬다 |
| **추적성** | 모든 워크패키지는 PRD의 FR/NFR ID와 연결된다 (7절 역참조) |

### 3.0과 4.0의 구분 기준

두 대분류의 경계가 모호해지기 쉬우므로 아래 기준을 적용한다.

| 대분류 | 판단 기준 | 예시 |
| :--- | :--- | :--- |
| **3.0 판단 로직 및 핵심 기능** | **무엇을 할지 결정하는 규칙과 알고리즘.** 하드웨어·프레임워크에 비의존적이며 단위 시험이 가능함 | 상태 전이 규칙, 안전 판정 조건, 추론 로직, 메시지 규약 |
| **4.0 소프트웨어 및 화면** | **그 결정을 실행하고 표시하는 구현체.** 프레임워크·하드웨어에 의존함 | 펌웨어 골격, UDP 송수신, 대시보드 서버·UI, 로거 |

> 이 구분은 6.2 단위 시험의 대상 범위와도 일치한다. **3.0의 산출물은 하드웨어 없이 pytest로 검증 가능해야 한다.**

## 1. 팀 구성 및 역할 (기능별 수직 분할)

| 역할 | 담당 영역 | 주 기술 스택 | 계획 공수 |
| :--- | :--- | :--- | ---: |
| **A · 임베디드** | 하드웨어 검증, 모션 펌웨어, 온보드 안전 로직, 펌웨어 CI | Arduino / C++17 / ESP32 | **17.0 M/D** |
| **B · 인지·AI** | 비전 노드, 스트림 수신, 객체 검출 추론, 대시보드 화면, 성능 튜닝 | Python / OpenCV / ONNX Runtime | **16.0 M/D** |

> ⚠️ **A/B/C 는 작업 성격 분류이며 인원 배정과 1:1 대응하지 않는다.** 실제 인원 배정은 **담당자 기준** 절을 따른다 — 팀장이 A·B·C 의 소프트웨어 전부를 담당하고, LiDAR·공간 파트에 2인이 배정된다.
| **C · 시스템·통합** | 통신 규약, FSM, 대시보드 서버, CI/CD, 문서·일정 관리 | Python / FastAPI / GitHub Actions | **18.5 M/D** |

> C의 공수가 약 10% 높은 것은 **인터페이스 정의(3.1)와 통합 검수(6.4)를 함께 담당**하기 때문이다. 3주차 리뷰에서 편차가 벌어지면 4.4(설정·로깅) 또는 5.3(CI)을 재배분한다.
>
> **설계 의도** — 인터페이스의 주인과 통합의 주인을 같은 역할에 둔다. 합류 지점에서 책임 소재가 흐려지는 것을 방지하기 위함이다.

### RACI 표기

| 기호 | 의미 |
| :---: | :--- |
| **R** | Responsible — 실제 수행자 (공수가 집계되는 역할) |
| **A** | Accountable — 최종 승인자 |
| **C** | Consulted — 사전 협의 대상 |
| **I** | Informed — 결과 공유 대상 |

### 부하 — 팀장 집중은 **임시적**이다

| 인원 | 원공수 | AI 보조 반영 | 가용 (20일) | 부하율 |
| :--- | ---: | ---: | ---: | ---: |
| L1 | ~11.3 | ~7.5 | 20.0 | 38% |
| L2 | ~11.3 | ~7.5 | 20.0 | 38% |
| **S (팀장)** | **~49.0** | **~30** | **20.0** | **150% ← 임시 피크** |
| **합계** | **70.0** | **~45** | **60.0** | **75%** |

> **150% 는 4주 평균이 아니라 3주차 피크값이다.** 그리고 **그 시점이 정확히 L1·L2 의 펌웨어가
> 끝나 여력이 생기는 시점**이다. 즉 편중은 일정에 내재된 **일시적 상태**이며, 이동으로 해소된다.

#### 주차별 부하 추이

| 주차 | 마일스톤 | L1 · L2 | S (팀장) |
| :---: | :--- | :--- | :--- |
| **1** | **M0** 하드웨어 검증 | **높음** — 2.0 전체(6.0) + 5.1 환경 + 2.1.1 Wi-Fi | **중간** — 3.1 프로토콜 · 6.1.1 목업 · 4.4.1 config |
| **2** | **M1** 제어 링크·페일세이프 | **높음** — 4.1 펌웨어 + 3.2 온보드 안전로직 | **중간** — 4.3 통신 · 3.4 FSM · 4.5 대시보드 서버 |
| **3** | **M2** 비전 파이프라인 | **낮음** → **이동 발생** | **⚠️ 피크** — 3.3 비전 · 3.7 PPE · 4.6 화면 · 6.3 측정 |
| **4** | **M3** FSM 통합 | 중간 — 검수 지원 · [P2] SLAM | 높음 — 통합 · 행동 튜닝 |

**1~2주차는 세 사람이 고르게 붙는다.** 하드웨어 검증과 펌웨어가 L1·L2 를 채우고, 팀장은 그 사이에
프로토콜·목업·통신 기반을 깐다. **편중이 나타나는 것은 3주차뿐이며, 그때 L1·L2 의 펌웨어가 끝난다.**

> ⚠️ **다만 이동이 자동으로 일어나지는 않는다.** 사람이 "지금 넘긴다" 고 말해야 한다.
> 그래서 아래 트리거를 **조건이 아니라 시점으로** 정의한다.
>
> 그리고 **이동은 왕복이다** — 게이트를 통과해 LiDAR 가 도착하면 L1·L2 는 Phase 2 로 돌아간다.
> 넘긴 작업은 **그 전에 끝나는 크기**여야 한다(아래 대상 선정 기준).

## 8. 다중 개체 운용 계획

### 전제 — MechDog 3대 (팀원 각 1대 보유)

하드웨어 점유 경합이 없어 **3인이 각자 실기 테스트를 병렬 수행**할 수 있다. 다만 개체가 늘면 별도 문제가 생기며, 관리하지 않으면 "내 로봇에서는 되는데"로 통합 단계에서 시간을 잃는다.

### 개체차 대응

| 문제 | 원인 | 대응 |
| :--- | :--- | :--- |
| **서보 영점 편차** | 개체마다 `MechDog_offset[9]` 값이 다름 | **2.4.1** 개체 프로파일로 분리 |
| **보행 이동량 편차** | 조립 공차·바닥 마찰 | 개체 프로파일에 gait odometry 계수 포함 (Phase 2 FR-6.4 직결) |
| **배터리 상태 편차** | 충전 이력·셀 노화 | 저전압 임계는 공통 유지. 잔량 추정은 보수적으로 판정 |
| **검수 재현성 상실** | 3대 각각 통과 ≠ 통합 통과 | 👇 기준기 규칙 |

### 기준기(Reference Unit) 규칙

| 규칙 | 내용 |
| :--- | :--- |
| **기준기 지정** | 3대 중 1대를 **기준기(REF)** 로 지정한다. 2.4.1에서 결정하고 물리적으로 표시한다 |
| **검수는 기준기에서만** | 게이트 검수(6.4.1 / 6.4.2 / 6.4.3)는 **반드시 기준기에서** 수행한다. 개발기 통과는 검수로 인정하지 않는다 |
| **개체 프로파일 필수** | 모든 실기 실행은 `--device <unit-id>`로 자신의 프로파일을 명시한다 (4.4.1) |
| **개체 ID 로깅** | 구조화 로그에 `device_id`를 포함한다 (4.4.2) |
| **성능 수치의 출처** | NFR 측정치는 기준기 실측값으로 문서화하고, 개체별 편차는 참고치로 병기한다 |

### 기준 PC(Reference PC) 규칙 — ⚠️ 임시

로봇과 마찬가지로 **PC 사양도 개체별로 다르다.** 성능 수치의 출처를 고정하지 않으면 보고서에 쓸 숫자가 정해지지 않는다.

| 항목 | 규칙 |
| :--- | :--- |
| **기준 PC** | **팀장 PC** — 역할 배정으로 추론 부하가 팀장에게 모였으므로, **가장 강한 GPU 를 팀장이 쓰고 그 PC 를 기준으로 삼는다.** 팀장 PC 사양 확인만 남았다 (OI-14) |
| **선정 근거** | **파이프라인을 돌리는 사람이 한 명뿐이므로 "가장 약한 머신" 규칙이 불필요해졌다.** 이전에는 3인이 각자 추론을 돌릴 것을 전제해 낮은 쪽을 기준으로 삼았으나, 이제 팀장 PC 가 유일한 추론 환경이다 |
| **재검토 조건** | LiDAR 파트 조기 종료로 **1명이 소프트웨어로 이동해 추론을 돌리게 되면**, 그 PC 에서도 NFR 을 재측정하여 참고치로 병기한다 |
| **NFR 측정은 기준 PC에서만** | NFR-1.1(E2E 250ms) · NFR-1.2(추론) · NFR-1.3(15fps) 측정치는 **기준 PC 실측값**으로 문서화한다. 타 PC 값은 참고치로 병기 |
| **환경 기록 의무** | 성능 리포트(6.3.1)에 GPU 모델 · EP · 드라이버 버전을 함께 기록한다 |

### 역할별 GPU 요구 수준

| 인원 | 추론 부하 | GPU 요구 | 배정 결과 |
| :--- | :--- | :---: | :--- |
| **S · 소프트웨어 (팀장)** | 모델 선정·학습·비전 파이프라인·성능 튜닝 전부 | **높음** | **가장 강한 GPU 가 필요하다** |
| **L1 · 공간·항법** | `slam_toolbox` 는 CPU 연산 | 낮음 | GPU 무관 |
| **L2 · 하드웨어·측위** | 없음 | **낮음** | GPU 무관 |

> **인원 배정이 GPU 요구를 단순화했다.** 추론 부하가 팀장 한 사람에게 모였으므로,
> **팀 내 가장 강한 GPU 를 팀장이 쓰면 된다.** 다른 두 명은 GPU 사양이 성능에 영향을 주지 않는다.
>
> 다만 **기준 PC(성능 수치의 출처) 규칙은 그대로 유지한다** — NFR 측정치는 한 대에서 뽑아 문서화하고
> 타 PC 값은 참고치로 병기한다. 팀장 PC 가 가장 강하다면 **기준 PC 는 팀장 PC 가 된다**(OI-14 갱신 필요).

> **참고** — 기준 PC(RTX 3080)는 본 프로젝트에 성능상 충분하다. 가장 무거운 조합(개방 어휘 검출기 + PPE 모델 + 디코드)을 골라도 프레임 예산 66.7ms 안에 들어온다. GPU는 병목 순위에서 최하위다(사람 공수 → 탑재중량 → Wi-Fi 대역 → … → GPU).

### 네트워크 동시 운용

| 항목 | 규칙 |
| :--- | :--- |
| IP 할당 | 개체별 고정 IP 또는 DHCP 예약. 2.4.2 할당표에 기록 |
| 포트 할당 | 명령·텔레메트리 포트를 개체별로 분리 (예: `500X` / `510X`, X = 개체번호) |
| 대역 경합 | **3인이 동시에 MJPEG를 스트리밍하면 2.4GHz가 포화된다.** ESP32/ESP32-S3는 **2.4GHz 전용**이므로 로봇 링크를 5GHz로 옮길 수 없다. ① 시간대 분리 ② Host PC를 5GHz/유선으로 붙여 AP의 2.4GHz 부하 절감 ③ 개발 전용 AP로 채널 분리 ④ 해상도·fps 적응 조절 (PRD RISK-05) |

### 6.1.1 목업의 존재 이유

하드웨어 병목이 없으므로 "대기 시간 해소" 목적은 해당되지 않는다. 그럼에도 필요한 이유는 둘이다.

1. **CI 러너에는 로봇이 없다** — 5.3.1 Python 품질 잡이 성립하려면 목업이 필수다
2. **안전 시나리오를 실기로 재현하기 어렵다** — 저전압·전도·패킷유실을 실물에서 반복 재현하는 것은 위험하고 느리다. 6.2.1·6.2.2 검증의 실질적 수단이다

### 제외 범위 (Out of Scope)
