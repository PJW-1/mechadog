## 0. 하드웨어 예산 — RTX 5070 (VRAM 12 GB) 기준

동시에 올라가는 것만 더한다. 오프라인 작업(음원 합성·학습)은 예산 밖이다.

| 구성 | 용도 | VRAM (추정) | 비고 |
| :--- | :--- | ---: | :--- |

## 1. PPE 이미지 모델 (`3.7.x`) — 추천안

### 1.1 계열 결정: **YOLOX-Nano** (직접 학습)

| 후보 | 판정 | 이유 |
| :--- | :--- | :--- |
| **YOLOX-Nano/Tiny** | ✅ **추천** | Apache-2.0 · ①번과 동일 계열이라 **어댑터 재사용**(`ADAPTERS["yolox"]`) · 공식 `tools/export_onnx.py` 로 ONNX 바로 추출 |
| Ultralytics YOLOv8/11n | ❌ | **ADR-24 가 이미 탈락시켰다** — AGPL-3.0 은 팀 코드 전체의 공개 의무다. ⚠️ WBS `3.7.2` 의 *"ultralytics 버전과 하이퍼파라미터를 기록"* 은 이 결정과 충돌하는 잔재로 **정정 필요** (아래 5절) |
| RTMDet-tiny (mmdet) | △ | Apache-2.0 · 정확도 좋지만 export 에 MMDeploy 필요 — ADR-24 가 같은 이유로 이미 버림 |
| 색상 휴리스틱 단독 | △ 보조 | 학습 없이 HSV 비율로 판정 — 아래 1.5 의 **베이스라인/라벨링 보조**로는 유효, 단독은 조명·원근에 취약 |

**YOLOX-Nano 인 이유** — 4클래스·작은 입력이면 nano 급 용량이면 충분하고, 2단 모델은
사람 프레임에서만 돌아가므로 프레임당 비용이 사실상 없다. 학습 프레임워크가
`coco.onnx` 와 같아 **전처리·디코딩 규약을 공유**한다 — 어댑터는 이미 클래스 수를
`raw.shape[1] - 5` 로 일반화해 두어 **4클래스 출력도 그대로 동작한다**(학습 후 시험으로 확인).

### 1.2 데이터셋 설계 (3.7.1 · OI-13)

> **OI-13 결정 (2026-09-15) — 이 절의 제안과 다르다.** 학습 주체는 **공개 데이터셋**이고, XIAO 실사는 **검증·시험 세트부터** 모은다. 실사를 학습에 섞는 것은 검증 성능이 모자랄 때다. 아래 *"자체 촬영이 주 데이터"* 와 촬영 물량(클래스당 300~500)은 채택하지 않았다. 촬영 조건표·라벨링 규약은 검증셋을 찍을 때 그대로 쓴다.

⚠️ **자체 촬영이 주 데이터다.** 공개 PPE 세트는 전부 *눈높이 CCTV·작업자 시선* 사진이다.
우리 카메라는 **높이 15cm 에서 위를 본다** — 같은 물체도 형태·비율·배경이 완전히 다르다.
공개 데이터로만 학습한 모델은 우리 화각에서 도메인이 안 맞는다.

| 소스 | 목표 물량 | 용도 |
| :--- | :--- | :--- |
| **자체 촬영 — XIAO 실기** | 클래스당 **300~500 프레임** (합계 1,200~2,000) | 학습 주체. 팀 계획의 "안전모×3·조끼×3 를 3개 장소에서" 그대로 |
| 공개 세트 (사전학습·증강) | 3,000~8,000 장 | 다양한 사람·자세·배경의 범용성 + 네거티브 |
| **검증셋** | 자체 촬영분 중 **홀드아웃 20%** (장소·인물 겹침 없이 분리) | mAP·리콜 판정은 **이 세트로만** |

**자체 촬영 조건표** — 촬영 전 팀원에게 돌린다.

| 축 | 반드시 포함할 변형 |
| :--- | :--- |
| 장소 | 3개소 (조명·배경 상이) — **장소별로 검증셋을 갈라 데이터 누수를 막는다** |
| 거리 | 1m · 2m · 3m (판정 가능 조건 FR-9.2 기준) |
| 자세 | 정면·옆·뒤 · **웅크림**(FR-9.3 필수) · 팔 들기·몸 기울이기 |
| 착용 조합 | 안전모+조끼 / 안전모만 / 조끼만 / 둘 다 없음 — **4조합이 라벨의 정답지** |
| 기타 | 머리가 프레임 상단에 잘리는 샷(판정 보류 경로 검증용) · 조명 어두움·역광 |

**라벨링 규약** — 클래스 경계를 미리 못 박는다.

| 클래스 | 정의 | 경계 사례 |
| :--- | :--- | :--- |
| `helmet` | **머리에 쓴 안전모의 bbox** (사람 머리가 아니라 모자 영역) | 손에 든 안전모는 라벨하지 않는다 — 착용만 |
| `no_helmet` | **안전모를 안 쓴 머리의 bbox** | 후드·모자·헤어 전부 `no_helmet` — "안전모가 아닌 것"으로 통일 |
| `vest` | 몸통에 걸친 조끼 bbox | 가방끈·하네스는 조끼가 아니다 — 형광 조끼 형태만 |
| `no_vest` | 조끼 없는 몸통 bbox | 반팔·긴팔·점퍼 전부 해당 |

⚠️ **`no_*` 는 "해당 물건이 없는 신체 부위" 에 라벨한다.** 배경에 라벨하면
"아무것도 없는 곳" 이 위반으로 학습된다 — PPE 세트에서 가장 흔한 실수다.

**공개 데이터 후보** (라이선스 확인 후 데이터 카드에 기록):
- SHWD (Safety Helmet Wearing Dataset, ~7.5k) — `hat`/`person` 2클래스 → `helmet`/`no_helmet` 매핑
- Roboflow Universe "PPE/vest detection" 다수 — **각 데이터셋의 라이선스를 개별 확인**한다 (CC-BY·CC-BY-NC 혼재, NC 는 제외)

### 1.3 학습 하이퍼파라미터 (시작점 — `3.7.2` 산출물에 그대로 기록)

| 항목 | 값 | 이유 |
| :--- | :--- | :--- |
| 모델 | YOLOX-Nano, **공식 COCO 가중치에서 fine-tune** | 4클래스 처음부터 학습은 데이터가 모자라다 |
| 입력 | 640×640 | `coco.onnx` 와 동일 — 어댑터·letterbox 공유 |
| epochs | **100** (early stop patience 20) | 1.2k~2k 장이면 60~80 에 수렴하는 게 보통 |
| batch | 16 | RTX 5070 기준 nano 는 32 도 들어가나 16 이 안전 |
| optimizer | SGD momentum 0.9 · lr 0.01 (cosine decay, warmup 5ep) | YOLOX 공식 레시피 |
| augmentation | HSV(±0.015/0.7/0.4) · scale 0.5 · translate 0.1 · flip 0.5 · mosaic 1.0, **마지막 15ep mosaic OFF** | ⚠️ **색 채도 증강은 약하게** — 주황·형광이 판정 단서인데 색을 크게 흔들면 특징을 지운다 |
| 평가 | mAP50 + **클래스별 recall** | 아래 임계값 근거 |

### 1.4 임계값·판정 상세 (가중치 아닌 **운용 수치**)

| 값 | 초기값 | 근거·조정 규칙 |
| :--- | :--- | :--- |
| `vision.ppe.conf_threshold` | **0.5** (config 기존값 유지) | ⚠️ 조정 기준은 mAP 가 아니라 **`no_helmet`/`no_vest` recall ≥ 0.90** — *"위반을 통과로 읽는 것"* 이 최악의 오류다. recall 이 부족하면 임계를 0.4 까지 내려 재측정 |
| `vision.ppe.iou_threshold` | 0.45 | coco 와 동일 |
| `head_margin_px` | 8 (config 기존값) | person bbox 상단이 프레임 경계 8px 이내 → **판정 보류** (`require_head_visible`) |
| 판정 윈도우 | **시간 창 1.5초 안 위반 3히트** (신규 제안) | `person` 게이트와 같은 구조(ADR-25) — 단발 오검출 1장으로 경고를 내지 않는다 |
| 위반 해제 | 창이 완전히 빌 때 | 진입·해제 비대칭 — 게이트 떨림 방지 |
| 정지 대상 조건 | `ppe.static_threshold_px` / `static_frames` (config 기존) | 움직이는 사람은 추종 불가 — 판정은 대상 정지 시에만 |

### 1.5 색상 휴리스틱 — 베이스라인 겸 반자동 라벨러

주황 안전모 + 연두 형광조끼는 **학습 없이도 HSV 에서 잘 분리되는 색**이다. 쓸 곳 둘:

1. **자체 촬영분 1차 라벨링** — person bbox 상위 25%(머리대)의 주황 비율, 중간 55%(몸통)의
   연두 비율로 초안 라벨을 달고 사람은 검수만 한다 → 라벨링 공수를 크게 줄인다
2. **모델의 대조군·백업 판정** — "색만으로 되는데 왜 학습하나" 를 실측으로 답하는 근거.
   조명 변화·원근 왜곡에서 어디서 깨지는지 기록해 두면 모델 필요성이 정량화된다

### 1.6 ONNX export · 연동

- `YOLOX/tools/export_onnx.py --output-name ppe.onnx --opset 11 --input 640` (고정 batch 1)
- `config.yaml`: `vision.ppe.model_family: yolox` · `model_path` 기존값 · **학습 버전·날짜·데이터셋 커밋/해시를 주석으로** (FR-9.1.2 재현성)
- 배선: `worker` 가 person 확정 프레임에서만 `ppe_detector.detect(person_crop)` 호출 — **풀프레임이 아니라 person bbox 크롭**을 넣는다 (2단 구조의 취지: 입력이 작아져 정확도·속도 둘 다 이득)

### 2.2 용도 경계 — **판정에는 쓰지 않는다** (기존 원칙 유지)

`wonderecho-audio/README.md` 의 결정과 일치한다: **LLM 은 이름을 지어낼 수 있다.**
실제 Whisper 가 무음을 감사 멘트로 환각시킨 전례(`no_speech_prob 0.753`)가 있다.

| LLM 에 맡긴다 | 규칙 기반으로 남긴다 (LLM 금지) |
| :--- | :--- |
| 자유 발화 의도 파악·되묻기 | 신원 판정(`claimed_name` 형식 + 등록 명단 대조) |
| 회사 Q&A 답변 문장 생성 | 로봇 명령 실행(화이트리스트 매핑만, 4.7.11) |
| 순찰 리포트 문장 (4.7.12) | 안전 관련 상태 보고의 **수치** — 텔레메트리 실측 주입(4.7.10) |

⚠️ RAG(4.7.6)는 **문서 검색 결과를 프롬프트에 주입**하고, 검색에 없는 내용은
*"확인되지 않은 정보"* 라고 답하게 프롬프트에 못 박는다 — 모델이 지어내는 것을
막는 유일한 방법은 컨텍스트에 없는 것을 말하지 않게 하는 규칙이다.

## 4. 로컬 VLM (4.8.1 대안) — **보류 권고**

기준·현재 이미지 비교 문장을 로컬로 옮기려면 `Qwen2-VL-2B-Instruct`(GGUF ~2 GB)가
최소 후보다. 다만:

- 위 예산표에서 여유는 ~3 GB — 올리면 **풀가동 시 여유 0**에 가깝다
- 클라우드 VLM(4.8.1)은 *"실패해도 주행에 영향 없음"* 이 이미 설계 원칙이라
  로컬 전환의 이득이 크지 않다
- **권고: 클라우드 유지 + 나중에 VRAM 여유가 생기면(whisper small 전환 등) 재검토**

## 5. 디지털 트윈 — Isaac Sim 합성 데이터 + 시뮬레이션 환경

> ⚠️ **보류 · 저장소에서 제거 (2026-09-15 · #160).** WBS 항목 없이 들어왔고 카메라 화각이 폐기된 값(32°·24°)이었다. 합성 데이터는 OI-13 에서 쓰지 않기로 했다. **아래는 당시 제안 기록이지 현재 계획이 아니다** — 다시 넣으려면 팀 합의와 WBS 등재가 먼저다.

### 5.1 방향 (제안 · 보류)

실사 사람 데이터는 공개 세트에 풍부하다 — 우리가 없는 것은 **로봇 시점의 환경**
이다. 그래서 Isaac Sim 에 환경을 **두 가지 버전**으로 만든다 (5.5 절):

- **공장 씬** — 실사풍 공장 + 사람 + 물건 → PPE 학습 데이터·시뮬레이션
- **라이다 실측 씬** — 실제 공간 재현 → 자율주행 동선 계획·검증

로봇의 15cm 카메라가 씬을 보고, 그 시야는 **웹 스트리밍 + 학습 데이터** 두 곳에 쓴다.

⚠️ **합성 데이터의 역할은 보충이다.** 실사와 섞어 쓰되 단독 학습은 하지 않는다 —
렌더된 사람은 재질·조명·JPEG 특성이 실사와 다르다(도메인 갭). 혼합 비율은
검증셋 성능으로 정한다.

### 5.2 공간 재현 — 라이다 측정값이 씬의 뼈대

```
실제 공간 ──LD19──▶ tools/lidar_slam.py ──▶ OccupancyGrid(2D 평면)
                                            │
                                            ▼
                                     벽을 수직 압출(extrude)
                                     → USD 씬의 벽·기둥·가구 배치
```

- 도구는 이미 있다 — `host/slam/occupancy.py` 의 `OccupancyGrid` 가 셀 단위
  점유 격자를 저장한다. 격자의 점유 셀을 벽 세그먼트로 묶어 씬에 놓는다
- ⚠️ LD19 는 아직 로봇에 배선되지 않았다 — **첫 씬은 줄자 실측 평면도로 시작**하고,
  라이다 지도가 나오면 같은 변환기로 재생성한다. 변환 입력을 "평면도 스펙"
  (`sim/room_spec.yaml`)으로 추상화해 두면 입력원이 바뀌어도 씬 코드는 그대로다

### 5.3 카메라 — 실측값 그대로

| 파라미터 | 값 | 출처 |
| :--- | :--- | :--- |
| 높이 | 15 cm | 실기 설치 |
| 아래 경사 | ~7° | 2026-09-13 실측 추정 |
| 수평 화각 | **~74°** | 2026-09-13 실측 확정 ([측정 요약](measurements/2026-09-13-camera-fov.md)) |
| 수직 화각 | **~59°** | 동일 — ⚠️ 이 문서 초안의 32°·24° 는 마커 배정 오류에서 나온 **폐기된 피팅값**이었다 |
| 해상도 | 640×480 | XIAO 스트림 VGA |

씬의 카메라 prim 에 이 값을 그대로 넣는다 — **시점 재현이 이 작업의 목적이므로
화각 오차가 곧 데이터 오차다.**

### 5.4 사람 + PPE + 라벨 자동 생성

- Isaac Sim 내장 사람 애셋 + **주황 안전모·연두 조끼 재질**을 입힌 변형을 만든다
- Replicator 로 도메인 무작위화: 사람 위치·자세·착용 조합(4종)·조명·배경 텍스처
- **라벨은 Replicator writer 가 자동 생성** — 2D tight bbox. 이것이 생성 이미지
  모델과의 결정적 차이다: 라벨링이 필요 없다
- 출력을 YOLO 형식으로 변환해 `datasets/ppe/images|labels/` 에 합류시킨다 —
  **session 이름을 `sim_v1` 등으로 구분해 출처가 데이터에 남게 한다**

**시뮬레이션이 특히 값어치 있는 케이스** — 실사로 찍기 어려운 것들:
쓰러진 사람 · 몸이 절반 가려진 경우 · 극단 거리 · 머리가 프레임 상단에 잘리는
경계 케이스(판정 보류 경로의 시험 데이터) · 조명 극단(역광·어둠).

### 5.5 두 환경 — 같은 로봇 코드, 환경만 교체 (제안 · 보류)

| 환경 | 내용 | 용도 |
| :--- | :--- | :--- |
| **A. 공장(factory)** | 실사풍 공장 씬 + 사람 + 물건 배치 | **이미지 학습 데이터 생성** + PPE·행동 시뮬레이션 |
| **B. 라이다 실측 환경** | LD19 점유격자로 잰 **실제 공간** 재현 | 자율주행 **동선(route) 계획·검증** — 실기 전에 씬에서 경로를 짜고 돌려본다 |

로봇은 **같은 코드·같은 모델**이고 환경만 바꾼다 — LabKeeper 의 `isaac_hal.py`
패턴과 같다(제어기는 HAL 만 보고, HAL 이 실기냐 시뮬이냐를 가른다).

**15cm 카메라의 역할 둘** — ① 씬 안 로봇 시야를 **MJPEG 으로 웹 스트리밍**
(LabKeeper 가 `:8080/stream` 으로 이미 구현 검증) ② 그 프레임을 그대로
학습 데이터로 저장.

### 5.6 기존 자산 재사용 — LabKeeper 프로젝트 (2026-08)

이전 프로젝트(LabKeeper · 작성자 개인 저장소)의 `robot-sim/` 에
**이 구조 전체를 돌려본 코드가 있다.** 새로 짤 것이 아니라 이식이다:

| 자산 | 이식 대상 |
| :--- | :--- |
| `isaac_project/lab_world.py` + `labkeeper_lab_v2.usda` | 씬을 코드로 조립하는 방식 — 우리 공장/실측 씬에 같은 기법 |
| `ai_vision/generate_isaac_dataset.py` | **헤드리스 렌더 → YOLO 합성 데이터** — 대상 prim·가림체(occluder) 지정 방식 그대로 |
| `isaac_project/isaac_hal.py` | 로봇 HAL — `set_motion` 등 실기와 같은 5메서드 인터페이스 |
| `isaac_project/waypoint_controller.py` + `obstacle_avoidance.py` | **웨이포인트 순찰 + 장애 회피** — B 환경의 동선 실행기 |
| `live_patrol_stream.py` (MJPEG :8080) | 시뮬 카메라 → 웹 스트리밍 |
| `ai_vision/train_yolo.py` · `export_edge_model.py` | 학습·내보내기 파이프라인 참조 |
| `collect_real_lab_data.py` | 실사 데이터 수집 파이프라인 참조 |

⚠️ 차이점: LabKeeper 로봇은 Raspbot(차동구동 바퀴), 우리는 MechDog(사족보행)이다.
시뮬에서 **보행 물리를 흉내낼 필요는 없다** — 이동체는 미끄러지듯 움직여도
되고(카메라 포즈가 전부), 다리는 시각적 형상으로만 둔다. Raspbot 모델 코드
(`raspbot_model.py`)를 참고해 MechDog 치수의 프록시를 만든다.

## 6. 정리 — 이 문서에서 새로 결정을 제안한 것

| # | 제안 | 상태 |
| :--- | :--- | :--- |
| 1 | PPE 계열 **YOLOX-Nano** — WBS `3.7.2` 의 "ultralytics" 문구 정정 필요 | ⬜ 승인 대기 |
| 2 | 데이터셋 **자체 촬영 주체**(클래스당 300~500) + 공개 세트는 보조 | ❌ **다르게 결정** (OI-13) — 공개 세트가 학습 주체, 실사는 검증·시험 |
| 3 | 판정 목표를 mAP 아닌 **`no_*` recall ≥0.90** 로 | ⬜ |
| 4 | 색상 휴리스틱을 라벨링 보조+대조군으로 | ⬜ |
| 5 | LLM **EXAONE-3.5-7.8B** | ✅ **채택·실측 완료** (09-14 종단간 ~1 s) |
| 6 | VLM 은 **로컬 미도입·클라우드 유지** | ⬜ |
| 7 | person bbox **크롭**을 PPE 입력으로 | ⬜ |
| 8 | **디지털 트윈 2환경**: 공장 씬(데이터) + 라이다 실측 씬(동선), 같은 로봇 코드 | ⏸ **보류** — 저장소에서 제거 (#160) |
| 9 | 씬 기하는 **LD19 점유격자 → 벽 압출** (LD19 미장착 전엔 줄자 평면도) | ⏸ 보류 (#160) |
| 10 | 합성 데이터는 **보충용** — 실사와 혼합, 단독 학습 금지 | ❌ 합성 데이터 미사용 (OI-13) |

승인되면 새 ADR(PPE 계열 · ADR-33 은 운용 모드 분리에 썼다)로 정리하고 `config.yaml` 에 반영한다.
LLM·TTS 는 이미 확정·동작 중이라 ADR 대신 이 문서의 실측표가 기록 역할을 한다.
