## 1. 왜 이 결정이 필요한가

Phase 2의 목표는 **자율주행**이다. 자율주행이 성립하려면 세 가지가 필요하다.

| # | 요건 | 본 프로젝트의 현황 |
| :-- | :--- | :--- |
| ① | **자기 위치를 안다** (측위) | ❌ **수단이 전혀 없음** ← 본 문서의 주제 |
| ② | 경로를 스스로 만든다 | ①이 있으면 소프트웨어로 해결 |
| ③ | 장애물을 피한다 | 초음파 반응형 회피 보유 (Tier 1) |

MechDog에는 **바퀴 엔코더가 없고**, 순정 IMU도 접근 가능한지 미확인이다. 즉 "얼마나 움직였는지"를 알 방법이 없다. 측위 수단을 외부에서 도입해야 한다.

**핵심 제약** — 예산 약 30만원, **발주 기회 1회.** 잘못 사면 되돌릴 수 없다. 따라서 **구매 전에 무료로 검증 가능한 것을 모두 검증**한 뒤 결정한다.

## 3. 원리 비교 — 스케일과 드리프트

두 개념을 구분해야 한다. 혼동하면 잘못된 결론에 이른다.

| 개념 | 의미 |
| :--- | :--- |
| **스케일 모호성** | 거리를 **아예 모름**. "3m 앞인지 6m 앞인지" 구분 불가 |
| **드리프트** | 거리는 알지만 **오차가 누적**됨 |

### 왜 카메라 하나로는 스케일을 모르는가

카메라는 **각도만 측정**한다. 장면 전체를 임의의 배율로 확대·축소해도 촬상 결과가 동일하므로, 원리적으로 절대 거리를 복원할 수 없다. (실제 건물 100m 앞 ≡ 모형 건물 1m 앞)

### IMU가 자를 제공한다

가속도계는 **실제 가속도(m/s²)** 를 측정한다. 두 번 적분하면 **실제 이동 거리(m)** 가 나온다.

| | 카메라 | IMU |
| :--- | :--- | :--- |
| 강점 | 방향·구조·형태 (정밀) | **절대 거리 (미터)** |
| 약점 | 절대 거리 모름 | 방향 정밀도, 드리프트 |

두 센서를 융합하는 것이 **VIO(Visual-Inertial Odometry)** 이고, **ARCore가 바로 VIO 시스템**이다. `pose.getTranslation()`의 반환값 단위는 **미터**다.

> **결론: Track B에 스케일 모호성 문제는 없다.** 단안 SLAM의 약점은 IMU 융합으로 해소된다.

### 남는 문제는 드리프트

| | 스케일 | 드리프트 | 루프 클로저 | 실내 정확도 |
| :--- | :---: | :---: | :---: | :--- |
| **A · LiDAR SLAM** | 실측 | 있음 | **있음** (재방문 시 보정) | 수 cm |
| **B · ARCore VIO** | **실측** | 있음 | 약함 | **10~25 cm** (5m 이동 기준) |

**방 하나 규모(약 5×5m)의 실내 시연에서는 두 방식 모두 충분하다.** "위험구역에 도착했다"를 판정하는 데 20cm 오차는 문제되지 않는다.

## 4. 앵커와 마커는 다르다 — 개념 정리

Track B의 앵커(Anchor)를 Track C의 마커와 동일시하는 오해가 발생하기 쉬우므로 명시한다.

```
【 ArUco 마커 (Track C) 】              【 ARCore 앵커 (Track B) 】

  마커가 보일 때만 측위 가능              공간 전체의 자연 특징점으로 상시 측위
  ┌────────────────────┐                ┌────────────────────┐
  │   [마커3]          │                │ ·  ·  · · ·  ·  ·  │ ← 벽 무늬, 가구 모서리,
  │      ↑             │                │  · ·[앵커]· ·  ·   │   바닥 패턴 (특징점 수천 개)
  │   보임 → 측위 OK    │                │ ·  ·  ·  · ·  ·  · │
  │                    │                │  ·  · · ·  ·   ·   │
  │   ← 여기선 위치 모름 │                └────────────────────┘
  └────────────────────┘                 앵커는 이 지도 위에 꽂은
                                          "목적지 핀"일 뿐
  마커 = 측위의 원천                       앵커 = 목표 지정 수단
```

| | ArUco 마커 | ARCore 앵커 |
| :--- | :--- | :--- |
| **위치를 아는 근거** | **마커 그 자체** | **공간 전체의 자연 특징점** |
| 대상이 시야에서 사라지면 | **위치 상실** | **계속 측위 유지** |
| 환경 개조 | 인쇄물 부착 필요 | **불필요** |
| 역할 | 측위 + 목표 | **목표만** |

> **중요** — 목표를 사람이 지도 위에 지정하는 것은 **모든 SLAM 시스템의 표준 방식**이다. PRD의 **FR-4.6 Zone Manager**("맵 위에서 위험구역을 지정")가 정확히 같은 개념이다. 앵커 방식은 타협이 아니다.

### 설계 규칙 — 절대 좌표를 쓰지 말고 앵커를 쓴다

ARCore 앵커는 **인식된 특징점 지도에 붙어 있어** ARCore가 자기 지도를 보정하면 앵커도 함께 이동한다. 따라서 드리프트에 강하다.

| 방식 | 드리프트 영향 |
| :--- | :--- |
| ❌ `목표 = 좌표 (3.2, 1.5)` | 드리프트가 그대로 누적됨 |
| ✅ `목표 = 앵커 B` | ARCore가 지도를 보정할 때 앵커도 따라 보정됨 |

**Track A(LiDAR)에서도 동일한 원칙을 적용한다** — 웨이포인트는 맵 프레임에 고정된 개체로 관리하고, 오도메트리 누적값으로 목표를 지정하지 않는다.

## 5. 자율주행 3요건 충족 비교

| 요건 | C · ArUco | B · ARCore | A · LiDAR SLAM |
| :--- | :---: | :---: | :---: |
| ① 어디서나 자기 위치를 안다 | ❌ 마커 볼 때만 | ✅ | ✅ |
| ② 경로를 스스로 만든다 | ❌ | ✅ | ✅ |
| ③ 장애물 회피 | 초음파 반응형 | 초음파 반응형 | ✅ **점유격자 기반 사전 계획** |
| **판정** | **자율주행이라 부르기 애매** | **자율주행 성립** | **완전한 자율주행** |

### Track B의 한계 — 장애물 지도가 약하다

ARCore는 위치는 정확히 주지만 **점유격자(occupancy grid)를 제공하지 않는다.** 희소 점군과 평면 정도다. 따라서 "저 소파를 미리 우회하는 경로"를 계산할 수 없고, **가다가 초음파로 감지하면 회피하는 반응형**에 의존한다.

> ARCore Depth API로 깊이맵을 얻어 바닥 평면에 투영하면 거친 점유격자를 만들 수는 있으나, 추가 작업이며 품질은 LiDAR에 못 미친다. 본 프로젝트에서는 **선택 과제**로 둔다.

## 6. 하드웨어 비교 — 무게보다 무게중심

```
      【 Track A · LiDAR 】              【 Track B · 폰 】

          ┌────┐  ← 높다                
          │LiDAR│    수평 360°를 쏘므로   
          └──┬─┘    몸통 위로 띄워야 함   ┌────────┐
          ┌──┴─┐                        │  폰    │ ← 낮게, 앞으로 기울임
          │마스트│    (자기 몸통이       ┌─┴────────┴─┐  (전방만 보면 됨)
        ┌─┴────┴─┐    장애물로 찍힘)     │  MechDog   │
        │MechDog │                      └────────────┘
        └────────┘

         85 g / CG 높음                   168 g / CG 낮음
```

**4족 보행은 절대 무게보다 무게중심 높이에 훨씬 민감하다.** Track B는 무게가 2배지만 마스트가 필요 없어 무게중심이 낮다. **따라서 두 부하 테스트는 서로 독립적이며, 한쪽이 실패해도 다른 쪽은 통과할 수 있다.**

| | Track A | Track B |
| :--- | :--- | :--- |
| 추가 무게 | 85 g | 168 g |
| 마운트 | **마스트 8~10cm 필요** | 낮게 눕혀 부착 |
| 무게중심 | 높음 | **낮음** |
| 전원 | **보조배터리 공용** (승압 불요, DR-10) | **폰 자체 배터리** |
| 배선 | UART 4핀 + 전원 | **없음** (Wi-Fi만) |
| 상시 장착 | **필수** (측위에 계속 필요) | **필수** (동일) |

> **왜 상시 장착인가** — SLAM은 "지도 만들기"와 "지도 위에서 내 위치 찾기"의 두 기능이며, 자율주행에는 **후자가 움직이는 내내** 필요하다. 센서를 떼면 지도는 그림에 불과하다. 따라서 두 트랙 모두 시연 중 상시 장착이다.

## 7. 개발 리스크 비교

| | Track A · LiDAR | Track B · 폰 ARCore |
| :--- | :--- | :--- |
| 새 기술 스택 | **ROS2** (숙련도 낮음 — RISK-06) | **Android / ARCore** |
| 핵심 작업 성격 | **SLAM 파라미터 튜닝** | **앱 하나 제작** |
| 작업 범위 | 열려 있음 (언제 잘 될지 예측 곤란) | **닫혀 있음** (되거나 안 되거나) |
| 실패 판명 시점 | 며칠 걸릴 수 있음 | **하루 내** |
| 디버깅 도구 | rviz2 (학습 필요) | Android Logcat + 화면 |
| 실패 양상 | tf 트리 단절, 타임스탬프 불일치, odom 드리프트, 스캔 왜곡 | 트래킹 상실, 앵커 소실 |

**"Track B가 새 기술이라 더 위험하다"는 판단은 성립하지 않는다.** 앵커 앱 제작은 범위가 명확한 작업이고, SLAM 튜닝은 범위가 열린 작업이다. RISK-06을 고려하면 **Track B의 예측 가능성이 오히려 높다.**

### Track B의 실제 난관 — pose 추출

ARCore가 폰 내부에서 위치를 계산해도, 그 값을 **PC로 꺼내야** 한다.

```java
// 개념 코드 — ARCore "Hello AR" 샘플에 추가하는 수준
Pose pose = camera.getPose();
float[] t = pose.getTranslation();          // x, y, z (미터)
float[] q = pose.getRotationQuaternion();
udpSend(toJson(t, q));                       // → Host PC
```

코드 자체는 20~30줄 수준이며, 실제 부담은 **Android Studio 환경 구성과 기기 배포**다. 초행이면 0.5~1.0 M/D로 추정한다.

### Track B의 실무 이점 — 세션 내 매핑

ARCore 앵커는 기본적으로 **앱 세션 내에서만 유효**하다(영구 보존은 Cloud Anchors 필요, 복잡도 증가). 그런데 이것이 오히려 운영을 단순하게 만든다.

| | Track A | Track B |
| :--- | :--- | :--- |
| 시연 준비 | 사전에 지도 파일 생성·저장 → 시연 시 로드. **환경이 변하면 안 맞음** | **시연 1시간 전 현장에서 앵커 설정 후 그대로 시연** |
| 실패 요인 | 어제 만든 지도가 오늘 안 맞음 | 세션이 끊기면 앵커 소실 |

## 8. 결정 게이트 — 모두 무료, 구매 전 수행

### 게이트 A — LiDAR 탑재 가능성

```
준비물: 500원 동전 약 15개 (≈85g), 종이컵 1개
설치:   종이컵을 뒤집어 8~10cm 높이 → 그 위에 추, 몸통 중앙

시험:  ① 완충 상태  → 직진 3m + 선회 보행 원 한 바퀴 (좌·우)
       ② 반쯤 방전  → ① 반복        ← 진짜 판정
```

> **②가 필수인 이유** — 배터리 전압이 떨어지면 서보 토크도 떨어진다(8.4V → 7.0V). 완충에서만 통과하고 시연 중반에 비틀거리는 사태를 막는다.

| 결과 | 판정 |
| :--- | :--- |
| ①② 모두 통과 | **Track A 가능** |
| ① 통과 / ② 실패 | Track A 조건부 — 시연을 완충 직후로 제한 |
| ① 실패 | **Track A 불가** |

### 게이트 B — ARCore 트래킹 생존성

```
① 폰에 AR 앱 실행 (구글 "Measure" 등 ARCore 기반 앱)
② 바닥에 가상 물체 하나 배치
③ 폰을 로봇에 낮게 부착하고 보행
④ 보행 중 그 가상 물체가 제자리에 고정돼 있는지 관찰
```

| 결과 | 판정 |
| :--- | :--- |
| 가상 물체가 제자리 유지 | **Track B 가능** — 보행 진동을 견딤 |
| 흔들리거나 이탈 | **Track B 불가** — 트래킹 상실. 앱 제작 무의미 |

**추가로 168g 부하 테스트도 병행한다** (폰을 낮게 부착한 상태로 게이트 A와 동일한 동작).

> **두 게이트는 한 번에 수행할 수 있다.** 어차피 폰을 로봇에 올리므로, AR 앱을 켠 상태로 부하 테스트를 하면 두 실험이 동시에 끝난다.

## 8-1. 다중 개체 관점 — 뒤늦게 드러난 판단 근거

앞선 비교는 **로봇 1대를 전제**로 쓰였다. 그런데 팀은 로봇 3대를 갖고 있고
예산 30만원 안에서 **LiDAR 는 2개까지만 확보된다**(대당 약 10만원 + 중계 MCU·전원).
**3대 중 1대는 측위 없이 운용된다.** 이 비대칭이 트랙 선택에 직접 영향을 준다.

> **이 비대칭이 기준기를 Phase 별로 나눈 이유다.** 기준기를 1대로 고정하면 그 개체에 LiDAR 가
> 없을 때 Phase 2 측위 검수를 기준기에서 할 수 없다 ([WBS 8절](WBS.md)).

### ① Phase 1 은 어느 트랙이든 영향받지 않는다

먼저 오해를 제거한다. **Phase 1 의 P1 기능 7종은 측위를 쓰지 않는다.**

| | 필요한 것 |
| :--- | :--- |
| FR-1~4 (링크·순찰·인지·대시보드) | 카메라 · 초음파 · IMU |
| FR-8 변화 감지 | 카메라 + **구역 마커 1장** (좌표 아님) |
| FR-9 PPE · FR-10 인증 | 카메라 · 마이크 |

3대 모두 전 기능을 병렬로 개발·시연할 수 있다. **측위 트랙 결정이 늦어져도
착수는 막히지 않는다.**

### ② Track A 는 2인·2대로 병렬 검증한다

LiDAR 2대를 L1·L2가 각자 한 대씩 맡으므로 SLAM 입력·중계 펌웨어·장착 차이를 병렬로 확인할 수 있다.
공식 게이트 값은 `phase2_reference` 한 대에서 기록하고, 다른 한 대는 재현성·개체차 자료를 제공한다.

Track B 는 팀원 각자 스마트폰이 있으므로 3명이 병렬로 붙을 수 있다.

### ③ Track A 만 ROS2 를 요구한다 — 이것이 가장 큰 공수 차이다

| | Track A | Track B |
| :--- | :--- | :--- |
| 측위 산출 | slam_toolbox 가 스캔에서 맵·pose 생성 | **ARCore 가 6DoF pose 를 직접 제공** |
| ROS2 | 필요 (`slam_toolbox` · `rviz2` · `tf2`) | **불필요** |
| 컨테이너 | 필요 (WBS 5.4.1, 1.0 M/D, DR-17) | 불필요 |
| LiDAR 노드 펌웨어 | 필요 (UART→UDP 중계, OI-7 미정) | 불필요 |
| 추가 학습 비용 | ROS2 · SLAM 튜닝 | Android/ARCore 앱 |

**Track B 를 고르면 ROS2 스택 전체가 범위에서 사라진다.** 팀의 ROS2 숙련도가
낮다는 점(A-8 전제)을 감안하면 이 차이는 무게나 정확도보다 크다.

> 다만 **범위가 열린 작업(SLAM 튜닝) vs 범위가 명확한 작업(앱 제작)** 이라는
> 기존 판단(7절)과 방향이 같다. 새로운 근거가 아니라 **같은 결론을 다른 축에서
> 재확인**하는 것이다.

### ④ Track A 는 기준기를 Phase 별 개체로 나눈다

LiDAR 를 마스트에 얹으면 **무게중심이 바뀌어 보행 이동량이 달라진다.** 같은 개체의 장착 전·후
프로파일을 바꿔 쓰는 대신, `phase1_reference`(LiDAR 미장착 P1 표준 구성)와
`phase2_reference`(LiDAR 장착 측위 검수용)를 **서로 다른 물리 개체로 지정**한다.

LiDAR 장착 2대는 각각 자신의 개체 프로파일에 gait odometry 계수를 기록한다. 이 중 1대만
`phase2_reference`이고 다른 1대는 개발·재현용이다. 미장착 상태에서 얻은 계수를 LiDAR 장착기에
그대로 복사하지 않는다.

### ⑤ 예산이 통째로 남는다

| | 지출 | 잔액(30만원 기준) |
| :--- | ---: | ---: |
| Track A | LiDAR 가격 + 약 44,000원 | 상품 확정 후 산출 |
| Track B | 0원 | **약 300,000원** |

> Track B 도 완전히 0원은 아니다. XIAO 전원(보조배터리)은 트랙과 무관하게 필요하며,
> 보유분으로 해결되면 실제 0원이 된다.

Track B 를 고르면 예산을 **PPE 데이터셋 확보(OI-13)** 나 예비 부품에 돌릴 수 있다.
직접 촬영·라벨링이 4~6 M/D 로 잡혀 있는데, 이쪽이 공수 리스크가 더 크다.

| 게이트 A (85g) | 게이트 B (ARCore) | **선택** | 근거 |
| :---: | :---: | :--- | :--- |
| 통과 | 통과 | **Track A** (B는 백업 카드로 보유) | 자율주행 수준이 가장 높음. 장애물 지도 확보 |
| 통과 | 실패 | **Track A** | 유일한 자율주행 옵션 |
| 실패 | 통과 | **Track B** | 무게중심이 낮아 통과 가능. 비용 0원 |
| 실패 | 실패 | **Track C 또는 Phase 2 포기** | Phase 1(M0~M3)만으로도 완결된 산출물임 |

> **위 매트릭스는 8-1 절을 반영해 다시 읽어야 한다.** 두 게이트가 모두 통과한 경우
> 기존 표는 Track A 를 권했으나, 그 판단은 *로봇 1대·ROS2 비용 무시* 를 전제로 한 것이다.
> **다중 개체·ROS2 공수·예산을 넣으면 두 트랙의 우열이 뒤집힐 수 있다.**
> 이 경우는 게이트 결과가 아니라 **팀 논의로 결정한다.**
>
> | 무엇을 더 중시하는가 | 선택 |
> | :--- | :--- |
> | 자율주행 완성도 · 장애물 지도 · 포트폴리오 임팩트 | **Track A** |
> | 3인 병렬 개발 · 공수 안정성 · 예산 여유 | **Track B** |
>
> **Phase 2를 포기해도 프로젝트는 완결된다.** PRD 7절에 따라 M3 완료 시점에서 FR-1~FR-5 전체와 NFR 전항이 충족된다. 측위 확보에 실패한다고 프로젝트가 실패하는 것이 아니다.

> 먹이면 5V 가 확보되고(LD19 허용 4.5~5.5V) 충전도 배터리가 담당하므로, **전 과정 납땜이 0 이 된다.**

>
> **XIAO 전원은 Track 과 무관한 Phase 1 항목이며, 보조배터리 보유분으로 해결되면 비용이 0 이다.**

**발주 시 확인 항목** (전체 목록은 [하드웨어 조립](HARDWARE_ASSEMBLY.md) 8절)

| ✔ | 항목 | 이유 |

| ② | ⚠️ **실제 무게 60g 이하** | 무게가 유일한 하드 제약. 스펙 페이지 실측치 확인 |
| ②' | ⚠️ **LD19 로 확정** (FHL-LD19 / D500 키트) | 아래 반례 참조 |
| ③ | 로직 레벨 3.3V TTL | ESP32 직결 조건 |
| ④ | ROS2 드라이버(`ldlidar_ros2`) 존재 | 없으면 패킷 파서 자체 구현 필요 |

> **반례 — YDLIDAR X4 Pro 를 사면 안 된다.** 국내에서 93,500원(VAT 포함)에 팔려 LD19 보다 싸지만
> **무게가 178g**(110.6 × 71.1 × 52.3mm)으로 **무게 예산 85g 의 두 배를 넘고, Track B 의 폰(168g)보다도 무겁다.**
> 폰은 낮게 부착할 수 있고 LiDAR 는 마스트 위로 올라가므로 무게중심까지 불리하다.
> 시동 전류도 800~1000mA 로 LD19(~200mA)의 4~5배다.
> **9만원을 아끼려다 못 쓰는 부품에 예산을 쓰는 셈이며, 발주가 1회이므로 복구할 수 없다.**
>
> | | X4 Pro | **LD19** |
> | :--- | ---: | ---: |
> | 무게 | **178 g** | ~50 g |
> | 가격 | 93,500원 | 130,000~160,000원 |
> | Baud | 128000 | 230400 |
> | 커넥터 | PH2.0-8P | PH2.0-4P 계열 |
>
> 참고로 X4 Pro 데이터시트에서 확인된 사실 하나는 다른 제품 검토에도 쓸 수 있다 —
> 모터 제어 핀(`M_CTR`)은 **0V 일 때 최고 속도**이므로 PWM 을 구동하지 않아도 회전한다.
> **LD19 는 데이터시트에서 확인되었다** — PWM 미연결·Hi-Z 또는 접지 시 내부 제어로 10Hz 회전한다. **PWM 배선이 불필요하다.**
