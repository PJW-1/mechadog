# LiDAR 입력 이상 오프라인 진단

저장소 루트에서 실행한다. 포트·기기·런타임을 열지 않는다.

```sh
python -m tools.lidar.input_anomaly RECORD_DIR --out REPORT_DIR/input-anomaly.json
python -m pytest tests/test_lidar_input_anomaly.py
```

JSON과 같은 이름의 `.txt` 표, 표준 출력 표를 만든다. 기존 출력은 덮어쓰지 않는다.
입력은 런타임 `--record-dir`의 `events.jsonl`과 선택적 `summary.json`이다.
장착 보정이 있다면 실제 런타임과 같은 `--mount-yaw-deg` / `--angle-direction`을
지정한다. `--device-id`로 특정 LiDAR만 선택할 수 있다.

## 판정과 비교

- 기본 1초 창. 호스트 수신 `t` 기준으로 장치별 분석하며 부팅 사이 패킷을 조립하지 않는다.
- 완성 수는 현재 host `ScanDecoder` → `RevolutionAssembler`를 오프라인 재생한 값이다.
  실제 운용 로그의 완료 카운터가 아니다. 원본 각도 통계에는 거리 0도 포함하지만,
  조립에는 호스트와 동일하게 유효점만 들어간다(5° 72칸 중 66칸, 최대 300ms).
- 관측 길이 300ms 초과·3패킷 이상일 때 완성 0, 5° 한 칸 집중률 ≥80%,
  거리 0 비율 ≥50% 중 하나면 이상이다. 임계는 진단용이며 원인 확정 기준이 아니다.
  옵션 `--window-ms`, `--concentration`, `--zero-ratio`로 바꿀 수 있다.
- 거리 0 비율의 분모는 숫자 거리값이 있는 원본 점 수다. 별도로 원본/유효/무효점 수,
  패킷당 점 수, 원시 최소/최대각·원형 최소 포함각·5° 분포·최빈각을 남긴다.
- 패킷 간격과 seq 누락은 창 경계를 넘는 첫 패킷에도 계산한다. seq는 device/boot별
  최고값과 비교하며 역순·중복은 따로 센다. 부팅 변화에는 수신 시각과 전후 ID를 남긴다.
- 이상 에피소드의 `previous_normal_window`, `first_window`, `last_window`,
  `recovery_window`는 같은 device의 `windows` 인덱스다. 표는 직전 정상/발생/마지막 이상/
  회복 행을 나란히 비교한다. 정상 기준이나 회복이 없으면 null/unavailable로 남긴다.
- 창 경계에 걸친 짧은 이상은 희석될 수 있다. 시작/끝 짧은 창과 1~2패킷 창은
  충분한 근거가 없으면 `insufficient_data`다. 마지막 SCAN 뒤 다른 기록이 지속되면
  `no_packets` 창을 남기지만, 첫 SCAN 이전이나 기록 종료 뒤의 무수신은 추정하지 않는다.
- 녹화 도중 읽으면 마지막 잘린 줄과 누락 summary가 issues에 남는다. 최종 판단은
  닫힌 원본 사본으로 재실행한다. SHA256은 읽은 events 바이트에 대한 값이다.
  issues/recorder 손실을 먼저 확인한다. 전송 손실과 기록 손실은 seq만으로 분리할 수 없다.
- 종료 코드 0은 분석 성공(이상 발견도 포함), 2는 입력/출력 오류 또는 SCAN 없음이다.
  정상 판정은 입력 휴리스틱 통과일 뿐 측위 정확도나 보행 승인 근거가 아니다.

## 설치본 5f8f4dc 정적 분석: 조사 우선순위

아래는 원인 확률표가 아닌 다음 관측의 우선순위다. 실제 설치 바이너리와 이 커밋의
동일성은 작업 지시서에서 인계받았으며 이번에 장치에서 확인하지 않았다.

| 순위 | 가설 | 소스 근거와 구별할 증거 |
| --- | --- | --- |
| 1 | 센서가 의미상 고착된 프레임을 계속 출력: 센서 내부 상태·전원/접촉 포함 | `src/ld19.cpp`의 `Ld19Parser::feed`는 헤더/길이 바이트·CRC만 검사한다. 시작/끝각 범위, 회전속도, 센서 stamp 진행, 거리 유효성을 검사하지 않는다. CRC 정상인 고정 시작/끝각·0거리가 그대로 통과할 수 있다. 재발 중 센서 전원단 측정과 UART 진단 증가량을 함께 확보해야 전원 가설과 내부 상태 가설을 좁힐 수 있다. |
| 2 | UART 손상/유실 뒤 잘못 잡힌 프레임이 CRC까지 우연히 통과 | `resync_`는 다음 `0x54`부터 다시 모으며 payload 안 헤더 후보도 택한다. 이후 `0x2c`와 CRC를 다시 검사하므로 단순 바이트 밀림만으로 장기간 동일 정상 패킷이 생긴다고 단정할 수 없다. 오류 시 `crc_fail`, `bad_verlen`, `resync` 증가 여부를 비교한다. CRC 통과 후 각도 범위 검사가 없다는 한계는 남는다. |
| 3 | 시작/끝각 보간·청크 배출이 고착 증상을 지속적으로 전달 | `ScanAssembler::addFrame`는 시작각 감소만 회전 경계로 판단한다. start=end이면 12점 모두 동일각이 된다. 끝각<시작각이면 36000을 더해 11등분한다. 범위 밖 입력도 modulo 처리되어 거짓 분포가 가능하다. 스케치 `loop`의 pending≥청크 크기 `flush`는 회전 완료 없이도 전송한다. 따라서 sent 증가/호스트 완성0이 양립한다. 이 경로는 0거리를 만들지 않고 원본 dist를 복사하므로 단독 근본 원인 설명은 약하다. |
| 4 | Wi-Fi/호스트 수신·기록 손실 또는 조립/장착 차이 | 패킷 공백·seq 누락은 완성 부족을 만들 수 있다. 그러나 원본 각도 집중과 0거리 생성은 설명하지 못한다. 동일 부팅에서 seq가 연속인지, recorder 손실이 없는지 확인한다. `serviceWifi`의 재연결 시 UART 대기 바이트/부분 프레임/미완성 점 폐기와 `reconnect_discard_bytes`도 비교한다. |

`src/scan_encoder.cpp`는 이미 계산된 각도와 원본 거리를 JSON으로 옮긴다.
읽은 경로에 347°를 하드코딩한 분기는 없다. host의 유효점 필터는 dist≤0을 버리므로
원본의 0거리 비율 상승은 유효점/각도 커버리지 감소로 이어진다.

주의: 설치본 진단 `drop_full`은 `ScanAssembler::points_dropped()`이다.
**UART 하드웨어/RX 링버퍼 overflow 카운터가 아니다.** 값 0으로 UART 유실을 배제할 수 없다.
`scans`는 중계의 시작각 감소 횟수, `sent`는 전송 성공 패킷 수라 호스트 완성 바퀴와 다르다.
원본 SCAN에는 CRC, 원본 start/end, speed, intensity, sensor stamp가 보존되지 않는다.
이번 도구만으로 센서·전원·UART·중계 중 근본 원인을 확정할 수 없다.

## 검증 상태

합성 회귀 시험은 정상→347.38°/거리0→회복, 거리0 전체각도, 부팅/seq 경계,
중복/역순, 다중 장치, 수신 공백, 기록 손실, base64/잘린 줄, 0° 경계,
정상 기준 없음, 출력 원본 보존을 다룬다. 작성 환경에서 Python/py 실행기를
찾지 못해 실행 결과는 미검증이다. 하드웨어·포트 접근과 펌웨어 설치는 수행하지 않았다.
